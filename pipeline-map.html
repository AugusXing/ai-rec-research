Recommendation Pipeline Map · 更新至 2026.09.15

把研究放回真实推荐链路：召回 → 粗排 → 精排 → 重排 / 混排 → 跨阶段统一

这里不按“模型名字”分类，而是看工作应该落在真实系统哪一层。9/15 的变化非常具体：MIMA 重写多兴趣召回的监督方式；Generative Verifier 在召回与粗排之间新增一个可插拔 verification 层；ChronicleRec / DRIFT 重写精排如何消费超长用户历史；OneLA 把生成式推荐 Serving 的 beam-state 管理纳入跨阶段成本模型。

链路总判断：下一代推荐/搜索系统更像统一 state / supervision / verification contract + stage-local executors + cheap controller + state-aware runtime。召回负责覆盖与多意图 ownership；verifier 负责把 relevant candidate 推进真正消费的 prefix；精排消费可缓存的长期 user state；重排做结构约束；runtime 管 beam/KV/cache/speculative budget。

Tab 01.5 · 召回后验证 / Retrieval Verification

新增一个边界层：Pool Recall 不等于 Consumed-prefix Recall

为什么单独成层：实际 cascade 中粗排只能消费前几十/几百候选。很多召回错误并不是“正样本没召回”，而是“已经在 top-1000，却没进 top-100”。这类问题直接重训 retriever 可能代价过高。

工作输入动作工业意义
Universal Generative Verifierretriever query state + top-K candidate计算 item identifier token likelihood，RRF 融合后重排冻结召回器做 post-hoc output adaptation；大 catalog 收益更明显
GeneralQPPscore distribution判断检索是否充分决定是否触发 verifier / 扩召回
Downstream teacher粗排/精排 survival label蒸馏 candidate survival未来可把 verifier 训练目标从 next-token likelihood 推向 stage survival

重点指标：Recall@poolK、Recall@consumeK、Verifier Lift、额外 P50/P95、verify-K、粗排 survival、最终 CTR/GMV。只有 Recall@10 涨而 downstream 不涨，不能算成功。

值得押注：request-adaptive verify-K：高 confidence 请求直接过，边界请求才验证；如果 verifier 仍不确定，再扩 pool 或触发重召回。

下一步：粗排不只看 local AUC，还要联合监控 candidate survival、verifier rescue rate、stage margin、latency、feature freshness 与 controller 误升级率。

Tab 03 · 精排 / Ranking

长序列从“全部在线重算”转向“Cacheable Long-term State + Real-time Recent State”

工作研究问题价值 / 落地方式
PTDG任务依赖不应固定item-conditioned dynamic task graph
MOREtask signal 只在 tower 末端出现太晚task anchor 进入 backbone 各层
UniRec精排 fusion 与粗排 fusion 独立会抵消ranking agent 与 pre-ranking agent 同图优化
ChronicleRec数千/万级历史每 candidate 重算太贵时间锚 Chronicle Tokens 每 user 压缩一次并缓存；线上 GMV +1.61%
DRIFT长历史包含错误兴趣阶段噪声按 preference drift 切 subsequence，recent context 选择性读取长期阶段

最值得押注的 Serving 形态：Long-term cached state + Recent real-time state + Candidate interaction 三层。长期 token 按小时/天刷新，近期行为分钟/秒级刷新，candidate-specific cross 只在精排内层执行。这样比单纯把 max sequence length 从 1K 拉到 8K 更可控。

重点监控：token cache age、state refresh QPS、cache hit、recent override rate、GAUC、long-tail user gain、增量更新 correctness、模型版本与 state version compatibility。

Tab 04 · 重排与混排 / Re-ranking & Slate

从逐 Item 打分走向结构化 Assignment、可验证约束与 Whole-page Decision

工作关键问题落地启发
hLLM / Hungarian assignment排序是 permutation，不必自回归生成 N 个序号single-pass score matrix + assignment
MIMA 的 Hungarian supervision结构化 assignment 也可用于 latent interest ownershipassignment 不只属于 slate，也适合训练时 credit allocation
CHyD解释/引用必须来自 evidencehard constraint 保证生成结果可验证
TimelyRAG相关但过期内容应降权temporal validity 作为 rerank constraint
Magenta / Ecdysis失败后不知道重召回、重排还是改系统verifier + error attribution + selective repair / harness evolution
SAFARI重排不确定时接受还是补证据把追加召回 / 用户澄清视为有成本 exploration action

趋势：重排越来越像“结构决策 + 约束验证”，而不是再加一个更大 pointwise 模型。将 assignment、diversity、freshness、creator/business constraints 与 explanation 一起放入可验证 decision layer。

Tab 06 · 跨阶段统一 / Cross-stage Control Plane

统一的不只是 Backbone，而是 State、Ownership、Verification、Budget 与 Runtime Contract

当前最重要的架构变化：为每个 request 定义 compact state schema：user-state version、interest activation、retrieval confidence、pool/consume recall proxy、stage margin、verify confidence、beam/runtime budget、failure reason。每个 stage 消费并更新这份 state，而不是互相只传 candidate list。

可以直接做的工程实验：① 线上日志补充 pool-K→consume-K survival；② 用 request 内多正样本离线复现 MIMA-style assignment；③ 将长期用户表示移出 candidate loop，做 state TTL/刷新仿真；④ 生成式 path 加 beam-state bytes 与 HBM traffic dashboard；⑤ speculative path 记录 acceptance by request cohort，验证 adaptive verification 是否有空间。

链路演进一句话：召回正从“相似度匹配”变成“多意图 ownership + coverage”，召回与粗排之间开始长出 verifier，精排把超长历史变成 cacheable state，生成式路径把 beam/runtime 变成显式成本；跨阶段层最终会变成真正的状态化控制平面。
