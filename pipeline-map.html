这个页面回答工程问题：一项工作最终改变推荐/搜索链路的哪一段？替换什么、复用什么状态、增加多少在线成本、有没有真实 A/B？今天没有新的召回/排序论文需要硬塞进链路，新增的是一组更底层但会影响所有阶段的 Runtime State：host cache 去重、NVFP4 KV capability、MoE router precision、safe GPU kernel toolchain。

今日链路判断：未来链路不会简单从“五段式”变成“一个大模型”。更可能是：传统高吞吐 retrieval/ranking 主干继续存在，每一段多出可复用 state layer，跨阶段再由 runtime controller 管理 cache locality、precision、model/device route 与 freshness。今天 SGLang / vLLM / CUDA Rust 的共同信号，就是这个 controller 下面还需要一层清晰的状态与数值契约。

从“找候选”升级为“经营可检索空间”

Tab 02 · 粗排

不是“更小的精排”，而是低成本保留后续最有用的状态

粗排最重要的是覆盖、吞吐和 state reuse。趋势不是把完整 cross-attention 前移，而是让 user/context 只算一次，候选做轻量 interaction，并把 uncertainty 暴露给后续 router。

Tab 03 · 精排

Context State + Dynamic Task Graph，而不是固定漏斗永久不变

精排仍是推荐工业最成熟的收益区。PTDG 攻击的是非常现实的问题：不同样本的任务依赖强度不同，稀疏深层目标最容易在固定传递结构中衰减。

Tab 05 · 跨阶段统一

统一的不是“一个大模型”，而是 Namespace、State、Policy、Runtime 与 Budget

跨阶段统一有两条路线：TGR 式 shared backbone/full-stack generation；以及把每一段最有价值的中间状态做成 contract。后者目前正在快速变得更重要。

跨阶段状态图：Catalog State（Semantic ID / generated expansion / dense vectors）→ User/Context State（sequence/context/atomic memory）→ Candidate State（reusable prefix）→ Policy State（inventory-grounded guidelines）→ Runtime State（GPU/host KV、quant scales/layout、device/load）→ controller 决定 recall/rank/rerank/Agent 路径。

2026-09-09 新增判断：Runtime State 不能再只写成“KV cache”。HiCache 表明 state 有 ownership / duplication；NVFP4 表明 state 有 dtype / scale / backend capability；MoE routing 表明 precision policy 会改变计算路径；cuTile Rust 则表明 custom kernel 的 memory safety 也应该纳入 contract。

值得押注：跨阶段 state schema、version/TTL、一致性、实验归因、state-aware routing、precision policy，以及“何时刷新 state vs 何时重训模型”的自动 controller。

如果按落地优先级排序：成熟电商搜索主干先看 SAM-D2Q；多目标精排先看 PTDG / UniCon；LLM rerank 先看 DoPR / hLLM；Agent/Search 先看 IGPO；长期用户记忆看 AtomRec；如果你已经开始上大模型推荐 Serving，则把 HiCache / NVFP4 / MoE precision / GPU compiler 当成跨阶段基础设施，而不是“推理团队才需要懂”的旁支。
