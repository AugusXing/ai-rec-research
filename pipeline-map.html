Recommendation Pipeline Map · 更新至 2026.09.16

把研究放回真实推荐链路：召回 → 粗排 → 精排 → 重排 / 混排 → 跨阶段统一

今天最关键的变化是：VARG 在召回侧建立一条 value-aware generative fast lane，生成候选可绕过 item-level pre-rank 后交给 final ranker；LazFormer 把一年行为生成式预训练真正迁进工业精排；LION 给持续偏好单独的 mutable memory；Question’s Gambit / DiBud 则把搜索第一步与 retrieval depth 变成 controller 可管理的预算。

链路总判断：下一代推荐 / 搜索更像多路召回 + 生成式 fast lane + verifier / budget controller + foundation ranker + versioned user state + stage-local executors。不是让一个大模型吞掉全部 stage，而是让 stage 之间共享 state、preference、confidence、cost 与 downstream survival 信号。

Tab 01.7 · 召回后验证 / Retrieval Verification

Pool Recall 不等于 Consumed-prefix Recall：Verifier 成为新的 stage boundary

问题：粗排只能消费短 prefix，很多 relevant item 已在 top-1000 却没进 top-100。直接重训 retriever 成本高，也不一定解决“候选顺序”问题。

代表工作：Recommendation Retrievers Need Verifiers 冻结 retriever，只对 top-K candidate identifier 做 generative likelihood 验证，再用 RRF 融合。VARG 进一步把 downstream ranker advantage 前置进生成式训练。

9/16 最强信号：LazFormer 2 周线上 Orders +3.38%、GMV +9.85%，A10 单机 QPS 只 -12.1%。这说明“更长历史 + 更深 backbone”并非不能上线，前提是预训练 transfer、序列压缩、sparse attention、feature isolation一起设计。

推荐系统下一版 API 值得多返回什么：除了 score，再返回 confidence、interest/source ownership、state version、business prior、expected downstream gain、estimated cost、failure reason。这样 controller 才能决定是否扩召回、走 generative fast lane、升级 ranker、读取更长历史或直接停止。

2026.09.16 · 推荐工程优先级

最值得在真实系统里验证的 5 个实验

1. Generative Fast Lane：传统召回不动，新加 VARG-style reserved quota，最终仍让现有 ranker 决策。
2. Pretrain Transfer：sparse-only vs sparse+dense；adapter on/off；sparse reset multi-epoch on/off。
3. Three-tier User State：长期 cache + recent state + sparse mutable memory，分别定义 refresh clock。
4. Budgeted Retrieval：把每路固定 Top-K 改为访问成本 telemetry，再做 dynamic allocator。
5. Request-level Compute：MoE expert count、verify-K、beam、sequence length 都纳入同一个 latency/quality controller。
