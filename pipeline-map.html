Recommendation Pipeline Map · 更新至 2026.09.14

把研究放回真实推荐链路：召回 → 粗排 → 精排 → 重排 / 混排 → 跨阶段统一

这里不按“模型名字”分类，而是看一项工作落在推荐/搜索系统的哪个阶段、解决哪个瓶颈、离工业上线还有多远。9/14 最大变化不在某一个 ranker，而在跨阶段控制面：Gated-Memory Routing 让控制器维护 compact execution state；SAFARI 让系统学习是否值得继续探索；Ecdysis 让 bad-case 先跨请求归因再决定是否修改全局 harness；GPT-6 Astra 则更清楚地定义了昂贵 frontier executor 的适用边界。

链路总判断：下一代推荐/搜索系统不会简单消灭 cascade，而更像统一训练 / 表征资产 + stage-local executors + compact state + cheap control plane + frontier hard-case executor + runtime resource governor。Controller 决定“要不要继续算、要不要继续找信息、调用哪个专家、是否扩大召回、何时停止”；runtime 则管理 cache、GPU/NPU、队列、启动与 deadline。

Tab 02 · 粗排 / Pre-ranking

从“轻模型筛候选”走向“下游偏好感知 + 联合训练 + 动态计算预算”

核心任务：在极紧 latency 下保住真正会被精排选中的 item。传统优化往往只追粗排本地 AUC/NDCG，容易出现 stage mismatch；下一步要让 control plane 根据 query 难度与 downstream margin 决定粗排算力。

工作核心机制工业信号当前启发
COPR / Rethink / HCCPranking supervision → pre-ranking alignment成熟工业路线下游 preference 应进入上游训练，但仍多为单向 teacher-student
UniRecshared embedding + vertical consistency + joint fusion快手已全量部署粗排 fusion 本身要与精排共同优化，而不只改 backbone score
ReST / shared user state长序列 user representation 复用线上 A/B 路线把更多预算留给 candidate interaction，而不是重复编码 history
Fugu 式 orchestrationquality/cost-aware expert selection产品化 API迁移为轻粗排 / 重粗排 / LLM-enhanced 路径按 request 动态路由
Gated execution state只保留对后续决策有用的 stage state学术原型不要把全链路日志重新拼给 controller；维护 compact stage summary / margin / failure state

重点指标：除本地 NDCG/AUC 外，必须看 ASH / ranking top-K survival / candidate recall、latency、feature freshness、downstream consistency，以及 query-level compute budget、stage queue pressure 与 controller 的误升级率。

下一步：task-aware foundation ranker + request-level user state + candidate-adaptive compute + cross-stage consistency + multi-objective group-relative regularization；controller 决定“本 request 值不值得进入更贵的 ranking path”，并用 cost per successful decision 而不是单纯 token price 评估升级。

Tab 04 · 重排与混排 / Re-ranking & Slate

从逐 item 打分走向结构化 assignment、可验证约束与精确失败回退

工作关键问题落地启发

Exploration Policy重排置信度低时，是接受当前 slate 还是补证据？把“追加召回 / 用户澄清 / tool call”看成有成本的探索动作

值得押注：assignment + diversity + freshness + creator/business constraints；生成式 rerank 的目标不是“会生成列表”，而是把复杂 constraint 与 explanation 做成可验证 structured decision，并能定位失败 stage 和控制额外探索预算。

当前最重要的架构变化：统一的不应只是 embedding 或 backbone，而应是一个可版本化的 state/control protocol：每个 stage 输出 score 之外还输出 confidence、margin、evidence、cost、状态版本与失败原因；cheap controller 根据这些状态选择下一执行路径。

推荐工程下一步可直接实验：① 设计一个 10–20 维 compact request state，替代把全量日志喂给 LLM router；② 用历史 replay 数据训练“继续检索是否有增益”的 exploration label；③ 给 LLM hard-case path 建立 $/successful-task、P95、升级率与回退率 dashboard；④ 将 Agent bad case 按 query cohort / stage failure 聚类，再决定全局 prompt/harness 是否需要改；⑤ 线上模型评测加入 cold-start、rollout、recovery 和 hardware fallback。

链路演进一句话：召回越来越像“可探索的信息获取”，粗排/精排越来越像“联合训练但分阶段执行”，重排越来越像“可验证结构决策”，而跨阶段层正在长成一个真正的状态化控制平面——它管理 state、budget、model、tool、exploration、harness 与 runtime。
