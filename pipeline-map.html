召回 / 粗排 / 精排 / 重排与混排 / 跨阶段统一

这个页面不按“模型家族”分类，而是回答工程问题：一篇工作最终改变推荐/搜索链路的哪一段？它替换什么、复用什么状态、增加多少在线成本、有没有真实 A/B？今天新增的最重要变化是：召回侧出现“LLM 离线写索引 + 局部向量纠偏”，精排侧出现“动态 task graph”，跨阶段侧出现“inventory policy / atomic memory”两类可热更新状态。

今日链路判断：未来链路不会简单从“五段式”变成“一个大模型”。更可能的形态是：传统高吞吐 retrieval/ranking 主干继续存在，但每一段都多出一个可复用 state layer——召回有 generated index / semantic namespace，精排有 shared user/context state，重排有 reusable document state，Agent 有 policy/memory store；跨阶段 controller 决定哪些请求值得走更贵路径。
Tab 01 · 召回

从“找候选”升级为“经营可检索空间”

召回侧当前最关键的三种状态分别是：索引文本/扩展资产、Semantic ID namespace、dense vectors。今天 SAM-D2Q 与 Embedding Surgery 分别回答“如何生成更多可检索表面”和“如何在反馈后局部修补向量”。AlleCompanion 则强调 category constraints 依然是工业召回的重要边界。

Tab 02 · 粗排

粗排的核心不是“更小的精排”，而是用最低成本保留后续可用信息

粗排阶段最重要的是候选覆盖与 feature/state reuse。最近的研究趋势不是单独堆复杂结构，而是让上游输出更富语义、让用户/context state 只算一次，并把高成本 reasoning 推迟到少数 hard cases。

工程判断：如果粗排吞吐压力很大，优先研究 shared user/context state 和候选侧轻量 interaction，而不是把 full cross-attention 直接前移。粗排的理想输出也不应只有 score，还应包含可被精排/重排复用的 compact state。

值得押注：shared prefix/state cache、candidate-adaptive depth、粗排 uncertainty 作为后续 router feature、跨阶段蒸馏。

Tab 03 · 精排

从静态 feature fusion / 固定漏斗，走向 Context State + Dynamic Task Graph

精排仍是推荐工业最成熟的收益区。今天 PTDG 的价值在于：它没有试图用 LLM 替代 MTL，而是直接攻击多目标系统最现实的问题——不同样本的任务依赖强度不同，稀疏深层目标又最容易信号衰减。

Tab 04 · 重排与混排

从完整 Cross-encoding + Autoregressive List Generation，走向 Reusable Candidate State + Structured Decode

重排最核心的成本来自两处：候选文档/商品反复编码，以及排序列表逐 token 生成。DoPR 与 hLLM 分别针对这两处下刀，因此非常适合组合阅读。

值得押注：DoPR × hLLM、Hungarian/assignment 中直接加入 diversity/business constraints、GPU batched matching、candidate prefix quantization/versioning。

Tab 05 · 跨阶段统一

“一个大模型”不是终点，统一的是 Namespace、State、Policy 与 Budget

跨阶段统一目前有两条不同路线：一条是 TGR 式 shared backbone / full-stack generation；另一条是把各阶段最有价值的中间状态做成可复用 contract。今天 IGPO 与 AtomRec 强化了第二条路线：Policy Guidelines 与 Atomic Memory 都是独立于主模型 checkpoint 的可更新状态。

跨阶段状态图：Catalog State（Semantic ID / generated expansion / dense vectors）→ User/Context State（sequence/context/atomic memory）→ Candidate State（reusable prefix）→ Policy State（inventory-grounded guidelines）→ Runtime State（KV/cache/device/load）→ controller 决定 recall/rank/rerank/Agent 路径。

值得押注：跨阶段 state schema、version/TTL、一致性、实验归因、state-aware routing，以及“何时刷新状态 vs 何时重训模型”的自动 controller。

如果按落地优先级排序：已有成熟电商搜索主干，先看 SAM-D2Q；多目标精排收益压力大，先看 PTDG / UniCon；正在做 LLM rerank，先看 DoPR / hLLM；正在做 Agent/Search，先看 IGPO；正在建设长期用户记忆，再看 AtomRec。真正的跨阶段机会，是把这些论文中的 state 变成你们内部统一的可复用资产。
