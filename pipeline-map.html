今天最值得写入链路图的变化不是又出现一个更大的 ranker，而是三个更基础的接口：用户侧由 Raw History 转向 Densed Behavioral Tokens；生成式召回的 History / Target Token Grammar 开始分化；在线排序开始更明确地区分长期兴趣与 Request Trigger。 同时，Generative Search 的 Context Allocation 与 Agent 的 Risk-aware Reranking 说明“候选召回以后如何分配有限决策预算”正在成为推荐、搜索、Agent 共用的问题。

Tab 02 · 粗排

粗排：从“精排的小模型”转向 Candidate Budget Allocator

Tab 03 · 精排

Shared User State + Semantic Item Asset + Request Trigger

精排最值得关注的变化是三层 state 同时存在：长期共享 User State、候选 Item Semantic Asset、当前请求 Trigger / Session State。工业效果往往来自如何把三者在低延迟内融合，而不是单纯扩大 backbone。

CRRN 最值得借鉴的是：Trigger 不只是一个额外 feature，而应进入 interaction、attention query 和 auxiliary loss。长期历史则优先做共享 / densify，当前 request anchor 保持高时效；最终在线 ranker 只做候选交互，避免每次请求重算完整历史。

跨阶段统一的落地结构

Densed Shared User State / Semantic Item Asset→Dense / SID / Structured Recall Router→Elastic Candidate Budget→Foundation + Trigger-aware Ranker→Utility / Risk / State-aware Re-rank→Context / Memory / Cache / Hardware Policy

2026 年最值得研究的不是“取消召回/粗排/精排”，而是哪些 representation、semantic namespace、teacher、memory 与 serving asset 可以跨阶段复用，以及每个请求该使用什么信息密度、什么 token grammar、什么 context width 和什么计算路径。

推荐算法工程师精读顺序

按落地收益排序

第一层：用户与 Item 表征——Densing Law → Dynamic SID → SST，理解“更多历史 / 更多 token”为什么开始失效；
第二层：精排——OneModel → CRRN → RankMixer / OneRank，理解 Shared State 与 Request Trigger 如何协同；
第三层：Context / Re-ranking——Reasoning Gap → Risk-aware Rerank → Context Allocation，理解“选什么信息、为什么选、付多少预算”；
第四层：系统——CacheRoute → LiLiCorr → AsmEvo，理解算法收益如何最终变成 QPS、Latency 与真实硬件收益。
