Recommendation Pipeline Map · 更新至 2026.09.12

把研究放回真实推荐链路：召回 → 粗排 → 精排 → 重排 / 混排 → 跨阶段统一

这里不按“模型名字”分类，而是看一项工作落在推荐/搜索系统的哪个阶段、解决哪个瓶颈、离工业上线还有多远。今日最重要更新是 UniRec 把粗排与精排的 fusion 从阶段内独立优化推进到跨阶段联合训练；同时 GeneralQPP、TimelyRAG、GLIE、REVA、VikingRAG 进一步完善召回与跨阶段 control plane。

链路总判断：下一代推荐/搜索系统不会简单消灭 cascade，而会出现训练时更统一、Serving 时仍按 SLA 分阶段的形态。每个阶段都开始暴露 state、confidence、version 与 fallback 接口，使跨阶段 controller 能决定“算多少、复用什么、何时升级”。

值得押注：hybrid sparse+dense+graph、temporal/provenance score、confidence-controlled depth、query-adaptive precision、generated index asset、embedding code + quantization。

Tab 02 · 粗排 / Pre-ranking

从“轻模型筛候选”走向“下游偏好感知 + 与精排联合训练”

核心任务：在极紧 latency 下保住真正会被精排选中的 item。传统优化往往只追粗排本地 AUC/NDCG，容易出现 stage mismatch。

工作核心机制工业信号当前启发
COPR / Rethink / HCCPranking supervision → pre-ranking alignment成熟工业路线下游 preference 应进入上游训练，但仍是单向 teacher-student
UniRecshared embedding + vertical consistency + joint fusion快手已全量部署粗排最终 fusion 本身要与精排共同优化，而不只改 backbone score
ReST / shared user state长序列 user representation 复用线上 A/B 路线粗排要把更多预算留给 candidate interaction，而不是重复编码 user history

重点指标：除本地 NDCG/AUC 外，必须看 ASH / ranking top-K survival / candidate recall、latency、feature freshness 与 downstream consistency。

Tab 03 · 精排 / Ranking

从共享 Backbone 走向 Task-aware Information Flow 与跨阶段 Fusion

工作研究问题价值
PTDG任务依赖不应对所有 item 固定item-conditioned dynamic task graph
MOREtask signal 如果只在 tower 末端出现已经太晚task anchor 进入 backbone 各层；陌陌线上多目标提升且 latency 约 -30%
UniRec精排 fusion 与粗排 fusion 独立会互相抵消ranking agent 与 pre-ranking agent 同图优化；AppUsageTime +0.616%
UniCon上下文级 candidate interaction推动 candidate/context 统一建模

下一步：task-aware foundation ranker + request-level user state + candidate-adaptive compute + cross-stage consistency + multi-objective group-relative regularization。

Tab 04 · 重排与混排 / Re-ranking & Slate

从逐 item 打分走向结构化 assignment、可验证 evidence 与业务约束

工作关键问题落地启发
hLLM / Hungarian assignment排序是 permutation，没必要自回归生成 N 个序号single-pass score matrix + assignment 更符合结构
CHyD生成解释/引用可能不来自 evidencehard lexical constraint 保证引用来自检索上下文
TimelyRAG相关但过期的文档/内容应该降权temporal validity 可看作 rerank constraint
MORE / multi-objective ranker不同业务目标需要不同 evidence flow最终 slate 之前保持 task-specific representation

值得押注：assignment + diversity + freshness + creator/business constraints；生成式 rerank 的目标不是“会生成列表”，而是把复杂 constraint 与 explanation 做成可验证 structured decision。

Tab 05 · 跨阶段统一 / Cross-stage Control Plane

训练边界、状态边界、预算边界正在同时重构

Temporal / Version StateTimelyRAG把有效期、版本与 provenance 变成 ranking contract

终局形态：不是“一个超大模型吞掉所有阶段”，而更像 统一训练/表征资产 + stage-local executors + runtime controller。Controller 根据 confidence、SLO、cache/state compatibility、freshness、业务价值决定下一跳。

推荐算法工程师当前最值得补的技能：① multi-stage learning / distillation / joint optimization；② retrieval + ANN + quantization；③ LLM/RAG serving 与 KV/state lifecycle；④ routing / confidence calibration / escalation；⑤ structured reranking 与 business constraint；⑥ 用线上 A/B、stage survival、latency/cost 一起判断研究价值，而不只看离线 AUC。
