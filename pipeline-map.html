今天的推荐链路已经不是“每一层一个独立小模型”。召回开始生成化和状态化，粗排开始 GPU 深模型化，精排开始 foundation / continual scaling，重排开始 reasoning / context construction，而跨阶段层负责共享 representation、state、measurement 与 serving policy。

召回粗排精排重排与混排跨阶段统一
链路总判断：未来不是取消所有 stage，而是让 user/item state、Semantic ID、objective、counterfactual logs 跨 stage 共享；不同 stage 则按 inventory size、latency、feature availability、precision 与 hardware 选择 specialist executor。9/24 的 Spotify Robust Fusion 进一步补上一个重要变量：特征是否可用，本身也应定义 execution regime。

从 ANN / 多路召回 → Generative Retrieval → Stateful / Multi-executor Recall

核心目标：在百万/十亿级库存中，用极低成本最大化 downstream value coverage，而不是只最大化 embedding similarity。

Tab 02 · 粗排

从小模型过滤器 → GPU Deep Pre-ranking → Feature-join-aware Serving

核心目标：在数万候选到数百候选之间，尽量避免不可逆的信息损失，同时满足极窄 SLA。

LinkedIn Connected Content Retriever

十亿级 connected-content index 经网络约束到数万候选，再用 GPU sorted-search 在约 5–10ms 内 join viewer-author 图亲和与文档特征，使 pre-ranker 能使用更完整 ranking model；参数规模约提升 50×，线上 content time spent +2.5%。

精读 →

这一层的核心矛盾

粗排的瓶颈不再只是 FLOPs，而是 feature join、memory layout、batch shape、graph lookup 与 GPU utilization。如果特征获取够快，粗排模型未必必须“小”。

值得押注

  • GPU-resident / near-GPU feature store 与 sorted join。
  • teacher-ranker distillation + high-capacity pre-ranker。
  • 动态 candidate budget：复杂用户/查询多算，简单请求早退。
  • 召回 source provenance 在粗排阶段显式建模。
Tab 03 · 精排

从 Feature Interaction → Foundation Ranker → Behaviour-aware LLM Ranker

核心目标：在有限候选上最大化多目标业务价值，同时稳健处理长历史、行为偏差、分布漂移和多任务。

Spotify Robust Fusion · Personalised Search LLM Rerank

0.6B cross-encoder 同时消费 Semantic ID、query/item 文本、用户近期行为与 QSS；dual-sample feature dropout 让模型在行为统计缺失时仍保持语义排序能力。离线 NDCG@7 在 QSS 存在时约 0.549→0.622；线上 search success 约 +2%。

Tab 04 · 重排与混排

从 Listwise → Set-wise → Reasoning / Context Construction → Learned Search Policy

核心目标：候选已经不多，最终问题从“谁分高”变成“这一组是否完整、互补、可信、满足约束，并值得花多少 reasoning budget”。

Answer-Oriented Context Construction

把 AI Search 最后一段从 document relevance 改写成 Answer Support → Trustworthiness → Context Organization，将检索评估与最终回答质量串起来。

Tab 05 · 跨阶段统一

Shared Representation + Shared State + Execution Controller + Measurement

这一层不是另一个 ranker，而是新的系统骨架。 它负责让 stage 之间共享语义、状态、策略和可观测性，同时允许 retrieval/rank/serving 仍使用不同 executor。

Flash-dLLM · IO-aware Runtime

把 cache 与 verify 联合设计，证明 serving policy 必须理解真实 HBM traffic。

跨阶段下一步

  • 统一 state contract：user/item/semantic/behaviour/evidence/KV 都有 version、TTL、confidence。
  • 统一 controller：输出 source、budget、model、precision、reasoning、cache、halt 的 execution plan。
  • 统一 measurement：candidate provenance + stage attribution + propensity + trajectory failure。
  • 统一回滚：representation 可以共享，但 executor / policy 必须可分阶段降级。
