KDD 2026 收官后的推荐主线：
Transformer-native Ranking、20K 长序列与可对齐 Foundation Model

过去 24 小时公开索引的新推荐论文数量有限，因此今天不硬凑“新标题”，而是结合刚于 8 月 13 日结束的 KDD 2026，对最值得补齐的工业推荐工作做一次收官式筛选，并补充最新 arXiv / RecSys 2026 Industry Track 工作。重点不是会议名单，而是三个正在合流的系统问题：Ranking 架构统一、长序列 Serving、Foundation Model 的业务目标对齐。

今日核心结论：① Ranking 正从“Transformer Encoder + 多任务 MLP Tower”转向 Transformer-native end-to-end prediction；② 长行为序列不再只拼长度，Teacher 保全信息、Student 压 Token 的 Distillation 正成为更现实的 Serving 路线；③ 推荐 Foundation Model 的后训练开始显式区分“下游适配”和“业务指标对齐”；④ LLM 推荐里的 RAG / Agent 也在走推荐系统熟悉的 Router → Expert → Policy 路线；⑤ 生成式推荐的 Semantic ID 正从“统一编码”走向“共享粗粒度 + 域自适应细粒度”。

时间口径：KDD 2026 于 2026-08-09 ～ 08-13 在济州举行。部分今天重点补齐的论文预印本提交日期早于过去 24 小时；这里将“刚结束会议中值得补齐的工业工作”和“最新 arXiv 工作”明确区分，不把会议展示日误写成论文提交日。

重点论文 01 · Ranking Architecture · KDD 2026

OneRank: Unified Transformer-Native Ranking Architecture for Multi-Task Recommendation

RUC × Shopee × NTU · KDD 2026 · Multi-task Ranking / Transformer-native / Production A/B

OneRank 最值得看的不是“又一个 Transformer Ranker”，而是它直接质疑工业排序里延续多年的结构惯性：为什么强大的 Transformer 只能负责 Encoder，最后还要把所有任务压成共享表示，再交给静态 MLP Tower 做 Click / Cart / Order 预测？

1. 现有问题：Transformer 变强了，但 Prediction 端还停在 DNN 时代

传统多任务 Ranker 常写成 Encoder F(X) → Shared Representation Z → 多任务 Predictor G(Z)。模型规模扩大后，这个接口产生三类瓶颈：任务差异被过早压进同一个 Z；不同任务的梯度在共享 Encoder 中发生 seesaw；Attention 的动态信息路由最终被静态 MLP Head 截断。也就是说，模型“前半段像 LLM，后半段还是经典 CTR Tower”。

2. 核心方案：把多任务推理内化进 Transformer

  • Task-specific Token + Mutual Invisibility：每个候选拥有不同任务 Token，同任务获得专属信息通道，不同任务 Token 互不可见，避免一开始就把任务语义揉在一起。
  • Candidate-aware Contextualization：用 Situational Descriptor 对整组候选做 Cross-Attention，显式看到候选之间的竞争关系，缩小 point-wise training 与 list serving 的 gap。
  • Cross-task Relational Attention + Gradient Detach：前向允许任务间读取信息，反向切断 off-diagonal 梯度，把其他任务变成“read-only memory”，减少负迁移。
  • Dynamic Matching Scoring：用 task-aware global state 与 candidate representation 做匹配，替代固定 MLP Scorer。

3. 训练：Listwise + Pointwise 同时保留

OneRank 没有为了“统一”而丢掉工业系统对 Calibration 的需求。它把 InfoNCE listwise objective 与 BCE pointwise objective 联合训练：前者服务候选相对排序，后者保留可解释、可融合的概率口径。这一点比只做 list generation 的学术 Ranker 更容易进入现有业务链路。

4. Serving：统一架构不等于一次把所有候选塞满

Shopee 在线场景可面对最高 4096 个候选，论文采用 8×512 的候选分组并行评分，并对 user-specific context 做 KV cache。这里暴露了 OneRank 的现实边界：Candidate-aware Attention 的价值来自 list context，但候选数越大，跨候选上下文化成本也越明显。

5. 线上 A/B：商业指标和体验指标同时正向

线上指标作者报告相对提升
GMV / UU+1.01%
Paid GMV / UU+1.17%
AR / UU+0.81%
Bad Query Rate−2.29%

Shopee 主个性化排序场景，7 天 A/B（2026-01-08 ～ 01-14），10% treatment / 10% control；以上均为论文作者报告，不是第三方复现。

6. 我认为真正的研究价值

OneRank 把“Ranking Foundation Model”往前推了一步：不是把 Encoder 做得越来越大，而是尝试让 Representation、Task Interaction、List Context、Scoring 都保持同一种 Attention-native 信息流。它与 RankMixer / OneTrans 的关系更像“继续统一架构”，而不是单纯堆参数。

7. 局限与下一步

  • 论文主配置规模仍不算大，是否能稳定扩展到数亿/数十亿参数 Ranking Model 尚未被证明。
  • Cross-task mask 仍含领域先验；更值得研究的是自动学习哪些任务该读谁、读多少。
  • Gradient detach 是强约束，可能也切掉部分有益的反向协同。
  • 候选上下文化需要继续与粗排/精排预算联合设计，而不是只看模型离线 AUC。

8. 对推荐工程师的启发

如果你研究精排/多目标，OneRank 比“再叠一层 Expert”更值得读。未来精排的研究问题可能从 Feature Interaction 转向 Tokenization、Attention Mask、Cross-task Memory、List Context 与 Serving Layout。

重点论文 02 · Long Sequence × Serving

TM20K: Teacher Retains Full Tokens, Student Merges Efficiently

ByteDance · 2026.08 · E-commerce Ads · 20K Sequence / Full Attention / Distillation

长序列推荐最容易陷入“序列越长越强，但 Serving 越做越重”。TM20K 的价值在于它没有退回轻量 Target Attention，而是坚持 Teacher / Student 都使用 Full Attention，再把昂贵的完整 Token 信息集中在训练期 Teacher，线上 Student 用 Token Merge 控成本。

1. 核心矛盾：长序列的信息量和二次复杂度同时增长

20K 级电商行为同时包含长期品类偏好、近期购买意图、重复曝光和跨场景行为。传统 Search/Cluster Compression 会先删信息；DIN 类 Target Attention 又往往只能建模“当前 Target 看历史”，难以充分捕获 history-history 的结构关系。TM20K 选择先让 Full Transformer 把信息学全，再解决压缩。

2. Teacher–Student 设计

20K Full Tokens→Full-Attention Teacher→Distillation→Token-Merged Student→Online Serving

Teacher 是一次性重训练的高成本模型，尽可能保留完整序列；Student 同样保留 Full Attention 的建模方式，但在进入深层计算前通过多种 Token Merge 策略压缩长度。随后两阶段蒸馏把 Teacher 的能力传到 Student。这里的关键思想是：压缩放在 Student 的计算图里，而不是在数据入口粗暴删历史。

3. 工业结果

证据结果口径
最长行为序列20KByteDance 电商广告线上系统
ADSS+1.036%作者报告线上业务指标
Serving Latency仅 +5.6%相对在线 SOTA 基线
训练/Serving Cost近似保持作者描述

4. 为什么比“单纯长序列”更重要

这篇论文把 Scaling 的问题从“能不能吃 20K”改成“谁需要吃完整 20K，以及完整信息在哪个阶段最值钱”。它和 Sona 的 History Compression、KSA 的 Summary Token 本质上在回答同一个工业问题：保留长时兴趣，但不要让每一层、每一次请求都为所有 Token 付费。

5. 局限

  • Teacher 成本被移到训练侧而不是消失，大规模频繁迭代时仍需算总 TCO。
  • Token Merge 如果只对平均用户有效，极少数“稀疏但关键的远距离行为”可能被压掉。
  • 论文证据集中在电商广告，内容推荐/搜索中的 Query-sensitive 历史压缩仍需重新验证。

6. 下一步研究问题

比固定 Merge Ratio 更值得押注的是 request-aware token budget：不同用户、不同 Target、不同请求阶段动态决定保留哪些 history token、在哪层 merge、是否调用长序列 Teacher/Heavy Student。

重点论文 03 · Foundation Model × Post-training

Progressive Alignment of Recommender Foundation Model through Multi-Phase Post-Training

WEBTOON · RecSys 2026 Industry Track · LP → FFT → RFT · Open Source

这篇论文很像推荐版的“Foundation Model Alignment 教科书雏形”：预训练模型学到长周期用户行为，并不等于下游 SFT 后自然对齐业务目标。作者明确把 Adaptation 和 Business Alignment 拆成两个问题。

1. 为什么单阶段 SFT 不够？

点击、点赞等标签密集，适合训练 Policy；真正关心的业务指标往往更稀疏、延迟更长。如果直接拿稀疏业务标签 Fine-tune 大模型，梯度不稳定、数据覆盖不足；如果只用 Click/Like，则 Policy 可能学得很准但并不对齐平台价值。

2. 三阶段后训练

  • Linear Probing (LP)：先冻结 Foundation Model，只把随机初始化的下游 Head 调稳，避免一上来 FFT 让随机 Head 的噪声污染预训练表示。
  • Full Fine-Tuning (FFT)：在 Head 已经进入合理工作区间后，再联合更新整个模型，完成场景适配。
  • Reinforcement Fine-Tuning (RFT)：Policy 继续从密集 implicit feedback 学习，而稀疏业务目标用于训练 Reward Model，再通过 reward 对 Policy 做 alignment。

3. 最值得借鉴的设计：Sparse Business Label 不直接承担 Policy Supervision

这解决了推荐 RL 中一个经常被忽略的问题：Reward 的标签和 Policy 的可学习密度不是一回事。把业务指标当 Reward supervision，而不是硬塞进每个样本的多任务 loss，可以把“偏好学习”和“业务价值校准”解耦。

4. 证据

作者报告 LP-FFT-RFT 在离线实验中优于单阶段适配方案，且 Reward-based alignment 的最终 Policy 优于直接拿 Reward Model 做 Ranking；大规模线上 A/B 相对传统非 Foundation Model 基线取得正向提升。论文摘要未披露可安全引用的具体线上百分比，因此本站不自行补数字。

5. 工业价值与局限

它的价值不是提出新的 RL 算法，而是给推荐 Foundation Model 一个更清晰的生命周期：Pretrain → Stable Adaptation → Business Alignment。局限也很明显：Reward Model 的偏差、分布漂移和 reward hacking 会成为新单点风险；不同 serving surface 是否共享同一 Reward Space 仍是开放问题。

重点论文 04 · LLM Recommendation × KG-RAG · KDD 2026 Oral

MixRAGRec: Mixture-of-Experts KG-RAG for Multi-Agent LLM Recommendation

KDD 2026 Oral · Multi-Agent / KG-RAG / MoE Router / MMAPO

MixRAGRec 把 RAG 推荐里最关键、却常被固定配置隐藏掉的问题显式化：不同 Query 到底该拿多细的 Knowledge Graph Evidence？简单请求拉一大块 Subgraph 是过检索，复杂请求只拿几个 Triple 又是不足检索。

1. 三个协作 Agent

  • MoE Retrieval Agent：把 Query 路由到不同粒度 KG Expert，学习“Direct / Triple / Subgraph”一类不同检索预算。
  • Knowledge Preference Alignment Agent：把结构化 KG 转成 LLM 更容易消费的偏好证据，降低 Graph-to-Text 的结构损失和噪声。
  • Recommendation Agent：用 Contrastive Preference Feedback 学最终推荐。

2. MMAPO：Router 没有直接标签怎么办？

“这条 Query 应该选哪个粒度”通常没有 ground-truth，只能从最终推荐效果反推。论文因此用 Mixture-of-Experts Multi-Agent Policy Optimization 联合训练三 Agent，使 retrieval choice、evidence alignment 和 recommendation outcome 在同一目标下信用分配。

3. 为什么值得推荐工程师看？

它和工业推荐的 Router/Cascade 很像：请求难度不同 → 选择不同 Expert/Cost → 中间证据需要对齐 → 最终用业务/偏好结果训练 Router。换句话说，Agentic RAG 正在重新发现推荐系统早已熟悉的 adaptive compute allocation。

4. 证据与成熟度

论文在多个真实数据集上给出离线提升，并被作者页面标为 KDD 2026 Oral；当前没有真实生产线上 A/B，因此工业成熟度低于 OneRank/TM20K。优点是代码公开，可复现性明显更好。

前沿工作 05 · Generative Cross-domain Recommendation

HD-Rec: Hierarchical Quantization with Domain-Adaptive Sparse Routing

2026.08 · Semantic ID / Cross-domain / Sparse MoE

Cross-domain GenRec 的核心冲突是：SID 要跨域共享才有迁移价值，但不同域又需要足够表达容量。HD-Rec 用“共享粗粒度 Codebook + 路由到域相关细粒度 Codebook”解决这组矛盾。

模型进一步加入常开 Shared Expert + 动态 Specialized Expert 的 Sparse MoE，并用 Cross-granularity Routing Consistency 约束同一个 Item 的多个 SID Token 不要各走各的专家。三个公开跨域推荐 Benchmark 上均优于有竞争力的 Sequential / Generative / Cross-domain Baseline。

我的判断：这比“每个域单独 tokenizer”更值得研究，因为它开始把 Semantic ID 本身变成可路由的层级表示。但目前仅有离线证据，尚不能和 Sona/JD GenRec 的工业成熟度相提并论。

前沿工作 06 · Ranking Model Optimization

MISO: Model-Internal-State-Guided Optimization for Ranking Models

2026.08 · RecSys 2026 OARS Workshop · Model Debugging / Scaling Workflow

MISO 不是一个新的 Ranker，而是在回答一个算法团队每天都会碰到的问题：模型已经很复杂时，下一轮到底该扩哪层、删哪层、替换哪个组件？

它从训练好的 Ranking Model 中抽取参数、激活、梯度、归一化统计等 Model Internal States，形成 ranking / alignment / comparison signals，再给出少量可解释的候选修改。每次重训练后重新提取状态，因此不是一次性诊断，而是迭代式 model optimization loop。

Ads Ranking Case Study 中，作者报告 MISO 在改善 Normalized Entropy 的同时，所需验证轮次显著少于专家手工和黑盒 Scaling Workflow。它当前更像“推荐模型研发 Agent”的底层观测层：未来若与自动代码修改/A-B Agent 结合，模型内部状态可以成为比最终指标更细的反馈。

今天这些工作放在一起，意味着什么？

一句话趋势：推荐系统正在从“把更多能力堆进一个大模型”转向“把计算、任务、Token、Reward 和 Expert 都变成可路由、可对齐、可分阶段训练的系统资源”。OneRank 在任务维度统一信息流，TM20K 在 Token 维度分配计算，Progressive Alignment 在监督信号维度拆适配与业务目标，MixRAGRec/HD-Rec 则在 Knowledge/SID/Expert 维度做动态路由——这些看似不同的论文，正在收敛到同一个问题：Adaptive Computation + Structured Alignment。

对你当前研究方向最值得跟的 4 个问题

  1. 精排：Task Token + Cross-task Attention 能否替代 MMoE/PLE 式 Expert Routing，并稳定扩到更大 Ranking Model？
  2. 长序列：Token Merge 是否可以从静态规则升级成 Target/User-aware learned router，并与 KV Cache/History Compression 联合优化？
  3. 重排/生成式推荐：Reward Model 如何同时表示 CTR/GMV/体验/长期留存，而又避免 reward hacking？
  4. Agent/Search：Router 的训练是否可以直接复用推荐系统的 Calibration、Cascade、Bandit 和 cost-aware ranking 经验？
