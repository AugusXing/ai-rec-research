重点论文 01 · Full-stack Generative Recommendation

Sona Technical Report

Yandex Music · 2026.08.11 · Generative Recommendation / Unified Retrieval & Ranking

这篇论文最重要的不是 Semantic ID 或某个 Transformer 结构，而是它在真实线上流量里回答了一个架构问题：成熟推荐系统的“15+ Candidate Generators → Pre-ranking → Ranking”是否可以被一个联合训练的生成式模型替代？Sona 给出的答案是：在 Yandex Music 的一个核心场景里可以，而且关键指标显著提升。

1. 项目背景：为什么要挑战 Cascade？

大型工业推荐系统往往不是一个模型，而是多年叠加出来的 pipeline。Yandex Music 原生产链路包含 15 个以上候选生成器、Pre-ranker、Ranker，以及数百个手工/统计特征；Ranker 还消费来自大型 Transformer 用户模型 Argus 和 target-attention scorer 的信号。这样做的优势是模块职责清晰、容易逐步优化，但代价也明显：每个阶段重复学习用户兴趣、特征工程和 Serving 依赖越来越复杂，且 Recall 与 Rank 的训练目标并不天然一致。

2. 核心问题

  • Representation Fragmentation：Recall、Pre-rank、Rank 维护不同 User Representation，重复计算“这个用户现在喜欢什么”。
  • Pipeline Complexity：多路召回和数百个 engineered features 增加开发、迭代、数据一致性与 Serving 成本。
  • Generator–Ranker Distribution Mismatch：Ranker 训练看到的候选分布和当前 Generator 真正生成的候选可能不同。
  • 生成式召回的 Coverage 风险：自回归模型天然容易集中于高概率 Item，可能失去传统多路 Recall 的长尾覆盖。

3. 技术方案：Shared Encoder + Decoder + Ranking Module

User Event History→Shared User Encoder→Generative Decoder→Candidate Items→Ranking Module

用户的时间序列日志只编码一次。Encoder 输出同时被自回归 Decoder 和 Ranking Module 使用；Next-token Prediction 与 Ranking Distillation 又共同反向更新 Encoder，所以 Retrieval Signal 与 Ranking Signal 最终汇聚在同一个 User State 中。

Semantic ID：Item 不再是一个超大 Softmax ID

每首歌曲被编码成多层 Semantic ID。内容侧先利用多模态模型提取音频、标题、歌手、Tag 等语义，再通过协同行为做 refinement，因此 token 既包含 content semantic，也包含 collaborative semantic。这样 Decoder 可以像语言模型生成 token 一样生成 Item，而不是在千万级原始 Item ID 上直接做巨大 Softmax。

History Compression：8192 个历史事件不等于 8192 个 Token 全层 Self-Attention

Sona 最终使用多达 8192 个用户历史事件，但把近期兴趣和长期兴趣按不同计算分辨率处理：近期行为进入更深层 self-attention，较旧历史使用更轻量的处理与跨块信息交换。这一设计的工程含义很直接：long-term memory 可以低分辨率，short-term intent 必须高分辨率。

Teacher Rollout Distillation：解决“生成器与评估器不一致”

训练期还有一个更强的 Teacher Ranker，但它不进入线上 Serving。当前 Decoder 先通过 beam search rollout 出它真正会生成的候选，再由 Teacher 给这些候选打分，Ranking Module 学习 Teacher。相比静态蒸馏，这种 on-current-policy 的 candidate distribution 更接近线上分布，因此显著缓解 Generator–Ranker mismatch。

4. 训练目标

可以粗略理解为两个目标共同优化 Shared Encoder：一部分是自回归 Next-token Prediction，学习“用户下一步可能消费什么”；另一部分是 Teacher Ranking Distillation，学习“这些当前生成候选如何排序”。这使生成和排序不再是两套割裂表征。

5. 效果：线上 A/B 才是这篇论文真正有分量的部分

最终实验持续 7 天，Control 与 Sona 各覆盖约 15% 随机用户；Sona 直接替换原推荐 Stack，同时保留必要 hard rules。

7. 局限与未来研究

  • 尚未 Full Traffic，长期数月实验仍待验证。
  • 目前主要验证一个 recommendation surface，跨场景泛化未知。
  • Coverage / Exploration 是最关键未解问题之一。
  • 作者提出 MoE、Sparse/Linear Attention、Persistent Cross-request KV Cache、Beam-based Test-time Scaling 与 RL。
  • Recommendation RL 下一步真正困难的是长期 Reward：Likes、Watch Time、留存与兴趣探索如何共同优化。

8. 对推荐工程实践的启发

如果你在研究生成式召回/重排，最值得复用的不是把现有系统“一刀切换成生成式”，而是三个思想：共享 User Foundation Representation、让 Ranker 训练分布跟随当前 Generator rollout、把 Teacher 放训练端而非 Serving 端。这三点都可以先局部迁移到现有 Recall/Rank 架构。

重点论文 02 · Agentic Search / Context Ranking

Mitigating Context Interference for Reliable and Efficient Search Agents

ACL 2026 · 2026.08 · Search Agent / Context Refinement / RL

这篇论文把 Search Agent 的失败拆成了两个阶段：Retriever 有没有找到证据，以及 LLM 在一堆证据里能不能正确使用它。作者发现，最主要的干扰甚至来自“最新一次检索返回的文档”，因此提出先 Refine Context，再继续 Reasoning。

1. 背景：Search 越多为什么可能越差？

多轮 Search Agent 会不断累积 Query、Retrieved Docs、Reasoning、Observation。传统直觉是更多检索意味着更高 Recall，但 Agent Context 有容量和注意力限制：每一轮 Top-K 中的 irrelevant passages 会直接参与后续推理，从而形成 Context Interference。

2. 一个很重要的诊断实验

作者分别消融旧 Query、旧 Reasoning、旧 Documents 等 Context 组成，发现主要干扰来源不是“很久以前的历史”，而是最新检索结果中的噪声文档。这意味着传统 IR 指标里“召回到了答案”并不能保证 Agent 最终回答正确：Retrieval Success ≠ Knowledge Utilization Success。

3. Context Refiner

Search Query→Retriever Top-K→Context Refiner→Critical Evidence→Reasoning

Refiner 的任务不是泛化式摘要，而是围绕当前 Query 提取真正支撑下一步推理的 Evidence。强 Teacher 先生成高质量 refined context，再蒸馏给较小模型；作者还使用 entailment 检查，尽量确保 Refiner 不凭空引入外部事实。

4. CRRL：把 Context Refinement 放进 RL Rollout

作者进一步提出 Context-Refined Reinforcement Learning：Agent 在训练 rollout 中每次 Search 之后先做 Refine，再 Reason / Act。这样训练时看到的 trajectory 就更干净，而不是只在 inference 末端做一次 post-processing。

5. 实验结果

Qwen2.5-7B 平均结果EM ↑Avg Retrieval Times ↓
IRCoT27.52.6

6. 与传统 Reranking 的关系

这项工作的工程意义非常像在 RAG 中增加一个新的精排层：Retriever 排“哪些文档要找回来”，Context Ranker/Refiner 决定“哪些 Evidence 值得消耗 LLM Context Budget”。未来的 Agent Search 很可能形成 Query Planning → Retrieval → Evidence Ranking/Compression → Reasoning → Next Search 的结构。

7. 局限与未来

  • 当前以封闭 QA 和 Wikipedia 为主，长网页、开放 Web、企业知识库仍待验证。
  • Refiner 还是外挂模块，未来可以把“Observation → Select Evidence → Act”内化到 Agent Policy。
  • 值得研究的目标从 relevance 扩展到 downstream utility：一个 passage 是否相关不重要，重要的是它是否改变下一步正确决策。

8. 对搜索/推荐工程师的启发

Learning-to-Rank 的能力可以直接迁移到 Agent：以后不只排 Item/Document，还要排 Evidence、Tool、Memory、Model。Context Budget 本身会成为新的稀缺资源。

论文 03 · Multi-modal Recommendation

TimeRoute: Time-Aware Modality Routing and Diffusion for Multi-Modal Recommendation

多模态推荐过去常问“文本和图片怎么融合”，TimeRoute 进一步问：为什么同一个用户在不同时间还要使用固定的模态权重？

背景与问题

文本、图片、音频的价值会以不同速度随时间漂移。节日、季节、生命周期和短期意图可能让视觉、文本或协同信号的重要性发生快速变化；固定的 global fusion weights 会把过时模态继续传播进用户图。

方案

  • Temporal-aware Modal Router：根据用户聚合行为与 temporal context 输出个性化 modality distribution。
  • Diffusion-based Graph Reconstructor：用同一个 temporal profile 通过 FiLM 条件化图重建。
  • Long / Short-term dual denoising heads：在图传播前抑制过时或噪声模态边。

效果与判断

在 TikTok、Amazon-Baby、Amazon-Sports 上，作者报告 Recall/Precision/NDCG 最高提升 9.8%，并采用 10-seed paired tests。不过它目前只有公开数据集离线结果，没有线上 A/B，因此我会把它归类为“思路值得跟，工业成熟度待验证”。

未来方向

更值得延展的不是 Diffusion 本身，而是 Dynamic Modality Routing：把时间进一步扩展为 scene、device、traffic source、promotion、user lifecycle 等实时状态，做 request-level 模态预算分配。

工程动态 04 · Agent Execution Model

NVIDIA Nemotron 3.5 Lightning

真正值得关注的不是“30B 模型”本身，而是 Agent 系统开始明确拆成 Planning Model 与 Execution Model。

Lightning 是约 30B 总参数、每 token 约 3B active parameters 的 MoE，定位 tool calling、validation、delegation 等高频、结构化执行任务，而不是承担所有高难 reasoning。它支持 speculative decoding、NVFP4/BF16 等部署选择。NVIDIA 的性能数字属于厂商自报，需等待独立 benchmark。

工程启发：Agent Serving 很可能像推荐系统一样发展出“粗排/精排式模型级联”：大模型只处理高价值困难步骤，大部分 routine actions 由便宜模型执行。

工程动态 05 · Model Routing

NVIDIA NeMo Switchyard

Model Router 开始从简单的“按规则选模型”变成同时考虑任务难度、质量、成本、Latency 与 Agent State 的可学习决策层。

Switchyard 支持 classifier、stage、escalation、A/B 等 routing 策略，也支持 OpenAI、Anthropic、自托管 vLLM/NIM/Ollama 等 backend。NVIDIA 报告的一个 escalation 实验中，只约 7% 请求升级到 frontier model，成本约降低 74%，代价是约 6 个百分点准确率下降；这是厂商/合作方 benchmark，不应直接外推到所有 workload。

为什么推荐工程师会很熟悉：Task ≈ User Request，Candidate Models ≈ Candidate Items，Router ≈ Ranker/Policy，目标则变成 Quality − Cost − Latency。未来 Model Routing 本质上会越来越像 Learning-to-Rank。
