推荐系统的新控制面：
Representation × Freshness × Adaptive Compute

过去 24 小时最值得关注的一组工作来自 arXiv 8 月 26 日新批次。今天不是又出现了一个“更大的推荐 Transformer”，而是多个工业团队同时把问题往更底层推进：快手 TAGR 证明生成式推荐如果不能让 Semantic ID、用户意图和 Preference Optimization 随环境变化而更新，就很难进入直播广告这种分钟级非平稳场景；腾讯 Tlow 与 WeMM-Embedding 分别从离散 Tokenizer 和连续 Embedding 两端重做 Item Representation；淘宝 NMRL 则用线上实验反证“直接把 CTR loss 端到端反传给多模态 Encoder”这一看似自然的路线；阿里 RecGPT-Mobile-V2 进一步把推理长度和端云路由都变成按请求动态分配的预算。今天最重要的共同信号是：Representation 已不再只是模型输入，而正在变成推荐 / 搜索系统的控制面。

今日核心结论：下一阶段的工业推荐，不会靠“一个统一的大模型把所有信号都吃掉”，而会靠一组可动态管理的共享接口：Fresh Semantic Namespace、Task-native Embedding、Intent State、Evidence Graph 与 Request-level Compute Budget。 对推荐 / 搜索工程最值得押注的三条线是：① Semantic ID 从静态量化走向可更新、可并行、可跨域的 Token Infrastructure；② 多模态表示从通用预训练走向 Recommendation-native Supervision，但监督必须先去噪而不是直接吃原始 CTR；③ Serving 从固定模型 / 固定维度 / 固定 CoT 走向 query-conditional compute allocation。

01 · Full-stack Generative Recommendation / Ads · 今日精读

TAGR：生成式推荐真正进入动态广告场景，关键不是更大 Backbone，而是“三层时序自适应”

Research Impact Score / 研究价值 9.9/10工业成熟度 ★★★★★创新性 ★★★★★与你方向相关度 ★★★★★是否官方开源 否 / 未确认是否有线上 A/B 是阅读优先级 最高

背景 / 业务动机

直播广告是生成式推荐最难工业化的场景之一：直播间内容、正在售卖商品、主播状态和用户反馈都在分钟级变化。传统判别式召回至少可以依赖实时特征和在线索引，而很多 GenRec 方案默认 Item Semantic ID 是离线固定、用户行为序列用一个统一时间尺度建模、Preference Optimization 又依赖滞后的离线样本。这样一来，生成器学习到的其实是“昨天的 inventory 与昨天的 preference”。TAGR 的价值就在于它没有只改网络，而是把 Token、Intent、Alignment 三层一起改造成可随生产环境更新的系统。

现有问题

作者把失效拆成三类。第一，Static SID 对直播广告不稳定：同一个直播间今天卖鞋、十分钟后卖美妆，静态内容 token 很快过期。第二，单尺度行为序列无法同时表达“长期偏好”和“刚刚进入几个直播间形成的短期意图”。第三，持续用最新行为做 on-policy preference optimization 虽然新鲜，却容易破坏已有生成分布；完全离线训练又会错过环境漂移。

技术方案与关键模块

LSID（Live Semantic-Collaborative ID） 定期根据当前直播画面与在售商品刷新 active ad 的语义表示，再分配层次化 token，同时保留稳定 token vocabulary，并用主播哈希等方式降低碰撞。关键不是“每天重训 tokenizer”，而是保持语法稳定、映射可更新。IAG（Intent-Aware Generation） 将直播间进入序列作为主意图通道，以不同 stride / 时间尺度编码短期与较长时段兴趣，并把点击、加购等辅助行为分通道输入；训练时不再对所有 NTP token 等权，而用 post-request 行为强度、用户价值和商业价值共同加权。IOPO（Intermittent On-Policy Preference Optimization） 则周期性从当前 policy 采样候选做行为 / 价值对齐的 GRPO，中间穿插监督 NTP maintenance step，避免持续 RL 把基本行为分布冲掉。

训练方法

主训练仍以自回归 Next Token Prediction 为稳定底座，IAG 把 post-request intent evidence 与商业价值写进 token loss 权重；Preference 阶段同时有 Behavior-Aligned 与 Value-Aligned reward，后者由 Reward Model 对 post-exposure engagement 与 normalized eCPM 建模。IOPO 的设计非常值得工业团队参考：不是把整个推荐器长期置于纯 on-policy RL，而是让新鲜 policy rollout 只作为间歇校正，再回到可控的监督分布。

推理 / Serving 方案

系统每分钟级刷新活跃直播广告的 LSID，更新 LSID↔LiveID 在线映射而无需重建全局索引。请求到来时自回归 beam search 生成 Top-256 LSID，再解析成 active live ads，进入下游过滤与排序。论文给出的工程指标非常硬：经过 decode 与 cache 优化后，单张 L20 GPU 超过 2500 QPS，端到端生成式召回延迟低于 100ms。这证明 GenRec 是否能工业化，核心约束其实是“动态 namespace + constrained decode + cache/index 协同”，而不只是离线 Recall。

实验设置 / 离线指标 / 线上 A/B

线上是多周随机实验，覆盖 10% 生产流量、超过 4000 万用户，主指标是真实广告收入。完整 TAGR 相对生产 DLRM：直播间进入率 +8.5%、加购点击率 +7.4%、Revenue +16.1%；低价值用户收入 +28.8%，冷启动直播流收入 +18.4%。分阶段消融也很清晰：仅 LSID 已将收入提升推进到约 +9.9%，加入多尺度意图 / 加权 NTP 后继续上升，最后 Value-Aligned IOPO 到 +16.1%。这比只报告离线 HitRate 更能证明“Freshness”是生产 GenRec 的一级变量。

效率 / 成本收益

TAGR 没有通过频繁全量重训解决变化，而是把高频变化收敛到 SID assignment、在线映射、意图输入和小段 on-policy 更新。这样把“分钟级 freshness”与“较慢 backbone 学习”解耦。工程上它带来的启发是：高动态业务首先应该设计可局部更新的 representation plane，而不是把所有变化都压给参数 refresh。

与主流方法的优劣势 / 适用场景

相对静态 OneRec / Semantic-ID GenRec，TAGR 的优势是能处理 inventory 与 meaning 同时变化的非平稳环境；相对 DLRM / Two-tower，它能把召回目标和价值信号统一到生成过程，但 Serving 和 namespace 管理显著更复杂。它最适合直播、电商广告、热点内容、短生命周期 item；对稳定长尾 catalog，如果变化不快，动态 LSID 的收益可能抵不过运维成本。

局限 / 尚未解决的问题 / 未来研究方向

当前方案仍依赖固定层次 vocabulary，频繁 remap 会引入 token churn、历史样本可解释性和模型记忆错位；IOPO 的 reward 也主要来自平台内部 engagement / value。下一步真正值得研究的是 version-aware SID、跨时间 token consistency、fresh-item zero-shot assignment、policy update 与 namespace update 的双时间尺度稳定性，以及生成式召回和下游精排之间如何共享价值模型。

对推荐 / 搜索算法工程落地和职业技能的启发

如果准备下一代推荐系统，不要只会训练 Transformer。需要具备四类能力：Semantic ID / Tokenizer、实时特征与索引、RL/Reward Modeling、GPU Serving。TAGR 很典型地说明，未来高级推荐算法岗位的边界会从“model owner”扩大到“representation + runtime owner”。

02 · Semantic ID / Generative Retrieval · 今日精读

Tlow：先把 Embedding 空间“变简单”，再做 Tokenization，可能比继续堆复杂量化器更重要

Research Impact Score / 研究价值 9.8/10工业成熟度 ★★★★★创新性 ★★★★★与你方向相关度 ★★★★★是否官方开源 是是否有线上 A/B 是阅读优先级 最高

背景 / 业务动机

Semantic ID 的一个长期矛盾是：RQ-VAE 能保留层次语义，但 residual codebook 有强依赖，生成时必须逐层 decode；PQ / OPQ 可以独立量化、并行解码，却默认各子空间相对独立，而真实语义 embedding 往往高度相关、分布也很复杂。Tlow 的切入点非常好：不要先问“量化器还能多复杂”，而是先问“为什么要在一个难量化的空间里硬做量化？”

技术方案与关键模块

Tlow 在 item semantic embedding 和独立 tokenization 中间加入一个可逆 Normalizing Flow。具体是 Glow 风格的 ActNorm + Invertible Linear + Affine Coupling，把原始复杂分布映射到近似标准正态 latent，使维度相关性显著降低。随后用简单独立分块量化即可得到 token。第二个关键模块是 Codebook Guidance：让量化 codebook 的几何关系与推荐模型里 token embedding 的几何关系保持一致，避免 tokenizer 学出的 code 在下游序列模型中被重新扭曲。

训练方法

论文使用 Sentence-T5-base 的 768 维 item semantic embedding，Flow 采用多 block / 多 step 可逆变换；latent 分块后做独立 K-means / product-style tokenization。序列推荐侧使用 GPT-2 风格 Transformer。与 RQ-VAE 最大的结构差异是：多个 token 之间不再有 residual dependency，因而可以在一次 forward 中并行预测，而不是层层 autoregressive codebook decoding。

推理 / Serving 方案

在线微信图片召回中，模型读取最近约 500 个点击 item 的 token 序列，12 层 Transformer 生成用户表示 / token 表示，再作为 DSSM 之外的补充召回通道。部署上一个很关键的收益是参数表：例如 C=16、每个子码本 256 个 code，只需要约 4096 个 token embedding，而不是数千万 item ID embedding；新图片发布时只要通过内容 encoder + Flow + tokenizer 就能立即得到 token，因此天生适合冷启动。

实验设置 / 离线指标 / 线上 A/B

四个 Amazon 数据集的 16 个核心指标均取得最好结果，相对强基线提升约 1.97%–11.52%；跨域和多模态实验仍保持优势。工业结果更重要：微信图片推荐单域 pathway 对比中，CTR +4.79%、UCTR +10.32%，新品 CTR +8.46%、UCTR +11.64%；跨域场景 CTR +6.23%、UCTR +7.20%，新品 CTR +9.09%、UCTR +9.45%。真实 A/B 的平台核心指标也有增益：单域 24h 图片 CTR +0.78%、新品 +1.94%，跨域人均图片 CTR +1.05%，头部账号曝光占比下降 1.15%，说明 long-tail coverage 同时改善。

效率 / 成本收益

它的效率收益来自两个层面：一是 token 独立，可并行生成；二是把巨大的 item embedding table 换成小型共享 token vocabulary。对数千万 / 亿级 item catalog，第二点可能比模型 FLOPs 更值钱，因为它同时减少参数、同步、冷启动等待和跨域重复存储。

与主流方法的优劣势 / 适用场景

相对 RQ-VAE / residual tokenizer，Tlow 的优势是 decode 简洁与低依赖；相对纯 OPQ，它通过 Flow 主动改善数据分布。最适合多模态 item、跨域召回、新品多的内容平台。代价是 Flow 本身也要学习并维护，且“标准正态 + 低相关”是否总是最适合推荐任务仍取决于原 embedding 的质量；若原表示缺少 collaborative signal，几何变简单也不会凭空补出协同信息。

局限 / 尚未解决的问题 / 未来方向

下一步值得把 Tlow 和近期 Dynamic Single-Level SID、SST、ANR-DiffRec 放到同一个问题框架里：先优化 representation geometry，再决定 code hierarchy，再决定 history / target grammar，再决定 serving decode path。此外需要研究 Flow 版本变化带来的 token churn、增量 item 映射稳定性，以及是否可以把 collaborative graph / CTR supervision直接纳入 flow target。

对工程落地和职业技能的启发

Semantic ID 不应只被当作“一个 VQ-VAE 小模块”。真正有价值的工程能力包括 embedding geometry audit、码本 utilization、token collision、cold-item assignment、index/serving compatibility。Tlow 是很适合精读并自己复现的一篇。

03 · Multimodal Foundation Representation / Retrieval · 今日精读

WeMM-Embedding：多模态 Embedding 从“离线榜单模型”变成微信检索 / 排序 / 序列建模的共享基础设施

Research Impact Score / 研究价值 9.8/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向相关度 ★★★★★是否官方开源 是是否有线上 A/B 是阅读优先级 最高

背景 / 业务动机

推荐和搜索里的“多模态 embedding”过去经常是一个旁路 feature：视觉模型单独训练，离线抽向量，再 concat 到主模型。WeMM-Embedding 更接近 Foundation Representation：同一套模型覆盖文本、图片、视频、视觉文档和交错多模态输入，并直接服务 Candidate Retrieval、Ranking Feature、User Sequence Modeling、Cross-domain Understanding。对工业系统而言，这比某一个 benchmark SOTA 更重要，因为它意味着内容语义第一次可以成为跨链路共享资产。

技术方案与关键模块

模型提供 2B / 4B / 9B 三档。训练是两阶段：Stage 1 在数亿级异构多模态 pair 上做广覆盖对齐，把不同任务统一成 source-target matching；Stage 2 用更高质量 curated data、graded relevance、reranker supervision 与跨尺度 distillation 精调。为处理“不是所有正负样本差异都一样”，引入 score-gap-aware 的 CoSENT 类目标；同时使用 Matryoshka Representation Learning，使同一模型可以按部署预算输出多种 embedding width。小模型还从 9B teacher 蒸馏，9B 最终通过 specialized checkpoints 合并增强通用能力。

训练方法

核心仍是大规模对比 / 排序式 embedding learning，但监督不是简单 binary pair：Stage 2 强调 graded relevance 与高质量 hard negatives，并按任务选择 reranker teacher。Matryoshka 让多个前缀维度同时接受监督，因此推理侧可以在一次 forward 后截取 64/128/256/... 等不同宽度并归一化，而不是为不同索引成本训练多套模型。

推理 / Serving 方案

WeMM 使用专用 embedding token / hidden state 提取统一表示，可处理单图、文本、视频和交错输入。生产里同一表示既能进入 ANN retrieval，也能变成 ranking similarity feature，还能作为用户序列中的语义 item state，甚至进一步量化成 Semantic ID。这里最重要的架构趋势是：Embedding Model 不再属于某一个召回通道，而是成为 Retrieval → Ranking → Sequential Rec 共用的 Representation Service。

实验设置 / 离线指标 / 线上 A/B

MMEB-v2 上 2B 模型达到 77.9，已经略高于此前 8B 开源强基线 Qwen3-VL-Embedding-8B 的 77.8；4B 达 79.2，9B 达 80.6，论文按 2026-08-24 leaderboard 状态称其位列第一。内部 26 个任务也取得显著提升。更关键的是，模型已经用于微信公众号、视频号、朋友圈与电商等推荐 / 搜索系统，并在 14 个线上 A/B 中持续获得正收益，随后推广到生产；论文未逐项披露每个业务的具体百分比，因此不应把离线榜单提升误写成线上提升。

效率 / 成本收益

2B 即能达到 / 超过许多 8B 级公开 embedding 模型，说明其 data curriculum 与 distillation 带来的“每参数有效性”很高。Matryoshka 又允许不同场景在相同模型上按存储 / ANN latency 选维度。对亿级 item 系统，embedding width 的降低直接影响向量库存储、网络传输、ANN bandwidth 和 cache residency，因此是实打实的成本变量。

与主流方法的优劣势 / 适用场景

相对 CLIP-style 双塔，WeMM 对任意多模态组合更灵活；相对把通用 MLLM 直接取 hidden state，它通过专门 embedding objective、curation 和 distillation 获得更稳定检索几何。适合图文 / 视频内容平台、商品搜索、跨域检索和多模态冷启动。局限是 MLLM 级 encoder 的离线抽特征成本仍高，实时 query 侧如果包含复杂视觉输入也要考虑 latency。

局限 / 尚未解决 / 未来方向

当前仍未覆盖音频；线上 A/B 只披露“一致提升”而没有任务级数字；通用表示与业务 native 表示之间仍存在 NMRL 所指出的 supervision gap。未来非常值得研究 WeMM-like universal encoder + task-native adapter / mining + AdaWidth-style request width routing + Tlow-style discrete tokenization，把连续与离散 representation 真正统一成平台能力。

对推荐 / 搜索算法工程落地和职业技能的启发

值得把“Embedding Engineering”当成独立技能栈：对比学习 / CoSENT、hard-negative mining、distillation、Matryoshka、ANN、向量量化、线上 feature reuse。它已经不只是 NLP / CV 基础模型团队的工作，而会越来越直接影响推荐主链路。

04 · CTR / Multimodal Ranking · 今日精读

Native Multimodal Representation：淘宝用生产数据证明“CTR 端到端联训 Encoder”并不天然正确

背景 / 业务动机

工业推荐常见两阶段范式：先训练一个场景多模态 encoder，再离线抽 item representation，冻结后喂给 ID-based CTR 模型。直觉上更进一步的做法是把 encoder 接到 CTR 网络里端到端联训，让下游 loss 直接塑造内容表示。但淘宝的实验结果恰恰说明：在已有强多模态 encoder 和强 ID 模型的前提下，这个直觉会失败，而且失败不是调学习率能解决的。

现有问题

作者给出两个本质原因。第一，CTR label 不是纯内容语义监督：点击还受到价格、位置、曝光偏差、偶然点击、兴趣疲劳等因素影响，单靠 image/text similarity 对 CTR 的可解释性很弱。第二，共享多模态 encoder 会让这些非语义因素的梯度在大量 item 之间传播；ID embedding 因参数局部化反而不会出现同样污染。实验证据很强：原有 SCL 训练的梯度一致性明显高于 CTR E2E 联训，而直接 E2EM 甚至带来性能退化。

技术方案与关键模块

方案叫 Mine-Then-Train。不是让 encoder 直接吃所有 CTR 样本，而是先训练一个 Annotation Model，识别“这一次点击偏好有多少可以由多模态内容解释、并且提供了现有 ID / semantic feature 之外的增量信息”。随后从海量 CTR 日志中挖出高置信 preference triplet，再用这些干净的、multimodally interpretable supervision 微调原 SCL encoder。这样把“业务目标适配”与“原始点击噪声”隔离开。

训练方法

Mining 阶段冻结已有强 encoder，并在推荐模型内训练 annotation / residual preference 模块，筛选能够表达 user 对两件 item 内容偏好的 pair / triplet。Training 阶段用 ranking / triplet-style loss 对 encoder 做推荐原生化，同时保留原表示约束以避免 catastrophic forgetting。真正的关键不是 loss 形式，而是 先选择哪些 CTR 样本有资格监督共享表示。

推理 / Serving 方案

上线非常简单：训练完的 Native Multimodal Representation 继续按原有两阶段方式离线抽取，原 CTR Serving Pipeline 基本不变。NMR 被用于目标 item 与用户历史 item 的语义相似度、序列模块以及 ID representation 的融合。因此它避开了在线跑大多模态 encoder 的 latency，也避免 E2EM 给主训练图带来的显存爆炸。

实验设置 / 离线指标 / 线上 A/B

淘宝一个月展示广告数据上，强 baseline 已包含已有 SCL multimodal representation。直接 E2EM 不增反降；仅加入 Annotation Score，GAUC / AUC 约 +0.13% / +0.08%，而 Mine-Then-Train 得到的 NMR 约 +0.22% / +0.11%。更重要的是 2026 年初长期线上 A/B：CTR +1.5%，RPM +0.5%。对于成熟广告精排，这类线上收益很有分量。

效率 / 成本收益

论文也给出 E2EM 代价：不做端到端时峰值 GPU 约 3.37GB、step 1.02s；只联训 target encoder 已到 5.71GB / 1.94s；如果 target + sequence item 都联训，峰值显存 84.56GB（25.09×）、step 7.32s（7.18×）。Mine-Then-Train 把大 encoder 训练从日常 CTR 主任务中拆出去，收益不仅是更准，也是训练系统显著更可控。

与主流方法的优劣势 / 适用场景

相对“通用多模态 encoder 冻结使用”，它更贴近真实点击偏好；相对 E2E co-training，它通过 sample mining 避免 label ambiguity 和梯度污染。适合已有海量 CTR 日志、强多模态基础表示和成熟 ID ranker 的电商 / 广告系统。缺点是 mining pipeline 较复杂，annotation model 自己的 bias 会决定最终表示学到什么。

局限 / 尚未解决 / 未来方向

一个非常值得追的方向是把 “Mine-Then-Train” 与在线学习结合：哪些行为可以解释为内容偏好可能随场景、用户生命周期变化；还可以把 click 之外的 conversion、dwell、skip、purchase 与 causal debiasing 纳入 sample qualification。更进一步，Representation Model 的训练目标可能应该由 多任务可解释增量 定义，而不是任一单目标 CTR。

对推荐 / 搜索算法工程落地和职业技能的启发

这篇对精排工程师特别重要：不要默认“端到端”就是更先进。共享 encoder 的梯度是不是干净、label 是否能归因到该 modality、主任务 cost 是否可接受，都要做机制诊断。推荐算法能力正在从“搭模型”升级到 supervision design + gradient audit + representation data engine。

RecGPT-Mobile-V2：把“用户行为 → Query Recall”做成端侧能力，真正创新点是 Sufficiency-oriented Reasoning

Research Impact Score / 研究价值 9.6/10工业成熟度 ★★★★★创新性 ★★★★★与你方向相关度 ★★★★★是否官方开源 否 / 未确认是否有线上 A/B 否 / 未披露阅读优先级 最高

背景 / 业务动机

Personalized Query Prediction 的目标是把隐式推荐行为——点击、收藏、购买、购买后的继续浏览——转换为显式搜索 intent，再形成一个新的 query-based recall channel。相比直接 next-item 预测，它能进入搜索基础设施、覆盖不同 inventory；但端侧部署又带来三重挑战：用户轨迹很长且噪声大，同一轨迹往往有多个合理 query，所有请求统一跑长 CoT 会浪费算力，而完全压短又伤害复杂意图。

技术方案与关键模块

RecGPT-Mobile-V2 是一个完整 staged system：先做 Evidence-preserving Trajectory Compression，把数百条原始行为过滤 / 聚合成更短的 intent-bearing history；再做 Recommendation-native Domain Adaptation + SFT；随后只有在 rollout 已满足 grounding / utility 条件时才加入 reasoning-cost optimization。Teacher 最后蒸馏成小型 student，并结合低比特、结构压缩和 device-cloud routing。最核心理念不是“最短 CoT”，而是 Sufficiency-oriented Reasoning：只保留做出正确 query 所需的最小充分证据。

训练方法

论文显示短而证据聚焦的 rationale 反而比完整五阶段解释更好：ROUGE-L 0.228→0.315，Jaccard 0.174→0.248。RL 使用 grouped relative optimization，但对长度惩罚做了系统消融。简单直接扣长度会把模型推到“不思考直接输出”的 reward hack；最终方案使用质量 gate、input-specific budget、单侧超预算惩罚、multiplicative reward 与 rank protection，使模型先保证 query quality，再压缩多余 reasoning。

推理 / Serving 方案

系统先评估请求复杂度 / 置信度：简单轨迹直接本地生成，中等请求允许更多内部 compute，歧义 / 多意图或预算风险高的请求才升级到更重路径 / 云侧。Teacher→Student 后再进行 tensor-granular mixed precision、QAT recovery、权重 / activation / KV 的硬件友好低比特执行。它真正把 Model Routing + Reasoning Routing + Device/Cloud Routing 放在了一张图里。

实验设置 / 离线指标 / 在线证据

控制实验中，quality-only RL 的 Query quality 73.2%、hard failure 3.6%、CoT P50 62 token；完整 A6 策略达到 78.6%、hard failure 1.6%、CoT P50 14 token，相当于在质量更高的同时把中位 reasoning 长度减少 77.4%。论文没有披露标准业务 A/B 百分比，但线上 retrieval analysis 表明生成 query 的召回结果与既有 recall channel 有明显互补性，因此应标注“线上分析有，正式 A/B 未披露”。

效率 / 成本收益

Accelerator 路径平均 latency 从 3.00s 降到 0.76s（3.95×），P95 8.00→1.70s，P99 10.0→2.5s；isolated decode 2.12×，TTFT 1.42×、TPOT 1.27×；Desktop CPU 总 latency 4.13→2.70s。这个结果说明端侧 LLM 优化不能只看量化：先减少无效 reasoning token，再做 low-bit / kernel 优化 的收益往往更大。

与主流方法的优劣势 / 适用场景

相对传统 Query Rewrite / Query Suggestion，它能从非搜索行为推断 intent；相对云端大 LLM，它通过 request-aware budget 和 student 化适合隐私 / latency 敏感端侧。适用于电商 App、内容搜索入口、跨推荐→搜索召回。缺点是 Query quality evaluation 本身依赖复杂 rubric / teacher，且“互补召回”还需要转化到真实 CTR / CVR / GMV 才能确认长期价值。

局限 / 尚未解决 / 未来方向

下一步需要把路由策略和真实 downstream value 联动：不是按语言复杂度决定 cloud escalation，而是预测“额外 20ms / 20 token 是否会增加有效 recall”。同时可与 User Behavioral Densing Law 结合，把 history token budget、reasoning token budget、embedding width、模型大小统一成 request-level compute allocator。

对推荐 / 搜索算法工程落地和职业技能的启发

做 LLM + 推荐不要只盯 SFT / GRPO。端侧场景要求掌握 trajectory compression、reward design、distillation、quantization、latency decomposition 和 routing。未来推荐系统里的“推理优化”会越来越像一个策略学习问题。

EviGraph：把 Agent 搜索从“找到了什么”推进到“哪些证据真正支持了哪些结论”

Research Impact Score / 研究价值 9.2/10工业成熟度 ★★★☆☆创新性 ★★★★★与你方向相关度 ★★★★☆是否官方开源 否 / 未确认是否有线上 A/B 否阅读优先级 高

核心不是再加一个 Retriever，而是把 Evidence Construction 变成可验证的中间状态与可训练 reward。

Executor 负责规划简洁 query；冻结的 evidence verifier 从网页抽取逐字 evidence 并显式标注 polarity；训练 policy 再把 evidence 写成 add/support graph request，由 deterministic validator 检查结构。Graph 同时作为 persistent working memory 与 dense process reward 来源，避免只在最终答案正确/错误时给一个稀疏信号。BrowseComp-Plus 上 Qwen3-8B EviGraph 在相同交互预算下达到 35.9%，同一 dual-role 架构不做 RL 为 26.9%，monolithic agent 仅 2.7%，且 rollout token 更少。对搜索 / 推荐的可迁移点是：未来复杂 rank / agent pipeline 需要显式保存“为什么这个候选被保留”的 evidence state，而不是只保存自然语言 trace。

07 · Recall / Cold Start / Open Index · 高价值补充

RetrievalFormer：Search + Recommendation 共用索引时，“能随时接纳新 Item”本身就是模型能力

Research Impact Score / 研究价值 9.0/10工业成熟度 ★★★☆☆创新性 ★★★★☆与你方向相关度 ★★★★★是否官方开源 否 / 未确认是否有线上 A/B 否阅读优先级 高

它最值得读的不是一个新 Transformer，而是把“开放索引 vs warm 推荐精度”的代价算清楚。

在同时覆盖 search / recommendation 的公开日志里，38.6% held-out query-search impressions 对应此前从未曝光 / 访问过的 item；ID-softmax 推荐器要等重训才能纳入它们，而 feature dual tower 可以立即编码进入 ANN。严格 zero-leak cold-start 下内容塔 Recall@20 为 0.172±0.006，是最强专用 retrained baseline 0.124±0.007 的 1.4×；但 warm 推荐仍落后强序列模型：MovieLens Recall@20 相对差 5.2%、NDCG@20 差 11.4%，MIND 差距约 0.8–3.6%。论文进一步发现 ANN 不是主要损失源，真正的瓶颈是训练：Exact full-softmax 相比 sampled InfoNCE 可让 MIND-small Recall@20 +54%，但到 240K catalog 就显存耗尽。结论很有工业意义：Search/Rec 统一召回的核心 open problem 不是 ANN，而是 catalog-scale exact-quality contrastive training。

AdaWidth：同一个 Dense Retriever，不同 Query 不应该支付相同向量宽度

Embedding dimension 也可以像模型路由一样，按请求难度动态付费。

固定 Matryoshka truncation 给所有 query 同一前缀宽度，而 query-specific arbitrary mask 又要求后端仍存取完整向量。AdaWidth 先学习一个正交 prefix adapter，对 query / doc 做相同旋转，在不改变 full-width inner product 的前提下把关键信号集中到前部维度；在线 router 从当前 ranking 的 order statistics 判断 Top-K 是否已经稳定，不够稳定才升级到更宽 prefix。六个检索任务、五种 frozen encoder 上，在接近 SOTA NDCG@10 的同时平均每 query 少用 55–84% 维度。它与 RecGPT-Mobile-V2 今天形成同一个趋势：Serving Budget 必须 request-aware。

今日技术判断 · 从 8 篇工作抽象出的路线

今天值得带走的不是 8 个模型名，而是 5 个工程判断

Static Representation→Task-native / Fresh Representation→Shared Retrieval & Ranking Asset→Request-aware Budget→Closed-loop Feedback
  • Semantic ID 会平台化。 Tlow 解决 geometry / parallel decode，TAGR 解决 freshness；未来 tokenizer 的 KPI 会同时包含语义、协同、碰撞、稳定性、增量更新和 serving cost。
  • 通用 Embedding 与业务 Native Embedding 会分层，而不是二选一。 WeMM 提供强共享底座，NMRL 说明业务适配要先筛 supervision，再做 task-native fine-tuning。
  • Cold Start 不是一个“补丁任务”，而是索引是否开放的系统属性。 RetrievalFormer 说明 search / rec 统一时，能否 features-only 接入新 item 会决定整个架构。
  • Adaptive Compute 会横跨多个层级。 AdaWidth 调 embedding width，RecGPT 调 reasoning / model / device path；下一步自然是统一成 expected utility per FLOP / per millisecond 的路由器。
  • Agent / RAG 需要结构化中间状态。 EviGraph 把 evidence graph 变成 memory + reward，和推荐里的 SID / user state 一样，核心资产逐渐从“模型参数”转向“可验证、可更新的中间表示”。
