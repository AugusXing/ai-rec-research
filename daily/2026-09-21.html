Deep Dive 01 · Sparse Attention / llama.cpp

Qwen4 Sparse FA：Sparse Attention 开始真正进入通用推理 Fast Path

Research Impact Score / 研究价值 9.1/10 · 工业成熟度 ★★★★☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★☆ · 是否官方开源 是 · 是否有线上 A/B 否 · 阅读优先级 S

一句话：这次 merge 的价值不是“又快了 10%～20%”，而是 Qwen4 的 sparse attention 不再停留在模型定义层，llama.cpp 已经开始为它建立条件化的 CUDA 执行路径。

背景 / 业务动机

长上下文里 full attention 的主要问题不只是 FLOPs，而是每一步需要重新处理越来越大的 KV 范围。Qwen4 的稀疏注意力若在 runtime 里仍按完整 KV 处理，就无法兑现架构设计的成本优势。PR 明确指出此前这条 attention path 未优化，整个 KV cache 会被反复重新打分。

现有问题

稀疏结构只有在“被选中的 token 足够少”时才值得切 fast path；过早切换会让 gather、索引与 kernel 固定开销抵消收益。因此 runtime 需要不仅知道模型是 sparse，还要知道当前 context 长度与候选 token 上界。

技术方案与关键模块

实现以 ncols1=8 聚合实际使用 token 的 union；根据最多会触达的 token 数决定是否启用 sparse FA。Qwen4 当前阈值对应约 32,768 context：在短 context 继续走已有路径，长 context 才切到 sparse fast path。这是一种非常典型的 shape-aware execution routing。

训练方法

不适用。这是推理 runtime merge，不修改模型训练或权重。

推理 / Serving

优化落在 CUDA Flash Attention 路径，Serving 价值随 context 增长而增加。对生产系统更重要的是需要把“模型结构 + 当前 shape + kernel crossover point”一起纳入 dispatch，而不是静态绑定一种 attention backend。

实验设置与离线指标

官方 PR 在 DGX Spark 上给出 Qwen4 experimental A3B IQ1_S 测试：prefill pp2048@d10k/20k/50k/100k 的 speedup 约 1.08× / 1.09× / 1.16× / 1.26×；decode tg32 在相同 depth 下约 1.03× / 1.14× / 1.18× / 1.18×。收益随长上下文增长，是符合 sparse fast path 预期的曲线。

线上 A/B / 成本收益

没有线上 A/B。成本收益目前是单机 runtime benchmark；尚不能直接外推到 continuous batching、多并发和不同 GPU。

相对主流方法的优劣势

优势：保留原模型输出语义，直接减少不必要 attention work；无需额外训练。不足：当前仍有 KV rescore 等后续优化空间，而且 crossover point 强依赖模型、硬件和 batch shape。

适用场景 / 局限 / 未解问题

最适合长 context 本地推理、长文档 RAG、Agent memory。值得继续看三件事：KV 选择能否增量维护；continuous batching 下不同 sequence 的 sparse pattern 如何合批；runtime 是否能在线学习阈值而不是硬编码。

对推荐 / 搜索算法工程的启发

这和推荐粗排/重排的动态预算本质相同：不是所有 request、候选、历史 token 都值得付全量计算。未来做推荐 foundation model，除了模型结构，还要懂 kernel crossover、KV/state layout 与 batch scheduler。

Deep Dive 02 · mHC / vLLM

DSV4.1 mHC Overlap：跨层系数生成进入 Side-stream Scheduling

Research Impact Score / 研究价值 9.0/10 · 工业成熟度 ★★★★☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★☆ · 是否官方开源 是 · 是否有线上 A/B 否 · 阅读优先级 S

一句话：mHC 的核心成本越来越不是一次大 GEMM，而是“小 batch 下很多结构性小操作无法隐藏”；vLLM 开始把系数生成主动与 attention / FFN overlap。

背景 / 现有问题

DeepSeek V4.1 一类 mHC / hyper-connection 结构引入额外 coefficient 与跨层混合。小 batch decode 时，GPU 更容易处在 launch / dependency bound，而不是算力饱和。若系数生成串行阻塞主路径，即使单算子很小，也会拉长每 token critical path。

技术方案

vLLM 保留统一的 mHC dispatcher，但对满足条件的小 token batch，把 shifted mHC coefficient generation 放到 side stream，与 attention/FFN 重叠；decoder 在真正消费结果前 join。启用条件包括 SM100/DeepGEMM、无 ubatching、投影维度满足约束，并用 16 tokens 作为保守 cutoff；大 batch、draft layer、piecewise/breakable graph 继续 native path。

训练方法

不适用，纯 Serving scheduling。

实验 / 指标

GB200×4、TP4 的固定 forward 测量中：1 token 约 -1.49% latency，6 token -4.42%，8 token -4.28%，12 token -1.57%，16 token -1.12%；24/48 token 开始转负，因此选择 16 作为 crossover。最终 head 的 real 8K/1K C1 mean TPOT 从 5.013ms → 4.992ms（约 -0.4%），forward-only 约 -1.5%。79 个 GPU focused tests 通过。

准确率 / A/B

无线上 A/B。最终 GSM8K flexible extraction 1266/1319 → 1271/1319，作者强调 cross-arm 不是 bitwise parity，并对 JIT warmup 与 serving tail burst 给出限制说明。这类透明 caveat 本身很值得学习。

成本收益与局限

这是典型“小收益、巨大规模价值”的 infra 优化：单请求只有 0.x%～4.x%，但 decode critical path 会被每个 token 重复。局限是收益强依赖 shape / hardware，不能把 TP4 GB200 的 cutoff 机械复制到所有拓扑。

与推荐 / 搜索的连接

推荐线上系统同样常被“小算子 + 同步 + RPC barrier”限制。模型结构变复杂后，应建立 critical-path profiling + overlap scheduling + shape-aware fallback 的工程能力，而不只看 FLOPs。

Deep Dive 03 · mHC Kernel Fusion / SGLang

GLM-5.3-Flash mHC Boundary Fusion：小 batch 时，Launch Count 本身就是模型结构成本

Research Impact Score / 研究价值 8.9/10 · 工业成熟度 ★★★★☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★☆ · 是否官方开源 是 · 是否有线上 A/B 否 · 阅读优先级 S

一句话：GLM-5.3-Flash 一次 forward 有 90 个 mHC post→pre boundary；在 6-token verify batch 下，每个 boundary 的 3 次 launch 已经比实际计算更值得优化。

问题与方案

原路径是 mhc_post → pre-norm GEMM → mhc_pre_big_fuse 三次 launch。SGLang 复用 DeepSeek-V4 已有的 fused boundary dispatcher，把 mhc_post 合并进 pre-norm GEMM，变成两次 launch；45/90 个 boundary 可融合，其余还需要 cross-layer deferral。为了避免大 shape 退化，GLM callback 只在 ≤16 tokens 启用。

训练 / Serving

训练不适用。Serving 中这个优化尤其适合 speculative verify 的小 token batch；当 c=64、verify batch=384 tokens 时自动拒绝 fused path。

实验设置与指标

GLM-5.3-Flash，TP4，4×GB300，8192 in / 1024 out，c=1。官方按 session 交错测试，verify steps/s 分别 78.55→79.07（+0.66%）、77.99→79.82（+2.34%）；c=64 基本不变。GPQA Diamond thinking-on 为 92.42%（183/198）。微基准显示 ≤6 tokens 约 1.40×，8–16 约 1.17×，24 接近 1.00×，32 开始退化，因此 threshold 有明确证据。

优劣势 / 局限

优点是复用共享 dispatcher，避免模型专属 kernel 体系继续分叉；局限是阈值只覆盖一组 GLM shape / hardware，17–23 tokens 未充分测量，而且另一半 boundary 仍未融合。

下一步

更值得研究的不是继续手调一个 cutoff，而是让 runtime 维护 kernel cost model，按 {model shape, batch, TP, speculative width, GPU} 自动选择 fusion / overlap / native path。

Deep Dive 04 · MoE Precision / Speculative Serving

MiMo V2：BF16 Router + MXFP4 Experts + DFlash 把“精度预算”拆到模块级

Research Impact Score / 研究价值 8.9/10 · 工业成熟度 ★★★★☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★☆ · 是否官方开源 是 · 是否有线上 A/B 否 · 阅读优先级 S

一句话：低比特 Serving 正从“整个模型 FP4”变成“router 保 BF16、expert 用 MXFP4、再叠 speculative decoding”的组合优化。

业务动机 / 现有问题

MoE 的 router 决定 token 送到哪个 expert，误差会改变离散路径；expert GEMM 则更适合低比特吞吐优化。因此把 router 与 expert 用同样精度并不一定合理。与此同时，MoE 大模型 decode 仍需要 speculative path 降低 target forward 次数。

方案

SGLang 新增 MiMo V2 的 MXFP4 MoE、BF16 MoE router、DFlash speculative decoding 支持。官方 launch example 覆盖 TP4/EP4 的 MiMo V2 flash 与 TP8/EP8 的 Pro，结合 DeepGEMM、DeepEP、FA4、DFlash，context length 示例达到 1,048,576。

训练方法

不修改训练；使用官方/公开模型权重与 draft model。该 merge 主要解决 runtime operator、parser 与 serving plumbing。

实验 / 指标

PR 没给公开端到端吞吐数字，但新增 8-GPU runner 的 FP4 MiMo-V2 DFlash GSM8K + acceptance-length coverage，并明确通过。这里应把它视为“能力进入主线 runtime”，而不是宣称已有确定的性能领先幅度。

工程价值

对推荐大模型很直接：未来大规模 MoE ranker / generative retriever 也应该把 routing-sensitive path 与 matrix-heavy expert path 分开制定 precision policy，而不是只做统一量化。

Deep Dive 05 · Speculative Decoding Correctness / vLLM

Dummy Draft Step 写坏 KV：高性能 Runtime 最难的问题常常不是 Kernel，而是“状态语义”

Research Impact Score / 研究价值 8.8/10 · 工业成熟度 ★★★★★ · 创新性 ★★★☆☆ · 与你方向的相关度 ★★★★☆ · 是否官方开源 是 · 是否有线上 A/B 否 · 阅读优先级 S

一句话：Data Parallel 空闲 rank 为保持图执行而跑 dummy batch，但 draft multi-step decode 仍通过持久 block table 计算了真实 slot mapping，最终把 drafter K/V 写进旧请求的 prefix-cache block。

现象为什么危险

在 GLM-5.2、MTP k=5、DP=4 EP、prefix caching 场景中，故障表现为某个 conversation 的 MTP acceptance 永久掉到 0，直到 reset prefix cache；target model 的 KV 仍正常，只有 drafter K/V 被污染。这类问题极像“模型突然不会 speculative decoding”，而不是常见 crash。

根因与修复

之前的保护只清了 read-side input block tables，但 fused multi-step path 内部重新计算 slot mapping 时仍读取 persistent table。修复把 dummy / CUDA-graph padding 的 idx_mapping 统一设为 -1，kernel 遇到负值直接输出 PAD_SLOT_ID，绝不 dereference block table。保护放进 kernel，是因为 CUDA graph replay 期间 Python 层来不及重新拦截。

验证

4×GB200 的生产几何复现中，未修版本 transition hunt 首轮即可出现 DEAD；修复后 3×20 chain 0 dead、6/6 hunt trials 0 dead，记录的 66,164 次 dummy draft decode step 全部为 PAD。单测 10 passed。

线上 A/B / 成本

没有 A/B，也不应该用 A/B 衡量这种 correctness fix。其价值是消除低频但会污染后续请求的 latent state bug，避免 prefix cache 把错误跨请求传播。

对推荐 / 搜索工程的启发

推荐系统里 cache、feature snapshot、session state、candidate pool 都可能跨请求复用。性能优化中必须明确 dummy/padding/expired request 的 state ownership，并把 invariant 放在真正执行写入的底层，而不是只在上层 API 做校验。

Update 07 · Ascend / GDN / SSM State

SGLang：Chunk Gated Delta Rule + 统一 SSM State Layout
