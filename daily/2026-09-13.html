Magenta 的 statement judge 与 error-attribution judge、RecGP 对 transfer robustness 的研究都说明：仅看最终 reward 不够，必须显式建模验证、归因、边界与风险。

Deep Dive 01 · Small Foundation Model / Agent

MiniCPM5-2B：2B 模型真正值得看的不是参数量，而是“训练资产 + Agent 能力 + Serving 格式”一起交付

Research Impact Score / 研究价值 9.3/10工业成熟度 ★★★★☆创新性 ★★★★☆与你方向的相关度 ★★★★☆是否官方开源 是：权重/数据/多格式 artifact是否有线上 A/B 否阅读优先级 S+

背景 / 业务动机：在推荐、搜索、Agent 系统里，绝大多数在线决策都不值得调用最大模型：query 改写、意图分类、召回充分性判断、工具参数抽取、简单 rerank、memory write gate 更需要低成本、低延迟、可本地部署。小模型真正的价值因此不是“和大模型比聊天”，而是能否成为稳定的control-plane model。

模型与关键模块：MiniCPM5-2B 为 2,516,756,480 参数标准 LlamaForCausalLM，42 层，GQA 16 Q heads / 2 KV heads，原生 131,072 context。官方同时提供 BF16 final、SFT-only、midtrain、base、GGUF、MLX 4-bit、GPTQ 4-bit、LiteRT-LM，以及独立 DSpark draft model。这一点对工业部署比单一 leaderboard 分数更重要：同一训练体系可以覆盖服务器、Apple Silicon、llama.cpp 和端侧 runtime。

训练方法：训练链条分 base training、mid-training、post-training。post-training 先使用 400B tokens deep-thinking SFT，再训练 math/code/agentic/writing 等多个 RL teacher，最后用 On-Policy Distillation（OPD）把 16 个 expert model（其中 5 个 agent expert）回蒸馏到单一 release checkpoint。OPD 在每个位置用 teacher/student full-vocabulary reverse-KL 构造 advantage，直接复用 RL teacher prompts，不再额外造一套蒸馏 corpus。

数据开放：官方同步公开 UltraX、UltraData-Code、UltraData-SFT-Agent-2609（500K agent training samples）和 UltraData-RL-2609（80K+ math/code/general/long-context RL samples）。这使它比“只开权重”的小模型更有研究价值：可以追训练 recipe 的贡献，而不是只做黑盒 benchmark。

实验结果：官方比较集平均分 53.9；LiveCodeBench v6 69.1、AIME 2026 86.5、NoLiMa 68.1、τ²-Bench Telecom 97.1、BFCL v4 66.6、SWE-bench Verified 46.4、BrowseComp-ZH 43.5、GAIA Text-103 88.7。官方消融称 RL+OPD 相对前阶段使 reasoning/general 平均 +10.96 points，agentic 能力平均 +6.96 points。这些数字是官方报告，不等同于独立第三方复现。

推理 / Serving：官方给出 vLLM、SGLang、llama.cpp、Transformers 路线；SGLang 还可挂载 MiniCPM5-2B-DSpark 做 speculative decoding。这里最值得推荐/搜索团队借鉴的是：目标模型与 draft/control model 可以被成套设计，而不是推理优化阶段再临时找一个 drafter。

效率 / 成本收益：官方没有给统一的 server QPS / TTFT 成本表，因此不能仅凭 2B 参数推断线上节省比例。但从 4-bit artifact、GGUF/MLX、standard Llama architecture 和 DSpark draft 的完整性看，它明显以多硬件低成本部署为一等目标。

与主流方法的优劣势：相比 Qwen/Gemma 同量级模型，优势是 Agent 数据与多阶段 checkpoint 更开放、tool/search/coding agent 指标较突出；劣势是模型更小导致知识与复杂推理上限仍受限，且官方榜单不替代你自己的 query/rerank 分布评测。

推荐/搜索落地：优先测试四个位置：① query understanding / rewrite；② retrieval sufficiency 与 rerank gate；③ tool/router；④ offline annotation teacher 的 student。不要先拿它替代精排主模型，而应先评估“每 1ms / 每 1k token 能做多少控制决策”。

局限 / 未解决：缺线上 A/B；官方 benchmark 与业务 request distribution 有距离；长上下文 128K 不代表端侧可以经济地实际跑满；小模型在高风险 tool execution 上仍需要 verifier / policy guard。

未来方向：Small control model + large expert model 的联合训练、routing-aware distillation、推荐 query / item domain SFT、draft model 与业务 prefix cache 协同，会比单纯扩大 2B 模型参数更值得研究。

Deep Dive 02 · Model Routing / Multi-agent Orchestration

Fugu Max / Ultra v2：Model Routing 的终局可能不是“挑一个模型”，而是学习如何组织一组可替换专家

Research Impact Score / 研究价值 9.2/10工业成熟度 ★★★★★创新性 ★★★★★与你方向的相关度 ★★★★★是否官方开源 底层研究论文公开；产品 orchestration/weights 未开源是否有线上 A/B 未披露传统 A/B阅读优先级 S+

背景 / 业务动机：单模型 routing 通常把任务映射到一个 endpoint，但复杂任务包含搜索、代码、视觉、长上下文、验证等异质子问题。若每个请求直接打最贵 frontier model，cost/latency 不可控；若只选便宜模型，hard case 又损失质量。Fugu 把目标改写为能力—成本 Pareto frontier。

技术方案：Sakana 官方说明 Fugu 建立在 TRINITY 与 Conductor 两项 learned orchestration 研究之上：系统学习如何 assemble、route、coordinate expert agents，而不是靠手写 workflow。Fugu Max 扩大 open/specialized model pool，动态把任务送到“足够解决问题的最轻模型”；Fugu Ultra v2 则允许更重的多步协调以追求 peak quality。

Serving：两者都通过 OpenAI-compatible API 直接提供；Fugu Max 价格为每百万 input/output tokens $2/$6，Ultra v2 为 $5/$30，cached input 分别 $0.25 与 $0.50。已有 Fugu 客户切换模型只需改 model id，说明 orchestrator 被包装成标准模型 endpoint，而不是要求调用方理解内部 Agent 图。

实验：官方报告 Ultra v2 在 8 个 hard benchmark 中有 5 个 best/joint-best、7 个 top-2；Chartography 48.3，对比 Opus 5 的 27.3、Fable 5 的 29.5；DeepSWE 74.3。官方还特别强调训练 cutoff 为 2026-08-28，且 Fable 5/5.1、GPT-6 Astra 不在 Ultra v2 agent pool 中。

成本收益：Fugu Max 的主要价值不是单项 SOTA，而是把 open/specialized experts 纳入成本曲线；官方称其在相近性能区间推进 Pareto frontier。这里的工程启发与推荐多路召回非常像：不是让每一路都最强，而是学习哪个 request 值得调用哪组专家。

优势 / 局限：优势是供应商可替换、能力与成本联合优化、API 对上层透明；局限是内部路由策略与完整成本分解不可见，难以独立复现实验，也没有披露业务 A/B 与 per-task latency distribution。

推荐/搜索落地：可以直接映射为“召回/重排专家池”：轻 query 走 sparse+dense，小部分 ambiguous query 才调用 LLM rewrite / graph retrieval / expensive reranker；真正值得学的是router 的 reward 要同时包含 quality、cost、latency、cache hit 与 fallback risk。

未来方向：Model routing 会继续与 context routing、tool routing、retrieval depth、cache-aware placement 合流，最终 controller 输出的不再是 model id，而是一条 budgeted execution plan。

Deep Dive 03 · Agent Serving / Sandbox Memory

AgentZip：高并发 Agent 的内存问题，本质上是“同模板、多分叉执行”的跨 sandbox 冗余

Research Impact Score / 研究价值 9.0/10工业成熟度 ★★★★☆创新性 ★★★★★与你方向的相关度 ★★★★☆是否官方开源 截至今日未确认是否有线上 A/B 否阅读优先级 S

背景 / 业务动机：coding/deep-research Agent 会为一个 task fork 多个 sandbox。传统容量规划常只算 LLM KV cache，却忽略 browser/code/tool sandbox 的 OS memory。多个 sandbox 来自同一 template，随后执行相关轨迹，内存页不是完全相同却高度相似。

现有问题：Linux 通用 memory compression 不理解 template-relative redundancy，也不利用 cross-sandbox similarity；为了避免 page fault 又会保守地少压缩；而压缩触发通常只看 memory pressure，不知道此刻 Agent 正在等 LLM 还是在执行工具。

技术方案：AgentZip 同时利用 template-relative 与 cross-sandbox redundancy；把“该不该压某页”的约束从 compression-time 移到 restore-time prefetch，使更多 page 可以进入 profitable representation；并把高开销 compression 尽量放到 Agent 等待 LLM 的阶段，减少对 foreground tool execution 的干扰。

实验 / 效率：在 LLM training 与 inference agent workloads 上，AgentZip 把 sandbox-owned memory 最多降低 8.7×，Linux 配置为 2.1×。restore prefetch + execution-aware scheduling 把 aggressive compression 的 slowdown 从最高 3.1× 降到 1.40×，同时几乎保留全部 memory saving。

Serving 含义：这类技术会改变 Agent capacity 的计算方法：同一节点能承载的并发 agent 数不再只是 GPU tokens/s / KV bytes，还受 sandbox RSS、restore bandwidth、tool burst phase 控制。未来 scheduler 很可能同时调 GPU batch 与 sandbox memory。

优势 / 局限：优势是直击 high-fanout agent 独有冗余，且利用“LLM 等待窗口”做 phase-aware scheduling；局限是不同 workload 的页面相似度、tool memory locality 差别很大，8.7× 不是通用保证，restore prefetch 也需要稳定预测后续访问。

推荐/搜索启发：如果未来推荐侧引入大量 per-request agent / simulator / sandbox（例如策略生成、商家 Copilot、离线自动实验），系统优化必须把模型状态与执行环境状态同时当成一等资源。

Deep Dive 04 · Agent Runtime Scheduling

Tail-aware Scheduling：Agent workflow 的关键不是“turn ready 了就发”，而是控制已释放但未完成的 work budget

Research Impact Score / 研究价值 8.9/10工业成熟度 ★★★★☆创新性 ★★★★☆与你方向的相关度 ★★★★☆是否官方开源 截至今日未确认是否有线上 A/B 否阅读优先级 S

核心问题：Agent workflow 是 LLM turn 与 tool turn 交替的 DAG/sequence。多数 runtime 一旦某 turn ready 就立刻提交，但在高负载下会产生大量“released but unfinished”任务；一旦交给下游 inference queue，workflow scheduler 就失去重新排序权。

技术方案：论文把 readiness 与 release 解耦：用 mean-CVaR 目标显式关注 tail risk，用在线 turn-work estimate 决定 ready turn 的优先级，并根据 queue pressure 动态调整 released-work budget。直觉上就是：不要让下游队列被尚不紧急的工作填满，保留调度自由度给最可能拖慢 P95 的 workflow。

实验：使用真实 software-engineering Agent execution traces、多个 LLM 与多种 arrival rate。轻负载下与 eager release 相当；争用加剧时，P95 workflow flow time 最多获得 3.50× speedup。

和普通 LLM continuous batching 的差异：continuous batching 优化 token-level/device utilization，而这里优化 workflow-level critical path。两者应组合：上层决定何时 release 哪个 turn，下层决定已 release turns 如何 batch。

推荐/搜索启发：同样适用于“cheap stage → expensive stage”的 cascade：如果昂贵 rerank/LLM stage 已拥塞，不一定要让所有 ready query 立即进入队列；可以用业务价值、deadline、confidence、remaining work 做 release control。

局限：效果依赖 work estimate 与 arrival distribution；workflow 之间存在 tool-side resource contention 时，单看 LLM queue pressure 可能不够；论文没有线上生产 A/B。

Deep Dive 05 · Recommendation Robustness

RecGP：推荐投毒的迁移性来自“平坦攻击解”，防御也应该看 decision boundary 稳定性

Research Impact Score / 研究价值 8.8/10工业成熟度 ★★★☆☆创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 未确认是否有线上 A/B 否阅读优先级 A+

背景：推荐攻击者通常只能训练 surrogate model，再构造 fake users 去影响未知 target recommender。问题是 surrogate 上最强的攻击点常位于 sharp loss region，模型参数稍变就失效，transferability 差。

技术方案：RecGP 在生成 fake-user adversarial examples 时正则 gradient magnitude，把解推向更 flat 的 loss region，使扰动对 surrogate→target 参数变化更稳定。RecGP-RS 进一步针对离散交互空间做 semantic-aware neighborhood sampling，并通过 first-order interpolation 近似二阶信息，减少资源消耗。

实验：MovieLens-1M 与 Gowalla；论文报告在 Gowalla、8 个 target models 上攻击成功率相对 baseline 平均约 +8%。RecGP-RS 保留约 98% 攻击效果，同时 GPU memory 相对 RecGP -42%。

工业意义：对防守方最大的提醒不是复现攻击，而是：离线 robustness 不能只在同架构 attacker/defender 上测。应建立 cross-model、cross-seed、cross-checkpoint 的 attack transfer matrix，并监控热门 item score 在小参数/数据扰动下的 margin。

与主流防御的关系：异常用户检测、robust aggregation 往往在 input/user 侧；RecGP 揭示的是 optimization landscape 侧的 transferability。未来防御可以把 decision margin、gradient flatness、cross-model disagreement 加入风险信号。

局限：公开数据规模与工业 recommender 差距大；攻击成功不等同于商业目标真正被操纵；没有线上环境、实时反作弊与多阶段 cascade 评测。

Deep Dive 06 · Verified Reasoning

Magenta：高可靠 Agent loop 的价值不在“再多想几次”，而在失败后知道该回到数学还是只修 Lean

方案：训练-free pipeline：自然语言解题 → 生成 Lean 4 statement → machine-checked proof。statement judge 先判断 formalization 是否真的保持原题含义；若失败，error-attribution judge 判断是数学推导错了还是 Lean 局部证明错了，分别路由到 re-derivation 或 local repair。

实验：论文报告 AIME 2025、AIME 2026、HMMT Feb 2026 全部 100%；搭配 open-weight K2-Horizon-7B 时解出 IMO 2026 全 6 题。作者强调 statement adjudication 对避免 false certificate 必不可少，feedback-guided correction 在困难题上优于 independent resampling。

对推荐/搜索的迁移：模式可以直接迁移为 retrieve → answer/rank → constraint checker → error attribution → selective repair。例如 rerank 失败到底是召回缺证据、业务 constraint 冲突，还是生成器格式错？不同失败应回退到不同 stage，而不是统一“再跑一次大模型”。

局限：数学 formal verification 有 Lean 这样的硬 verifier，推荐/搜索很多业务目标没有完备 verifier；100% benchmark 结果需要关注题集规模与正式复现。

vLLM TokenSpeed MLA：Blackwell + FP8 KV 的 decode backend 继续专用化

vLLM 9/12 文档出现 TokenSpeed CuTe DSL MLA decode backend，目标硬件为 Blackwell，KV cache 走 FP8。当前公开 API 文档细节有限，因此今天不夸大具体加速倍数。真正值得关注的是趋势：MLA、speculative decoding、FP8 KV、Blackwell kernel 已经不再是彼此独立的开关，runtime 正逐步形成“按模型结构 × cache dtype × GPU generation”选择专用 backend 的矩阵。

工程判断：推荐/搜索团队如果开始自托管 reasoning/rerank LLM，benchmark 不应只记模型名和 GPU；必须同时固定 attention backend、KV dtype、spec decode、batch/concurrency、context distribution，否则吞吐数字不可比较。
