背景 / 业务动机

推荐和搜索链路常见「系统健康、结果不佳」：每个 RPC 绿灯并不意味着用户看到的多模态卡片、局部结果组合合理。靠最终 CTR 反推链路错误存在多重混杂。WISE 把 System Quality Diagnosis 形式化为可审计的多阶段归因，而不是孤立的 badcase 打标签。

传统方法的问题与核心矛盾

传统 LLM Agent 容易从日志里找一个貌似合理的责任模块，出现事后解释、工具轨迹与证据不一致；单用 SFT 也会把教师探索中的幻觉步骤学进去。完整体验涉及视觉内容、用户查询及召回/排序内部追踪，缺一不可。

技术方案 / 模型结构与关键模块

三层：① 体验观察器只看用户真正看到的搜索页和多模态内容，提出 issue；② Trace-attribution 在上下游召回/排序/过滤及特征路径中定位证据；③ ReTrace 对教师诊断轨迹重构，使每一步操作可由同一 case 观测支持。AHPO 按失败类型分别调整 agent Harness（工具/检索工作流）与模型 Policy（决策能力），避免所有错误都靠模型参数解决。

训练方法、数据与 Loss / Reward

WISE-Bench 是 12,000 个专家诊断样本，8k/2k/2k 切分。使用 ReTrace 修复教师轨迹，经监督微调再做基于验证反馈的 Harness/Policy 优化，论文的 AHPO 包含对 Policy 的强化优化。训练目标是端到端问题归因 exact match，而非直接把线上 CTR 当 token reward；评测时需把工具访问正确性纳入。

推理 / Serving 执行路径

线上按样例抽样获取前台快照与带权限的内部链路证据，Agent 执行多步归因并导出结构化问题及触发规则；异步质检与异常报警为主，不应把多工具诊断塞进推荐在线关键链路。引入证据 ID、工具日志版本、错误归属和置信度以便复核。

实验设置、样本与基线

工业多模态搜索 SQD 任务：WISE-Bench 含用户所见证据与专家责任标签；不同 Qwen3.5 模型规模对比未经训练、SFT 和 AHPO，并测 ReTrace 精简对轨迹效率的影响。线上另用诊断产出的相关性训练样本迭代模型，不是把 Agent 直接加入实时排名。

离线指标、数值与消融

Qwen3.5-35B-A3B 端到端准确率 35.25%→69.80%（SFT）→75.20%（AHPO）；4B 20.25%→58.25%→69.85%。ReTrace 教师轨迹 token 约 32.0k→20.4k（−36.25%），且归因精度未下降。生产衍生 220 万条训练样本/30 天，相关性模型 F1 0.573→0.631、MSE .0638→.0606。注意准确率为特定 SQD 标签一致性，并不是 Reward calibration。

线上 A/B / 因果证据界限

下游重新训练的相关性模型于 7 天 5% 线上流量 A/B：IQRR −0.11%（95% CI [−0.17,−0.05]）、CTR +0.15%（[+0.06,+0.24]）、LVR +0.20%（[+0.07,+0.33]）。这证明「利用归因数据优化模型」的效果，不证明 Agent 单独带来同比例收益。

训练与 Serving 效率 / 成本

论文报道支持约 12 万例/天，归因成本估计 ¥25.60/千例，相比人工 ¥5714.29/千例降约 99.55%；该数字依赖人工工时/调用计价假设，不等于所有企业复用后的 TCO。ReTrace 还能降低轨迹 token 开销，但调用与数据权限治理仍是成本。

对比主流方案的优势与代价

优于只看延迟/错误率的 AIOps、仅对结果打标签的离线质量评估；与 pointwise Judge 相比提供可检验的过程归因；代价是内部链路数据依赖更强、诊断标签主观性与归因错误可能被传播到下一轮训练。

推荐 / 搜索 / 商品评价场景应用

商品评价 List 可按「用户看到了什么观点/真实性与多样性问题 → 哪次候选召回、曝光、Reward 或生成动作造成 → 针对该模块重采样/修复」拆出可验证的因果假设。优先生产旁路的 Badcase 归因 Agent，而非先改主排序模型。

局限与尚未解决的问题

没有公开数据与官方复现仓库；评价标准依赖内部专家，外推到其他平台需要重建责任树；下游 A/B 与 Agent 本体效果不能混为一谈；尚不能证明多故障同时出现时的可识别性。

未来研究方向与可验证假设

建议研究 Counterfactual attribution（如果去掉某重排规则，错误是否消失）、多目标满意度分解、Agent 诊断不确定度、证据最小充分集和跨版本根因一致性。

背景 / 业务动机

信息茧房和短期 CTR 贪心会让用户一直看到已知品类。传统探索通过直接抬高冷门商品曝光，容易放大缺少反馈的样本，因精排本就对稀疏域过高预估造成推荐体验损失。

传统方法的问题与核心矛盾

历史 ranking pipeline 对大量高分候选完成了昂贵的特征与打分，最终却因为最终 List 尺寸与竞争关系没有展示；常规系统扔掉这些「已计算但未曝光」的信息。而直接注入冷候选既不能保证转化，也容易破坏预测分数校准。

技术方案 / 模型结构与关键模块

记录排序高分但未展示的候选，分布式做用户粒度近 30 日聚合、去重和品类发现标记；只选较久未曝光的品类候选建立持久化候选池，下一次请求在召回入口注入，而后继续由正常粗排/精排/重排控制最终曝光。该设计让「探索候选」来自已被模型评过分的可预测分布。

训练方法、数据与 Loss / Reward

方法显式 Training-Free：不修改精排 loss、权重及参数；新增离线去重聚合和召回候选复用规则。训练数据层面的难点是保存曝光结果与实际高分未曝光事件的时间戳，防止候选后来已被曝光或已不可售。

推理 / Serving 执行路径

用户键值映射持久化在线 KV，入站请求 O(1) 读取相应候选列表并走常规召回合并；在线增加时延 <1%，对千万级活跃用户已持续服务 6 个月以上。须保障日志回放、过期清理、用户隐私、库存失效、召回预算上限。

实验设置、样本与基线

以淘宝 Feed 为真实实验，比较直接 boost 新品/冷品、随机候选注入、不同窗口长度（1 日与 30 日）、URE​​D 的曝光与内容丰富度。使用线上 A/B 配合 CUPED 方差缩减，并关心完播及流量总量。

离线指标、数值与消融

直接给稀疏探索候选较高排名曝光会导致 PCOC 由约 1.042 恶化到 1.147、RMSE 从约 .325 恶化到 .368，凸显校准失真。URE​​D 产生的发现率为平台平均的 13.9 倍、近线强基线的 6.3 倍，必须同时考量「进入召回池的分布」与「最终真正曝光质量」。

线上 A/B / 因果证据界限

随机线上实验：新发现品类 +3.47%，内容丰富度 +8.47%，完播播放数 +2.62%；总播放量 +0.36% 未达统计显著。1 日窗口发现品类仅 +0.55% 且不显著；纯随机注入在参与度上呈 −0.17% 倾向。不要把这些相对变化外推为商品评论成交增长。

训练与 Serving 效率 / 成本

重用已有排序算力而非再训练大模型，在线查一次 KV 并走已有流程；成本重心转移至日志保留、窗口聚合、用户×候选 TTL 与多路召回流量预算。低在线成本不等于零维护成本。

对比主流方案的优势与代价

比纯 epsilon-greedy 和热门/冷门强制提权更容易控制校准风险；但有「只复用已被当前模型高分选中的偏好」的问题，不能发现模型系统性低估的陌生兴趣，因此探索能力有结构性上界。

推荐 / 搜索 / 商品评价场景应用

评价推荐可建立「被 Ranker 高分但最终 List 没显示」的评论缓存，按观点、属性、正反立场去重，作为 List Generator 的额外可用候选；先在召回层验证事实覆盖与用户满意度，再改 Reward，以免生成器背负所有长尾发现职责。

局限与尚未解决的问题

新兴趣的定义与品类聚合依赖平台；30 日高分候选仍受历史模型选择偏差影响；总播放量增幅未显著，未来成交及长期留存未在摘要中给出强因果证据。

技术方案 / 模型结构与关键模块

推理 / Serving 执行路径

CPU 侧编译合法集合，与模型 prefill overlap，再把 request-scoped CSR 上传 GPU，GPU kernel 查每步的 allowed token，完成 beam 选择后更新父约束状态。三个 token 的短路径让预处理摊销特别敏感；并行请求需要注意 buffer lifetime 与 snapshot TTL。

背景 / 业务动机

BM25/SPLADE 第一阶段拉回上千条 document，MonoT5 等第二阶段 reranker 在固定 1000 条上打分。容易 query 只需 50 条，难 query 需要更多，固定预算会浪费计算或错失高相关尾部候选。

传统方法的问题与核心矛盾

以往仅少量文档有人审标签，无法密集观察每个 query 不同 rerank depth 的 DCG 曲线。即使拥有 oracle 最优深度，也不能在线访问真实答案；找到只靠初排结果的可泛化预测器是关键。

技术方案 / 模型结构与关键模块

先以密集 LLM relevance judgments 构造每个 query 的 depth→quality 曲线，再找到最佳或足够饱和的深度；从一阶段结果推断初排 IR-DCG@10 作为代理分数，决定本 query 该送多少文档给二阶段 reranker。

训练方法、数据与 Loss / Reward

不是训练通用 LLM 或生成式排序器，而是以 LLM 评估的检索质量作为弱标签训练/选择 depth predictor。QPP 常规统计难以可靠预测最优深度；自动 relevance labels 自身的噪声和与人工标注一致性必须审计。

推理 / Serving 执行路径

请求进入后先对 Query/首阶段检索列表算低成本质量 proxy，再条件化分配 rerank K，保留上限和下限；只把 top-K 文档送到神经交叉排序，避免对极长 list 做等额计算。若 Proxy 本身需要昂贵 LLM 在线调用，净收益可能消失，宜蒸馏成轻量模型。

实验设置、样本与基线

MS MARCO DEV 和 TREC DL2019；BM25→MonoT5 等一、二阶段搭配，额外讨论 SPLADE、MonoELECTRA 条件；对比固定 K、传统 QPP 与 oracle depth。

离线指标、数值与消融

IR-DCG@10 predictor 在合适设置可将平均 rerank 深度约 1000 降到 331 左右，即约 3 倍候选减少，同时保留总体检索效果；知道真实相关性标签的 oracle 可以 5 倍压缩并提高质量 >7%，但 oracle 不可直接部署。

线上 A/B / 因果证据界限

没有真实在线用户 A/B，也没有 query-level P99/吞吐已落地的数据；候选减少不是用户体验提升的充分条件。

训练与 Serving 效率 / 成本

第二阶段复杂度近似 O(K·cost_cross_encoder)，K 从 1000 到 331 是较大潜力；必须减去质量 Proxy 的计算、批处理 padding 和 GPU 并行度损失。平均 K 降低也不等于 P99 成比例降低。

对比主流方案的优势与代价

背景 / 业务动机

推荐/QA 混合 RAG 系统常同时支持 sparse、dense、hybrid 和图检索；没有一条 retriever 在所有 Query 里最优。固定选一路或学习 Query→预定义检索器标签的 router 在新模型/新语料上泛化差。

传统方法的问题与核心矛盾

Query-only Router 只记住训练时的检索器 ID 与 query 模式，面对未知 retriever/collection 缺少输出定义；简单 fusion 可能把高噪声证据合在一起，甚至拖累后续 Reader。

技术方案 / 模型结构与关键模块

对每条 Query 从多个 retriever 拉回 passage sets，使用可跨来源比较的 reranker 提取「一组证据对回答有用」的质量表征。通过对比式训练让优质证据集在决策空间更靠前，轻量 comparison head 在集合之间选择，从而不绑定 retriever 参数。

训练方法、数据与 Loss / Reward

对照证据集实际生成回答质量构造对比监督，并微调 reranker；comparison head 获得少量收益。训练标签基于 QA answer quality，既有成本，也必须防止用评测 Reader 的相同偏好评估自身。

推理 / Serving 执行路径

每个 Query 先跑多条 Retriever，再打分结果集合并选路交给 Reader；相对「先 Query 路由再跑一路」增加检索成本，适合高价值、可缓存或者延迟较宽松的请求。未来可通过先轻路由再多路重排序做级联。

实验设置、样本与基线

对比最强固定 Retriever、融合 baseline、三种 query-only router 以及 prompted 8B LLM；关注 unseen corpus、unseen retriever、unseen reader 的跨域迁移，不只同分布平均 F1。

离线指标、数值与消融

论文报告相对最佳固定 retriever 答案 F1 +28% 的相对增幅；证据重排序的对比训练贡献主要收益，comparison head 是次要增益。这个增幅是 QA Answer F1 而非 Search CTR 或评论成交。

线上 A/B / 因果证据界限

无生产端点击/购买 A/B，也未提供多路检索并发成本的完整线上预算。

训练与 Serving 效率 / 成本

关键新增成本是同一 Query 运行多个 Retriever、计算 passage set score 和可能多次 Reader 试评；训练路由器不绑定源 ID 可降低新检索器接入重训成本，但线上吞吐取决于并行策略。

对比主流方案的优势与代价

比 query-only router 在新语料和 unseen retriever 上更有理论泛化优势；比固定融合能主动避开劣质证据集，但多路预取比单路路由贵，并非所有业务都值得。

推荐 / 搜索 / 商品评价场景应用

商品评价召回可同时运行关键词、向量、商品属性与争议观点四路索引，以「该路返回评论能否支持用户问题/是否包含正反证据」作为质量得分，再决定重排或生成器输入配额。

局限与尚未解决的问题

答案 F1 受 Reader 偏差影响，且对新语言、检索深度及大规模生产 QPS 未充分验证；文中无可核验官方代码。

未来研究方向与可验证假设

成本感知先验 Router、边际证据增益的动态检索终止、Cross-List Reward 和用户满意度作为路由标准。

给商品评价生成式重排的实验优先级

P0｜Reward 可信度：以 WISE 的证据链思路建立「评论观点→候选来源→曝光位置→下游用户决策」可审计事件表；用 FocalSwap 的匹配真实 donor 替换最新查询/评价交互，检查 Reward 特征是否 OOD 敏感。离线指标：分桶 calibration、PCC/Kendall、人工规则违例；在线：成交与满意度双 guardrail。

P1｜候选内容覆盖：复制 URED 的 unexposed high-score memory 到评论召回，不要将旧页面未曝光候选视为负反馈；评测差评/长尾属性观点 Recall、同义去重、冷品校准，并将真实曝光概率纳入训练样本权重。

P2｜效率合同：用 Supply-Constrained GR 的 prefix 合法性 mask 保证违规评论无法生成；用 Optimal Re-Ranking Depth 的 query 质量代理动态设置候选 K。主要看同等 GMV/满意度下 P95/P99 和 GPU-ms，不单看 token 速度。

P3｜多模态偏好冲突：借 PMRecBench 构造「满足当前查询但违背用户偏好」硬负例，拆成 Query Compliance、Personal Utility、Truthfulness、Diversity 分值，优先修 Reward 而非先加推理步数。
