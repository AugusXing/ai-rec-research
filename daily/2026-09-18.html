今日核心结论：① 检索不再只是选文档，而是先选“检索计划”：DRAG 联合路由 retriever 与 generator，DUPAR 在 fast cache path 与 full-index slow path 间切换，On-device Tool Routing 则证明 selection 与 abstention 应拆成不同问题。② 跨轮状态开始成为检索系统的一等资产：DUPAR 把上一轮正确证据扩成下一轮可复用 evidence cache，把“对话历史”从 prompt 变成 retrieval state。③ 推荐系统正在把偏好推理从隐式 latent state 改成可检查的显式 preference state：Re2A 用 rubric 约束偏好推理，再做 preference-conditioned alignment。④ 长尾检索的主要矛盾可能不是模型容量，而是训练数据没有精确覆盖“易混淆尾部概念”：REPAIR 通过诊断→事实扩展→hard negative differentiation 的闭环修复数据。⑤ Agent / LLM 的下一个控制层正在从外部 memory/router 延伸到“实时生成权重”和“在线监控内部表征”：Infinite-Parameter LLMs 探索把 live data 编译进低秩权重，reward-hacking monitor 则尝试用内部向量在行动前预警异常。

今日最值得看

🥇 DUPAR · Fast/Slow Retrieval + Cross-turn Cache

对搜索 / RAG 工程最直接：fast path 查跨轮 evidence cache，低置信再进入 audio+ASR 的 full-index slow path；干净语音上相对 ASR+Text Encoder 3.75× query-side speedup，噪声 Recall@10 0.771→0.875。它把“缓存、置信路由、fallback”整合成一个可迁移的检索架构。

🥈 Re2A · Explicit Preference State

推荐侧最值得跟进。不是直接让 LLM 从上下文端到端生成推荐，而是先用 rubric 产出显式偏好状态，再让 response optimization 同时对齐 preference satisfaction 与 situation consistency。对 Agentic Rec / 对话推荐尤其重要。

🥉 DRAG · Joint Retriever / Generator Routing

核心发现很工程化：更强 retrieval 往往比单纯增加 generation effort 带来更大收益，但二者都有递减甚至非单调回报。于是每个 query 都不该默认走“最贵配置”。

⭐ REPAIR · Long-tail Retriever Data Loop

不是继续堆更大 encoder，而是对长尾概念做 diagnosis、API-grounded evidence expansion、hard-negative differentiation，形成自演化训练数据闭环；在 9 个材料 / 生物医学 benchmark 上超过 19 个强 baseline。

技术趋势

Fixed Pipeline → Query-conditioned Execution Plan

昨天 ORDER 把 index / chunking / metadata / reranker 变成 query-conditioned route；今天 DRAG 再把 retriever 与 generator 配置一起路由。下一步很可能是一个统一 controller 同时决定 source、index、top-K、reranker、model、reasoning depth 与 latency budget。

Prompt History → Retrieval State

DUPAR 把对话的可复用信息存成证据缓存并一跳扩展，而不是每轮重新从全库检索。对推荐系统可对应为 session candidate cache、interest neighborhood cache、recent-positive expansion。

Latent Preference → Explicit / Auditable State

Re2A 的 rubric-based reasoning 与近期 Agent evaluator / harness evolution 形成同一趋势：中间状态需要可读、可评估、可回放，否则端到端生成很难稳定迭代。

More Parameters → Better State Placement

Infinite-Parameter LLMs 问的是“新信息应该留在 prompt / retrieval / memory，还是编译进 session-specific weights”；DUPAR 问的是“跨轮证据应该留在全库还是近邻 cache”。共同问题是状态应该放在哪里、保留多久、何时刷新。

Deep Dive 01 · Search / RAG / Conversational Retrieval

DUPAR：把“低延迟检索、跨轮记忆、fallback”统一成 Fast / Slow 双路径

Research Impact Score / 研究价值 9.5/10 · 工业成熟度 ★★★★☆ · 创新性 ★★★★★ · 与你方向的相关度 ★★★★★ · 是否官方开源 公开索引声称有代码，但本次未确认到可访问的官方仓库 · 是否有线上 A/B 否 · 阅读优先级 S+

背景 / 业务动机：语音助手常见链路是 Speech → ASR → Text Retriever → RAG。它的问题不是只有 ASR 准确率：ASR 本身引入一段延迟，识别错误又会进一步污染检索。直接做 speech retrieval 虽能省掉 ASR，但 audio embedding 与文本知识库之间存在跨模态对齐误差。

现有问题：多数系统每一轮都重新查全量 index，完全忽略对话连续性。现实 follow-up query 往往围绕上一轮证据附近展开；把每轮都当独立 query，会浪费计算，也把模型再次暴露给全库中的干扰项。

技术方案与关键模块：DUPAR 有两个互补路径。Fast path 用 task-adapted audio encoder 对齐 frozen BGE-M3 text embeddings，只搜索跨轮 evidence cache；Slow path 在 cache confidence 不足时触发，把 audio retrieval 与 ASR-transcript retrieval 做融合并搜索完整 index。成功检出的 evidence 通过 one-hop graph expansion 刷新下一轮 cache。

训练方法：核心训练对象是 audio encoder，使其进入与 frozen BGE-M3 文本表示兼容的检索空间。冻结文本塔的好处是已有文本 index 不必为音频入口重建；论文摘要没有公开更细的 loss 组合与 mining 细节，本站不补写未证实超参。

推理 / Serving：这是本文最值得借鉴的部分：先走近场、小候选集、低成本 fast path；只有置信不足才升级到 full-index + ASR 的 slow path。可以直接类比推荐中的“session candidate cache → 全库 recall fallback”，或搜索中的“recent evidence cache → ANN / lexical / reranker escalation”。

实验设置与离线指标：在 domain-specific knowledge base 上，训练后的 audio encoder 在 clean speech 上接近 text retrieval accuracy，同时比 ASR + Text Encoder 获得 3.75× query-side speedup；noise benchmark 的平均 Recall@10 从 0.771 提升到 0.875；多种合成 speaking style 上 overall Recall@1 提升 4.2 个百分点。

线上 A/B：未披露生产线上 A/B。当前证据是 benchmark / workload 层面的检索质量和 query-side latency。

效率 / 成本收益：真正收益来自两处：省掉大部分轮次的 ASR+全库检索，以及把 follow-up query 缩到高相关局部 cache。论文给出 query-side 3.75× 加速，但没有披露 end-to-end P95/P99、cache hit rate、memory footprint 与多租户吞吐。

与主流方法优劣：相比纯 ASR cascade，DUPAR 更快且对噪声更稳；相比纯 direct speech retrieval，它保留 ASR slow path 作为安全网；相比一般 conversational RAG，它把历史信息从“拼进 prompt”变成可路由的 retrieval state。代价是需要维护 evidence graph、cache confidence 与失效策略。

适用场景：语音助手、客服搜索、对话式商品检索、连续问答、session 内兴趣高度连续的推荐。若用户每轮主题跳跃很大，cache 命中和 one-hop expansion 的收益会显著下降。

局限 / 未解决问题：cache 里的错误证据会不会被下一轮放大？置信阈值如何按 query 自适应？跨轮 cache 何时过期？graph expansion 是否导致热门节点污染？这些比单纯再调一个 encoder 更接近真实线上问题。

未来研究：学习式 fast/slow router、cache TTL / eviction、错误传播检测、跨轮 counterfactual replay、把 retrieval budget 与 downstream generation confidence 联合优化。

对推荐 / 搜索工程与职业技能的启发：值得重点补的不是“再会一个 embedding 模型”，而是 retrieval controller、cache state、fallback、confidence calibration、P95/P99 与端到端成本。这类能力更接近高级推荐 / 搜索架构岗。

Deep Dive 02 · Recommendation / Preference Reasoning

Re2A：先把用户偏好推理成显式状态，再让生成结果对齐“用户需要 + 当前场景”

Research Impact Score / 研究价值 9.4/10 · 工业成熟度 ★★★☆☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★★ · 是否官方开源 论文给出官方仓库地址，但本次检查为 404 / 尚不可访问 · 是否有线上 A/B 否 · 阅读优先级 S+

背景 / 业务动机：传统 conversational recommendation 已经要理解多轮对话；situated conversational recommendation 更进一步，还要理解用户和助手共同看到的真实场景，以及场景内 item 属性。用户说“这个看起来太正式了，我想要更轻松一点”，偏好并不只存在于文字里，而是在 dialogue × scene × item attributes 的交叉处。

现有问题：端到端 LLM 可以生成流畅回答，但很难回答两个工程问题：模型到底推断出了什么偏好？最终推荐失败是偏好理解错了，还是生成阶段没有遵守偏好？当中间 preference state 完全 latent 时，bad case 很难归因。

技术方案：Re2A 把 SCR 拆成 reason-then-align。第一步 rubric-based preference reasoning，用自动化 rubric 引导模型输出显式 preference states；第二步 preference-conditioned optimization，让生成同时优化 user preference satisfaction 与 situation consistency。

训练方法：重点不是简单 SFT 一个推荐答案，而是用 rubric 把“偏好理解”作为独立中间任务，再把这个状态作为后续 response optimization 的条件。公开摘要没有说明全部 optimizer / reward 细节，因此本站只保留论文明确给出的结构，不虚构具体 RL 算法。

推理 / Serving：线上可以拆成 Preference Reasoner → Structured Preference State → Response / Recommendation Generator。工程上这允许 preference state 被缓存、审计、A/B、回放，也允许后续把 generator 换成传统 ranker / reranker，而不必把整个系统绑死在单个 LLM 上。

实验设置与离线指标：论文在两个 SCR 数据集上与 SOTA 方法比较，并报告一致领先；当前公开摘要没有给出可安全引用的具体数值，因此这里不填造数字。最值得检查的后续指标是 preference-state accuracy、grounded consistency、response quality，以及不同 scene complexity 下的退化曲线。

线上 A/B / 效率：未披露工业 A/B，也未给出线上 latency / token cost。两阶段推理会增加调用成本，但显式 state 可带来缓存、蒸馏和小模型化空间；是否净省成本需要生产 workload 验证。

与主流方法对比：相比端到端生成，优势是中间偏好可解释、可评估；相比传统 slot/profile extraction，优势是 rubric 可以表达更复杂的 situated preference。缺点是 rubric 的质量会成为新瓶颈，而且显式状态可能丢掉难以结构化的微妙偏好。

适用场景：导购 Agent、线下拍照 / AR 场景推荐、旅游 / 餐饮对话推荐、需要解释“为什么推荐”的高价值商品。对简单 feed ranking，完整两阶段 LLM 可能成本过高。

局限 / 未解决：rubric 是否跨域泛化？偏好冲突如何表示？长期偏好与当前情境偏好怎么融合？用户反悔时 state 如何更新？这些问题直接决定它能否从 benchmark 走到工业系统。

未来研究：把显式 preference state 接到传统 candidate/ranker pipeline；做 state versioning / TTL；用真实行为反馈而非仅 response rubric 做 alignment；研究 preference state 与 Semantic ID / user memory 的联合表示。

工程 / 职业启发：推荐算法工程师未来需要具备“模型 + evaluator + structured state + online feedback loop”的能力，而不仅是训练一个 CTR 模型。如何把 LLM 推理结果变成可供推荐链路消费的结构化状态，是值得长期投入的方向。

Deep Dive 03 · RAG / Model Routing

DRAG：RAG 不该每个 Query 都跑同一套 Retriever × Generator 配置

Research Impact Score / 研究价值 9.2/10 · 工业成熟度 ★★★☆☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★★ · 是否官方开源 未确认 · 是否有线上 A/B 否 · 阅读优先级 S

背景 / 业务动机：固定 RAG 的最大浪费在于把所有 query 当成同样难。事实型单跳问题可能 cheap retriever + small model 就够，而 multi-hop / composition query 需要更强 retrieval 或更强 generation。

现有问题：过去 adaptivity 常单独优化 retrieval depth 或 generation model；但两者存在耦合。更强 retriever 可能让小 generator 足够，弱 retrieval 则不是增加 reasoning token 就能补救。

关键发现：跨 factoid、bridge、composition 任务，论文观察到增强 retrieval 通常比增加 generation effort 带来更大收益，但两者都有 diminishing / non-monotonic returns，即“越贵越好”并不成立。

技术方案：DRAG_QPP 是 training-free router：用 Query Performance Prediction 信号选 retriever，再根据 retrieved context 的 perplexity 类信号选 generator；DRAG_SFT 则 fine-tune LLM，联合预测 retriever-generator configuration。

训练：QPP 版本不需要训练 router；SFT 版本把配置选择变成监督预测。真正值得工业化的下一步是把监督目标从“最佳离线配置”改成 utility = quality - λ·latency - μ·cost - risk。

Serving：在请求前先做轻量 route，随后只启动选定的 retrieval / generation 组合。部署难点不是 router FLOPs，而是多 retriever / 多 model pool 的 warm residency、batch fragmentation 与 fallback。

实验：覆盖 3 个 LLM family、4 个 QA benchmark。DRAG_QPP 在效果接近强 static RAG baseline 的同时显著降低 inference latency；DRAG_SFT 相比 static 与 training-free adaptive baseline 持续提升效果。摘要未给出统一可引用的具体百分比。

线上 A/B：无。当前仍是 benchmark-level evidence。

优劣：相比固定 pipeline，按 query 花钱；相比只做 model routing，DRAG 把更关键的 retrieval 也纳入路由。缺点是配置空间扩大后 supervision 和 observability 复杂度上升，并可能发生 router error 导致不可恢复的上游信息缺失。

适用场景：企业 RAG、搜索问答、客服、Agent tool research、需要在 latency/cost 与 answer quality 间动态权衡的产品。

未解决：QPP 在 domain shift 下是否稳定？retrieval 和 generation 能否一次联合决策而非级联？怎样对 P95/P99 而不是平均 latency 优化？怎样把 abstain / human review 也纳入 route？

推荐 / 搜索启发：把它映射到推荐链路，就是每个 request 动态选择召回源、召回深度、粗排模型、精排模型、重排策略和序列长度预算。Model Routing 不应只理解为“选大模型还是小模型”。

Deep Dive 04 · Dense Retrieval / Long-tail Data

REPAIR：长尾检索的“修模型”路线，转向诊断并修复模型最缺的训练事实

Research Impact Score / 研究价值 9.1/10 · 工业成熟度 ★★★☆☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★★ · 是否官方开源 未确认 · 是否有线上 A/B 否 · 阅读优先级 S

背景 / 业务动机：科学检索尤其容易失败在罕见概念、相似术语和事实敏感的细粒度区别上。通用 dense retriever 往往学会头部语义，却没有足够训练信号区分长尾概念。

现有问题：直接用 LLM 合成 query/document 可以扩数据，但 LLM 自身会 hallucinate；随机 synthetic augmentation 又不知道模型真正缺什么，容易大量生成已经会的简单样本。

技术方案：REPAIR 做一个循环：diagnosis 找出长尾知识缺口 → API-guided evidence expansion 用外部事实来源扩充可信证据 → differentiation 用 hard negative mining 强化近邻概念区分。重点是 synthetic data 不再“一次性生成”，而是被检索失败驱动地迭代。

训练方法：框架持续把经过事实验证的正例和难负例加入 dense retriever 训练集。它更像 data-centric self-improvement，而不是修改 backbone 架构。

Serving：线上仍可保持标准 dense retrieval，因此训练期复杂度不会直接传导为 query latency；代价主要在离线 diagnosis、API 证据调用与数据迭代。

实验：论文在 9 个材料科学和生物医学 benchmark 上与 19 个强 baseline 比较，并报告显著领先；公开摘要未给统一可安全引用的具体增益数字。

线上 A/B：无。

效率 / 成本：相对“线上换更大模型”，REPAIR 把成本移到离线数据工程；如果修复后的 retriever 可以继续用相同 encoder size，线上成本几乎不变。需要关注 API augmentation 成本、事实源更新和周期性重训。

优势：诊断驱动、事实约束、直接攻击 hard negatives；风险：外部 API 的覆盖偏差会变成训练偏差，长尾概念的自动发现本身也可能漏检。

适用场景：电商长尾商品 / 属性检索、广告 query-ad 匹配、企业内部术语、医疗 / 科研搜索、技能 / tool catalog retrieval。

未来研究：把线上 bad-case / zero-result / downstream reject 反哺 diagnosis；用 uncertainty / influence score 决定最值得新增的数据；在 continual retriever 上控制 synthetic data 导致的 forgetting。

职业启发：高级检索工程越来越像“模型 + 数据闭环 + hard-negative system + evaluation slicing”。能够定位模型在哪些分布切片失败，并自动构造高价值训练数据，比单纯换 backbone 更稀缺。

Deep Dive 05 · LLM Architecture / Live Adaptation

Infinite-Parameter LLMs：把 Live Data 从 Prompt / Memory 编译成 Session-specific Low-rank Weights

Research Impact Score / 研究价值 8.9/10 · 工业成熟度 ★★☆☆☆ · 创新性 ★★★★★ · 与你方向的相关度 ★★★★☆ · 是否官方开源 未确认 · 是否有线上 A/B 否 · 阅读优先级 S

背景：今天 LLM 从用户那里学到的新事实，通常被塞进 prompt、RAG 或 memory，下一次又重新读取。作者提出更激进的问题：既然 MoE 可以按 token 激活不同参数，能否把运行时数据直接“编译”为当前 session 的有效权重？

技术方案：一个 compact hypernetwork 把 live data 映射成 shared base FFN 的 low-rank modulation。与一次性 context→adapter 不同，系统维护生成器 latent code 的 Bayesian belief，每轮甚至可按更细粒度在线更新，再从该 belief 重新生成有效权重。

“Infinite”应该怎么理解：不是无限知识，也不是突破 scaling law。它指固定存储 footprint 下，hypernetwork 可从不同 live data 编译出理论上无穷多个 session-specific effective weight instances。适应仍受低秩、latent dimension、数据质量和 base model 能力约束。

训练 / 推理：训练要同时学 base network、weight generator 与 latent update mechanism；推理则维护一个可递归更新的 belief state，并生成低秩权重。理论收益是信息无需每轮在长 prompt 中重复读取，可释放 context window，并把跨轮信息持久化在 session weight state 中。

实验 / 证据：当前公开材料重点给出架构与 evaluation protocol，明确要求与 ICL、retrieval、one-shot weight generator、point-estimate test-time training、stored-bank MoE 做对比。本次可获取摘要没有足够工业 / benchmark 数字，因此不把它包装成已验证成熟方案。

线上 A/B / 成本：无。真正成本取决于 hypernetwork 生成权重与在线 Bayesian update 的频率，以及这些 low-rank delta 如何在 batch serving 中共存。

与 RAG / Memory 对比：RAG 可追溯、易更新、适合事实证据；动态权重可能更适合反复使用的行为约束和 session personalization，但可解释性、遗忘、污染与回滚更难。二者更可能互补而非替代。

对推荐的启发：可把它看成“用户实时偏好 delta 是否应该进入 user embedding / memory，还是进入模型参数”的极端版本。未来可能出现 base ranker + per-user/session low-rank adapter，但工业化首先要解决 batching 与安全更新。

未解决：错误 live data 如何撤销？多用户 batch 如何高效执行不同权重？如何防 prompt injection 变成 weight poisoning？state 持久多久？这些都是大规模 Serving 前置条件。

Notable 06 · Agent / Tool Routing

Selection Is Retrieval, Abstention Is Not：Tool Router 最该花神经网络预算的地方是“拒绝错误工具”

Research Impact Score / 研究价值 8.8/10 · 工业成熟度 ★★★☆☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★☆ · 是否官方开源 未确认 · 是否有线上 A/B 否 · 阅读优先级 A+

论文把 tool routing 拆成两个任务：selection（库里有合适工具时选哪个）与 abstention/applicability（库里到底有没有合适工具）。在 600 个韩英双语请求、70 个本地 action 上，character 3-gram BM25 对 lexical match 选对 162/164，但 paraphrase 只有 85/166；把候选限制为 7 后 paraphrase 均值升到 0.825。BM25 score feature 上的 in/out catalog classifier AUC 不超过 0.697，而 frozen multilingual-e5-base 达 0.806。只用 encoder 做 abstention，可让 376 个请求保持本地处理，同时在 150 个需要 delegation 的请求中误路由 9 个。

工程判断：这对推荐 / 搜索同样成立：候选排序与“是否该扩大候选池 / fallback / escalation”不是同一个问题。一个 cheap retriever 可以负责候选选择，神经模型更值得放在 OOD、拒绝和升级判定上。Neural ranker 虽提升质量，但论文因 latency / memory 拒绝它，这种“质量不是唯一目标”的设计非常有工业价值。

VoiceTrace-Bench 的 query 同时包含“要找什么”的文本和“由谁说”的 reference speech。VoiceTrace-Emb 负责大规模 embedding retrieval，VoiceTrace-Reranker 再对 query-candidate pair 做细粒度联合判断。论文报告在传统 semantic speech retrieval 上达到 SOTA，并在新的 who+what hybrid benchmark 上显著优于 cascade。
