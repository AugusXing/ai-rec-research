Serving 优化正在变成 Contract Engineering：
图捕获、KV 布局、量化 Schema 与状态所有权必须同时正确

统计窗口为北京时间 2026-08-30 10:02 → 2026-08-31 10:02。由于周末 arXiv 的 recent 列表最新批次仍停留在 8 月 28 日，过去 24 小时没有新的正式论文批次值得重复填充；因此今天严格聚焦 vLLM / SGLang 主干在窗口内合入的 7 组高价值工程进展。它们共同说明：当 LLM / 生成式推荐进入 speculative decoding、MLA、MoE、低比特量化和多级 KV cache 后，性能瓶颈已经不只是 GEMM 或 Attention，而是执行图的内存预算、物理布局、量化配置语义、跨 stream 数据所有权与请求级 KV 状态。

重点精读 01 · Speculative Decoding / Graph Runtime

vLLM：AITER MLA Speculative Decoding 终于可以进入 FULL CUDA Graph

Research Impact Score / 研究价值 9.6/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是，已合入 vLLM main是否有线上 A/B 否；有 MI355X serving benchmark阅读优先级 最高

背景 / 业务动机

Speculative decoding 的理论收益来自用 draft 一次提出多个 token，再由 target 验证；但生产系统的实际收益往往被 Python launch、device-host sync、动态 allocation 和 graph break 吃掉。尤其 MLA + DSpark 这类 verify path，一次 step 会处理 1 + num_speculative_tokens 的 token block，如果 attention backend 只声明“单 token decode”，整个 engine 会被降级到 PIECEWISE graph。

现有问题

PR #51171 找到两个独立阻塞点。第一，TritonMLAMetadataBuilder 对 DSpark draft group 仍报告 UNIFORM_SINGLE_TOKEN_DECODE，导致 engine 取最小 support level 后整体不能 FULL capture；实际上该路径用 device-side repeat/interleave 处理多 token，满足 UNIFORM_BATCH。第二，AITER MLA 的 small-head verify path 会在每一层把 paged-KV range 展开成逐 verify-token rows，内部有 4 次 device→host sync 和依赖读回值的动态 allocation，这些操作直接破坏 HIP graph capture。

技术方案与关键模块

方案一是在 KV cache group 被标记为 non_causal_multi_token_decode 时，提升 graph support level；方案二把 verify row expansion 移到 `_build_decode`，每个 step 只做一次，并写入持久 buffer，保证 graph replay 地址固定。另一个看似小但非常关键的修复，是让 worker 同步 cache_config.kv_cache_size_tokens：否则 verify buffer 用 max_model_len 推导上界，实际会预留远超真实 KV capacity 的空间。

训练方法

不涉及训练；target 与 draft 权重、接受算法都不变。该工作纯粹改变 runtime graphability 与 buffer planning。

推理 / Serving 方案

测试模型是 Kimi-K3，DSpark draft，TP8，MI355X；把原来的 PIECEWISE graph 变成 FULL graph。关键思想不是“强制 capture 所有东西”，而是先把 graph region 中的 host sync、动态尺寸与不稳定地址移出，再让 attention group 明确声明真实 execution semantics。

实验设置与离线 / Serving 指标

PR 报告在随机 1K input / 256 output benchmark 上：并发 1 的 output tok/s 从 12.10 → 46.30，mean ITL 从 186.98ms → 34.26ms；并发 16 的 output tok/s 从 174.01 → 326.46，mean ITL 从 188.28ms → 92.91ms。Acceptance length 基本不变，说明收益来自执行路径而非 draft 质量。代价是 graph capture memory/rank 从约 0.51 GiB → 2.11 GiB。另外补齐真实 KV capacity 后，verify buffer 预留从约 295.3 MiB → 46.6 MiB/rank。

线上 A/B、成本收益与优劣势

没有业务线上 A/B。优势是吞吐/ITL 改善巨大，且 acceptance 不变；劣势是 graph capture memory 显著增加，对小显存或需要大 KV cache 的请求不一定适合。相比只写更快 kernel，这项优化的价值在于把“graph support level、host sync、persistent buffer、真实 KV capacity”统一起来。

适用场景 / 局限 / 尚未解决的问题

适合 ROCm、MLA、spec decode、低到中并发在线生成。当前 benchmark 使用 synthetic random prompts，draft acceptance 约 21%，绝对吞吐不代表真实业务；不同模型、不同 head 数、不同 speculative method 的 graph envelope 仍需分别验证。FULL graph 与 KV memory 的最优点还需要 runtime 自适应，而不是静态开关。

对推荐 / 搜索算法工程落地和职业技能的启发

生成式推荐、LLM reranker 一旦用 speculative decoding，优化能力不应停在模型结构。要能读 profiler，理解 host sync、capture address stability、KV buffer sizing、TP/DP topology，并把“模型算法 → runtime contract → hardware behavior”连起来。未来高阶推荐工程师会越来越需要这类 systems-aware reasoning。

重点精读 02 · MLA / KV Layout Correctness

vLLM：Sparse MLA 的逻辑 Block 与物理 Row Stride 不能混为一谈

Research Impact Score / 研究价值 9.5/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是，已合入 vLLM main是否有线上 A/B 否；有 H200 + GLM-5.3 deterministic validation阅读优先级 最高

背景 / 业务动机

MLA / sparse attention 为了减少 KV 访问，会引入更复杂的 cache layout。BLHNC 这类 block-outermost layout 会让不同 layer 的 pages 在物理地址上交错；逻辑上“某层的下一个 block”并不等价于物理地址加一个 block_size。

现有问题

FlashInfer sparse index conversion 曾把 physical block id 直接乘以 logical block_size，decode 可能读到另一个 layer 的 page；同时 DeepSeek-V3.2 / GLM fused cache writer 又从 physical block stride 反推 logical block size，写入也可能落到错误 block/layer。最危险的是：这类错误可能不 crash，只会让模型在某些 layout 下生成错误结果。

技术方案与关键模块

修复从实际 FlashInfer KV-cache view 中推导 physical row stride，并把它同时传给普通 sparse-index conversion 与 DCP remapping；写入侧则显式传递 logical MLA block size，不再从物理 stride 猜。核心原则是把 logical indexing 与 physical storage geometry 分成两个独立 contract。

训练方法 / Serving

不涉及训练。Serving 侧影响 FLASHINFER_MLA_SPARSE、BLHNC、DCP 以及 DeepSeek-V3.2/GLM cache writer。

实验设置、指标与效率

Focused CUDA regression 在 H200 通过；模型级验证使用 GLM-5.3、TP8、FP8 KV cache、CUDA graphs，三个 deterministic prompts 各生成 128 tokens，BLHNC 与 LBHNC 结果 token-for-token identical。该 PR 主要是 correctness 修复，没有宣称吞吐提升。

线上 A/B、优劣势与局限

无线上 A/B。优点是用 layout-invariant validation 直接证明不同物理布局语义一致；局限是目前覆盖已知 sparse MLA / DCP 组合，未来新增 cache layout、offload layout、跨设备 remapping 仍可能重复出现“把逻辑尺寸当物理步长”的错误。

对推荐 / 搜索工程的启发

当生成式召回 / reranker 的 KV、embedding、ANN posting 或 feature cache 开始做分层、分片、压缩和跨设备映射时，一定要显式区分 semantic index / logical id / physical offset。建议所有 layout 优化都加 reference layout differential test，而不是只测某一个默认布局。

重点精读 03 · Quantization / MoE Correctness

vLLM：Checkpoint 写着 NVFP4，不代表它一定是 W4A4

Research Impact Score / 研究价值 9.4/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是，已合入 vLLM main是否有线上 A/B 否；有 end-to-end model validation阅读优先级 最高

背景 / 业务动机

低比特 Serving 正从“统一量化格式”走向 weight-only、weight+activation、per-tensor/per-channel、不同 kernel family 共存。模型配置文件里的一个 quant_algo 字段已经不足以唯一决定执行路径。

现有问题

某些 ModelOpt checkpoint 标记 quant_algo=NVFP4，但实际只量化权重，所有 config group 的 input_activations 都为 null。旧逻辑仍把它送入 W4A4 fused MoE path，并读取根本不存在的 input_scale。如果未初始化 buffer 恰好是 0，权重 scale 会全部乘成 0，专家全部“死亡”，模型输出重复 token 垃圾，而且没有异常。更糟的是 allocator 返回的旧页内容不同，使问题在 sm120 / sm121 等环境表现不一致。

技术方案

在 config parse 阶段判断：如果 checkpoint 声称 NVFP4，但所有 group 都没有 activation quantization，则提升为 W4A16_NVFP4，走 Marlin path；Marlin 将权重反量化到 BF16，不读取 activation scale。真正 W4A4 checkpoint 维持原路径。

训练 / Serving / 实验

不涉及训练。CPU config test 覆盖 weight-only promotion 与 genuine W4A4 保持不变；端到端通过关闭 CUDA caching 让未初始化 buffer 稳定读到 0，复现“修复前重复垃圾 token、修复后正常响应”。

离线指标、线上 A/B 与成本收益

没有传统精度指标或线上 A/B；收益首先是 correctness。代价是 weight-only checkpoint 走 W4A16 / Marlin 后不再享受 W4A4 activation quantization 的潜在计算收益，但这是与真实 checkpoint 语义一致的唯一路径。

与主流方法的优劣势 / 局限

相比按模型名或 GPU 架构做 heuristic，这种 schema-level dispatch 更稳，因为它看实际量化字段。但长远看仅靠 nullable config 仍不够；量化格式应显式声明 weight dtype、activation dtype、scale semantics、grouping 与 compatible kernels，并在 load time 做强校验。

对推荐 / 搜索算法工程的启发

在线大模型排序、生成式召回如果做 INT8/FP8/FP4，不能只关注“离线量化误差”。模型 artifact 本身要有可验证 schema，Serving loader 需要 fail-fast；否则最可怕的不是 OOM，而是系统继续 200 OK 地返回错误结果。

重点精读 04 · Runtime Policy / Memory Economics

vLLM：CUDA Graph Coverage 也需要 Memory Budget，不是越大越好

Research Impact Score / 研究价值 9.3/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是，已合入 vLLM main是否有线上 A/B 否；有 H200 nightly gate阅读优先级 最高

背景 / 业务动机

为了让更多 speculative decode batch width 进入 FULL graph，之前的 sizing 逻辑会自动追加 off-stride capture sizes。问题是每多 capture 一组大 shape，就要长期占用更多 graph memory，而这些内存直接与 KV cache 竞争。

现有问题

在 H200 nightly 中，默认 capture size 被扩到 2176 与 6400 tokens；suffix spec decode 发生 FULL graph capture OOM，DFlash case 则把可用 KV cache 压到 0.94 GiB，而 workload 需要 5.12 GiB，最终 engine 无法正常启动。

技术方案

保留动态 tier / safe off-stride coverage，但生成的默认 graph size 不得超过平台既有 ceiling：H200 512 tokens，数据中心 Blackwell 1024。超过 ceiling 的宽 batch 直接 eager fallback；用户仍可显式配置更大的 capture sizes。也就是说，graph coverage 从 feature 变成受预算约束的 runtime policy。

训练 / Serving / 验证

不涉及训练。Serving 行为只在超出默认 capture envelope 的 shapes 上从 graph 改为 eager。专项 config tests 26 passed / 1 skipped，并用两个精确 nightly 失败宽度作为 gate。

效率 / 成本收益、优劣势、局限

优势是避免“为了少量 latency 收益导致整机 KV capacity 崩掉”；代价是某些宽 batch 失去 graph acceleration。长期最优解不是固定 ceiling，而是基于显存、请求长度分布、KV hit ratio、并发和 graph reuse 价值动态选择 capture set。

对推荐 / 搜索工程的启发

推荐系统里同样存在“预计算越多越快”的诱惑：预热更多 shape、缓存更多用户 state、保留更多候选 embedding 都会吃内存。要把 latency saving / memory opportunity cost / fallback safety 联合建模，而不是只报 microbenchmark。

重点精读 05 · MoE / Multi-stream Overlap

vLLM：ROCm Dual-stream Decode 的收益，前提是 Shared / Routed Expert 不共享危险 Buffer

Research Impact Score / 研究价值 9.0/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★☆是否官方开源 是，已合入 vLLM main是否有线上 A/B 否；有 8×MI300 serving benchmark阅读优先级 高

背景 / 问题

MoE decode 中 shared expert 与 routed experts 可以放到不同 stream 重叠执行，降低 TPOT。但 Qwen3.5 的 routed expert 输入未量化时，shared expert 与 hidden state 复用同一个 tensor；多 stream 并发对同一 buffer 读写就会形成 race。DeepSeek-V3 的 routed expert 输入经过 FP8 quantization，会隐式产生独立 buffer，因此相同 overlap 策略反而安全。

技术方案

在 ROCm 上仅当 routed expert input 被量化、buffer ownership 安全时启用 dual-stream；否则自动关闭。shared expert 提前放到 aux stream、dispatch 与 routed expert 并行，并保持 hipgraph compatibility。

训练 / Serving / 实验

不改变训练。Qwen3.5 在自动禁用 multi-stream 后 GSM8K 精度恢复正常；DeepSeek-V3 保持 overlap。PR 报告在 DP 场景约 3–4% TPOT 改善，且强调 Fused Shared Experts 在可用时可能更快。

线上 A/B、局限与启发

无业务 A/B。局限是策略依赖具体 MoE 实现与 quantization path；真正通用的 runtime 需要显式 buffer alias / mutability metadata。对推荐系统而言，如果把 feature interaction、retrieval、rerank 多模块做异步并行，也必须先证明它们不共享可变状态。

重点精读 06 · Kernel Fusion / Numerical Contract

SGLang：把 Qwen-Image 的 Bias Add 吸收到 Residual / Norm，端到端约快 6%

Research Impact Score / 研究价值 8.6/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★☆☆是否官方开源 是，已合入 SGLang main是否有线上 A/B 否；有 GB300 E2E benchmark 与质量评测阅读优先级 高

技术方案

ModelOpt FP8/NVFP4 path 原本在 attention / FFN output projection 后单独 materialize bias，再进入 residual 与 LayerNorm。新路径用 skip_bias_add 延迟 bias，把它融合进后续 bias + gated residual + LayerNorm + scale/shift 与 final residual kernel。

实验 / 效率

GB300、Qwen-Image-2512 NVFP4、1024×1024、50 denoise steps：denoise/step 489.077 → 459.205 ms (-6.108%)，end-to-end 24.578s → 23.085s (-6.074%)；每 step BF16 aten::add launch 673 → 449 (-33.3%)。Microbenchmark 中 fused residual/norm 约 1.81–2.37×。

正确性 / 质量

值得注意的是输出并非 bit-identical：把 bias 从 cuBLASLt epilogue 延迟到后续 BF16 运算改变 rounding point。作者没有隐藏这一点，而是报告 SSIM 0.950545、PSNR 29.262dB、LPIPS 0.042544、pixel cosine 0.995333。这个做法比单纯写“精度无损”更可信。

训练 / A/B / 局限

不涉及训练，无线上 A/B。Fast path 目前刻意限制在 GB300 / SM10.3、BF16、batch1、hidden 3072 等已验证 shape；B200 等其他路径保留旧实现。对推荐 / 搜索的通用启发是：kernel fusion 的验收应同时报告 latency 与 end-to-end output drift，尤其低精度模型不能只看 operator-level bit exact。

重点精读 07 · KV State Ownership

SGLang：把 KV 的 protected / committed / allocated / req_pool_idx 收回一个 Owner Record

Research Impact Score / 研究价值 8.3/10工业成熟度 ★★★★★创新性 ★★★☆☆与你方向的相关度 ★★★★☆是否官方开源 是，主干连续合入是否有线上 A/B 不适用；行为保持型重构阅读优先级 高

背景 / 问题

HiCache、Unified Radix Cache、Spec-v2、Session 恢复等能力越来越多后，一个请求的 KV 状态包含 protected length、committed length、allocated length、req-to-token row、released/held 状态。如果这些字段分散在 Req、SessionSlot 和 allocator 中，就容易产生双写、save/restore 漏字段和生命周期 owner 不清。

技术方案

#37078 把 kv_committed_len 移入 ReqKvInfo，形成 [protected, committed, allocated] 的单记录；#37085 再把 committed length 的写入移动到 alloc path，和 allocated length 同步发生；#37094 把 req_pool_idx 也移入 ReqKvInfo，并让 is_held 直接由该记录判断。三项本身几乎不改变性能，却在构造一个更清晰的 KV state machine。

训练 / Serving / 实验

不涉及训练，属于 behavior-preserving refactor。它的价值主要是降低未来 spec decode、session restore、HiCache offload、LoRA/MLX 等路径扩展时的状态耦合。

局限与未来方向

当前仍是内部字段归属整理，不等于已经有完整 transactional KV protocol。下一步值得看的是是否会进一步统一 allocation generation、offload generation、cache protection、remote transfer ownership 和 failure rollback。

对推荐 / 搜索工程的启发

Shared User State / Session State 一样需要 single owner。跨召回、排序、Agent 复用状态时，不要让“同一个 user/session id”隐式承担所有生命周期语义；应明确 version、generation、committed boundary 与 physical owner。
