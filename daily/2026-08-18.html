每日研究简报 · 2026.08.18

Retrieval 不再只有一个固定模型，
Agent 也重新需要“先排序、再推理”

今天最值得记住的主线是：检索系统的下一阶段不是简单用 Agent 替换 Search，而是把模型大小、Embedding 宽度、Token 数、候选范围、交互次数都变成按请求分配的计算预算。Tevatron-Elastic 把 Retriever/Reranker 的多种压缩轴统一成单 checkpoint 的弹性运行点；大规模 RAG Scaling Study 与 RARG 则从两侧证明：Agentic Search 在大语料上仍需要强全局排序作为执行先验。

时间口径与质量控制：本轮扫描窗口为 2026-08-17 10:00 ～ 2026-08-18 10:00（北京时间）。公开 arXiv 分类页/搜索索引在本轮仍存在公告与抓取延迟，未能稳定提供足够 5–10 篇“窗口内全新首发”的高质量 cs.IR / RecSys 工作。因此本期明确区分：本轮首次确认并补入站点的高价值一手工作、KDD 2026 刚结束后的研究议程信号、以及昨日关键工作的一日追踪。原始提交日期均保留，不把旧稿伪装成今日首发，也不以低质量论文凑数。

今日核心结论

  • Elastic Retrieval 是“动态算力”真正可工程化的接口。 Tevatron-Elastic 用一个统一 Granularity 抽象覆盖 Depth / Token / Embedding Width，让一个 checkpoint 在部署时切换不同延迟、显存、索引体积与精度 operating point。
  • Agentic Search 不能跳过 Global Candidate Ranking。 BM25 Scaling Study 在 28 个严格嵌套语料规模上显示：小规模时 File-System Agent 很强，但规模放大后全局词法排序重新占优；Agent 更适合接在 ranked discovery 之后。
  • “相关性”从 Top-K Gate 变成 Agent 的执行先验。 RARG 不再只让 relevance 决定哪些文档进 Context，而是决定先搜哪些文件、从哪里开始、哪些局部 grep match 先暴露给模型。
  • KDD 2026 的两个教程给出同一个产业信号：推荐系统研究正在从“LLM 能不能用于推荐”转向 Tokenization / Retrieval / Augmentation / Optimization / Deployment 的全链路设计。
  • Stopping 与 Elasticity 应该放在同一个 Runtime Policy 里。 昨日 Search-R1 Stopping 学“何时不再检索”；今天 Tevatron-Elastic 解决“每次检索到底跑多大的模型”。下一步自然是统一 Request Value Router。

重点论文 01 · Elastic Retrieval / Reranking

Tevatron-Elastic: A Unified Abstraction for Training Elastic Retrievers and Rerankers

arXiv:2608.08809 · 2026-08-09 · Information Retrieval / Elastic Serving / Model Compression

这篇工作的关键不是提出一个新的压缩技巧，而是把过去互相割裂的“少跑几层、少算一些 Token、缩短 Embedding”统一成一个可训练、可部署的运行时接口。对搜索/推荐工程而言，这比再拿到 0.2 个点的静态 SOTA 更有长期价值。

1. 背景 / 业务动机

生产 Retriever/Reranker 面临的不是单一精度约束：离线大批量索引更在乎吞吐与 GPU 成本，在线高价值 Query 更在乎质量，Embedding Width 影响索引存储与 ANN 搜索成本，Cross-encoder 的层数/Token 数影响实时延迟。过去 MRL、Early Exit、2D Matryoshka、Layer-wise Token Compression 往往各有训练代码和部署逻辑，难以组合。

2. 核心方案

  • Granularity：一个 frozen dataclass 描述 operating point，三个轴分别是 Depth（执行到第几层）、Token（上层保留多少位置）、Width（最终 Embedding 维度）。
  • GranularitySchedule：训练时声明多个运行点，在同一 backbone forward 中对这些运行点计算损失，得到一个 checkpoint。
  • 统一 Retriever / Reranker：抽象建立在 Hugging Face Transformer 已有的 hidden states、layer ModuleList 与 pooling 接口上，因此 encoder/decoder、dense retriever/cross-encoder reranker 可以复用。
  • MLTC：在统一接口上还能训练多个 token-compression ratio 的 Matryoshka Layer-wise Token Compression。

3. 训练

训练目标不是让每个 operating point 单独训练一个模型，而是在一个 schedule 中联合优化。作者发布的脚本覆盖 BERT、ModernBERT、Qwen3-0.6B，Retriever 与 Reranker 两类任务，以及 pure-depth、MRL、2D、token compression 等配置。这样部署时不需要为每个 SLA 维护独立 checkpoint。

4. 推理 / Serving

Depth 主要减少 Transformer FLOPs/Latency；Token Compression 对长 passage 或 Cross-encoder 上层计算更敏感；Width 直接减少向量索引存储和 ANN distance compute。生产上最有价值的不是固定选某个压缩比，而是让 Router 根据 Query Value、负载、候选规模、P99 延迟动态选择 operating point。

5. 实验与可复现性

作者训练了 20 个公开 checkpoint，覆盖 3 个 backbone、Retriever/Reranker 两类任务和多个弹性轴；论文报告 quality curve 随运行点平滑变化，一个 elastic checkpoint 的训练成本只比单一 size 模型略高，并通过 controlled wall-clock study 验证实际加速。官方仓库同时给出训练/评测脚本，Hugging Face 已发布对应模型集合。

6. 与主流方案比较

优于单点压缩：不必给 Early Exit、MRL、Token Pooling 各建一套系统。相对传统 Cascade：它不是替代 Cascade，而是给每个 Stage 增加连续可调的 compute knob。相对 MoE/Model Routing：不需要维护多个完整模型，切换粒度更细，但不同 operating point 仍共享一个大模型权重，占用基础模型显存。

7. 局限 / 未解决问题

目前主要证明“一个 checkpoint 可以覆盖多个点”，但真正生产价值仍取决于 Router：哪些 Query 值得更深层、更宽向量、更高 token ratio？运行点切换在动态 batching 下是否会制造 GPU fragmentation / scheduling inefficiency？对十亿级向量库，Width 切换还涉及多版本 Index 或可截断 Index 的工程合同。

8. 推荐 / 搜索工程启发

值得把“Model Compression”改写成 Per-request Compute Allocation：Query Difficulty Estimator → 选择 Retriever Depth/Width → 动态 Top-K → Reranker Depth/Token → Stopping。这个方向与推荐系统已有 Cascade、Calibration、Bandit、Cost-sensitive Learning 能天然结合。

重点论文 02 · RAG Scaling / Search Economics

BM25 Wins at Scale: A Scaling Study of Retrieval-Augmented Generation Paradigms

arXiv:2607.26497 · v1 2026-07-29 / v3 2026-07-31 · Lexical / Dense / Graph RAG / Agentic Search

这篇论文最重要的不是“BM25 又赢了”，而是提供了一个很少见的受控 Scaling 实验：问题与相关/对抗文档固定，只扩充语料规模，于是可以观察不同 RAG Paradigm 的准确率、Token、构建成本与延迟如何随 Scale 改变。

1. 研究动机

BM25、Dense Retrieval、Graph RAG、File-System Agent 经常在不同数据集、不同语料规模、不同 reader 下比较，容易把模型差异和 scale effect 混在一起。作者构造 28 个严格嵌套语料 tier，规模跨度约 450×，并固定 reader 与 judging protocol。

2. 核心实验设计

  • 固定问题与 bedrock：相关文档和 adversarial documents 始终存在，只逐层加入额外 corpus。
  • 统一指标：同时看 official accuracy、construction/query tokens 与 latency，而非只看 answer score。
  • 多范式：比较 lexical、dense、graph-based 与 agentic file-system search，并研究混合 Agent+Ranked Retrieval。

3. 关键结果

观察结果含义
最小共享规模File-System Agent 领先小空间里顺序探索可以靠推理补检索
Bedrock query tokensAgent ≈ 39× BM25Agent 的探索成本从一开始就更高
约 10M corpus tokens 后BM25 反超，并在更大 tier 持续领先规模扩大后全局 candidate ranking 价值上升
Full scaleBM25 对 File-System Agent 的 margin 接近 20 points纯 sequential exploration 难以扩大搜索空间

论文摘要的结论很克制：lexical retrieval 是最强的可扩展默认基线之一；agentic reasoning 更适合放在 ranked discovery 之后，而不是替代它。

4. 对推荐 / 搜索系统的真正意义

推荐系统早已知道“先 cheap global scan，再 expensive local reasoning”的 funnel 经济学。Agentic Search 的第一波研究有时试图绕过这个经验，让 LLM 直接在 corpus 上探索；这篇工作提醒：随着候选空间增长，全局排序能力不是旧时代包袱，而是降低搜索熵的关键基础设施。更合理的结构是 BM25/Dense/GenRetrieval 做 broad discovery，再让 Agent 做 query reformulation、evidence composition、verification 与 stopping。

5. 局限

这是受控研究，不意味着任何真实企业语料上 BM25 都会赢。结论受 corpus lexicality、reader、tool interface、任务类型影响；Dense Retriever 的训练强度、Hybrid Search 配置也会改变 crossover。它更适合作为“架构反例”：任何宣称 Agent 可以替代 Retriever 的方案，都应该补充 scale curve 与 full-system cost。

6. 未来方向

最值得做的是 Scale-aware Router：根据语料规模、query ambiguity、lexical overlap、retriever confidence 决定 BM25/Dense/Agent 的组合；同时把 construction cost、query tokens、latency、cache hit 与 answer utility 纳入同一目标。

重点论文 03 · Agentic Search / Relevance-guided Interaction

A New Role for Relevance: Guiding Corpus Interaction in Agentic Search (RARG)

arXiv:2607.24223 · v2 2026-08-03 · Tencent / IIE-CAS · Agentic Search

RARG 的核心观点很适合推荐系统工程师：Relevance 不应该只做一次 Top-K 截断，它还可以成为后续执行过程的先验。换句话说，Ranker 的 score 不只是“把谁留下”，还可以决定 Agent 的搜索顺序、初始落点与局部证据曝光顺序。

1. 背景 / 问题

Direct Corpus Interaction（DCI）让 Agent 通过 grep/ripgrep 等工具在语料中细粒度探索，适合需要定位、组合、验证证据的复杂问题；但 relevance-agnostic 的顺序搜索可能很晚才暴露关键线索。传统 Top-K Retrieval 又会把候选硬截断，丢掉后续组合证据。

2. 三层粗到细 Guidance

  • RARG：先用 embedding relevance 对 corpus 排序，生成 scope，让 `rg` 按相关性顺序遍历。
  • RARG+：额外给出 query-relevant paragraph 作为初始入口，帮助 Agent 更快形成精确搜索词。
  • RARG++：对更大的局部 grep match pool 再排序，让低排名文档里的高价值 excerpt 仍有机会进入 Context。

3. 关键实验

Benchmark / Model结果成本
BrowseComp-Plus 100K · GPT-5.4-miniRARG++ 84% Acc23.9 avg tool calls
DCI 同设置78% Acc99.1 tool calls
BC+ 扩到 1M docsRARG++ 79% Acc24.7 calls，仅 +0.8
BRIGHT 4 subsetsRARG+ 53.36 avg nDCG@10优于该表中的其他方法

4. 为什么对推荐有迁移价值

可以把它直接翻译成推荐链路：粗召回 score 不必只做 Top-K cutoff，还可以决定 候选簇探索顺序、长历史读取顺序、Reasoning Context 的曝光优先级、Rerank 的局部扩展方向。这使“召回”和“Agent Planning”不再是完全割裂的模块。

5. Serving / 成本

RARG 的优势来自把 cheap relevance score 前置为 execution prior，减少昂贵工具交互。对线上系统，真正需要核算的是 embedding ranking + rg + LLM tool-use 的端到端 tail latency；不同 Agent family 的 tool count 并不能完全直接比较，项目页也明确提醒这一点。

6. 局限 / 下一步

当前主要在 BrowseComp-Plus / BRIGHT 上验证，Corpus 文件接口与企业 Search Index 差异大；relevance score 的 calibration 和 freshness 也未被彻底解决。下一步最有价值的是把 relevance、uncertainty、cost、novelty 联合成 interaction utility score，再学习动态 stop / expand。

一日追踪 06 · Retrieval Runtime Policy

Search-R1 Stopping × Tevatron-Elastic：把“何时停”和“跑多大”合并思考

昨日 Search-R1 Stopping 将“证据够不够、是否继续搜”变成 learned judge，并报告 Retrieval Calls 减少 3.70%，同时诚实提醒 Judge 本身有推理成本。今天补入 Tevatron-Elastic 后，一个更完整的 Runtime Policy 轮廓出现：

Query/User Value → Retriever Size → Retrieval Depth/Top-K → Reranker Size → Agent Interaction → Stop / Expand。

对推荐系统，这可以对应：用户价值/请求难度 → 召回路数与候选数 → 粗排/精排计算量 → Reasoning/Rerank 深度 → 是否继续探索长尾/新颖候选。真正值得做的研究不是给每个 knob 单独设计 heuristic，而是学习统一的 Utility–Cost Policy。
