最值得看 / 技术趋势

① 长历史 ≠ 无边界 Full Attention

生成式推荐的可扩展性正在从“加长历史 / 堆宽 Beam”转向分层可达性、状态复用与可控计算。PFA、RoFiGR 与 LWR 分别在解码注意力、SID 粗路由和深层历史读取上优化“真正需要计算的证据”。

② Reward 应靠真排序探针而不是 Loss

更可靠的算法研发必须以真实排序指标替代容易误导的代理指标。RecRSI 用短试训全库 NDCG 作早期决策；PRISM 让历史表征携带每次真实交互上下文；二者适合支持评价 Reward 的样本/表征质量治理。

③ 共享 Generator 未必等于快

把 RAG 排序与最终生成合并并不自动提升在线效率。Glance 共享 LLM 预填充，改善部分离线排序与答案质量，但当前逐请求仍显著慢于小 Cross-Encoder；要按 QPS/P99/GPU-ms 取舍。

④ 检索证据必须可审计

AgenticDS 与 ZEST-Search 一端强调数据/检索结果的事实契约，一端强调任务生成与工具成本的 RL。这提示：先验证 Reward 所需样本是否真实可信，再优化 Generator 学到的行为。

问题背景 / 业务动机 / 已有方法缺陷

长历史让生成式推荐更准确，但 SID/列表自回归的每一步都对全历史做注意力，Beam 越宽重复 KV 读取越多。静态历史摘要可能删除重要偏好，逐步动态 TopK 又增加排序和非连续显存访问成本。

技术方案与核心模块

作者观察到生成步骤越往后越聚焦少量历史 token，且各步重要性排序较稳定。第 0 步做全注意力，第 1 步聚合各 Beam 的 token 重要度形成共享索引，把选中 KV 物理压成连续块；随后沿固定索引按几何比例缩小注意力长度，辅以 step-aware KV projection。核心假设是“第一次充分观察，再逐步收缩”，而非一开始永久丢掉历史。

训练方法 / Objective / Loss

推荐主干沿用生成式 SID 的自回归下一 token 训练；PFA 重点是推理解码路径而非新的 Reward Model。论文使用多阶段投影配合推理；不能把实现中的 step-aware KV 理解为已证明的 List-level 偏好损失。对评价场景应另外叠加成交/满意度监督。

推理与 Serving 方案

训练后按步骤执行 full attention→cross-beam importance aggregation→KV gather/compact→后续 step 共用有序索引与递减预算。工业部署须关注 Beam 批内分叉、KV 物理拷贝频次、prefix 失效与请求长度分桶；对动态增加的评价，需保留高风险新证据 token 进入预算。

实验设置、离线指标与对照

公开 Kindle、Tmall 与工业数据的 Recall/NDCG；工业实验共享索引在 Step 1 构建时 Recall@10=0.1695、推理 62ms/批，若提前到 Step0 为 0.1632、55ms/批。k=256、收缩率 r=0.5 为作者默认；这些离线“毫秒/批”不是线上 RT。

线上 A/B、证据等级与归因

7 天随机 A/B，两组各 10% 流量。对照组历史截断 128，实验组使用 PFA 扩至 512；REV +3.76%、CTR +0.34%、GMV +2.56%，实验方案在线 RT 11ms；直接用完整 512 历史对照方法 RT 15ms。需注意实验改变了“历史长度+解码策略”，不能把业务收益全部归因于稀疏注意力本身。

效率、算力与总成本收益

和完整 512 历史前向相比，11ms 对 15ms 体现服务端收益；离线 62ms/批与线上 11ms 不同配置不可直比。跨 Beam 共享 token 选择是主要节省点；GPU gather/compact 是否额外消耗带宽，需在目标平台 profiling。

与主流方法的优劣势

相比每一步重选 TopK，更少排序与随机读取；相比静态短摘要，保留早期全局观察。弱点是极度稀疏兴趣、转折性负评、突发兴趣可能不满足跨步稳定性；一次错误压缩可沿整个 beam 传播。

适用场景

适合生成式召回和大规模 List 排列、长用户行为的广告推荐，以及需要读取几十条评价证据的列表生成；如果评价列表本身很短，KV 改造的复杂度可能高于收益。

局限、尚未解决的问题与下一步研究

研究带重要性不确定度的 token 保留、含负面评价的安全保留集合、延迟预算感知的动态收缩和异常请求全注意力回退。建议固定 512 历史做 PFA on/off，以分离历史增益与算子增益。

对商品评价 List 推荐的启发 / 职业技能

给商品评价 List Generator 建两维实验：历史长度 × 注意力策略，观察 GMV、满意度、负面证据覆盖、P95/P99 和 GPU-ms。尤其对差评触发的购买顾虑，增加“证据必保留”约束，防止 TopK 注意力放大热门好评。

问题背景 / 业务动机 / 已有方法缺陷

LLM Agent 能改 sampler、loss、模型层和优化器，但旧流程每轮选一条修改完整重训后才知道 NDCG；早期训练 loss 既不能跨配方比较，也可能掩盖全库 hard negatives 排名失败。高昂训练资源浪费在坏编辑上。

技术方案与核心模块

RecRSI 先用 probe users 诊断父模型的排序失误，再一次生成 3 个异质编辑；通过静态合法性检查，给每个编辑从共同初始权重按自己的训练配置做 15% 完整训练步数，随后在留出的 probe users 上做全库 NDCG@10，选出表现最好的一条再完整训练。每轮沿“诊断—候选—短试训—重训—晋升—记忆”循环。

训练方法 / Objective / Loss

创新重点是“评价函数时机”，不是发明统一梯度损失。候选可以修改原有 CE、负例采样或结构；选择信号是同训练路径、同全库评估定义的 held-out NDCG@10，而不是候选损失或 LLM 对代码的静态打分。晋升需超过预设 margin，Test 用户始终不参与进化。

推理与 Serving 方案

论文优化离线训练配方；最终模型仍沿 SASRec/HSTU 的正常在线 serving，未提出专门在线推理加速。实验平台必须保证固定数据切分、同硬件与随机种子，否则短试训会放大实验噪声；部署阶段仍应随机 A/B。

实验设置、离线指标与对照

2 个推荐基座 × CDs/Office/LastFM 三域，参照 AlphaEvolve、DeepEvolve、Self-EvolveRec。SASRec 相对最强基线 Test NDCG@10：CDs +41.7%、Office +41.5%、LastFM +30.7%；HSTU：+17.6%、+102.0%、+16.1%。作者还报告 1 GPU-hour 同预算对比 NDCG@10 为 0.0622，最强已列基线为 0.0572。

线上 A/B、证据等级与归因

没有真实商业线上 A/B。论文的“晋升”是独立离线 held-out 排序质量改善，不能解释为线上成交或用户满意度提升。多轮编辑并非等预算天然优于单轮；需要将试训算力计入总账。

效率、算力与总成本收益

一轮含 3×15% 短训＋1 次全训，单位迭代计算高于只训一个编辑；但更多完整训练花在高质量编辑上。论文还给出等 GPU-hour 消融支持净收益；大模型评价 Reward 训练应优先考虑 GPU-hour/保留改进数，而不是只看改进率。

与主流方法的优劣势

相对 Agent 直接改代码后凭 loss 或 patch judge 选择，更接近真实排序目标；但早期学习曲线与最终质量未必一致，多个结构改动也可能无法用同一短预算公平比较，且高噪声业务标签更易早期错误淘汰。

适用场景

适合推荐算法实验平台、Reward Model 的 Loss/样本重加权搜索、评价列表生成器的 DPO/GRPO 配方探索；不是允许 LLM 直接自动操作线上高风险实验。

局限、尚未解决的问题与下一步研究

把多保真 early ranking test 扩展到候选 List-level 指标、位置偏差、满意度校准和置信区间；加入安全门槛、可回滚 CI、数据血缘与离线-在线一致性追踪。

对商品评价 List 推荐的启发 / 职业技能

评价团队可把“sampled loss 看起来收敛，真实 List 效用却未提升”当作诊断起点。建立独立探针用户组，对每次 Reward/Generator 改动短训后评估完整候选 List 的 NDCG、成交代理、负面覆盖及校准，再决定是否完整训练。

问题背景 / 业务动机 / 已有方法缺陷

传统序列模型每增加历史 token，深层计算也沿整个序列扩张；一次性 history pooling/select 让后续层无法再访问初期忽略的证据。长历史和更深推理被绑在同一高昂张量上，妨碍质量与成本的独立调节。

技术方案与核心模块

Latent Workspace Ranker 将按类型组织的历史证据保存在可随机读取的 bank 中，每个候选只维护一个固定小尺寸 workspace；每层以更新后的候选状态重新检索原证据，交互后保存紧凑 condensate，下一层再读。模型不是把全部历史每层重复传播，而是把“可寻址证据”和“需传播的推理状态”分离。

训练方法 / Objective / Loss

在精排任务上用正常监督目标与 normalized entropy (NE) 评估；创新在结构和计算分配，并非 Reward/Preference 训练。论文以 NE=E+A*C^{-α} 拟合不同历史长度×网络深度的最优训练计算边界，这条 scaling law 是实验拟合而非对所有推荐场景的定律。

推理与 Serving 方案

候选请求生成轻量 workspace，各层按 query 读取对应证据 bank，聚合后归档少量中间状态；长历史可以在共享存储/近线表征中维护。线上必须控制 bank 索引读取随机访问、candidate fanout、GPU 带宽、缓存有效期和跨天 state 兼容性。

实验设置、离线指标与对照

固定深度把历史从 3K、5K 拉到 10K；固定 10K 历史独立增深；再遍历 468 个 history-depth 组合比较训练计算前沿。10K 时对 HSTU NE 改善 0.19%（更低更好），forward GFLOP/request 降低 69.6%；Surface 1 关键任务 NE 改善约 0.08–0.09%，Surface 2 相对 HSTU 改善 0.15–0.30%。

线上 A/B、证据等级与归因

未见线上随机 A/B，虽然研究在十亿规模场景评估，也不能把离线 NE 改善直接标作线上 GMV/满意度增益。

效率、算力与总成本收益

10K 历史下 69.6% forward GFLOP/request 降幅属于受控模型计算口径，不代表端到端服务 P99 下降同幅。必须加算数据读取、缓存失效、pipeline feature join 和候选并行开销。

与主流方法的优劣势

相比 HSTU 的长序列深层传播，LWR 历史读得多而状态传得少；相比一次性 TopK 历史筛选，后续层能重新检索被跳过的证据。缺点是证据 bank 的 IO 成本、读放大和系统集成较复杂。

适用场景

适合候选相关的长期偏好精排、商品评价内容的事实证据反复检索，以及用户/商品双长序列融合。对召回不一定能直接替换 ANN；该工作更贴近精排。

局限、尚未解决的问题与下一步研究

探索在线写入的 evidence bank、跨请求共享/去重、支持罕见负评的稀疏读保护，以及双阶段 List Generator/Reward 中 workspace 的一致性。

对商品评价 List 推荐的启发 / 职业技能

把评价列表判断拆成“有多少原始评价证据可访问”和“对当前商品/用户的每层推理深度”。实验固定一轴增大另一轴，同时上报满意度、覆盖、NE、GPU-ms 和 P99，避免只堆序列长度。

问题背景 / 业务动机 / 已有方法缺陷

简单按 query relevance 排序，容易检索出多篇重复解释相同观点的材料，却遗漏相反观点和关键事实。即使取得覆盖更全的证据，Generator 也未必真正把证据写进答案。

技术方案与核心模块

先把复杂问题拆成可检验子问题，coverage-aware 双塔粗筛，再用 cross-encoder 预测每篇文档对每个子问题的覆盖矩阵；以边际覆盖最大化/冗余惩罚贪心选上下文。第一轮生成后由 grounded self-feedback 识别虽已检索但未被回答利用的证据，第二轮针对缺口再生成。

训练方法 / Objective / Loss

监督层采用与覆盖信号相关的 bi-encoder/cross-encoder 训练，再通过贪心 maximal marginal coverage 推断选择子集；self-feedback 不是额外 RL 或离线 List Reward，而是基于生成文本和检索证据的自检查推理环。

推理与 Serving 方案

适合两阶段召回→coverage scorer→有限预算选证据→生成→可选二次生成。二次生成显著增加延迟与 token 消耗，工业服务应按问题复杂度触发，并在覆盖充分时提前终止。

实验设置、离线指标与对照

TREC RAG 2024 中 α-nDCG@10 从 0.625 提升至 0.702，接近 gold nugget 参考上限 0.718；二次 grounded feedback 后 V_strict（完全支持的必要信息片段比例）提高 +0.086。作者指出 oracle retrieval 召回更高也未转化成更高答案 nugget 覆盖。

线上 A/B、证据等级与归因

仅有离线 RAG 证据与答案评测，未报告商业线上 A/B，更不等价于“评价 List 提升 GMV”。

效率、算力与总成本收益

coverage cross-encoder 和多次生成都增加服务成本，收益是证据利用率提升而非吞吐证明。可用轻量 aspect classifier/向量聚合先估算边际增益，重型 cross-encoder 只跑 TopM。

与主流方法的优劣势

相对普通 relevance rerank 强在互补和缺口显式建模，但依赖稳定的子问题分解；若子问题分解本身有遗漏或错误，覆盖约束可能系统性放大错误。

适用场景

电商评价推荐可以将“材质、尺码、物流、负面体验、售后”视为 aspects，选择信息互补的评价 List；与 LLM 问答不同，还需显式考虑阅读负担与成交目标。

局限、尚未解决的问题与下一步研究

训练同时对齐 aspect coverage 与用户决策收益的双目标 List Reward；在重复负面证据、敏感风险信息、少数观点场景施加最低覆盖约束，研究可学习的边际覆盖函数。

对商品评价 List 推荐的启发 / 职业技能

原来的成交+评价满意度 Reward 可能高估热门高赞评论而忽略反面信息。新增 aspect coverage、contradiction/negative preservation 和 List-level novelty 特征，并做真实曝光相同候选集合的排列 A/B。

问题背景 / 业务动机 / 已有方法缺陷

固定人工问题集限制 Agent 能力边界；只按最终答对与否给 RL reward，等价对待“1 次检索就够”和“反复无谓检索”的策略，成本没有进入真实优化目标。

技术方案与核心模块

ZEST-Search 使用异质任务 proposer 与搜索 solver：proposer 围绕 solver 当前难度边界，以 answer-first 和 evidence-path-guided 路线从无标注问题生成可验证的新任务；solver 用外部工具多步检索并回答。两者交替进化，工具调用与证据路径纳入奖励计算。

训练方法 / Objective / Loss

proposer 奖励偏好中等可解难度，使任务既非过易也非不可能；solver 使用 task-local tool-aware reward，正确性结合冗余搜索惩罚进行 RL，避免把所有成功轨迹当成等价正例。零人工标签不等于零自动验证或零模型调用成本。

推理与 Serving 方案

训练出来的搜索 Agent 仍要执行真实检索/工具调用，论文关注训练后轨迹效率而非提出低层 GPU Serving 新算子。需要将工具 timeout、外部依赖费用与 retry 次数计入延迟预算；价值引导应受每用户/请求约束。

实验设置、离线指标与对照

论文报告在 7 个通用与多跳 QA Benchmark 中准确率和工具使用效率一致改善；摘要未给所有数据集逐项绝对指标，本站不凭空填入统一百分比。作者以异质造题、难度控制与 tool-aware reward 消融解释收益。

线上 A/B、证据等级与归因

无真实电商或搜索生产 A/B，工具数量减少与用户满意度变化需要另行验证。

效率、算力与总成本收益

工具调用数减少有潜在 API 成本收益，但在线搜索本身可并行/缓存，减少轮次不必然减少 P99；应汇报工具费、token 费、外部服务耗时及成功率四维 Pareto。

与主流方法的优劣势

比静态问答数据集和 outcome-only Agent RL 更匹配动态难度和工具成本；但自动生成任务分布可能渐渐偏离真实用户问题，证据验证器错误还会污染训练信号。

适用场景

多步 AI 搜索、研究 Agent、自动测试集生成，以及评论摘要真实性核验的证据检索；对于纯排序问题需更换终态回报和任务格式。

局限、尚未解决的问题与下一步研究

用线上失败请求反向指导 proposer，混合人工审核的 hard negatives，对伪证据、错引、无意义 tool retry 建立独立惩罚和不确定性门槛。

对商品评价 List 推荐的启发 / 职业技能

商品评价 Reward Model 的数据瓶颈可借用“围绕现有失误在线生成困难对比”，如负面观点漏选、同质评论过多、位置偏见等；但必须用真实曝光反馈校准生成标签，不能用模型自评无限互相强化。

问题背景 / 业务动机 / 已有方法缺陷

大规模训练数据集搜索不仅是语义相似：用户还有 license、训练阶段和任务适配等硬约束。普通 Dense/Sparse 检索只能找“像”的；自由工具 Agent 可以编出看似满足约束的数据集但没有证据。

技术方案与核心模块

AgenticDS 将自然语言训练意图编译成有类型的搜索计划，在 hybrid retrieval 与有限图扩展等确定性算子上执行；每个候选都须通过 provenance-grounded evidence 校验，未达约束时反馈明确类型化诊断，只允许局部修复而不是重编整条路径。

训练方法 / Objective / Loss

方案重心是 search planning/verification，而非把一次 LLM 生成直接当标签；检索候选有语义相关排序与硬约束可接受性，结果另用下游训练准确率验证真实效用。官方未披露可直接移植评价 Reward 的通用 Loss，工程端建议使用多约束排序/可解释证据校验。

推理与 Serving 方案

编译计划→执行检索/图扩展→证据验证→有界修复→结果。对线上训练数据搜索可采用异步缓存；对高频在线推荐，完整 Agent 规划成本较高，宜做离线数据平台组件。

实验设置、离线指标与对照

HuDS-Bench 含 200 个搜索问题、24,908 个分级相关性判断和 15 个系统的 pooled 评估；相对最强 Dense–Sparse hybrid 的 NDCG@10 +25.7%，相对商业 LLM Agent +18.9%；受控“搜数据→训练”实验在数学、代码和医疗任务得到最好下游准确率。

线上 A/B、证据等级与归因

未报告电商/广告生产线上 A/B；下游训练试验支持实用性，但仍需检验数据集版权/隐私、时间切分和线上漂移。

效率、算力与总成本收益

通过确定性算子代替自由生成在多数步骤降低错误修复风险；具体 GPU-ms、总 API 费与极端请求延迟需另测，检索高分不能替代训练收益。

与主流方法的优劣势

比只做 embedding 相似更重事实/条件满足，也比“Agent 自我宣布成功”有可审计契约；其局限是类型系统和元数据覆盖不完备，复杂跨数据集语义还可能超出计划算子表达能力。

适用场景

训练数据、Reward 标签来源追踪、评价场景高质量样本发现，以及遵守授权/时间区间的数据检索。

局限、尚未解决的问题与下一步研究

把可验证 provenance 扩展到训练样本粒度、标签冲突、样本重复与泄漏；以 downstream List Reward 校准搜索排序，建立失败修复闭环。

对商品评价 List 推荐的启发 / 职业技能

评价 Generator 最大风险不一定是 Loss，而是输入训练样本不满足“真实曝光、同候选、完整标签、无时间穿越”的硬契约。数据集选择器应先验证事实与权限，再讨论语义相关性和模型学习收益。
