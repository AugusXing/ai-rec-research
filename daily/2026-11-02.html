多目标价值优化 / Agent 与数值模型 · S+ ① · 原稿 2026-10-29 UTC

CASH · A Capability-Aware Subsidy Harness for Advertiser Subsidy Allocation

一句话研究判断：LLM Agent 能理解操作知识却可能缺少数值精确性；纯数据响应模型在低曝光或新业务组合上易外推失败。观察到的收益受历史决策政策选择偏差影响，不能直接当作每种补贴水平的因果增量。

业务背景 / 动机

广告平台给不同广告主分配账单补贴比例，目标是在总补贴率约束下提升业务收入与客户价值。固定分层规则无法处理账户×补贴档位的真实异质反应，也无法把共享预算优先用于高增量账户。

现有方法与核心矛盾

LLM Agent 能理解操作知识却可能缺少数值精确性；纯数据响应模型在低曝光或新业务组合上易外推失败。观察到的收益受历史决策政策选择偏差影响，不能直接当作每种补贴水平的因果增量。

技术架构 / 关键模块

并行建立知识引导 LLM Agent 与数值响应模型，针对账户—档位的局部可信性发放能力许可（决定应该由哪位专家预测），冲突处交由协调 Agent 复核。EPCG 识别新增探索样本最可能提高可靠可覆盖业务价值的区域，随后在全平台预算下配置账户补贴。

训练目标、Loss 与样本机制

主要学习路径为数值模型对反馈的响应拟合、局部可靠性估计与定向反馈迭代，并非统一生成式 CE/RL 目标；最终预算求解可视为带全局补贴率限制的拉格朗日分配。若反馈样本非随机，必须做反事实估计与置信区间约束。

推理 / Serving 及数据流

离线/近线计算各账户候选补贴级的两种预测与能力标签，仅在低可信/冲突组合上进行较贵的 Agent 裁决，再经预算求解批量落地。线上要有决策版本、总预算守恒、专家回退、跨账户干扰监测和滞后反馈校准。

实验设置及基线

作者披露 2026-09-14 至 10-14 的平台实验，CASH 约占 60% 流量；基线包括传统 Control 和纯数值 Tool。跟踪 Revenue/Account、ADVV、补贴率、LTV、留存与离线预测误差。跨账户共享预算使实验单位及同群体干扰值得额外注意。

离线指标与验证结果

数值模型 MAE 345.58 优于 Agent 的 360.17；但 RMSE 1336.51 稍逊 Agent 的 1328.32。误差指标相互交错支持“不同局部区域不同专家”的动机；不可从整体 MAE 断定一个专家到处更好。

线上 A/B 与归因边界

在补贴率近似不变时，CASH 对 Control 收入/账户 +15.35%，ADVV +19.86%；对数值 Tool 的收入再提高 +6.31%，Tool 对 Control +8.50%。作者按日 moving-block bootstrap 给出的收入改善区间约 [12.05%,17.77%]、ADVV [15.05%,23.18%]；特定平台策略组合结果，不是各组件独立因果归因。

计算、成本与效率收益

引入双模型、授权判定、纠错探索会增加工程复杂度与训练/推理成本；用能力许可缩小需要高价 LLM 复核的面积，并把反馈预算集中于高价值不确定区域。应以增量收益/美元、探索样本成本、P99、预算违规率核算 ROI。

相对主流方法的优势和不足

相比只用数值预估，兼顾低样本区业务先验；相比直接 LLM 全决策，可审计且按置信度限用专家。关键风险是许可本身误校准、分布漂移和预算竞争造成的关联干扰。

可落地的场景

广告补贴、商家激励、优惠券/权益预算及任何受统一资源约束的价值优化。评价列表场景可做规则/LLM 评委与真实反馈 Reward Model 的可信路由，而不是直接迁移补贴算法数值。

局限、未解问题与下一步研究

尚需严格拆出探索 EPCG、协调 Agent、响应模型各组件对在线结果的增量；研究更稳健的反事实 uplift、群体公平、策略切换前分布漂移门控及连续预算变化的稳定性。

对商品评价 List 算法工程及职业能力的启发

对评价 List：构建「场景×评论属性×位置×列表长度」分桶的成交/满意度校准集，比较 LLM Judge 与真实 List Reward 的误差与置信区间，只在授权区域采纳 Reward 监督。先以 holdout + 小流量随机实验验证可信度路由，再比较是否优于简单 Reward 加权。

一句话研究判断：直接上传用户自然语言解释容易把相同表面兴趣但不同购买决策混为一谈；传统 FedAvg 等参数联邦方式也不适合冻结大语言模型、异构客户端或以语言记忆驱动的流程。

业务背景 / 动机

具备长期记忆和推理能力的用户推荐 Agent 如完全孤立，就难以从群体行为中迁移知识；若把原始历史集中到服务器，又存在隐私、数据最小化和业务治理困难。

现有方法与核心矛盾

直接上传用户自然语言解释容易把相同表面兴趣但不同购买决策混为一谈；传统 FedAvg 等参数联邦方式也不适合冻结大语言模型、异构客户端或以语言记忆驱动的流程。

技术架构 / 关键模块

每个客户端将经验写成 C-T-R：条件、发生的动作/偏好转移、支持该行为的理由。服务端先按条件再按转移层级聚合知识，明确区分同条件下的不同选择；客户端保留语义偏好记忆和条件化决策记忆，以本地上下文检索共享推理。

训练目标、Loss 与样本机制

不是新推荐 CE/DPO Loss，也不更新 LLM 权重；核心是对局部经历归纳、服务端分层汇总和多轮知识共享。论文以 Qwen3-4B FP8 客户端与 8B 服务端构建多轮流程，并消融双记忆和知识结构。

推理 / Serving 及数据流

推理可使用端侧/隔离客户域的私有记忆检索 + 服务器可共享 C-T-R 表，动态按行为条件选择理由生成排序依据。上线应缓存知识树、限制长文本 token、控制知识版本/过期及端侧延迟，并防范解释文本泄漏私有行为。

实验设置及基线

Amazon CDs/Music/Office，分别在稠密与稀疏切分比较；时间先后分割，以 1 个正例 + 9 个随机负例的 sampled NDCG/MRR 衡量，使用短历史约 10 条和多种子实验，并对照联邦及 LLM 推荐基线。

离线指标与验证结果

相较最强比较方法，各设定 NDCG@10 约提升 1.54%—9.19%，MRR 约提升 3.01%—16.29%。由于只在采样 10 候选上排序，不能直接解释为百万候选召回、长尾冷启动或真实 CTR 提升。

线上 A/B 与归因边界

未报告真实线上 A/B；不上传原始交互并不能保证自然语言理由满足差分隐私，需检测成员推断、跨用户信息泄漏和恶意客户端知识污染。

计算、成本与效率收益

免去大规模客户端权重聚合、参数同步，但多轮知识生产和服务器 LLM 汇总仍会消耗 token、网络及缓存；按每用户个性化增益/传输字节及 P99 对比轻量用户向量模型。

相对主流方法的优势和不足

相比纯本地 Agent 能共享有用群体经验，相比全局粗粒度人群规则能保留条件化差异。弱点是稀疏行为条件归纳不稳、推理理由可能幻觉、隐私保证仍需形式化验证。

可落地的场景

端侧推荐、隐私敏感的个性化内容、低交互频次新品类。对于商品评价可共享「购物任务→需要何种负面/正面证据→后续满意度」的抽象决策趋势，而不共享可识别用户历史。

局限、未解问题与下一步研究

后续重点是隐私攻击指标、语义污染、长历史、full-catalog 评价、知识增量回滚和在线用户反馈；多轮共享是否真的超过更简单的特征蒸馏也需严格对照。

对商品评价 List 算法工程及职业能力的启发

建立按购物意图条件分层的短/长用户历史实验，分离 private user memory 与可共享群体 reasoning，用固定候选集评估列表 NDCG、覆盖、多目标 Reward；再比较加密聚合或轻量模型蒸馏的成本收益。

业务背景 / 动机

长文档切块后，一个段落的实体、定义和条件可能埋在前文；检索仅找一个能回答问题的 gold chunk 还不足以让 LLM 验证事实、比较相反证据或避免幻觉。

现有方法与核心矛盾

独立 chunk embedding 丢上下文，全篇唯一向量又会忽略细节。二值 gold 标签过于依赖切块策略，不能奖励多证据覆盖和可验证的回答；这是评价推荐中只找最相似好评的同类问题。

技术架构 / 关键模块

作者用 query-aware 上下文压缩 teacher，对文档 token 区分重要性并聚合为分级 chunk 相关性，学生学习完整文档语境下的各片段 embedding。以 VLM 基座兼顾文本与图像，发布 9B 和 0.6B 同空间的向量模型，评估答案块与验证证据块的双重覆盖。

训练目标、Loss 与样本机制

训练包含 teacher 软目标的 KL/分级蒸馏与文档级对比学习；目标不是单段二元相关性。教师构造 soft labels 需要离线开销，轻量学生负责在线召回。对于评论应另外监督情绪、属性、真伪与时间因素。

推理 / Serving 及数据流

文档建库时输出携带全局上下文的各 chunk 向量，查询端走独立 query encoder，再接 ANN/精排。0.6B 与 9B 的兼容空间便于混合使用，但版本变更、前处理、索引重编码、embedding 量化和图像块必须重验召回一致性。

实验设置及基线

评测 Context-bench、Q2D-Chunk（公开 leaderboard，但不能冒称全量标注数据开放）、ConTEB、ViDoRe-V3，指标包括 Answer@K、证据 Recall、alpha-nDCG 与达到覆盖所需 token。视觉文档使用图像 chunk 检索。

离线指标与验证结果

计算、成本与效率收益

相对主流方法的优势和不足

比句子独立向量更重视文档上下文；比整篇 embedding 保留分段定位；比 cross-encoder reranking 可离线预编码，但难以替代复杂交叉注意力的最终判别。

可落地的场景

业务背景 / 动机

Agent 深度搜索会多次查找、改写查询并阅读文档，最终结果好可能源于初始检索器强，也可能源于允许更多检索次数；没有可比搜索成本，难评估真实策略价值。

现有方法与核心矛盾

不同系统采取随机浏览、持续阅读旧排序结果、改写新 Query 等动作，但测量口径不一致。只用最终 RAG 答案正确率，无法区分召回器、查询生成器和多步选择策略。

技术架构 / 关键模块

把环境表示为若干 ranklists 和各自阅读位置；select 从现存排序列表取下一条未检查文档，spawn 发起查询改写并产生新的排序列表。每步更新搜索状态与 reward，将 CAL、Thompson Sampling、简单启发式等表示为统一策略。

训练目标、Loss 与样本机制

核心贡献是序贯决策抽象与评测，不应宣称作者训练了新的上线 RL 模型。reward 可以基于找到新的相关文档、成本、任务增量，框架具备 RL 解释，但实验里的规则/策略比较与 GRPO 训练不同。

推理 / Serving 及数据流

Agent orchestration 保存每条结果列表的 cursor、已读候选 set、查询改写版本及剩余 token/工具预算；对无增益的新列表触发 stop，去重相同文档，缓存重复请求。

实验设置及基线

High-Recall Information Retrieval（HRIR）任务，用相关文档发现、R-precision/Recall 和固定 judgment budget 比较不同初始排序器及搜索策略；因评测目标强调高召回，不应与一次性精排 NDCG 混用。

离线指标与验证结果

论文主要观察：同等阅读预算下，起始检索方法与深度搜索 policy 都会实质影响找到的相关文档比例。具体数值依任务/预算曲线而变，本期不杜撰未逐图复核的绝对增益。

线上 A/B 与归因边界

没有商业 A/B；寻找更多相关文档不等于最终回答/推荐质量提升，需要实验最终成交、满意度或问题解答真实性。

计算、成本与效率收益

select 利用现有 ranklist、成本主要来自审阅候选；spawn 增加检索调用和 query 生成，需以每次动作的边际相关证据增益 / token / GPU-ms 决定触发阈值。

相对主流方法的优势和不足

相比黑箱 Deep Research 提示词，可以分离检索器质量与决策质量；但二值相关性未反映事实冲突、负面证据和用户偏好，统一任务 reward 仍是难点。

可落地的场景

复杂商品咨询和多属性评价列表召回，避免一个查询只覆盖一个属性；适合高价值会话而非毫秒级大流量每次曝光。

局限、未解问题与下一步研究

用户真实曝光和被判断文档存在选择偏差，现有离线 HRIR 标签可能放大已有召回器的覆盖偏好；未来研究带反事实校准的轨迹 Replay 和动态预算调度。

对商品评价 List 算法工程及职业能力的启发

定义 select=继续看当前候选评价，spawn=基于缺失属性扩展检索主题，固定总候选曝光数量，测新增独立观点、负面证据覆盖、最终 List Reward、工具调用数与 P99。

MoE / 专家路由 / 推理成本 · S ⑧ · 原稿 2026-10-29 UTC

Multi-View MoE · Multi-View MoE: Letting Every Router Shape Expert Computation

一句话研究判断：单路由分数和实际专家效用在中深层相关性可能很弱。增加多个 router 观察角度虽然丰富打分，但若只是算平均仍未让专家计算利用观点差异。

业务背景 / 动机

稀疏 MoE 保持每 token 少量专家激活，提高模型容量；但单个 Router 可能打分失准，把预算给并不最有效的专家。让所有专家先跑再挑又会失去稀疏优势。

现有方法与核心矛盾

单路由分数和实际专家效用在中深层相关性可能很弱。增加多个 router 观察角度虽然丰富打分，但若只是算平均仍未让专家计算利用观点差异。

技术架构 / 关键模块

Multi-Router 用不同初始化路由器的 sigmoid 偏好聚合专家选择；Multi-View 按选中专家在多个路由器上的相对得分混合一组可学习 latent view input。每个被选专家仅运行一次，实现选择与专家输入联合改善。

训练目标、Loss 与样本机制

基于常规稀疏 MoE 语言模型预训练，并增加路由器及 view mixing 参数，保持 top-k 专家侧预算；论文比较只有 Multi-Router 与完整 Multi-View，并统计真实专家效用和路由分数相关性。

推理 / Serving 及数据流

每个 token 的选中专家数量、专家 FLOPs 与 all-to-all 数据量在论文比较口径下维持不变；但多个 router 和视角混合仍增耗，不能等价为整体 P99 零成本，应实测不同 batch、专家热点与 kernel 融合。

实验设置及基线

24 层、10B 总参数/1B 激活的 MoE，708B tokens 训练，评估 9 个下游任务均值及不同层 router-专家效用排序一致性，与单路由基线和仅多路由消融比较。

离线指标与验证结果

九任务均值由基线 33.07 提高到完整方案 34.25（+1.18 个绝对百分点），仅 Multi-Router 33.69（+0.62 点）；路由-专家效用相关性整体相对改善约 8.1%，最弱层约 58%。

线上 A/B 与归因边界

未披露生产推荐系统的随机 A/B 或分布式服务 P99 指标；作者的固定专家 FLOPs 主张也不等于整个线上服务零额外开销。

计算、成本与效率收益

创新在固定专家算力预算内提质；更大 router、mixing 参数、负载分布和 GPU 访存可能抵消部分收益。工程上应比较 GAUC/NE、吞吐、GPU-ms、跨卡 all-to-all、P99 与单位调用电费。

相对主流方法的优势和不足

比加大 top-k 更节制专家侧 FLOPs，比单路由更能覆盖不同判断；风险是路由器分歧使专家不均衡、训练复杂且推荐 sparse features 的分布与大语言模型 token 不同。

可落地的场景

多场景共享底座精排、LLM Reranker、按商品属性和用户购买阶段激活专家的场景；先实验多目标专家负载而非盲目增加专家数量。

局限、未解问题与下一步研究

须解决路由不稳定、热点、模型增量训练专家漂移、混合视角是否真的减少最终奖励误差；未来结合 budget-aware router 和缓存友好的集群布局。

对商品评价 List 算法工程及职业能力的启发

为商品评价精排做 router-score 与各专家独立实际 loss/Reward 改善的校准图，识别单 router 错分配场景。保持激活专家数不变做对照，再通过小流量 A/B 和成本仪表盘决定是否上生产。
