Serving 优化进入“状态语义”时代：
RNG、Request Identity、TP Consensus 与 KV Ownership

过去 24 小时没有筛到达到本站阈值的新推荐 / 搜索论文批次或官方研究博客，因此今天不复读 Friday 的论文，而严格追踪 vLLM 与 SGLang 主干在 8 月 29–30 日合入的关键工程变更。最强信号不是“又快了几个百分点”，而是：当推理系统引入 speculative decoding、P/D disaggregation、KV offload、MoE 与低精度 kernel 后，随机数流、请求生命周期、并行 rank 决策、KV 分片归属和 kernel 路由条件都必须成为显式 contract；否则性能优化可能悄悄改变概率分布、让 rank 状态漂移，甚至让旧请求的异步回调污染新请求。

今日核心结论：① vLLM 修复 probabilistic speculative decoding 中 draft 与 target 复用同一 Gumbel noise stream 导致的分布偏差，说明“acceptance rate 看起来正常”不等于采样语义正确；② SGLang 为 Dspark / Dflash 在 TP>1 时增加 sampling decision broadcast，防止 token、accept length 与 KV state 跨 rank 漂移后死锁；③ HiCache 把 decode offload 生命周期从可复用的 rid 改为具体 Req 实例，揭示异步系统中 external ID 不应承担 generation identity；④ vLLM NIXL 将 P/D disaggregation 扩展到 MLA + DCP，KV transfer 开始真正理解“谁拥有哪一块 KV”；⑤ MoE 性能优化越来越像控制面优化：复用 Top-K routing metadata、按 M/K/N 选择 FP8 kernel、按 expected rows 调整 requant launch geometry，消除的是重复元数据工作和错误的静态路由，而不只是写一个更快 GEMM。

重点精读 01 · Speculative Decoding / Sampling Semantics

vLLM：Draft 与 Target 不能共享同一条 Gumbel 随机数流

Research Impact Score / 研究价值 9.6/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是，已合入 vLLM main是否有线上 A/B 否；有多模型 GB200 benchmark阅读优先级 最高

背景 / 业务动机

Speculative decoding 用便宜的 draft 先提议 token，再由 target 验证，从而减少昂贵 target forward。对 greedy decoding，很多实现只需要保证接受逻辑正确；但在 temperature>0 的 probabilistic draft 下，系统不仅要“生成看起来合理的 token”，还必须保证最终样本严格服从 target distribution。对在线搜索 Agent、LLM reranker 的 reasoning、生成式推荐等场景，一旦采样层有微小偏差，离线 benchmark 可能难以察觉，却会改变长期探索分布。

现有问题：为什么共享 Gumbel 会产生 bias

vLLM 的 probabilistic draft 使用 Gumbel sampling。问题在于 draft token 与 target 在 rejection 后做 residual resample 时，曾使用相同 seed / position 对应的 Philox offset，因此拿到 byte-identical 的 Gumbel noise。条件在“某 token 已经赢得 draft argmax”之后，其他 token 的 Gumbel 值并非独立无条件样本，而是被截断在 winner 以下；尤其 draft 中 q 较高但没赢的 token，更容易携带偏小 noise。随后 residual 再复用这组 noise，就会系统性低估这些候选，最终输出不再严格服从 target p。

这是一个很典型的系统 bug：acceptance rate 可能几乎不变，但 sample distribution 已经错了。普通宽词表单测每个 bin 样本太少，也很难看到这个偏差。

技术方案与关键模块

修复给 draft 的 Philox offset 增加独立 salt（1 << 30），显式拆开 draft 与 target 的 Gumbel stream。与此同时，PR 重构 sampling-stream position 的计算：每个调用点明确自己的 position convention，不再依赖隐式 +1；并修复 context 接近 max_model_len 时 position 由被 clamp 的 buffer 推导、可能导致连续两个 draft step 复用同一 noise vector 的潜在问题，新位置改为不截断跟踪。

训练方法 / 推理 Serving

这是纯 inference correctness 变更，不改变训练。Serving 只影响 draft_sample_method="probabilistic"；默认 greedy draft 没有调用 Gumbel sampling，因此 salt 对默认路径是 no-op。重要的是：修复不要求 draft 与 target RNG 对齐，反而要求它们在概率上独立；verification 仍通过 probability-ratio / rejection sampling 完成。

实验设置、指标与效率

作者新增窄词表、高样本量的分布检验：16 bins、200K trials，专门提升检测几个百分点 distributional bias 的统计功效，并覆盖 1 / 3 speculative steps。生产级 benchmark 使用 4×GB200、2K input + 2K output、512 prompts、concurrency 64，覆盖 DeepSeek V4 Flash + MTP/DSpark、MiMo v2.5 Pro + DFlash、Inkling NVFP4 + MTP、Gemma 4 E2B + MTP。吞吐变化在 -0.96%～+2.00%，acceptance length 在 ±0.61% 内，被判断为运行方差，没有系统性能回退。

优劣势、适用场景与局限

优点是修复非常局部，却恢复了概率语义；同时新增统计检验能防止未来回归。相对“只看 token-level exact match / acceptance rate”的测试，它更接近算法正确性。局限是当前 benchmark 仍是框架侧而非业务 A/B；对不同自定义 speculator、不同 RNG backend 是否存在类似 coupling，仍需要系统 audit。

对推荐 / 搜索工程的启发

当生成式推荐或搜索 Agent 使用 stochastic decoding 做探索、candidate generation、diverse beam / sampling 时，要把 RNG stream independence 当成 protocol invariant。建议测试体系不仅看 Recall/NDCG 或 throughput，还要加入 distributional parity test：固定 p/q，做大样本 chi-square / KL / TV 检验。未来模型越依赖 RL 与在线探索，这类“概率语义正确性”越重要。

重点精读 02 · Distributed Speculative Decoding

SGLang：TP>1 时，Speculative Sampling 决策必须形成 Consensus

Research Impact Score / 研究价值 9.5/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是，已合入 SGLang main是否有线上 A/B 否；有 TP2 稳定性与吞吐测试阅读优先级 最高

背景 / 核心矛盾

Tensor Parallel 的直觉是每个 rank 共同计算同一请求，因此 token state 应该一致。但为了降低同步开销，SGLang 某些 sampling 路径默认不跨 rank 同步 sampled token。对 Dspark / Dflash speculative decoding，这个优化会撞上一个更强的约束：draft Markov chain 的下一步依赖上一步 token，target verify 又决定 accept length、bonus token、KV commit。只要任意 rank 在任意一步做出不同离散决策，后面的 sequence length 与 KV cache 就开始不可逆分叉。

故障模式

PR 把需要一致的状态分成三层：① draft Markov proposal token；② target verify 产生的 correct_len / bonus / cap_trim_lens；③ prefill 后进入 draft path 的 next_token_ids。过去这些值可能各 rank 独立采样。状态一旦漂移，后续 collective 的 shape / step 次序不再一致，最终表现不是轻微精度下降，而是 deadlock。

技术方案

新建 SpecTpSync，用 TP group 的 PyNCCL communicator 广播 rank 0 的 sampling decisions。Markov proposal 在 eager 与 graph-folded sampling 中都逐步 broadcast——不能只在整个 draft block 结束后同步，因为后一步依赖前一步；verify path 在 finalization、token output、KV commit 之前同步 accept 相关字段；prefill 的 next token 也在进入 draft 前同步。作者明确没有选择“让所有 rank 使用相同 RNG seed”，因为不同 rank 即使 seed 相同，也可能因执行路径消费不同数量随机数而继续漂移，而且 non-RNG 差异同样无法覆盖。

Serving 代价

TP>1 时每个 decode step 增加约 gamma + 3 次 [batch-size] tensor broadcast，并需要在 CUDA graph capture 内维持 collective ordering。TP=1 是 no-op。这个设计体现了一个重要取舍：少量显式 consensus 通信，换取 distributed state machine 的确定性。

实验与稳定性

测试使用 2 台 DGX Spark、TP=2、DeepSeek-V4-Flash-0731、131K context、decode CUDA graphs 与 folded sampling。GSM8K 200 题 temp=0 得到 accuracy 0.965、invalid 0。作者还故障注入：人为让 rank1 的 accept length 每次少 1；修复前服务器在 startup warmup 就死锁，修复后 rank0 broadcast 会覆盖差异并正常启动。稳定性测试发送 42 个连续请求、每个 512 output tokens，共生成 21,504 tokens，全部 HTTP 200；temp=1 时 mean acceptance length 2.86（block size 4）。单并发性能记录为约 31.9 tok/s。

局限与未来方向

额外 broadcast 会增加 latency，尤其 gamma 较大、batch 较小时更敏感；PR 没有提供与“数学上稳定的 pre-fix TP baseline”的直接 A/B，因为原路径在该压力配置下无法可靠存活。下一步值得做的是将 consensus site 纳入自动 profiling：只有真正影响离散状态 / KV ownership 的字段同步，连续 tensor 尽可能保留 rank-local。

对推荐 / 搜索工程的启发

多卡推理不只是 tensor 数值并行，更是一个 replicated state machine。生成式召回、Agent search、在线 reranker 一旦引入 sampling / pruning / dynamic routing，要明确哪些离散决策是 consensus-critical。工程技能上，建议重点补 CUDA graph 内 collective、Philox RNG、TP/DP group semantics、KV commit lifecycle，这些正在成为高性能生成式推荐 Serving 的基础。

重点精读 03 · KV Cache / Async Runtime

SGLang HiCache：External Request ID ≠ Request Lifecycle Identity

Research Impact Score / 研究价值 9.3/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是，已合入 SGLang main是否有线上 A/B 否；有确定性 regression test阅读优先级 最高

背景 / 业务动机

HiCache 的 decode KV offload 会异步把 GPU KV 通过 D2H 搬到 host / storage。为了提高吞吐，请求完成后 scheduler 可以很快复用外部 request id（rid）；但 D2H copy 和 callback 不一定在 response 结束时同步完成。于是“逻辑请求已经结束”和“底层异步生命周期已经结束”并不是同一时刻。

现有问题

DecodeKVCacheOffloadManager 原先用 caller-provided rid 作为 offloaded_state 与 in-flight counter 的 key。旧请求完成后 state 可能被移除，但异步 copy 仍在飞；如果新请求复用相同 rid，它会读到 / 建立同一 key 下的状态，而旧请求稍后到达的 callback 仍会修改这个 key。结果是两个不同 generation 的请求共享 offload lifecycle，典型 ABA problem。

技术方案

修复把内部生命周期 key 从 rid 改成具体 Req instance：offloaded_state: dict[Req, OffloadedState] 与 offload_inflight: dict[Req, int]。rid 只保留给 external identity 与 logging。这样旧 callback 持有的是旧 Req object，即使 rid 相同，也无法再触碰新请求状态。PR 还加入两个不同 Req 复用同一 rid、且第一个请求 D2H 尚未完成的确定性回归测试。

训练 / 推理 / Serving

不涉及训练，也不改 model forward 或 kernel。它改变的是 KV offload control plane：状态归属、异步 ack、release host/GPU resources 的时序语义。对性能几乎没有可测额外成本，却显著强化 isolation。

实验与证据

作者给出不依赖 GPU timing 的 deterministic reproduction：只把 regression test 放回精确 base commit 即可失败；修复后 focused suite 14 tests 全部通过。由于不改模型输出和普通 decode compute，PR 没有 accuracy / speed benchmark。

优劣势、局限与未解决问题

优点是直接修正 identity model，而不是加 sleep、等待 D2H 完成或禁止 rid reuse。局限在于 object identity 仍依赖 Req 生命周期被 runtime 正确持有；更通用的系统可显式使用 monotonic generation id / request epoch，让跨进程、持久化日志与 distributed callback 也能验证 generation。类似问题还可能存在于 prefix cache、remote KV transfer、async tool call、streaming response cancel 等路径。

对推荐 / 搜索系统的启发

高 QPS 推荐 / 搜索服务也大量复用 request id、slot、batch index、embedding buffer。只要有异步 callback / DMA / RPC，就要区分 external ID、slot ID、lifecycle generation。特别是在动态 batching、P/D 分离、远端 embedding fetch 中，建议把 generation-aware ownership 写成接口 contract，并为 rid/slot reuse 做专门 race test。

重点精读 04 · P/D Disaggregation / MLA

vLLM NIXL：P/D 分离开始理解 DCP 下真实的 KV Ownership

Research Impact Score / 研究价值 9.2/10工业成熟度 ★★★★☆创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是，已合入 vLLM main是否有线上 A/B 否；有多并行组合 GSM8K sweep阅读优先级 最高

背景 / 业务动机

Prefill / Decode disaggregation 通过让不同 GPU 池分别负责长 prompt prefill 与 token-by-token decode，提高集群资源利用率。NIXL connector 需要在 P→D 之间搬 KV。原有 MLA 路径假设 KV 在 TP ranks 间完全复制，因此 decoder 只要从一个 canonical remote rank 读一次即可；但 Decode Context Parallel（DCP）会按 block 把 KV 分片到多个 rank，这个假设失效。

核心问题：KV transfer 不是 memcpy，而是 ownership mapping

例如 producer DCP=4 时 P0/P1/P2/P3 各持有四分之一 KV；decoder DCP=2 时 D0 需要读 P0+P2，D1 需要读 P1+P3。远端 rank 不再是冗余 replica，而是拥有 disjoint blocks。若 connector 仍按“选一个 TP rank”传输，就会缺失 KV。

技术方案与约束

PR 将 remote DCP size 加入 handshake / transfer plan，并扩展 rank mapping。为控制复杂度，它做了重要工程假设：每一侧 dcp_size 要么 1（完全复制），要么等于 tp_size（完全分片），不支持 1<DCP<TP 的 partial case；两侧 DCP degree 假设互相整除，因此可用 modulo mapping，避免通用 gcd/lcm overlap solver；连接 KV connector 时还把 cp_kv_cache_interleave_size 对齐到 block size，让 DCP ownership 与 transfer block 粒度一致。

Serving 方案

调度器与 worker 共同构建 transfer plan：根据 producer / decoder 的 TP、DCP degree，决定每个 local rank 需要从哪些 remote ranks 拉取哪些 block。对 pure MLA、hybrid SWA+FA 等路径新增测试，尤其处理不同 KV cache group prefix-hit 数量不一致时的 alignment。

实验设置与结果

在 DeepSeek-V2-Lite-Chat、block size 64 上 sweep 多种 P→D 组合，包括 TP4/DCP1→TP4/DCP1、TP4/DCP4→TP4/DCP4、复制→分片、分片→复制、TP2/DCP2→TP4/DCP4 等，全部 PASS；GSM8K strict-match 数值约 0.649–0.665。PR 的重点是功能 / correctness，而不是公开端到端 latency benchmark。

优劣势与局限

优势是没有在 connector 旁边另建特殊 MLA 旁路，而是把 DCP ownership 注入现有 NIXL abstraction。局限也很明确：partial DCP、degree 不整除、更多 heterogeneous topology 仍未覆盖；当前设计用限制 deployment space 换可理解、可测试的 routing logic。

对推荐 / 搜索落地的启发

生成式推荐 / 大型 ranker 进入 P/D 或 encode/decode 分离后，state transfer 也会成为一等算法系统问题。要掌握的不只是 NCCL/NIXL API，而是 state ownership algebra：哪个 shard 由谁产生、谁消费、跨 stage 如何重映射、cache hit 如何影响 block alignment。它与推荐中的 embedding shard / parameter server ownership 是同一种系统思维。

工程精读 05 · MoE Routing

vLLM：Top-K 已经算过的 Routing Metadata，不要每层每步再算一次

Research Impact Score / 研究价值 8.9/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★☆是否官方开源 是，已合入 vLLM main是否有线上 A/B 否；有 RTX 5090 microbenchmark阅读优先级 高

问题与方案

Triton kernels v3.6+ 的 topk() 已返回 SparseMatrix，构造过程中已经生成 bitmatrix、sorted dispatch/combine indices 与 per-expert histogram。GPT-OSS MoE forward 的 no-expert-map 路径却丢掉这些 metadata，再把 Top-K ids pack 成另一个 bitmatrix、重新构造 SparseMatrix，等于每个 MoE layer、每个 forward step 重复做完全相同的 routing bookkeeping。

新实现直接从 topk 产物构造 RoutingData / GatherIndx / ScatterIndx，只有 expert-map 真正改变 expert ids 时才保留 repack。作者加了 1/33/512 tokens × 32/128 experts、TopK=4 的 tensor-leaf parity test，确保新旧 routing 结构完全一致。

效率收益

RTX 5090、Triton 3.6 的 eager microbenchmark 中，routing construction 从约 458–564µs 降到 260–321µs，跨 1～4096 tokens 都节省约 43%；CUDA kernels 从 20 → 9，约少 200µs 和 11 launches / MoE layer / step。GPT-OSS-20B 有 24 个 MoE layers，因此固定开销可累积。作者也明确提醒：decode CUDA graph 会摊薄 launch overhead，但重复 bitmatrix pack/sort/histogram 本身仍会执行，所以收益不会完全消失。

工程启发

高性能推理优化不能只盯 GEMM。随着 MoE、Top-K router、expert parallel 复杂化，metadata is compute。推荐系统同样存在 candidate mask、segment offsets、ragged index、group histogram 的重复构造；应做 dataflow-level common subexpression elimination，把上游算出的结构化 metadata 作为一等产物复用。

工程精读 06 · Quantized Kernel Routing

SGLang：Kernel Selector 也需要“候选集 + Context-aware Ranking”

背景与问题

SM90 row/column-scaled FP8 路径此前主要按 K/N 判断是走 Torch/NVJet 还是 AOT kernel。这个 heuristic 对 large prefill 可能正确，却把 decode 的 M 维忽略了，导致 Llama-3.1-8B W8A8 batch=1 throughput 从约 215 tok/s 回退到 190 tok/s。具体 down projection shape 为 M=1,K=14336,N=4096；H200 上 AOT 26.50µs、Torch 51.12µs，AOT 快 1.93×；H100 也快 1.66×。

方案：从二维阈值变成实测 Context Envelope

新 selector 只有在 M>=8192 且满足两组 K/N 大投影条件时才选择 Torch/NVJet，其余 decode、小 prefill、narrow TP8 projection 保留 AOT。它不是追求一个统一“最快 kernel”，而是学习一个由 M/K/N 与 projection family 决定的 dispatch policy。

实验与结果

作者在 H100/H200 上扫 11 projection families × 12 M values，共 132 cases，并做随机边界复验。H200 被新 predicate 选中的 32 个 broad-grid case 全部 Torch 更快，中位 gain 2.50%（0.17–5.97%）；H100 同样 32/32 全胜，中位 gain 19.48%（1.36–56.53%）。最关键的是，被明确排除的 decode regression shape 回到 AOT。

对推荐 / 搜索的启发

这和 reranking 很像：kernel selector 本身也是一个“按请求上下文选择候选”的 ranking problem。模型服务里 batch size、sequence length、TP degree、hidden shape、hardware、quant mode 都应进入 routing feature。未来更成熟的方案会从手写 threshold 走向 profile-driven lookup / autotuner，但前提是必须有 guardrail，不能把 benchmark noise 学成规则。

工程精读 07 · DeepEP / Low-latency MoE

SGLang W4AFP8：低延迟 Kernel 的瓶颈常常不是算术，而是 Launch Geometry

Research Impact Score / 研究价值 8.8/10工业成熟度 ★★★★☆创新性 ★★★★☆与你方向的相关度 ★★★★☆是否官方开源 是，已合入 SGLang main是否有线上 A/B 否；有 H100/H200/B200 kernel benchmark阅读优先级 高

背景 / 现有问题

DeepEP low-latency path 需要把 per-token-group FP8 payload requant 成后续 CUTLASS W4A8 grouped GEMM 使用的 per-tensor FP8。算术本身极轻：每 element 约两次字节搬运、两次乘法。但旧实现被三个非算术因素主导：8 warps + 1024 elements 让每线程只有 4B access，Triton 不再 vectorize；scale 沿 element axis 反复 scatter-gather；m-grid 固定每 expert 32 programs，低延迟 decode 每 expert 只有极少 rows 时，大量 program 只检查 mask 就退出。

技术方案

新实现按 128-wide scale group 做二维 tile，让每组 scale 只 load 一次；改 4 warps 恢复 8B/thread vectorized access；expert 多时扩大 element tile；最重要的是 requant_launch_geometry() 根据 dispatcher 已知的 expected_rows 决定 m-grid，一般每 expected row 一个 program，最少 4、最多 32，并结合 expert count cap。这个 expected value 只是 launch hint，真实 rows 超过估计时 kernel 仍会循环处理，因此 correctness 不依赖预测准确。

实验、正确性与效率

H100/H200/B200 上对高 expert-count shape 做 bitwise equality，覆盖 0/1/3/7/64/all padded rows、两种 scale layout 和 skewed row count，全部一致；48 个单测跨两套 Torch/Triton toolchain 通过。性能在高 expert、低 rows 时尤其显著：H100 的 hidden=3584、512 experts、1 row 从 40.3µs → 3.3µs，约 12.1×；hidden=7168、256 experts、1 row 约 10.6×。较高 rows 下收益缩小但仍常为 1.2–2×。作者明确标注尚未做 multi-node end-to-end decode benchmark。

局限与下一步

heuristic 来自 H100/H200/B200 sweep，H20 未测，而且高 expert-count 下最佳 tile/warp 对架构仍有差异；常数 heuristic 已接近局部最优，但剩余几个百分点需要 autotuning。也就是说这项工作本身展示了下一步：把 expected workload distribution 直接变成 runtime/kernel configuration policy。

对推荐系统工程的启发

推荐模型的 sparse expert、jagged feature、variable-length sequence 同样经常是“低算术强度 + launch/metadata/memory bound”。优化时应先做 roofline 与 kernel timeline，问清楚瓶颈是 FLOPs、memory coalescing、scale/index load、program occupancy 还是空 program，而不是默认继续 fusion。

今日趋势判断

从“Kernel Fast Path”到“State Contract + Runtime Policy”

把今天 7 个变更放在一起，趋势非常统一：高性能 Serving 已不再是“写一个更快 CUDA kernel”这么简单。第一层是 semantic correctness：随机数流必须独立、TP ranks 必须对离散决策达成一致；第二层是 lifecycle correctness：异步 KV offload 要用真正的 request generation 作为 ownership；第三层是 distributed ownership：P/D connector 必须理解 DCP 下 KV block 属于谁；第四层才是 performance policy：复用 routing metadata、根据 M/K/N 选择 kernel、根据 expected rows 选择 launch geometry。

对推荐 / 搜索算法工程师最值得补的能力，不是再多背一个 CTR 模型，而是把模型、runtime 与系统正确性连起来：概率采样与统计检验、CUDA Graph / NCCL collective、KV cache 生命周期、P/D disaggregation、MoE routing、低精度 kernel 与 profile-driven dispatch。生成式推荐和 LLM reranker 真正大规模上线时，这些能力直接决定“模型增益能不能安全地变成线上增益”。
