业务动机与现有问题

推荐系统长期以不可解释的 dense user embedding 做召回/精排/用户分群。工程难点不是仅有一个漂亮的用户向量，而是当某个评价 List 的满意度下降时，无法解释是品类喜好、信息充分性还是负面观点关注造成的。直接用 LLM 给全部用户历史贴标签则昂贵，且需要原始行为。论文问：已有 user embedding 能否无监督地恢复可命名的行为模式？ PCA 的轴正交而真实行为模式相关；K-Means 强迫用户属于硬簇；LDA/NMF 假设可访问交互计数，忽略 Transformer 的非线性语义；端到端可解释推荐常需改动上游训练。作者用稀疏混合生成假设解释为何同一向量承载多种行为，再处理字典学习中的 feature splitting、冗余轴和 LLM 命名误差。

技术方案 / 关键模块

先固定现有 SASRec/BERT4Rec 或 SVD 等编码器得到用户向量 u；训练过完备字典的 ReLU SAE：z=ReLU(W_enc·u+b)，u_hat=W_dec·z。decoder 列是模式方向，z 的非负激活是用户在该模式上的强度。按高激活用户的代表行为让 LLM 命名模式；自然语言 query 与模式说明做相关度判别，再以相关模式激活加权检索人群。工作是 post-hoc 层而非替换主推荐网络；对密集表征可做缓存物化，不需要每次线上跑生成式 LLM。

训练方法 / Loss 与监督来源

训练目标 L_SAE=||u−u_hat||²₂+λ||z||₁，decoder 列归一化；字典宽度、激活稀疏度与不同编码器对照。文中 MovieLens transformer 用户向量 d=256，字典宽 1,024（4× overcomplete），平均 L0≈80；还对合成数据按可知 ground truth 的 mode alignment、decoder cosine 和 feature merging 做校验。若在评价内容场景迁移，应增加 mode stability（跨周）、匿名化、反事实评分和年龄/隐私敏感审计。

推理 / Serving / 工业系统设计

部署宜采用批处理 user embeddings→稀疏 mode topK→量化稀疏索引/人群倒排，query-time 只需将自然语言偏好转换为 mode 权重后向量/倒排打分；需要对 SAE 版本、上游 embedding 版本和 LLM 命名版本做一一绑定。业务列表重排可将模式强度作为 Reward 的分桶校准特征，而非让 SAE 直接决定最终排序。

实验设置与离线数据、线上 A/B 分界

合成数据验证已知模式；真实数据为 Open e-commerce（约 5027 用户、180 万购买）与 MovieLens-1M（6040 用户、约 100 万评分）。与 K-Means encoding、FastICA、PCA、Text Embedding 比较：品类检索 SAE AUROC 0.705，高于 K-Means 的 0.680；MovieLens SASRec SAE Coverage 0.977 vs K-Means 0.811。论文也承认 MovieLens 以 AUROC 看 SAE 与 K-Means 并非总显著胜出，文本嵌入基线覆盖率为 1.0。没有推荐 CTR、GMV 或线上 A/B。

相对主流方法：优势、代价与适用场景

优点：不需重训既有主塔、可解释人群的 query、可复用高价值现有 embedding；相较 K-Means 能表达多兴趣叠加。弱点：模式标签基于 LLM 自动解释，不代表因果行为或用户明确意图；稀疏度与字典宽度有调参成本，embedding 频繁更新会导致字典漂移；文本基线部分指标接近或更好，且未证明最终推荐提升。

局限、待解决问题、研究路线与工程启发

实验优先级：① 同一用户向量冻结 baseline 做 SAE 用户模式审计；② 评价列表满意度/成交 Reward 在不同模式与历史负面观点关注分桶上做 calibration/EGCE；③ 模式覆盖缺失的曝光 List 随机探索；④ 再做 Generator 加入 z 的消融和线上满意度守护。研究方向是模式与评论观点共现、模式可迁移性、可撤销隐私与真实行为因果解释。工程能力：SAE、可解释表征、post-hoc 校准和人群检索。

业务动机与现有问题

当前 LLM/生成式推荐常把 token 级 teacher supervision 看作比 sparse outcome reward 更高效，因此推崇 On-policy Distillation（OPD）。但数据效率、wall-clock、GPU-hour 并不等同总 FLOPs，特别是教师前向、长输出和专家预训练被漏算。多目标评价 List 中，成交与满意度监督常属于不同子域，究竟“单一 RL 训练”还是“分专家 RL 再蒸馏”更划算必须同预算比较。 常规 teacher-forced SFT 有曝光策略/状态分布偏移，OPD 虽让 student 自己 roll out，但外部强教师与 student token support/表征差异大可能导致回答变长、分布塌缩。单域的 self-GRPO checkpoint 已是目标模型，蒸馏它不能宣称节省整体计算；多域专家能力碎片化才需要一台融合 student。

技术方案 / 关键模块

在相同 student 初始化、prompt、rollout group 等约束下构建 GRPO、外部强教师 OPD、同源 GRPO checkpoint OPD、多教师按任务路由 OPD。GRPO 给同 prompt 的一组输出分配 r_i−mean(r_j) 优势；OPD 在 student 自采样轨迹的 top-16 token 支持集上计算 student→teacher reverse KL。多教师路径由当前 domain/query 选专家，蒸馏到同一 student；无需把教师当线上多路模型长期 Serving。

训练方法 / Loss 与监督来源

GRPO 目标约为 −E[Σ_i A_i Σ_t log πθ(o_it|context)]；OPD 目标为 E[KL(πθ^top16 || π_T^top16)]。按生成 token 计算 FLOPs：GRPO 约 10N_student/token（生成、recompute、反传），OPD 额外计冻结教师前向 2N_teacher/token；训练阶段分开记账，不偷换为单阶段收益。工程迁移：可先训练成交专家 π_GMV、满意度专家 π_SAT，冻结专家后按标签密集程度进行条件 OPD，最后以同一容量 student 验证 reward trade-off。

推理 / Serving / 工业系统设计

融合后线上保留单 Generator：和单域 RL 同一请求级 decoding 接口，不增加独立教师链路；若多专家训练数据与 reward 冲突，必须有 rule/condition routing 标签及安全区分。推理端测固定 max_length、List 合法率、EOS、KL 漂移、P95/P99 与 token 成本，不能把训练 FLOPs 节省误作线上加速。

实验设置与离线数据、线上 A/B 分界

作者比较数学、代码、MMLU-Pro 和 IFBench 等基准及不同 student/teacher family。两域专家训练约 10.7 EFLOP、融合约 0.55 EFLOP（5.2%）；四域专家约 14.4 EFLOP、融合约 1.15 EFLOP（8%）。以目标准确率计两域总 FLOPs 相较 joint GRPO 少 42%，四域少 31.6%。这些是模型训练评估，不是电商线上 Reward uplift。

相对主流方法：优势、代价与适用场景

相比简单宣称 OPD 训练快，这项研究明确外部教师 OPD 的失败区域，并给“domain specialists → same-origin consolidated student”可测试技术路线；缺点是二进制结果 reward 和数学/代码 benchmark 很容易比多噪声长周期 GMV+满意度更可验证，教师同源条件对真实推荐模型未必成立，多教师容量与冲突目标仍可能出现负迁移。

局限、待解决问题、研究路线与工程启发

建议先做三臂对照：A 单 Generator + 多目标 List RL；B 两个同源 RL experts + 按上下文 OPD 融合；C 外部高分 teacher OPD；相同总训练 FLOPs、候选列表/序列长度、线上请求成本、离线双目标 Pareto。最先检查 Reward 模型校准、train/serve candidate 过滤和 student 长度膨胀。未来方向：无偏 preference 标签、梯度冲突自适应教师路由与少量 online exploration。技能聚焦 RL、蒸馏计算审计、偏好/策略评估。

业务动机与现有问题

推理成本常被低比特权重和 KV cache 逼到质量边界：2-bit/3-bit 虽可显著省显存，却可能损害长上下文推断；把高精度权重/KV 完整 offload 到主机或 SSD，又可能被 PCIe/I/O 等待拖垮。对于商品评价 Generator，用户信号稀疏、评论内容很长、线上又对延迟敏感，这类质量—成本矛盾很直接。 传统 uniform quantization 默认所有 token/层同一精度；静态 offload 传很多没有必要的精度；decode 可能每步重复读同一残差，导致带宽昂贵。论文的核心不是简单再换一个整数位宽，而是让完整精度分布在 GPU、RAM、SSD 中按需求补足，且通过复用和 overlap 避免每步停机。

技术方案 / 关键模块

先保留 GPU 常驻的低比特基座（权重 2–4 bit、KV 2–3 bit），额外精度以分层残差/精炼表示在 host RAM / SSD；Serving 时依据当前步骤需求筛选要补回的精度块，选择性 streaming，prefetch/异步传输与 matmul 重叠，并复用之前加载的高精度部分。架构的关键张力是“精度修复带来的质量增益”与“补偿流量导致的 P99 抖动”。

训练方法 / Loss 与监督来源

本文重点是量化精度回补与 memory hierarchy 系统，不应混淆成新的 RL 或 SFT Loss；量化与残差表示需依据模型/层的 sensitivity 构建，验证 PPL 与推理任务准确率。严格细节以全文为准；本站没有在未核验的情况下杜撰专有 loss 公式。建议业务上用曝光 List 的离线一致性样本评估不同量化层，特别对负面评价与否定词召回进行误差分桶。

推理 / Serving / 工业系统设计

业务动机与现有问题

跨企业、跨地域或设备内的知识/评论数据不总能集中入一套索引：隐私、版权和实时所有权会阻止总收集。传统 P2P DHT 依赖全局结构维护；全量 broadcast 昂贵。ZeroRAG 尝试让查询自己沿语义邻近的节点走，并让网络通过历史查询逐步变得更利于检索。 跨节点搜索要同时优化相关召回与网络消息数，并在 peer 加入/离开、文档主题漂移和网络大面积损毁后恢复；仅靠每节点静态邻居会形成覆盖盲区。安全方面，语义广告可能暴露敏感内容并受到恶意 peer 诱导。

技术方案 / 关键模块

每个 peer 维护本地文档库 D、容量有限的邻居 FIFO N、邻居摘要广告 A 和最近 query 缓存 M；接收查询后先进行本地向量匹配，同时返回候选文档与更合适 peers 的 references。发起方维护 best-first frontier 按相似度扩展，聚合 topK 结果，并把提供最佳结果的 peer 纳入邻居表、必要时淘汰旧邻居，让拓扑按工作负载自组织。

训练方法 / Loss 与监督来源

主要是在线路由和缓存结构优化，没有提出需要训练一个新的大模型损失；语义 embedding 来自检索器，peer advertisement 的更新相当于轻量在线反馈。可扩展方向是学习 privacy-constrained peer score、跨地域成本/时效 penalty，但不能把论文声称为已验证 RL-based routing。

推理 / Serving / 工业系统设计

每次请求涉及多跳 neighbor RPC，在线核心指标是 recall/message、跳数、尾延迟、跨域 ACL、故障恢复及拓扑热度。对业务评价评论应优先确定归属/权限、商品池可用性与反诈，而不是把去中心化当作默认高性能替代 HNSW；单企业内部的一体索引仍可能更好。

实验设置与离线数据、线上 A/B 分界

作者用 AOL-IA、Amazon Electronics、PubMedQA 及 Semantica、DHT-LSH 等 baseline 比较，在部分 RAG 设定接近中心化 HNSW 的检索召回和问答正确率。对 100k peers 的表格 Recall@1 99.913% 是“目标文档至少一个 peer 有广告”条件下的结果；这不是全网任意文档的无条件 Recall。失去半数 peer 后恢复 recall 约 95.5%，说明路由有自修复能力。

相对主流方法：优势、代价与适用场景

优点：无需中心存储和协调节点、轻状态、适应更新；缺点：多跳尾延迟、广告/查询隐私泄露、恶意节点与 network partitions 影响、条件召回指标偏乐观，且与单机 ANN 性能不能直接比较。

局限、待解决问题、研究路线与工程启发

研究路线：中心 ANN→多路源选择→ZeroRAG peer routing→证据权限校验与 List-level utility。先在多数据中心/商家本地评价库模拟权限隔离，随机断 50% peers、时效变更、热度偏移，记录 Recall、P99、每请求网络字节和负面观点丢失率。工程技能：分布式索引、动态拓扑、隐私边界和 RAG evidence routing。

业务动机与现有问题

多轮会话中，每次重新派发独立检索 Agent 会丢历史证据；主 Agent 自行保留全部工具输出又占满上下文。推荐评价问答常问‘上一页差评为什么和官方描述不一致’这类依赖前文的 follow-up，最重要的是正确复用、引用和纠错。 非持久子 Agent 返回摘要会损失证据细节，主 Agent 无法自行核对；主 Agent 直接执行检索 Skill 虽简单，却持续复制工具结果，token 高。关键是缓存该缓存的检索状态，但不要让主 Agent 被过时总结绑定。

技术方案 / 关键模块

对照：① skill-based，主 agent 自调用 schema/Cypher 工具，维护检索内容；② non-persistent child 每次开新会话，返回 findings；③ persistent child 跨轮保留检索历史，向主 agent 返回直接证据并接受 revision/correction 任务。相当于将‘事实收集状态’和‘面向用户的最终文本’分离，允许 evidence provenance 回流。

训练方法 / Loss 与监督来源

这里主要是 Agent 编排/上下文管理设计，不是训练新的推荐 ranker。运行评估使用 GPT-5.4 执行 agent calls，GPT-5.4-mini judge 根据 ground truth 质量/一致性判对错；成本由记录的 cached+uncached+output token 与估计 API 单价计算。不要写成新的 RL Loss；若迁移可另加 retrieval policy 的成本正则与引用一致性惩罚。

推理 / Serving / 工业系统设计

实际 Serving 由父/子 Agent 历史状态、工具授权、缓存命中、schema version 和 session TTL 决定；应主动支持 stale evidence 标记、用户撤回信息、查询意图变化和跨会话隔离。长会话需要让子 Agent 只返回被实际使用的证据片段而不是全部历史。

实验设置与离线数据、线上 A/B 分界

ServiceNow harness：ITSM 57 问、HRSD 48 问和复杂依赖 ITSM 69 问，组合 5 种 multi-turn 设置并比较准确率、总 token、时间/估算费用。相对主 Agent skill 模式总体 tokens -43.3%/API 费用 -45%；但非持久方案更省 token/估算费用。个别设置准确率较低（ITSM Complex 89.85% vs skill 91.30%），说明成本与质量并非单调同步。

相对主流方法：优势、代价与适用场景

优势：直接返回来源证据、跨轮纠错，避免主 agent 持有过多重复工具输出；与无状态子 Agent 比延迟更低，但 token/估算费更高；数据为内部任务与 LLM judge，生产 A/B 和高并发多租户隔离均未验证。

局限、待解决问题、研究路线与工程启发

评价检索 Agent 的实验优先对比：A 主 Agent 搜索、B 无状态 child、C 持久 child；控制回答正确率/证据覆盖/负面观点保真，在不同对话长度测 cached token、成本、P95/P99、权限泄露与历史撤回。对接生成式重排时让这些证据作为 Reward 可解释特征而非无校验记忆。技能：Agent state、检索 provenance、跨轮缓存、成本审计。
