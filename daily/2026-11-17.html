AI × Recommendation / Search Research · 2026-11-17 · 北京时间 10:00

从长序列生成式推荐、List 不确定性，到低成本 JEV 与可追溯 Agent：把计算和证据用在值得的决策上

本期以北京时间 11/16 10:00—11/17 10:00 的新公告/新发现为筛选窗口；重点论文的 arXiv 作者 v1 提交日期均为 2026-11-13（UTC），部分进入 11/16 公告批次。明确区分首次投稿与公告日期，绝不将 11/13 论文冒充 11/17 首发。

今日核心结论：RecMem 把长期用户状态压缩成固定槽位，RACE 按排序不确定性分配算力，UltraBERT-JEV 将结构化判优压成单次前向，而 Verification Transport 说明证据被摘要抽象后可能让再强的 Judge 失真。它们共同指向可校准的 List Reward + 状态压缩 + 证据回溯 + 按价值激活计算。

最值得看

RecMem → RACE → UltraBERT-JEV：长行为用户状态压缩、List-level 不确定性预算分配、低成本裁判，直接对应生成式推荐的精度/成本边界。

关键风险

Verification Transport 指出证据压缩后的 verdict 不一定可信；和 CarryOn 的 state/evidence 分离联合阅读，补齐 Reward 数据来源的可信度链条。

工程趋势

StreamEmbed 的增量多模态索引、ModHarness 的可学习流程、RAG-FGO 的 Rewrite Controller，都指向「跨阶段条件化激活与可追溯测量」，不再盲目放大模型。

核心工程结论

优先级 1：Reward 的证据可信性。在商品评价曝光列表中，同一个 List 的真实点击、成交与满意度标签只能代表特定曝光/位置/候选条件下的反馈；优先做四层证据视图的 Judge 一致性、propensity 与负面证据 recall 审计，再改 Generator。

优先级 2：按难度分层 Serving。先用 UltraBERT-JEV 或轻 Judge 做有校准的快速比较，将 uncertain List 导向更强 Teacher 或更长历史；用 RACE 的排名不确定性思想优化升级成本。

优先级 3：长期用户状态压缩。RecMem 作为增量 memory 替代频繁扫描，需对比 full-history / recent-only / retrieval memory 的 List-level 人审与真实业务指标；不要将 216/1200 token 当成真实线上 5.6 倍 QPS。

统一实验护栏：固定候选池与召回预算、时间外切分、冷门/负面属性覆盖、多目标 Reward Calibration（ECE/Pairwise Agreement）、GMV/满意度真实 A/B、GPU P99 与每千次决策成本独立上报。8 项研究均未核验到电商随机线上 A/B。

1/8 · Generative Rec · Long-history Memory · Serving · arXiv v1 2026-11-13（11/16 新公告/关注）

RecMem: Recurrent Memory Compression for Long-Sequence Generative Recommendation

一句话判断：长历史推荐的目标不是无限放大上下文，而是让用户状态在空间固定、可持续更新的同时保留远期偏好；RecMem 是这一方向的具体实现。

阅读优先级S+

原始结果摘要：16 个 memory slots + 200 recent tokens；216 decoder tokens 对比 1200；Recall@10 42.36 vs 48.18；Recall@200 72.20 vs 74.44

1. 背景与业务动机

用户长期行为可能包含反复出现的购买意图、尺码、风格和价格敏感性；生成式推荐如果把数千条历史原样放进解码器，attention/KV 成本、长上下文噪声和实时更新压力会随行为数累积。评价推荐还需要同时保留长期偏好和本次商品的即时决策条件。

2. 已有方法与核心矛盾

Recent-only 截断快但丢失远期信号；传统检索式 memory 只按局部相似性取几条，未必保留跨周期关系；把全历史送入 HSTU 质量高却消耗大。问题是能否用固定容量状态逼近长序列条件分布，而不是仅把历史总结成不可训练的文本。

3. 方法与核心模块

模型采用共享底层与分叉上层的 Encoder/Decoder：历史按段经 Encoder 写入固定数目的 slot，forget gate 对每个 slot 执行保留/覆盖；Decoder 只读近期后缀和压缩状态。训练时把片段连续写入与 packed 形式的状态近似对齐，使在线事件逐个到达时状态不必重算全部历史。

4. 训练目标与稳定性

核心是 next-item 推荐监督加 stream-consistency：从顺序流写入的用户状态应与批量整段处理的决策尽量一致。论文在收缩性及近似半群一致条件下讨论历史长度无关的状态误差界；这是带条件的数学结论，不能直接推出线上漂移绝对有界。

5. 推理与 Serving

使用 16 个记忆槽，处理历史后保留 200 个 recent tokens，解码上下文固定 216。生产设计可把长记忆放在 user-state store，事件驱动增量更新；须为状态 schema、TTL、用户删除、冷启动和索引版本提供幂等契约。216/1200 是解码上下文长度比，不应直接当成 5.6 倍真实 QPS 提升。

6. 实验、对照与离线数值

在 MerRec 比较 full-context HSTU-1200、PHSTU、recent-only、retrieval baselines。RecMem-Stream Recall@10=42.36、Recall@200=72.20、NDCG@10=26.74；HSTU-1200 对应 Recall@10=48.18、Recall@200=74.44。也即保留完整 HSTU 的 87.9% Recall@10 和 97.0% Recall@200；质量有退让而非同时全面超越。

7. 线上 A/B 与效率证据

没有核验到生产随机 A/B；论文的 context-length 压缩与离线 recall 不能直接转换成 GPU 成本或 GMV 增益。上线前需要端到端 QPS、P99、状态写入失败、热键倾斜、GPU KV 和用户兴趣变迁分群实验。

8. 与主流方法的优劣势

较 full HSTU：空间成本显著降低但 top10 精度受损；较 recent-only/PHSTU：远期历史保留更好；较外部向量召回：写入的隐式状态更紧凑，但解释性和按证据删除的能力较弱。不能认为一套小 memory 天然替代证据库。

9. 适用场景、局限与未解问题

适用于数千次行为、session 跨天、多设备同步且推理预算严格的主流推荐；对突变兴趣、异常行为、群体稀疏或重要单次负面体验可能记忆不足。状态选择性遗忘、跨任务迁移、隐私删除和状态校准仍需实验。

10. 未来研究与评价推荐实验

建议对评价业务构造 recent-only / full-history / RecMem 三组，保持候选评价集合与 List Generator 不变，分别测试个性化满意度、长尾属性差评保留率、回访用户偏好、OOD 时变；结合用户反馈标签给记忆 gate 训练贡献估计。

11. 工程与职业启发

推荐算法工作从特征拼接向 state lifecycle engineering 扩展：要同时掌握事件流、序列压缩、Transformer KV 成本、状态一致性和线上因果实验；这类能力比单点模型调参更具跨场景迁移性。

2/8 · Ranking · Uncertainty · Dynamic Compute · arXiv v1 2026-11-13（11/16 新公告/关注）

RACE: Ranking-Uncertainty Aware Capacity-Adaptive Customization for Efficient Sequential Recommendation

一句话判断：将模型计算资源分配给排名仍不稳定的样本，而不是给每个用户序列同样的表示宽度与行为长度。

原始结果摘要：四数据集 SASRec：平均 NDCG@5 相对 +40.87%、Hit@5 +35.12%、FLOPs 降至约 1/2.37；特定基准与对照口径

1. 背景与业务动机

序列推荐并非每个请求都难。老用户常见高置信购买目标，冷启动或多兴趣用户则需要更多算力；固定宽度的 SASRec/BSARec 导致容易样本冗余计算，却不能自动把预算转移到难例。

2. 既有方案与核心问题

早退出常用单点分类概率或序列长度作为困难度，但推荐目标是候选间相对名次。若 topK 前沿彼此接近，微小扰动就可能改变最终曝光列表；若首位确定，粗粒度加深网络不一定有增益。

3. 核心技术路线

先估计 candidate ranking 的不确定性（论文采用均值/方差化不确定估计模块 VBLL），在较浅层预测后续计算收益，再以 hypernetwork 控制通道容量，以 progressive sequence pruning 去掉低贡献行为。区别于简单按序列长度设阈值，它把候选排序风险作为计算决策依据。

4. 训练方式与 Loss 机制

主干学习 next-item 推荐；不确定性分支拟合不同候选的排名波动，早层控制器用自监督信号预测更深网络的容量需求，配合轻量约束使减少 FLOPs 不致无差别破坏排序。评估时要确认训练阶段预测器是否使用测试标签或额外监督。

5. 推理 / Serving 设计

线上可采用二层策略：先以便宜的用户状态和候选接近度估计 List 风险，低风险直出，高风险启用额外通道或更长历史。GPU 批处理下动态通道与 token 裁剪可能破坏 shape 同质性，实际 P99 不必与理论 FLOPs 同比例下降。

6. 实验设置与主要离线结论

论文在 MovieLens100k、Douban、AmazonCD、AmazonGame 上比较 SASRec、BSARec 等骨干。作者报告四数据集平均：SASRec 的 NDCG@5 相对 +40.87%、Hit@5 +35.12%，FLOPs 约降 2.37 倍；BSARec 对应 +47.73%、+41.77%，FLOPs 约降 2.49 倍。这些是特定小/中数据设置下的相对结果，不能套算生产指标。

7. 线上 A/B 与成本收益

未发现作者披露线上 A/B。FLOPs 是理论计算 proxy；工业验收必须额外看 QPS、GPU 实测 latency、P95/P99、batch utilization、回源、客单价和评价满意度。需要分群核实困难请求是否被误分到轻量路径。

8. 优劣势与对照

相比固定宽度排序：按价值分配算力更有潜力；相比单纯 token pruning：加入相对名次风险，目标更贴近列表质量。局限是 uncertainty 自己需要校准，并可能在曝光偏置或长尾候选上过度自信。

9. 适用场景与挑战

适合海量短请求混合长尾难例、需要稳定 P99 的大规模精排及重排入口；当业务目标含多样性、负面证据、属性覆盖时，单个 NDCG 不确定性无法衡量全列表约束是否满足。

10. 待解决问题与未来方向

研究方向：把 ΔList reward、约束违例风险、置信区间与消耗的额外 GPU 毫秒统一成 cost-aware dispatch；支持不确定性校准、困难群体 fairness 和模型版本切换时阈值自动重估。

11. 评价推荐落地实验

固定评价候选和 GMV+满意度 Reward Model，以 topK margin、List-level entropy、Reward posterior interval 构造 easy/hard 分群；对 easy 先试小生成器，hard 升级大模型或额外 verifier；用同预算强 baseline 对比，不只比较均值 latency。

UltraBERT-JEV: Encoder models for System One Applications

一句话判断：结构化选择题型的裁判不一定要用自回归语言生成；小 Encoder 可用一次 forward 对多个候选做比较。

原始结果摘要：UltraBERT-380M test 69.7%→72.1%；小 Qwen3-0.6B 67.6%；单请求 A100 29ms vs 68ms，但显存 2.8GiB vs 2.2GiB

1. 业务动机

评价 List 的 Reward Model 或 JEV 经常只需要在几个互斥候选结果中判优，而不是生成长篇解释。把每个候选经生成式 LLM 单独判定，增加 token 开销和延迟，也带来解析失败。

2. 核心矛盾与任务前提

将“选最好的一个”转化为 encoder 中每个 option 对应一个 mask 的判别任务；但这种结构天然要求候选数可控、输入能够同屏拼接。它不能无改造替代开放式推理或需要逐项证据检索的生产 Judge。

3. 模型与关键模块

在 UltraBERT-380M encoder 里给每个 option 分配 mask，通过每个 mask 的 yes/no 词得分生成选项 logit；比较 only-yes、yes-minus-no、softmax、sigmoid normalization 与其他归一化变体。可在同一 encoder 输出上附证据位置的辅助预测头。

4. 训练 Loss 与监督

在与 Qwen3-0.6B LLM-as-JEV 相同的数据上做监督微调，直接按选项正确标签优化。证据头使用人工标注以及基于 SelfCite 规则构造的 evidence targets；该监督可能把引用质量和最终判优质量耦合，需要测弱标噪声。

5. 推理 Serving

一次前向同时得出所有 option 分数，不产生自回归输出；易于批量处理固定长度的“两个评价列表哪组更好”任务。选项次序置换、长度差、负样本位置及上下文截断仍需处理；批处理吞吐需要单独 benchmark。

6. 实验和离线指标

技术报告中 encoder 各 recipe test accuracy 69.7%—72.1%，yes-minus-no 使 69.7→71.3，sigmoid 再增加约 0.8 个百分点。小 Qwen3-0.6B 对照为 67.6%；更大的 Qwen3-4B LoRA 报告 77.3%，说明不能说 encoder 普遍胜过所有解码器。

7. 速度 / 显存 / 工业实证

A100 单请求决策 29ms vs 68ms，但 fp32 峰值显存 2.8GiB vs 2.2GiB（encoder 更高）。该实验不是服务集群峰值 QPS 或电商生产实验；线上 A/B 未披露。

8. 与主流方法优劣

相比 generative Judge：格式稳定、单次判别通常更便宜；相比 reward scalar regressor：选项相互对比可直贴业务排序，但可能对集合大小和选项模板敏感。还需检查概率校准而非只看 accuracy。

9. 适用性、局限与未知

适合 pairwise/listwise 质量判别、rerank early gate、人审预筛、离线 hard-example mining；不适合长链事实核验或复杂外部工具推断。跨商品迁移、Option 数量增加、校准稳定性及偏置未充分证明。

10. 研究方向与工程实验

固定真实曝光 List，先用可重复人审标注构造成对列表，再训练 encoder-Judge；评价 accuracy 外报告 Kendall/Spearman、校准 ECE、业务分层、位置交换 consistency 和误判高价值订单的代价；再用轻量判别器筛选少量样本交给强 Teacher。

11. 职业能力启发

不要把 Reward Model 研发等同于 prompt engineering：还需掌握 discriminative scoring、uncertainty calibration、证据归因、低延迟 GPU inference 和因果实验，形成系统级 Judge 设计能力。

3. 方法架构

将 Agent 状态表示为 typed blocks；分离 Compression（在学习前形成、在一段训练过程固定）和 Steering（根据轨迹迭代更新），通过生成候选 program、编译检查与轨迹重放评估进行选择。

4. 训练方案

在给定可执行 harness 下运行 GRPO 等 RL 流程，收集成功/失败轨迹，为 harness 更新提供 evidence；保持模型学习与外围程序迭代的对照，避免把 harness 额外上下文信息误当成参数能力。

5. Serving / Rollout

在线需要程序版本化与前后兼容，确保工具白名单、状态转移、日志格式和回滚。compression 频率、模型推理次数、沙箱执行时延与环境吞吐应纳入总成本核算。

6. 基准和指标

实验覆盖 CodeSearch、ALFWorld、BIRD SQL 等任务及多个 Qwen 规模；论文报告在部分 CodeSearch 配置相对固定 harness 约 +19% F1，且 Steering 和 Compression 在不同任务/预算约束下表现有别。不能将单场景数字夸大为所有 Agent 的统一增益。

7. 线上 A/B

未披露推荐/电商真实 A/B；离线 F1、Agent task success 和业务 GMV/评价满意度不是同一指标。训练时追加的自动 harness 搜索成本也需计入。

8. 优势与不足

优势是外部 workflow 可解释、可回滚，可在不更换大模型时提升数据质量；缺点是环境 replay 若不严格隔离，可能对 benchmark 过拟合，且复杂 harness 会带来维护负担。

9. 场景和待解

适用于多工具搜索、评价证据清洗、自动标注和闭环训练；对强监管或高度敏感流程，自动修改工具控制器需要更严格权限与人工审核。

10. 后续研究实验

把评价 List Generator 的 prompt/工具抽取/证据压缩作为 versioned harness；用固定模型权重做 A/B sandbox 对照，分别归因“更好样本”与“更好模型”带来的收益，并记录 Reward hacking、失败回放和成本。

11. 职业技能

模型研发需要扩展为实验平台工程：Agent trace、可复现环境、动态程序合成、RL 数据管道与安全沙箱，才能把学术离线增益转成可维护生产能力。

8/8 · RAG · Query Rewrite · Black-box Optimization · arXiv v1 2026-11-13（11/16 新公告/关注）

Dynamic Optimization of Query-Rewriting Agents for Generative RAG

一句话判断：检索 query rewriting 的好坏既受 prompt 结构影响，也受解码策略影响；单独微调一边可能陷在局部最优。

1. 背景与动机

多跳问题和含糊需求经常无法用用户原始 query 直接命中文档；重写查询能扩大召回，但单纯固定 prompt 模板可能在不同领域、不同检索器上失效。

2. 方法问题

Prompt 是离散结构，temperature、top-p 等解码策略是连续控制，联合搜索很难通过普通梯度下降；如果只优化某一组超参，生成 rewrite 质量与最终答案质量可能不一致。

3. 核心方案

把 rewrite Agent 表述为结构配置 C 与采样/解码参数 θ 的联合策略；组合全局结构跳跃、局部扰动和 elite candidate pool 的黑箱搜索，在任务 reward 上筛选可迁移配置。

4. 训练 / 优化

不等同于训练一个新的大语言模型或直接对线上成交做 RL；主要是对 prompt+decoding 的外层黑箱优化。需要关注候选评估预算、随机种子和 held-out 数据，避免利用评测集调参。

5. 推理与 Serving

上线把最佳 rewrite policy 固化为可回滚配置，配合查询难度判断是否需要重写；同时记录 rewrite 前后检索结果 overlap、证据来源和额外 token 开销。可通过小模型或规则对简单 query 走 fast path。

6. 实验设置与成绩

检索底座 E5-base-v2 + Wikipedia DPR passages/FAISS，重写模型 Qwen2.5-7B；在 HotpotQA、AmbigQA、PopQA 等数据集评估最终 EM。作者报告分别为 35.4 vs 34.2、53.2 vs 51.0、14.6 vs 12.2（最强对应 baseline）。

7. 效率 / A/B

没有电商随机 A/B；更高 EM 不直接意味着更低延迟。迭代调参产生的离线搜索 API 调用费用，以及在线重写、检索与生成全链路成本都应披露并统一比较。

8. 优劣势

优点是无需修改 base model 权重，可适配不同检索环境；相对 learned rewriter 的弱点是任务转移和长期 query 分布漂移时易失效，也缺乏内部可解释的因果保证。

9. 适用与限制

适合多跳问答、复杂商品属性比较、含糊评价证据检索；对短精确关键词，重写可能删除产品型号和否定词而降低 Precision，不能默认全量启用。

10. 开放问题与工程落地

基于真实评论 query 构造困难负例：商品型号、好评/差评 polarity、时间窗口、地区。对照 rewrite-off/fixed-prompt/black-box learned，在等 token budget 下测 Recall@K、重要差评保留和下游 List-level Reward，而不只看 QA EM。

11. 职业启发

从 embedding/retrieval-only 扩展至 query policy、offline evaluation、cost-aware controller 与 A/B；学会区分检索召回提升和终端用户满意度提升。

跨论文研究路线：下一步建议做的三组实验

实验 A · Judge/Reward 可信度：固定真实曝光 List，对全量原评价、裁剪 snippet、摘要和稀疏特征分别评估 pairwise/listwise 一致性、负面观点遗漏和 OOT 校准；强 Teacher 只处理拒答或边界样本，利用 UltraBERT-JEV 对低风险样本快速判别。

实验 B · 序列状态与推理算力：RecMem 16-slot vs recent-only vs full HSTU/现有 UserState；RACE 的候选相对排序不确定性做路由分桶；控制 candidate count、P99、GPU batch、曝光位置，按 GMV 与评价满意度联合验收。

实验 C · 证据与 Agent 生命周期：CarryOn 的任务状态与证据存储隔离，StreamEmbed 的视觉增量索引先做离线 Shadow，RAG-FGO 的 query rewrite 测重要负面评论保留率，ModHarness-RL 的程序版本与 replay 持续审计。

研究优先顺序：Verification Transport → UltraBERT-JEV → RecMem → RACE → CarryOn；其余作为多模态/Agent/检索基础设施支线。先分解 Reward 误差和样本可得性，再训练新 Generator，避免同时修改多个环节而无法归因。
