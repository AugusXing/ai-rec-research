Ranking Foundation 开始跨业务统一，
AI 系统进入 Runtime Control 阶段

今天最强的共同信号不是“再换一个更大的模型”，而是把昂贵能力变成可共享基础层，再用 Runtime Policy 决定何时、为谁、花多少计算。小红书 OneModel 将推荐、广告、商家三条业务流统一进长序列 Ranking Foundation；TTP 把 LLM 个性化推理离线缓存/蒸馏后送进毫秒级召回；FlashPrefill V2、Adaptive RAG Compression 则把 Long Context 的稀疏率与压缩率直接变成系统运行时决策。Agent 侧同样从单次成功转向 Workflow State、可靠性和可迁移 Skill Memory。

时间口径与质量控制：主扫描窗口为 2026-08-20 10:00 ～ 2026-08-21 10:00（北京时间），重点覆盖 arXiv 2026-08-21 公告批次。OneModel 在 2026-08-20 发布 v2，纳入严格窗口；Think-to-Personalize 首次提交略早于严格窗口，但前一日日报未覆盖，且具有罕见的搜索召回线上 A/B 与完整 Serving 设计，因此作为高价值补录。其余重点工作均为 2026-08-20 UTC 新提交。

今日核心结论

  • Ranking Foundation 正从“单场景大模型”升级为“跨业务共享基础层”。 OneModel 把推荐、广告、商家行为放进同一 Event Sequence，用 Scenario-aware Modulation 保留业务差异，再将长序列 User State 缓存化以满足线上精排延迟。
  • LLM Reasoning 进入 Retrieval 的正确姿势越来越像“离线重、在线轻”。 TTP 用 SFT + GRPO 学会显式推断用户意图，但线上通过 T+1 个性化缓存和 305M 蒸馏 Retriever 把额外延迟压到 0.15ms。
  • Long Context Serving 的研究重心从 Kernel 单点优化变成框架兼容。 FlashPrefill V2 不只追求稀疏 Attention 加速，还原生支持 paged KV cache、continuous batching、FP8，并直接接入 SGLang。
  • RAG Compression 应从固定超参变成 Runtime Policy。 Edge RAG 实测显示 Compressor 本身也消耗同一设备资源，最优压缩率依赖 Query、模型与设备实时状态；中等压缩可显著降低 GPU/SoC 能耗。
  • Agent Safety 正从“阻止一个危险 Action”转成“持续维护合规 Workflow State”。 PolicyGuide 把政策编译成 Workflow Graph，在每个用户轮次主动校验未完成步骤，而不是仅在工具调用时做动作级 Guard。
  • Agent 评测需要从 pass@1 转向可靠性曲线。 Thinkingbox 中最强模型 pass@1 为 65.36%，但连续 20 次都成功的 pass^20 只有 25.25%，说明“偶尔成功”与“可用于业务”之间仍有巨大鸿沟。
  • Experience / Skill Memory 不能只追求多。 新研究发现 task-level skill 往往拖累 Agent，而 subtask-level、文本化技能更容易跨任务迁移；Memory 应先做 utility audit 再检索注入。

重点论文 01 · Ranking Foundation / Multi-scenario Recommendation

OneModel: A Unified Foundation for Platform-Scale Multi-Scenario Ranking

arXiv:2608.18606v2 · Xiaohongshu · 2026-08-20

今天对推荐算法最重要的工作。它回答了一个比“单场景模型再大一点”更实际的问题：推荐流、广告、商家推荐共享同一个用户，为什么还要分别维护三套长序列模型、Embedding 和内容理解能力？OneModel 的核心价值是把跨业务行为视为一条连续 User Journey，同时用轻量 Scenario Modulation 防止负迁移。

1. 背景 / 业务动机

平台级用户行为天然跨流：内容消费透露兴趣，广告点击暴露商业偏好，商家交互提供更高价值的转化监督。过去三套 Ranker 各自训练会重复支付长序列、Embedding、内容理解与 Serving 成本，也切断了跨场景信号。真正难点是三条业务的 Feature Schema、目标与价值尺度完全不同，简单 Shared Bottom 很容易被高流量推荐场景主导。

2. 技术方案

  • Unified Event Token：场景特定 Feature Projection 将 ID、Category、Dense Feature 投到共享空间，再加入 Scenario / Action / Time-gap / Position Context。
  • Action-oriented Long Sequence：借鉴 GenRank，把 Action 作为预测目标而不显式交错 Item+Action Token，缩短有效序列；Candidate 间使用 Mask 防止同请求泄漏。
  • SAIM：Scenario-aware Information Modulation 在共享 FFN 中注入场景条件 Gate，同一计算图里保留推荐/广告/商家差异。
  • Stratified User Representation：Global Attention Pooling + 最后一层 Local State，同时表达长期兴趣与短期意图。

3. 训练

总 Loss 由跨流 Next-item Self-supervision、各业务 Supervised Objective 和 L2 构成；训练过程中逐渐降低自监督权重、提高业务监督权重，并让困难业务获得更高 Task Weight。为避免高频业务支配 Backbone，作者使用 cross-stream batch sampling；Warm-up 初期隔离业务塔对共享 Backbone 的梯度；超长序列只对高 perplexity 位置做 selective backprop。默认配置为 sequence length 500、768-d embedding、3 个 Transformer block、8 heads，bf16 + FlashAttention + gradient checkpointing + sampled softmax / in-batch negatives。

4. Serving

OneModel 没有在每次 Rank 请求里重跑整个 Transformer。长序列 User State 在新行为发生后增量更新并写入低延迟 KV Store；请求时仅把候选特征堆叠后做向量化 Scoring。配套 feature decomposition、user feature prefetch、共享 User Tower 与 graph-level inference optimization。这种“Shared Heavy User Foundation + Lightweight Candidate Scoring”是平台级 Ranking Foundation 更现实的产品形态。

5. 实验 / A-B

  • Ads Click AUC：HSTU 0.7644，GenRank 0.7648，OneModel 单流 0.7682，统一多流 0.7712。
  • 统一训练后 Ads Click AUC 相比单流 +3.0‰；Merchant 同样 +3.0‰，高资源 Rec 基本不退化，说明主要收益来自低资源业务借力共享轨迹。
  • Explore Feed：Time Spent +0.33%，Engagement +1.25%。
  • Feed Ads：广告价值 +3.43%，CTR +8.18%。
  • Merchant：DGMV +1.1867%，GPM +2.1585%。

6. 优势、局限与下一步

最大优势是把“模型 Scaling”变成跨业务共享资产，从数据、训练、Serving 三层降低重复建设；同时 SAIM 比完全独立 Tower 更容易复用表示。局限是三流仍共享大量参数，极端目标冲突、业务快速迭代、隐私/授权边界都会增加治理成本；此外论文数据因商业保密只给相对流量和聚合结果。下一阶段值得研究的是 Dynamic Scenario Router、跨流 Uncertainty/Conflict Detection，以及让共享 User State 同时服务 Retrieval、Ranking 与 Re-ranking。

7. 对工程与技能的启发

推荐工程师未来需要把“多场景推荐”从 MMoE/PLE 的多任务结构提升到跨业务 Event Schema、Long-context Backbone、训练预算分配、User State Cache 与推理图优化的系统级问题。只会改 Ranking Tower 已经不够。

重点论文 02 · Personalized Retrieval / Reasoning + RL

Think-to-Personalize: Unifying Reasoning and Retrieval for User-Centric Personalized Dense Retrieval

arXiv:2608.18855 · CIKM 2026 · Local-lifestyle E-commerce Search

这篇最值得看的不是“用 LLM 改写 Query”，而是它把Reasoning、Embedding Learning、RL Reward、Offline Cache、Online Distillation串成一个完整搜索召回系统。

1. 问题

本地生活搜索里大量 Query 很短、很泛，例如用户只输入一个品类词。传统 Dense Retriever 只编码 Query；History-aware 方法往往只是把历史 Embedding 隐式融合，难以从噪声购买序列里显式推断“这次用户真正想要什么”。

2. 方法

TTP 输入 instruction + user purchase history + query，让 LLM 先生成 reasoning / intent-enhanced query，再产生统一 Dense Embedding。关键是 reasoning 不作为展示文本，而是服务于 Retriever 表示。历史长度实验显示 N=10 最好，继续堆历史反而引入噪声。

3. 两阶段训练

  • SFT：联合生成目标与 contrastive retrieval objective，先建立稳定 cold-start reasoning / embedding 能力。
  • GRPO：每个输入采样一组 reasoning，Reward 包含 Format、Length Penalty、Retrieval Reward；再用 Group Relative Policy Optimization 对齐实际召回效用。
  • Dynamic Positive Selection：只把组内 retrieval reward 最好的 reasoning 对应 Embedding 用作 InfoNCE 正样本；如果这一组都无正收益，则退回原始 Query Embedding，避免错误 reasoning 污染表示。

4. Serving：为什么 LLM Reasoning 没拖垮延迟

作者采用双路径。T+1 离线用完整 3B TTP 为活跃用户 × broad-query 预计算 personalized embedding，覆盖约 10.59% QV / 11.80% UV；Cache miss 则由 305M Encoder-only Retriever 实时处理。这个 Student 同时学习 original query→item、rewritten query→item、original↔rewritten 三类对齐，平均 R@20 为 43.10，对比 3B Teacher 的 44.97。个性化通道与通用召回并行，候选在固定 Budget 下合并。

5. Online A/B

7 天线上实验保持通用 Recall、Candidate Budget 和后续 Ranking 不变，仅新增 TTP 个性化召回通道：QV CXR +0.41%，UV CXR +0.29%，Order Volume +0.46%，额外端到端延迟仅 +0.15ms，且已部署。

6. 优劣势 / 局限

优势是把“Reasoning 能否提升 Retrieval”直接交给 Retrieval Reward，而非依赖语言质量；Serving 也体现了典型 teacher-offline / student-online。局限是离线 Cache 对用户/Query 新鲜度敏感，T+1 会产生 stale personalization；购买历史含强偏置，显式 reasoning 可能放大历史兴趣并降低探索性。未来值得把 cache TTL、uncertainty、multi-turn intent 和实时行为增量统一进 Router。

7. 对推荐/搜索工程的启发

在搜索召回里应用 LLM，不要默认“线上直接调用大模型”。更现实的架构是：Teacher 负责发现个性化意图 → Reward 对齐 Retrieval Utility → 高频 Pattern 缓存 → Student 蒸馏长尾 miss → ANN 仍承担大规模候选搜索。

重点论文 03 · Long-context Serving / Sparse Attention

FlashPrefill V2: Block-Sparse Prefill Attention for Long-Context LLM Serving

arXiv:2608.19758 · Submitted 2026-08-20 UTC

FlashPrefill V2 的重要性在于它不再只证明“Sparse Attention 理论上更快”，而是补齐了精度修正、Hopper Kernel、FP8、Paged KV、Continuous Batching、SGLang Integration这些生产必需条件。

1. 从 Prototype 到 Serving Backend

  • Mean Correction：对被剪掉 Block 的 K/V 统计做补偿，在极高稀疏率下控制近似误差。
  • Kernel：PackGQA memory access + warp specialization + ping-pong pipelining，对齐 FlashAttention-3/4 的 Hopper 优化路径。
  • Quantization：原生 FP8，而不是只在 BF16 Demo。
  • Runtime：支持 paged KV cache、varlen request、continuous batching，作为标准 Attention Backend 接入 SGLang；Decode 阶段仍回退 Dense Attention。

2. 效率与精度

NVIDIA H20、128K Context 下，相对 FlashAttention-2，BF16 最多 27.19×、FP8 最多 47.26×；相对更强的 FA3/4-aligned dense baseline 仍有 17.54× / 30.49× Attention Kernel 加速。真正更有系统意义的是 SGLang 端到端 TTFT：128K Continuous Batching 下最多 3.4×（BF16）/ 4.8×（FP8）。在评测中 correction 后平均精度距 full attention 控制在约 0.9 point 内，128K 约 1.5 point 内。

3. 局限 / 未来

收益主要集中 Prefill；Decode 每步只有单 Query Token，Block Sparsity 空间有限。Attention Density 会随 Context 变化，实际生产仍需根据任务质量容忍度选择稀疏阈值。更进一步的方向是让稀疏度、KV 策略、模型路由与 SLA 统一成 Request-aware Runtime Policy。

4. 对推荐/搜索的启发

长用户序列 Ranker、RAG、Agent Memory 都会遭遇同一 Prefill 瓶颈。模型设计不能假设 Dense Attention 成本固定；未来 sequence length / attention density / precision 很可能像 Retrieval Top-K 一样成为动态系统参数。

重点论文 04 · Agent Runtime Governance

PolicyGuide: From Guarding One Action to Guiding the Whole Workflow for Policy-Compliant LLM Agents

arXiv:2608.19861 · Submitted 2026-08-20 UTC

Agent Guardrail 的下一步不是多写几个“禁止调用某工具”的规则，而是让系统知道当前业务流程走到了哪一步、还缺什么确认、哪些动作此刻才合法。

1. 核心设计

PolicyGuide 将组织政策编译成 Workflow Graph。每个用户轮次边界，一个独立 Verifier 根据 raw policy、tool schema、冻结的 workflow graph、对话历史和代码维护的 request state，检查所有 open request，并返回“第一个未满足步骤”的 remediation。Graph State 持久化，因此跨轮次不会忘记身份证明、确认、诊断、授权等程序约束。

2. 与 Action Guard 的区别

Action-local safeguard 只能问“这次 tool call 能不能执行”；PolicyGuide 能问“为了完成这个请求，前面哪些步骤必须先完成”。这对电商售后、广告账户修改、支付、企业权限等多步业务流程更关键。

3. 实验

在 τ²-bench airline / retail / telecom 上，GPT-5.4 agent+verifier 的平均 Pass^4 从 0.42 提升到 0.62；流程结构最强的 telecom 从 0.19 提升到 0.61。相同 Workflow Graph 还能迁移到 Claude Sonnet 4.6 与 Gemini 2.5 Pro。作者另测 adversarial user，报告最低攻击成功率与最强程序合规。重复 policy/workflow prefix 可以利用 prefix cache，Verifier 调用随相关用户轮次增长，而非随每个 tool result 都触发。

4. 局限 / 启发

代价是 policy→graph 编译本身可能错误，Verifier 仍由 LLM 驱动；复杂动态政策还需要版本治理。对推荐/搜索 Agent 来说，PILOT 这类实验 Agent 后续也需要类似的 Workflow State：实验审批→流量门槛→统计显著性→回滚→归档，不应只靠 Prompt 记住程序。

重点进展 05 · RAG / Edge Runtime Policy

From Retrieved Context to Runtime Control: Adaptive Compression for Edge-based RAG

2026 · ACM AI Leadership Summit · NVIDIA Jetson AGX Thor experiments

Context Compression 过去常是离线选一个固定 compression ratio；这项工作指出：在 Edge SoC 上 Compressor 与 Generator 竞争同一计算/能耗预算，因此压缩率必须由实时系统状态决定。

作者在 Jetson AGX Thor 上用 Llama/Qwen、Natural Questions/HotpotQA、LLMLingua-2 做测量。7B–8B Generator 中 Generation 可占约 90% query latency、91% GPU energy；中等压缩率最多降低约 53.2% GPU energy、48.2% SoC energy，同时保持可忽略质量损失。过轻压缩浪费节能机会，过强压缩又损害答案质量。

工程判断：RAG Router 的输入不应只有 Query；还应包含 Context Length、Model Size、Battery/Power、Device Load、Latency SLA，然后动态选择 retrieval top-k、compression ratio 与生成模型。这与推荐系统的 Request-aware Ranking / Dynamic Compute 是同一个系统问题。

重点进展 06 · Agent Evaluation / Stateful Workflow

One Success Isn't Reliability: Thinkingbox

arXiv:2608.19741 · Microsoft · Official Open Source

Thinkingbox 把 Agent Benchmark 从“回答像不像对”推进到最终 Backend State 是否正确、有没有多做/漏做副作用、重复运行是否稳定。

Sandbox 提供隔离 MCP-compatible Tool Session、完整 Execution Trace 和最终 Backend State 检查；Thinkingbox-bench 有 507 个带 Policy 的工作流，覆盖零售、酒店、车险、Neobank 内部 IT、咨询 IT/HR。最强模型 pass@1 为 65.36%，但 pass^20 只有 25.25%。大量失败 Trial 表面上正常结束、甚至执行了合法 Tool Call，却没有得到正确的端状态，说明 response-level / tool-call-level 指标严重高估业务可靠性。

对推荐 Agent 的启发：如果 Agent 自动改策略、建实验、改索引或发版，评估指标也应从“单次任务成功率”升级到 pass^k、state invariant、side-effect audit 与 rollback correctness。

重点进展 07 · Agent RL / Environment Generation

EnvHarness: Awakening Static Worlds for Agent Learning

arXiv:2608.19880 · Submitted 2026-08-20 UTC

Agent 会进步，但 Benchmark Environment 往往不会。EnvHarness 的思路不是重新生成一个完整世界，而是在既有 Environment 外增加可编程 Plug-in Layer，让训练环境针对当前 Policy 的弱点动态变难，同时保留原始 Verifier。

EnvRigger 把目标 Agent 当黑盒，观察失败 trajectory，诊断弱点，自动合成 Harness Component，再用 fresh rollout 验证。跨 5 个 Benchmark、4 个 Domain，held-out 最多提升 9.0 points，同时 Execution Steps 减少 9.8%；作者进一步将其作为 RL 的优化信号，让 Policy 与 Environment 持续共同演化。

对推荐/搜索的迁移：Ranking/Agent Simulation 也不应长期固定 Hard Negative 和用户 Simulator；可以根据当前模型的 failure cluster 动态生成 counterfactual case、edge case 与 adversarial session。

重点进展 08 · Agent Memory / Skill Transfer

Break It Down, Pass It On: Cross-Task Skill Transfer in LLM Agents

arXiv:2608.20274 · Submitted 2026-08-20 UTC

“把成功经验写进 Memory，下次检索出来”并不天然有效。该研究发现：Task-level Skill 大多让 Agent 比无 Memory Baseline 更差；Subtask-level Skill 平均反而提升；Text Skill 又比 Code Skill 更容易迁移。

作者用 specificity（技能和真实任务匹配程度）与 abstractness（技能能否均匀覆盖多任务）解释这一现象，并把两者组合成 Skill Utility Score。重要的是，这个分数只需要 skill text 与 task description，不需要真正执行新任务，就能在注入 Memory 前做预审。

对 rEDMRec / Recommendation Memory 的补充：昨天的 rEDMRec 强调把 reasoning 蒸馏成可编辑 Experience；今天这篇进一步提醒：Experience 粒度与迁移效用需要显式诊断。未来 Memory Store 可能需要 relevance × utility × confidence × freshness 四维 Router，而不是简单 Top-K cosine retrieval。
