今天的主线：Agent 的竞争开始从“模型更强”转向“状态压缩、主动探索、运行时自进化与高效 Serving”

今日核心结论：① GPT-6 Astra 的真正工程信号不是榜单继续上涨，而是 computer-use + harness + cost-per-task 被放在同一个产品目标里：OSWorld 2.0 72.6%，单任务耗时约比 GPT-5.6 Sol 少 47%，Codex harness 组合在 Mind2Web 上任务完成速度 1.9×；② Model Routing 正在变成“学习执行状态”：Gated-Memory Routing 不再给 router 塞完整历史，而是学习什么该写入、什么该检索、何时停止；③ Agent 的探索需要被训练，而不是靠 prompt 祈祷：SAFARI 用探索型轨迹 + 对比式 RL 校准“继续探索还是执行”的边界；④ Agent harness 也进入可学习/可演化时代：Ecdysis 说明逐条失败就改 harness 会过拟合，应该先跨任务聚类失败再修系统性缺陷；⑤ Serving 仍然是硬约束：vLLM 的 warmup/DeepSeek-V4 兼容修复与 SGLang 的 NPU 平台层、DeepSeek-V4.1 FlashMLA kernel 同日推进，说明 frontier 模型真正落地依赖模型×硬件×kernel×启动路径的持续协同。

今日最值得看

🥇 GPT-6 Astra · Model × Harness × Cost-per-task

OpenAI 今日新增面向 Work 的官方说明页，模型本体并非今日首发，但新披露更清晰地把“模型能力、computer use、Codex harness、token/重试效率、安全边界”合成一个系统指标。对搜索/推荐最重要的启发：未来昂贵模型更像 hard-case executor，而不是所有 request 的默认路径。

🥈 Gated-Memory Routing · Router 先学会“记什么”

Query-only router 看不到中间进展，full-history router 又被历史淹没。Gated-Memory Routing 引入 Memory Write Gate、Retrieval Gate、Role/Backbone Allocator 和 Adaptive Halting，在 5 个 reasoning/code benchmark 上平均最好，并相对最强 baseline 提升 2.44 points。

🥉 SAFARI · 主动探索不是多走几步

核心不是鼓励 Agent “更爱探索”，而是学习何时探索值得、何时是浪费。SAFARI 先蒸馏包含回溯/试错的树状轨迹，再用 Monte-Carlo 评估形成 contrastive preference，优化 explore-vs-execute 决策边界。

技术趋势

Routing → State Management

过去 router 的输入通常是 query；下一阶段更像在线控制器：维护压缩后的执行状态，按需读写，并决定 model、role、retrieval depth、tool、halt。Gated-Memory Routing 与昨天的 Fugu 共同把“routing”推向 execution-plan controller。

Agent Training → Exploration Policy

干净的成功轨迹存在 hindsight bias：它删除了真实决策中的试错与信息收集。SAFARI 表明，Agent 训练数据要保留“为什么探索、为什么回退、何时停止”的结构，而不仅是最终正确路径。

Harness → 可优化的软件层

模型冻结后，规划、工具协议、错误反馈、上下文管理仍然决定大量最终成功率。Ecdysis 把 harness 优化从逐 case patch 提升到跨任务 failure attribution；这和推荐系统里“不要被单个 bad case 驱动全局规则”高度同构。

Serving → Model × Kernel × Hardware Contract

vLLM 与 SGLang 的 24h 更新看似“工程细节”，实际决定新模型能否低风险上线：JIT warmup、expert-parallel 启动条件、NPU runtime abstraction、MLA kernel 都是生产 readiness 的组成部分。

Deep Dive 01 · Frontier Model / Computer-use Agent

GPT-6 Astra：值得关注的不是“又一个更高 benchmark”，而是能力、Harness 与任务成本被统一优化

Research Impact Score / 研究价值 9.5/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 否；API/产品可用是否有线上 A/B 未披露；有内部 rollout 与客户评测阅读优先级 S+

时间口径：GPT-6 Astra 模型本体已在上周发布；过去 24 小时 OpenAI 新增了面向工作场景的官方说明页，补充了客户侧、内部 rollout、任务成本与安全边界的信息。因此今天把它作为官方工程信号更新，而不是写成“9/14 新模型首发”。

背景 / 业务动机：Agent 进入生产后，单纯“回答更聪明”并不够。真正影响 ROI 的是：能否操控真实软件、是否少走弯路、是否需要频繁重试、能否遵守授权边界、每个完整任务而不是每个 token 要花多少钱。Astra 的官方叙事明显把目标从 model-level benchmark 转成 task-level usefulness。

技术方案与关键模块：OpenAI 只披露 Astra 由 pre-training、reinforcement learning 与 alignment 的长期投入共同训练，并未公开网络结构、参数量或完整 recipe。工程上更关键的是它与 Responses API / computer-use tools / Codex harness 的组合：模型负责视觉理解、规划、代码/工具操作与长程目标保持；harness 负责软件交互、确认策略、Auto-review、上下文和工具协议。

训练方法：官方没有给出可复现的 SFT/RL 配方，只明确指出 targeted training 面向 professional environments，并把 task boundary、computer-use safety、capability honesty 纳入对齐训练。由于 recipe 未公开，这一部分不应从 benchmark 反推具体 RL 算法。

推理 / Serving：API 型号为 gpt-6-astra。Standard 定价为每百万 input tokens 10 美元、output tokens 50 美元；Fast mode 最多约 2× 速度，价格为 Standard 的 2×。这意味着 router 的价值进一步放大：不是所有 query 都值得走 Astra，更合理的是先用便宜模型/规则判断难度、价值与风险，再升级到 frontier executor。

实验设置与离线指标：OSWorld 2.0（offline subset）72.6%，GPT-5.6 Sol 为 65.7%；官方 latency simulation 中 Astra 约 40 分钟/任务，对比 Sol 约 75 分钟，时间缩短约 47%。Terminal-Bench 4.0 为 57.9% vs 37.3%；AutomationBench 41.4% vs 18.1%；DeepSWE v1.1 74.1% vs 72.7%。OpenAI MRCR v2 的 512K–1M 长上下文区间为 96.3%。这些评测覆盖能力与系统交互，但仍不等同于你的线上 query distribution。

Harness 收益：OpenAI 还披露：Astra 与更新后的 Codex harness 组合在 Mind2Web 上相对 GPT-5.6 Sol 体验实现约 1.9× 的任务完成速度。内部工程团队曾用 Astra 找到 Codex test environment 的内存分配瓶颈，切换 allocator 后 turn latency 降低 25×、峰值内存约 +30%。这里的重点不是这两个数字可外推，而是模型本身开始成为 runtime optimizer 的一部分。

线上 A/B / 工业证据：没有传统意义的随机线上 A/B。官方提供内部 rollout、客户 early eval 与产品部署证据；Hebbia、Box、Databricks、Cognition 等给出各自的内部评测，但评测集与采样方法并不完全公开。因此把它视为强工业信号，而不是可复现学术证据。

效率 / 成本收益：官方强调“更少 token、更少 retry、成本按任务下降”。Terminal-Bench 4.0 上，官方估算 Astra 相比 GPT-5.6 Sol API cost per task 约低 9%。这再次说明未来选模不应只看 $/token，而应看 quality × attempts × tool calls × wall-clock × $/completed-task。

与主流方法的优劣势：优势是 computer-use、代码、长上下文、工具与安全边界协同强，且生产 API/harness 一体化；劣势是闭源、训练 recipe 不透明、公开 benchmark 与实际推荐/搜索 SLA 差异很大，且 $50/M output tokens 对高 QPS 在线链路依然昂贵。

推荐/搜索适用场景：不要把 Astra 直接替代在线 ranker。更合理的落点是：① hard query deep search；② 高价值用户/商家复杂任务；③ offline label/judge/analysis teacher；④ query plan / tool orchestration；⑤ 对失败 case 做自动 root-cause analysis；⑥ 生成复杂规则或评测脚本。主站推荐链路应由轻量 controller 决定是否升级。

局限与尚未解决问题：任务级 cost benchmark 尚未标准化；computer-use 成功率对 harness 非常敏感；长任务中的 context drift、权限边界与 monitorability 仍是问题。OpenAI 自己也披露 Astra 的 written reasoning 在部分 monitorability eval 上更难监控，这说明“能力更强”不会自动等于“更容易治理”。

未来研究方向：最值得跟的是 frontier executor 与 cheap controller 的分工、cost-aware routing、computer-use state compression、tool/harness co-design、task-level benchmark 以及安全 verifier 与执行策略的联合优化。

对推荐/搜索算法工程与职业技能的启发：仅会训练排序模型的边际价值会继续下降。更值得补齐的是 LLM evaluation、router、Agent runtime、tool protocol、成本建模、failure attribution。推荐工程师最有优势的地方恰好是长期擅长“多阶段系统 + SLA + 多目标权衡”，这套能力正在 Agent 系统里重新变成核心。

Deep Dive 02 · Model Routing / Multi-agent Memory

Gated-Memory Routing：真正的 Router 不该读完整历史，而该学习一个“足够用的执行状态”

Research Impact Score / 研究价值 9.4/10工业成熟度 ★★★☆☆创新性 ★★★★★与你方向的相关度 ★★★★★是否官方开源 是是否有线上 A/B 否阅读优先级 S+

时间口径：论文已被 EMNLP 2026 Main 接收，arXiv v1 为 8/31、v2 为 9/9；今天作为近期重要 routing 论文补位，而不是伪装成 24h 首投。

背景 / 业务动机：多 Agent 系统中的 router 面临一个典型两难：只看 query，无法知道前面已经尝试了什么、哪个步骤出错；把完整 trajectory 全塞给 router，又会让上下文不断膨胀，后续每次决策都反复读取低价值历史。作者把这个问题称为 execution-history overload。

现有问题：Query-only routing 是无状态控制器；full-history routing 是“什么都记”的控制器。前者信息不足，后者成本随轨迹增长，并把噪声、重复推理和错误过程一并带入后续决策。关键问题因此不是“选哪个模型”，而是当前系统状态应该压缩成什么。

技术方案与关键模块：Gated-Memory Routing 用一个联合训练的 policy 维护执行记忆。核心包括：① History-Aware Role Allocator，基于 query + compact memory 选择下一角色；② LLM Router，在可用 backbone 中选择模型；③ Retrieval Gate，对记忆记录做自适应读取，而不是固定 top-k；④ Memory Write Gate，只写入非冗余、高 utility reasoning；⑤ Adaptive Halting Controller，证据足够时停止继续调用 Agent。

一个很值得借鉴的设计：role/backbone 不是靠固定 ID embedding，而是编码它们的自然语言描述。这样 controller 更有机会迁移到新模型/新角色，而不是把路由器完全绑死在训练期 model pool。

训练方法：论文使用冻结的 sentence encoder（all-MiniLM-L6-v2，384d）构造语义表示，LLM backbones 冻结，训练的是 router/gates/controller。策略优化采用 group-relative、cost-aware 的目标：不仅奖励最终 correctness，也对模型调用成本与无效步骤施加压力。记忆读写是离散 gate，halting 通过 GRU/MLP 对当前状态做停止判断。

推理 / Serving：每一步并非把完整历史拼回 prompt，而是先从 memory 中选择相关记录，再决定 role + backbone。最终 aggregation 使用被选择最频繁的模型完成答案整合。Serving 上它多了 controller/gate 的轻量开销，却减少了昂贵 LLM 的历史 token 与无用调用；在高价多模型 pool 中这种交换通常是划算的。

实验设置：覆盖 MATH、GSM-Hard、MBPP、HumanEval、MMLU-Pro；模型池包含 Llama-3.2-3B、Llama-3.1-8B、Mistral-Nemo-12B、Qwen-2.5-14B、Qwen-2.5-32B 等，重点比较 query-only、full-history 与不同 multi-agent routing baselines。

离线指标：论文报告五个 reasoning/code benchmark 上取得最佳平均 accuracy，超过最强 baseline 2.44 points；HumanEval inference cost 相对最强 baseline 下降 31.9%。在 routing paradigm 对照中，GSM-Hard 的 gated-memory accuracy/cost 为 70.55 / $0.587，对比 full-history 70.27 / $0.985；HumanEval 为 89.84 / $0.032，对比 full-history 89.06 / $0.068。最重要的不是绝对美元，而是证明选择性状态能同时保精度、降上下文和调用成本。

线上 A/B：无。实验是公开 benchmark + API/开源模型定价环境，没有真实在线流量、P95、burst traffic 与动态模型可用性测试。

与主流方法的优劣势：相对 query-only router，优势是能感知 trajectory progress；相对 full-history，优势是 context compactness；相对纯 semantic retrieval memory，它把 write/retrieve/halt 和 model/role selection 联合优化。缺点是训练与状态管理复杂度更高，memory gate 自己也可能写错/漏写，而且多模型价格与质量随时间变化时需重新校准。

推荐/搜索落地：这篇几乎可以直接映射到多阶段推荐：把 query、召回置信度、已尝试的召回源、rerank margin、业务 constraint violation、上一阶段失败原因写进 compact decision state；controller 再决定扩大 top-K、切 embedding、启用重 reranker、调用 LLM、还是直接停止。关键是不要把完整日志当 state。

局限：没有超长 session、在线 drift、memory poisoning、模型上下线、价格波动、cache hit 等生产变量；benchmark task 数量也远小于真实推荐请求空间。Memory Write Gate 的错误是否会累积为不可恢复的状态偏差，是非常值得研究的问题。

未来研究方向：① cost/latency/cache-aware joint routing；② memory TTL 与版本化；③ uncertainty-aware write/retrieve；④ cross-stage recommender state；⑤ model pool 动态扩缩；⑥ safety/provenance 作为 memory schema 的一部分。

职业启发：Model Routing 不应只理解成“训一个 classifier 选模型”。真正高价值能力是把 state representation、decision policy、serving cost、queueing、fallback、evaluation 串起来。推荐算法工程师已有的 cascade / feature state / multi-objective 经验与这个方向非常匹配。

Deep Dive 03 · Agent RL / Exploration

SAFARI：Agent 训练最容易丢掉的，恰恰是“试错与探索”

Research Impact Score / 研究价值 9.2/10工业成熟度 ★★★☆☆创新性 ★★★★★与你方向的相关度 ★★★★★是否官方开源 是是否有线上 A/B 否阅读优先级 S

时间口径：arXiv 在 9/13 发布 v2 replace 信号，是今天窗口内最明确的论文更新之一。

背景 / 业务动机：多数 Agent SFT 数据是“成功后的干净路径”：正确工具、正确顺序、没有走错路。问题是线上真实任务往往不知道答案在哪里，Agent 需要先获取信息、验证假设、回退再尝试。把所有探索从 demo 中删掉会产生 hindsight bias；而 RL 初期如果几乎不采样有价值的探索动作，又会发生 exploration collapse。

技术方案：SAFARI 分两阶段。第一阶段 Exploratory Data Construction 用强 teacher 生成包含回溯、试错与信息收集的轨迹；第二阶段 RL Optimization with Contrastive Signal Guidance 不只优化最终 reward，而是专门校准“当前状态下 explore 还是 execute”。

关键模块 1 — Tree-Structured Context：探索轨迹不是一个不断增长的线性 prompt，而是树。失败分支可标为 [DEAD END]，次优路径可标 [SUB-OPTIMAL]，Agent 能回到父节点尝试另一分支。这个结构非常重要：它把“走错路”从噪声变成可学习的反事实证据。

关键模块 2 — Cognitive Notes：每个探索节点保留摘要/解释，帮助 student 学到“为什么这条分支不值得继续”，而不是只模仿工具序列。

数据筛选：teacher 生成多条 trajectory 后，用带长度惩罚的目标筛数据：r_final = r(h) - n·γ。因此“探索越多越好”并不是目标；成功但极度冗长的路线会被压分。

RL / Preference 方法：在状态 s_t 上，对 teacher/reference action 与 student candidate action 分别做 Monte-Carlo rollout，估计 r_step(a|s_t)=E[R(τ)|s_t,a]。只有两动作的价值差超过 margin threshold 时才构造 preference pair，再用 DPO 类目标优化。这相当于直接学习 exploration decision boundary。

推理 / Serving：Serving 不需要 teacher 或 Monte-Carlo rollout；训练后的 student 直接依据当前树状上下文决定继续探索还是执行。因此昂贵 rollout 是 offline training cost，线上开销主要来自它选择的额外环境交互。

实验设置：WebShop、InterCode-SQL、ScienceWorld 三类环境，覆盖购物搜索、数据库交互与开放式科学任务。公开解读显示 student 主要采用 Llama-3-8B 量级，teacher 使用 GPT-4o 级强模型。

离线结果：作者报告 Task Performance 相对强 baseline 有约 10%–15% 的提升，同时 Exploration Score 显著提高；8B student 在部分设置可达到或超过 teacher。更值得注意的是 exploration intensity 随任务难度增加：hard task 会主动多探索，而不是所有请求统一加步骤。

线上 A/B：无，当前仅在模拟/交互 benchmark 验证。

效率 / 成本收益：SAFARI 的核心 trade-off 是“多一步 exploration 能否减少后续错误”。Easy request 上过度探索可能反而损失 reward，因此真正落地时必须把探索预算与 query uncertainty、用户价值和 SLA 联动，而不能把 exploration 当成永远正收益。

与主流方法比较：相比普通 SFT，它保留失败分支；相比只用最终 reward 的 RL，它提供 step-level contrastive signal；相比 prompt 里一句“请多探索”，它用训练塑造 policy。缺点是 teacher data 与 Monte-Carlo rollout 昂贵，探索质量也受 evaluator 偏差影响。

推荐/搜索落地：非常适合三个场景：① 检索不足时是否扩 query / 换召回源；② 高客单价/复杂意图 query 是否进入 deep-search；③ rerank 置信度低时是否主动找更多 evidence。可以把“探索”具体化为扩大 top-K、query rewrite、图遍历、tool call、补充用户偏好，而不是泛化成无意义的多轮思考。

局限与未解决问题：探索得分本身是代理指标；teacher 是否真的提供最优探索模式未被证明；现实世界 exploration 可能有不可逆动作和真实成本；如果 reward 模型低估信息价值，policy 仍会过早停止。

未来研究方向：budgeted exploration、uncertainty-calibrated exploration、offline counterfactual evaluation、recommender slate exploration、safe irreversible actions，以及和 Gated-Memory Routing 结合——一个决定“是否探索”，一个决定“探索后哪些状态值得留下”。

Deep Dive 04 · Agent Runtime Harness Evolution

Ecdysis：不要因为一个 Agent 失败就改全局 Harness——先判断它是不是系统性缺陷

Research Impact Score / 研究价值 9.1/10工业成熟度 ★★★☆☆创新性 ★★★★☆与你方向的相关度 ★★★★☆是否官方开源 是是否有线上 A/B 否阅读优先级 S

时间口径：9/10 首投，属于周末 arXiv 空窗下的最新批次补位，不计作过去 24h 首发。

背景：Agent 的成功率不仅由模型决定，还由 runtime harness 决定：如何规划、暴露工具、解析 observation、处理 error、截断上下文、决定 retry。已有 self-evolving harness 方法常见做法是“某个 task 失败 → 让 coding agent 改 harness → 再跑”，看起来自动化，实际容易把当前模型的偶发缺陷写进全局基础设施。

作者诊断：一次失败可能来自两类原因：model-specific deficiency 或 systematic harness deficiency。如果不做 attribution，就会发生 model accommodation——Harness 越修越适配训练模型/训练样本，却伤害跨任务和跨模型泛化。

技术方案：Ecdysis 把 sequential per-case patch 改成 batch-level cross-instance failure aggregation。先收集一批 task 的失败，找 recurring pattern，再决定是否值得改全局 harness。随后使用 Failure-Driven Collaborative Refinement（FDCR），由 Analyst / Critic / Engineer 多角色协作：分析失败模式、质疑诊断、形成明确修改 specification；最后让 coding agent 只负责实现 specification。

训练 / 演化方式：它没有更新底层 LLM 权重，优化对象是 runtime harness code/config。关键训练信号来自跨任务重复失败，而非单条 trajectory 的 reward。这是一种“软件层 policy optimization”。

推理 / Serving：训练完成后 harness 固定，held-out evaluation 不再在线自改。这个选择非常重要：生产环境通常更需要可版本化、可回滚的 runtime，而不是请求执行中不断重写自己的基础设施。

实验设置与指标：论文使用 τ² / AgentBench 等 deterministic agent environments，指标包括 accuracy、Pass@3、Pass^3、wall-clock training time、eval tokens、cache/API cost，并额外人工分析修改是否属于 model accommodation。

核心结果：相对 self-evolution baseline，Ecdysis 报告 harness training 最多 1.84× 加速，所得 harness 的 reasoning accuracy 相对提升 18.56%。在 Qwen3-8B 的 τ²-Airline 子集上，Self-Evolution accuracy / Pass@3 / Pass^3 为 35 / 50 / 20，Ecdysis+FDCR 为 60 / 80 / 40；同一 harness 切到未参与演化的 Qwen3-32B，accuracy 也从 51.67 提到 68.33，说明部分规则确实具备跨模型性。

工业信号：论文还展示拆掉 harness layer 后平均准确率只有约 29.72%，人工固定 harness 约 50.28%，而“每失败一次就修”的 naive coding-agent evolution 约 43.33%。这非常有工程意义：自动化修改不等于自动化进步。

线上 A/B：无。环境仍是 benchmark / sandbox，且训练 task 数有限。

与主流方法比较：相比 self-evolving prompt/harness，Ecdysis 多了一层 failure aggregation + attribution；相比直接 fine-tune model，它更便宜、可审计、跨模型复用。弱点是“跨任务重复”仍只是系统性原因的 proxy，不是真正因果识别；复杂线上事故也可能低频但高风险，不能因为不重复就忽略。

推荐/搜索落地：这套方法可以直接迁移到线上 bad case 治理。不要看到一个 bad query 就改全局 prompt、rule、rerank constraint；先聚类：是特定模型错、特定 query type 错、retrieval stage 错，还是全局 harness/controller 缺陷？只有稳定的跨 case pattern 才升级成全局策略。推荐系统长期积累的 case mining / cohort analysis 正好可以嫁接到 Agent harness evolution。

局限：样本量小、benchmark 较确定性；自动诊断本身依赖 LLM；某些模型/任务上 FDCR 也会负收益；latency 可能因更复杂 harness 增加。生产环境还需要权限、回滚、灰度、A/B 与 change-point detection。

未来研究方向：failure cluster 与线上 cohort 统一、因果归因、harness diff 自动验证、multi-model shared harness、shadow traffic、rollback policy，以及“global rule vs per-query adaptive policy”的自动分流。
