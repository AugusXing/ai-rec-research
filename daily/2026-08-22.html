Semantic ID 开始从“生成编码”变成训练监督，
推荐系统进入 Continual Co-adaptation 与 Benchmark Audit

今天对推荐/搜索最强的信号不是又出现一个更大的生成式模型，而是离散语义结构开始反过来监督 Dense Retrieval，Retriever 与 LLM Reranker 开始持续协同更新，评测本身也开始被重新审计。阿里 SSR-GRPO 用 Semantic ID 同时做 Reward、Hard Negative 与 DPO 监督并给出天猫线上 A/B；SCoRD 研究 Retriever–Reranker 在非平稳数据流中的低成本持续适配；Spotify Research 则用极简单的 pairwise probe 证明多个经典序列推荐 benchmark 并不真正需要高阶序列建模。系统侧，ReCache 把 Tool/Skill Schema 变成可独立复用的 KV Asset，FleetSieve 把 LLM Serving 配置搜索改写为 SLO-aware 决策问题。

时间口径与质量控制：主扫描窗口为 2026-08-21 10:00 ～ 2026-08-22 10:00（北京时间）。周六没有新的 arXiv 日更批次，因此本期重点覆盖 2026-08-21 公告批次中前一日日报尚未纳入的高价值工作；这些论文大多于 8 月 20 日 UTC 提交、8 月 21 日进入 recent/new 列表。优先保留推荐、搜索、Agent 与 Serving 中有明确实验或生产证据的工作，避免为了凑数量重复收录。

今日核心结论

  • Semantic ID 正从 Generative Retrieval 的“输出格式”升级为跨范式监督接口。 SSR-GRPO 没有直接用 SID 替代 Dense Retrieval，而是用 SID 的层级结构提供 Reward、Hard Negative、Mask 与 Retrieval-DPO 监督；这条路线比“Dense vs Generative 二选一”更像工业系统的现实演进。
  • Retrieval RL 的关键瓶颈开始从优化器转向 Reward 与 Candidate Quality。 SSR-GRPO 说明，只用 batch 内 Top-K 和相似训练范式的 42B MoE Reward Model 会带来噪声与偏差；更轻的 dense+sparse SID reward 反而能获得更稳定的业务收益。
  • LLM Reranker 的工业问题不是一次训练成本，而是持续更新成本。 SCoRD 把昂贵 LLM Distillation 限制在约 20% 低置信度序列，其他时间依赖可复用 Semantic Assistant 和 Retriever 的稳定表征完成 continual update。
  • “Transformer 赢了”不等于 benchmark 证明了高阶序列建模有效。 Spotify Research 的 PCTM/SeqRules 在 4/5 个经典 benchmark 上击败 eSASRec 或 SASRec；推荐研究必须先做强 pairwise / recency probe，再谈复杂模型收益。
  • LLM 推荐不一定要把协同信号塞进 Prompt。 CoRRe 在 LLM 生成用户意图之后，再通过共购图修正 Item Embedding 的方向、用 Popularity 修正模长，在不做任务训练的情况下获得强结果，说明“Semantic Query + Collaborative Index”是很有工程吸引力的分层方式。
  • Agent Tool Schema 正在变成可缓存、可压缩、可路由的系统资产。 ReCache 通过 Resource-wise Attention 使 Tool/Skill KV 与组合顺序解耦，再做 layer/head 与字段级裁剪，TTFT 加速 3.655×、KV tensor memory 降 92.43%。
  • Serving 优化的对象正在从单个 Kernel 升级到 Fleet Decision。 FleetSieve 不追求把所有 TP×Load 配置都测完，而只测那些可能改变最终 GPU 分配与 SLO 可行域的点。

重点论文 01 · Dense Retrieval / RL / Semantic ID

SSR-GRPO: Integrating Supervision and Semantic IDs into Reinforcement Learning for Dense Retrieval in E-commerce

arXiv:2608.19595 · Alibaba Group · CIKM 2026 · 2026-08-20 提交 / 08-21 公告

今天最值得推荐/搜索工程师精读。它最有价值的地方不是“又把 GRPO 用到 Retrieval”，而是把 Semantic ID 从 Generative Retrieval 的离散 Item 表示，转成 Dense Retriever 的结构化监督信号：SID 同时参与 Reward、Hard Negative Mining、Masking 与 Retrieval-DPO，最后仍然输出可走 ANN 的 Dense Embedding。

1. 背景 / 业务动机

电商搜索的 EBR 需要从十亿级商品中快速召回。LLM Dense Retriever 能增强复杂语义，但传统 InfoNCE/SFT 仍主要依赖正负样本。R-GRPO 进一步把 Retrieval 变成多目标 RL：每个 Query 动态检索 Top-K Item，根据相关性、质量、独家召回价值等 Reward 优化。但工业场景出现两个明显问题：训练 batch 只能看到商品全集很小一部分，Top-K 中混入大量 easy/noisy negative；相关性 Reward 又依赖 TaoSR1 42B-MoE，训练成本高，而且 Reward Model 与 Policy 使用相似 RL 范式，判断可能相关偏置。

2. 技术方案与关键模块

  • Contrastive RQ-VAE Item SID：从预训练 query/item relevance embedding 出发，用共享 RQ-VAE 做 3 层残差量化；除 reconstruction/commitment 外加入 InfoNCE，让被同一 Query 共同召回的 Item 更容易共享 SID 前缀。
  • Generative Query SID：用历史搜索日志，把 click / add-to-cart / purchase Item 的 SID 当 target，训练自回归 LLM 从 Query 生成多个 SID；Beam Search 表达一对多意图。
  • Dual-perspective Reward：Dense 侧用多模态 relevance embedding 的 inner product，Sparse 侧用 Query SID 与 Item SID 的最长公共前缀深度打分（0 / 0.25 / 0.5 / 1.0），二者融合替代重型 LLM relevance judge。
  • 两类 Hard Negative：一类来自“能过 Pre-rank 但最终未曝光”的商业弱样本；另一类与正样本共享前两级 SID、仅最后一级不同，专门训练细粒度语义边界。
  • Mask + R-DPO：Hard Negative 既作为质量阈值过滤 GRPO 中过于简单的 Top-K，又构成 positive-vs-hard-negative pair 做 Retrieval-DPO，显式拉大打分 margin。
  • Dynamic Joint Weight：SID-R-GRPO 与 R-DPO 用 uncertainty-based trainable weights 自动平衡，避免高方差 RL 梯度压过稳定监督梯度。

3. 训练方法

两阶段训练：先用真实 Query–Item 正样本 + in-batch negatives 做 InfoNCE SFT；再进入 SSR-GRPO 联合训练。在线采样阶段将多卡候选汇成更大 batch，再取 Top-K 计算 Reward；GRPO 仍保留 relevance + quality + exclusivity 多目标，但 relevance 改成 dense+sparse SID。与传统 GRPO 的 token-level KL 不同，这里用 InfoNCE 作为语义空间 regularizer，更符合连续向量检索。

4. 推理 / Serving

最终 Serving 仍是 Dense Retrieval：Query / Item 编码成 L2-normalized vector，通过 ANN 做 Top-K。因此 SID 主要存在于训练、Reward 与 Hard-negative pipeline，而不是把线上所有召回都改成自回归生成。这一点非常关键：它保留 EBR 的吞吐和现有索引基础设施，同时吸收 Generative Retrieval 的层级语义结构。论文说明模型已部署到 TmallAPP 大规模搜索。

5. 实验设置与离线指标

工业训练数据来自天猫真实点击/购买日志，基础模型为 Tbstars-3B。离线看 HR@4k / GR@100：StructBERT 的 General HR@4k 为 0.7166，Tbstars-3B SFT 为 0.7872；加入 R-GRPO 后进一步提升，而完整 SSR-GRPO 达到 0.8218 HR@4k / 0.9372 GR@100，Long-tail HR@4k 达 0.5943。从组件消融看，移除 R-DPO 的损失最大，说明“结构化难负例 + pairwise margin”比单纯改 Reward 更关键。

6. 线上 A/B 与业务收益

天猫 App 两周 A/B：相对 Base，R-GRPO 的 UCTCVR +0.38%、GMV +1.01%；SSR-GRPO 达到 UCTCVR +0.99%、GMV +1.40%、Exclusive Impression +0.48%、Goodrate +0.61%。相对已经很强的 R-GRPO，仍有 UCTCVR +0.61%、GMV +0.39%。这是今天论文里最强的工业证据。

7. 优势 / 局限 / 未解决问题

优势：Dense 与 Semantic ID 不再二选一；SID 给 RL 提供更结构化、低成本的 Reward 和负样本空间，而且线上无需承担生成式 Beam Search 成本。局限：SID 本身来自 relevance embedding 与行为日志，可能把既有偏差重新编码；Query SID 还需要额外生成模型和离线维护；层级 prefix 相似是否在不同类目都能稳定代表业务相关性仍需验证。下一步：把 SID 的 uncertainty、freshness、coverage 与版本 churn 纳入 Reward；研究 Dense ANN 与 Generative SID path 的 query-aware hybrid routing。

8. 对推荐/搜索工程落地与技能的启发

推荐/搜索算法工程师值得重点补齐三组能力：Semantic ID / RQ-VAE、Retrieval RL / Preference Optimization、工业 Hard-negative Mining。更重要的是，未来生成式推荐的资产不一定只服务“生成”，离散 ID 也可以成为监督、诊断、索引分桶和策略路由接口。

重点论文 02 · Sequential Recommendation / Evaluation

Do Sequential Recommendation Benchmarks Really Require Higher-Order Sequence Modelling?

arXiv:2608.19833 · Spotify Research 等 · RecSys 2026

这篇论文不是提出更复杂的序列模型，而是质疑一个更基础的问题：我们用来证明 Transformer 有效的 benchmark，真的需要高阶序列建模吗？作者构造不学习高阶 sequence representation 的简单 pairwise capacity probes，在多数经典数据集上反而超过 SASRec/eSASRec。

1. 背景 / 现有问题

Sequential Rec 近几年不断借用 Transformer、LLM、State-space Model，论文通常把 Amazon/Movielens 上 NDCG 的提高归因于“更强的高阶行为依赖建模”。但如果数据本身主要由最近一次/几次 interaction 的 pairwise transition 决定，那么复杂模型胜负可能更多来自优化、recency bias 或容量，而不是它真正学到了高阶组合关系。

2. 方法：把 Benchmark 当成被测对象

作者使用 SeqRules 与新提出的 PCTM 作为 capacity probe。PCTM 没有 item embedding、没有 sequence encoder：历史中的每个 Item 都是一个 expert，模型只估计有方向的 pairwise transition P(next|history item)，结合 Bayesian smoothing、recency decay、加权 log-prob pooling 与 popularity correction。它故意限制表达能力：如果这种模型就能赢，说明 benchmark 本身无法证明高阶 modeling 的价值。

3. 实验与关键数字

使用 eSASRec 完全一致的 full-catalog evaluation、seen-item filtering、无 sampled test negative，并重跑 SASRec/eSASRec。NDCG@10：Beauty eSAS 0.0524 vs PCTM 0.0635；Sports 0.0324 vs SeqRules 0.0371；Toys 0.0533 vs PCTM 0.0738；MovieLens-1M 0.1739 vs PCTM 0.1815。只有 MovieLens-20M 中 eSAS 0.1969 明显高于 PCTM 0.1431。换言之，pairwise envelope 在 Amazon 三个数据集相对 eSAS 高约 14.8%–38.4%，ML-1M 高 4.4%，但 ML-20M 落后 27.3%。

4. Serving / 成本含义

PCTM/SeqRules 不是作者主张直接替换线上 Transformer，而是一个廉价的“必要性测试”：在启动大型长序列模型项目之前先跑 pairwise / recency probe。如果 probe 已接近上限，那么投入长序列训练、KV cache 与 GPU serving 的 ROI 可能很差；反之像 ML-20M 这种明显保留 higher-order gap 的数据，更值得做复杂 sequence model。

5. 优势、局限与下一步

优势：改变的是研究方法论；公开冻结配置、数据构建、复现 hash 与官方代码，极易作为团队 benchmark sanity check。局限：离线公开数据集不代表真实推荐 Feed；pairwise probe 也不能衡量长期满意度、多目标、曝光偏差和在线交互。下一步：建设明确包含 higher-order dependency、long-horizon intent shift、multi-behavior causal structure 的 benchmark，并把“probe gap”作为数据集说明的一部分。

6. 对工程与职业技能的启发

高水平推荐工程师需要的不只是“会搭更大模型”，还要会证明复杂度为什么必要。强 baseline、数据泄漏审计、full-catalog evaluation、sampling bias 与 counterfactual evaluation，会越来越成为比模型结构更稀缺的能力。

重点论文 03 · Continual Recommendation / Retriever-Reranker Distillation

SCoRD: Semantic-Assisted Continual Retriever-Reranker Distillation for LLM-Based Recommendation

arXiv:2608.19998 · CIKM 2026

SCoRD 把一个非常工业化、但公开论文相对少的问题摆到台前：ID Retriever + LLM Reranker 如何在用户兴趣持续变化时共同更新，又不反复支付 LLM 全量推理和蒸馏成本？

1. 业务动机与现有问题

两阶段推荐里，轻 Retriever 负责大规模候选，LLM Reranker 提供更强语义理解。常见做法是把 Reranker knowledge distill 给 Retriever，但 Continual Learning 场景中每来一批新 interaction 就重新跑 LLM、重新蒸馏、再 fine-tune 两边，成本过高；只更新 Retriever 又容易因为模型容量小、增量数据稀疏而跟不上兴趣漂移。

2. 三阶段 Co-adaptation

  • Semantic Reasoning Assistant：在 base block D0 用 LLM 生成并验证用户 latent intent，形成可复用 Dynamic Intent Memory；之后 Assistant 比完整 LLM 更便宜地提供 semantic guidance。
  • Stage 1 · Reranker→Retriever：根据 Retriever confidence 只选 top-r% hardest sequences（实验 r=20）做昂贵 LLM distillation，避免全量知识迁移。
  • Stage 2 · Retriever Continual Update：Assistant 与新的 collaborative signal 一起更新 Retriever；使用 intent-drift-aware negatives，而不是随机负例，专门学习用户兴趣变化。
  • Stage 3 · Retriever→Reranker：把更新后的稳定 Item Representation 与 Intent Drift 信号回流 LLM Reranker；Reranker 只训练 LoRA 与 item prediction layer。

3. 实验设置

Amazon Books、Yelp、Movies & TV 按时间切成 5 个 block：D0 为最早 60% interaction，D1–D4 各 10%；每个增量 block 更新时不可访问旧数据。指标除了 Hit/NDCG，还用 Retained Average 衡量稳定性、Learning Average 衡量可塑性，直接评估 continual learning 的 stability–plasticity trade-off。

4. 离线效果 / 效率

SCoRD 在三数据集的 RA、LA 与 harmonic mean 同时优于 CCD/PISA。效率上更有意思：Book 上 CoT-Rec 的 semantic generation 要 15.4h，SCoRD 只需 1.4h；Yelp 17.6h→1.7h；Movies 5.4h→0.5h，约 9–11× 降低语义生成时间。Book 的 N@5 / H@5 由 CoT-Rec 0.4682 / 0.5132 提升到 0.5088 / 0.5846。代价是 SCoRD 的常规训练时间更长，但 inference time 基本不变。

5. 关键消融

Book 上移除 Semantic Assistant 会造成最大下降之一；把 intent-drift hard negative 换成 random negative 的下降尤其明显，Reranker N@5 从 0.5088 降到 0.3549。这说明 continual rec 的核心不是“再训一次”，而是显式找出哪里发生了兴趣漂移、哪些样本最值得付 LLM 成本。

6. Serving、局限与未来

论文没有线上 A/B，Serving 侧保持原 Retriever/Reranker pipeline，主要把成本从 recurrent LLM generation 移到少量 hard sequence distillation + reusable assistant。局限是公开数据规模和生产负载差距较大，Dynamic Intent Memory 的 stale/错误积累、删除与隐私治理尚未展开。下一步值得研究基于线上 uncertainty / value 的 distillation router，以及 Memory freshness 与 retriever index refresh 联动。

7. 对工程与技能的启发

当 LLM 进入推荐系统，真正的长期成本会从“第一次训多贵”变成每天更新多贵。需要掌握 Continual Learning、Teacher–Student distillation、drift detection、hard-example routing 与 incremental index/update pipeline。

重点论文 04 · Agent Serving / KV Cache

ReCache: Efficient KV Cache Reuse and Compression for Tool-Augmented LLM Agents

arXiv:2608.19662 · SJTU / EIT / XJTU · 官方开源

Agent Prompt 中的 Tool/Skill Schema 会跨请求反复出现，但每次组合与顺序不同，传统 prefix cache 很难命中。ReCache 的核心是：让每个 Resource 自己形成与组合顺序无关的 KV block，然后只在真正有贡献的 layer/head/field 上让模型看到它。

1. 技术方案

  • Resource-wise Attention：不同 Tool/Skill Resource 之间不互相 attention，每个 Resource 的 position 从局部 0 开始，因此 KV representation 不依赖它在 Prompt 中的全局位置或邻居。
  • Structural Pruning：用对 invocation loss 的边际贡献，而不是 attention mass，评估 layer × KV-head-group route；只有高贡献 route 能访问 resource KV。
  • Semantic Pruning：Schema 不按普通文本压缩，而保留 resource name、argument name、argument description 和末尾 suffix token，避免工具名/参数名被压掉导致调用失败。

2. 训练与评测

Resource-wise Attention 改变了标准 attention pattern，因此作者用轻量 fine-tuning 适配。统一 benchmark 汇总 ToolACE、APIGEN、ToolMind、ToolRet、Toucan、SkillRouter、WildToolBench 七个数据源，并专门构建 resource-disjoint OOD split，避免模型只是记住 API 名称。

3. 推理 / Serving 收益

Resource-wise Attention 的 Invocation F1 为 82.3%，几乎等于 Dense baseline 的 82.4%，但 TTFT 提升 3.655×。完整 ReCache 把 allocated KV tensor memory 降低 92.43%，attention 加速 1.423×；随着 Resource 变长，TTFT/TPOT/attention latency 基本保持稳定，并把 KV tensor memory 控制在约 0.03 GiB。

4. 与主流方法的差异

Prefix Cache 要求相同前缀；CacheBlend/KVLink 一类方法尝试位置校正或局部重算；ReCache 更激进地改变建模假设：对工具调用而言，Resource 内部语义比 Resource 之间的相对顺序更重要，因此直接构造 composition-invariant cache。它特别适合大量动态检索 Tool/Skill 的 Agent，而不是所有自然语言 Context。

5. 局限与未来

Resource 之间真的“几乎独立”在复杂组合工具、共享参数约束、workflow dependency 中可能失效；轻量 fine-tuning 也意味着无法直接无损套到任意 closed model。下一步值得做 Tool Dependency Graph-aware cache、Schema version invalidation、cache provenance，以及与 Tool Retriever / Router 联动的端到端 Cost Policy。

6. 对推荐/搜索的迁移

这套思想对推荐 Agent 很直接：Experiment Skill、Feature Query、Recall Strategy、Policy Schema 都可变成可版本化 KV Asset，而不是每个请求重新 prefill；再结合前一日的 PolicyGuide/PILOT，就能形成“Resource Retrieval → KV Asset Reuse → Workflow Control”的 Agent Runtime。

重点论文 05 · Training-free Recommendation / Semantic + Collaborative Retrieval

CoRRe: Training-Free LLM-Based Recommendation with Post-LLM Item Refinement Using Collaborative Signals

arXiv:2608.19665 · KAIST / Snap 等 · CIKM 2026 Short · 官方开源

CoRRe 提供一个很“工程化”的反直觉：不要让 LLM 自己吞掉所有协同历史，也不要只在 LLM 前做 RAG；让 LLM 负责把用户历史压成 semantic profile，协同信号则直接改造 Item Index。

1. 方案

LLM 根据 interaction history 生成用户 profile，再用 text encoder 得到 Query Embedding；Item title 也编码成 semantic embedding。随后做两步无需训练的 refinement：Direction Refinement 在 item–item co-purchase graph 上传播表示，再与原 semantic vector 混合；Magnitude Refinement 用 item popularity 的幂次缩放向量范数。最终仍用 dot-product retrieval。

2. 实验

Amazon Sports/Toys/Beauty，各随机抽 1000 用户，leave-one-out，报告 H/NDCG@10/20。LLM-based 方法统一用 GPT-5.2 + text-embedding-3-large。CoRRe 在所有 training-free baseline 设置上取胜，最高相对最强 training-free baseline 提升 132.43%；Sports/Toys 还优于所有 training-based comparison，Beauty 排第二。Magnitude refinement 的影响尤其大，例如 Sports H@10 从去掉该模块的 0.0220 提升到完整模型约 0.0453。

3. Serving 与成本

没有任务级参数训练，主要成本在 LLM profile generation、离线 item graph propagation 与 embedding index；Item refinement 可以离线物化，在线只需 Query Embedding + ANN。相比“LLM rerank top-K”，这更容易扩到大候选池。

4. 局限 / 下一步

实验只抽样 1000 用户，且 GPT-5.2 profile generation 的真实成本没有工业 A/B；Popularity norm calibration 可能加剧 head bias，co-purchase graph 也有 exposure bias。下一步值得把 popularity 换成 uncertainty/calibrated prior，支持 temporal graph、cold item 与多行为图，并评估 profile cache freshness。

5. 工程启发

它把推荐系统重新拆成两个互补空间：LLM 负责 Query/User Semantic，Collaborative System 负责 Index Geometry。这比把所有 ID/协同信息硬塞进 Prompt 更容易维护，也与 Foundation Embedding Store 的工业路线兼容。

重点论文 06 · Agentic Search / Benchmark

Projecting BrowseComp-Plus onto ClimbMix: Toward More Realistic Corpora for Agentic Search

arXiv:2608.20317 · University of Waterloo / Castorini 等 · 官方开源

Agentic Search benchmark 经常看起来很难，但 Retriever 其实面对的是为每道题人工拼出的 10 万级 corpus。本文把 BrowseComp-Plus 的问题重新投影到 NVIDIA ClimbMix：400B tokens、5.53 亿文档、与 benchmark 无关构建的真实 Web mixture。

1. 为什么重要

BrowseComp-Plus 原来已经比 opaque Web Search 更可控，但 corpus 由题目 supporting docs + query-specific hard negatives 构成，Evidence 与 Distractor 都和题目绑定。Agent 可能在一个“为考试准备的索引”里搜索，而不是面对真实开放语料。

2. 投影方法

Pipeline 将问题拆成 atomic reasoning hops，然后在 ClimbMix 中逐 hop grounding；只有 automatic verifier、独立 Agent 和 human review 都确认每一 hop 有证据时才保留。830 个原测试问题最终留下 57 个 fully-grounded 问题，并提供 question-level relevance judgment。

3. 结果

换到真实大语料后，最强 Agent 的 Answer Accuracy 只下降约 5 points，但Evidence Recall 从 84.3% 暴跌到 21.4%，同时 Search Calls 增加 63%。这揭示一个很关键的错觉：最终 Answer Score 可能掩盖 Retrieval 极度脆弱，LLM 依靠先验/猜测也能答对一部分。

4. 对搜索/推荐的启发

Agentic Search 评估应该拆开 Retriever、Planner、Reader，并在“非为任务构建”的大索引上测 evidence recall、search budget 和 failure attribution。对推荐 Agent 同样如此：不能只看最终 GMV/成功率，还要测候选覆盖、工具选择、证据链与成本。

重点论文 07 · LLM Serving / Fleet Configuration

FleetSieve: Decision-Critical Profiling for SLO-Aware LLM Fleet Configuration

arXiv:2608.19659 · 2026-08-20

很多 Serving 团队会离线穷举 Tensor Parallel degree × Replica × Load，再选配置。FleetSieve 的思想是：Profiling 的目标不是把性能曲面测准，而是把最终资源决策做对。

1. 问题与方法

TP 增大并不保证吞吐/尾延迟单调变好，负载变化也会让最优配置翻转。FleetSieve 同时建模 capacity 与 tail latency，维护 conservative / optimistic 两套 fleet allocation；只测量那些最可能缩小两者决策差距的配置，当剩余 decision gap 低于 tolerance 就停止。

2. 实验 / 成本

在 H100 固定测量网格、31B open-weight model 上，FleetSieve 用 22,200 GPU-seconds 得到与 oracle 相同的 aggregate allocation，比 fixed comparison 的 uniform random profiling 少 6.9%；200 个 random reveal order 平均节省 5.4%（95% bootstrap CI 3.5–7.2%）。Chat workload 固定比较节省达 21.5%。更重要的是，joint capacity+tail modeling 避免选择 completion p99=46.4s、违反 30s SLO 的配置。

3. 工业启发

这类方法与推荐的 Runtime Routing 很像：我们真正关心的不是离线预测所有配置精确到小数点，而是“这个样本是否会改变决策”。同样思路可迁移到 Model Router profiling、ANN index 参数、sequence length、precision、batch size、GPU allocation 的主动测量。

4. 局限 / 下一步

当前实验主要是一个 31B 模型与固定 H100 网格，节省幅度依 workload 而变，Code workload 并非最省。后续需要跨模型、异构 GPU、preemption、动态价格与故障率，并把 profiling uncertainty 直接接到在线 autoscaler。
