从“优化模型”到“优化系统如何优化自己”

过去 24 小时最值得关注的一批工作集中在 8 月 27 日新提交论文。今天最强的信号不是又出现了一个更大的推荐模型，而是推荐 / 搜索系统的控制对象正在被学习化：阿里 Astar 直接学习“下一步算法应该改什么”，把历史 Git commit、实验曲线和 Reward Model 变成自动演进闭环；工业级 GNN 工作把 194M 用户、28B 边图上的 ID 表和时间采样成本压到可生产化；ProRetrieval 让 LLM 生成可执行检索程序而不是只改写 query；CoVeMem 把 Agent Memory 从文字摘要变成可训练的协同向量状态；MaskRec 则证明统一 Backbone 的关键不是全连接 Attention，而是显式控制信息拓扑。下一阶段的核心竞争力，会从“更强单模型”转向 Evolution / Retrieval / Memory / Topology 等可学习控制面。

今日核心结论：① 算法研发闭环本身开始模型化：Astar 用工业迭代历史学习 evolution direction，在 Lazada 广告连续自动迭代 20 次，线上 GMV +4.86%、广告收入 +1.82%。② 大规模图推荐真正的瓶颈是系统结构：Multi-hash 将 ID 表从约 203GB 压到 2GB，时间采样由线性扫描改为二分定位，线上推荐好友新增 +16%。③ Search Agent 的 action space 正从“搜什么”升级到“如何编排检索算子”：ProRetrieval 生成 SQL × 文本向量 × 图像向量的可执行 DSL。④ Agent Memory 不应只是一段自然语言：CoVeMem 用协同图状态作为 soft token，19/20 指标不弱于最强文本记忆 Agent。⑤ 统一推荐 Backbone ≠ 无结构全连接：MaskRec 用 TopoMask + Candidate-conditioned DualQ 控制跨域信息流，腾讯广告比赛数据 Test AUC 0.824902→0.834640。

01 · Self-Evolving Industrial AI / Ads · 今日精读

Astar：推荐算法研发本身，开始变成一个可训练的 Optimization Problem

Research Impact Score / 研究价值 9.9/10工业成熟度 ★★★★★创新性 ★★★★★与你方向的相关度 ★★★★★是否官方开源 否 / 未发现是否有线上 A/B 是阅读优先级 最高

背景 / 业务动机

工业推荐系统的真实进步来自连续迭代，而不是一次模型设计：提出优化方向 → 改代码 → 训练 → 评估。后 3 步已越来越能被 Coding Agent、训练平台和自动评估接管，但“下一步到底该改什么”仍依赖资深算法工程师。通用 LLM 看起来懂大量论文，却缺少某一业务模型多年实验积累出的隐性经验；论文甚至报告强通用模型提出的方向与系统真实瓶颈经常错位。Astar 的核心问题因此不是代码生成，而是：能否把一个推荐系统过去所有成功/失败实验，训练成会提出下一轮有效算法方向的模型？

现有问题

作者把困难拆成四类：历史 commit 数量通常只有数百，监督稀疏；commit 混有日志、重构、环境参数等大量无效改动；“模型结构 / loss / optimizer / data / feature”等方向空间巨大；真正执行一次 proposal 需要代码、训练、验证，反馈可能延迟数小时到数天。直接 RAG 历史实验只能让 LLM 记忆旧尝试，并不能稳定形成可泛化的“算法演进规律”。

技术方案与关键模块

Evolutionary Corpus 是最值得复用的部分。Astar 不只把相邻两个 commit 当样本，而是在同一实验序列里构造任意版本对，用完整 loss curve 判断哪个版本更好，把数百条顺序记录展开为近二次规模的 state→direction 监督。随后做两级去噪：代码层用 call-graph reachability、AST normalization、配置白名单只保留真正改变执行逻辑的 delta；语义层再由 LLM 把改动归为三级 Hierarchical Hints（粗方向→细动作→具体方案），无法解释为有效 evolution intent 的样本丢弃。输入还包含数据规模、特征维度和当前代码/模型摘要，避免只看 diff 猜方向。

Reward Model 则把昂贵的真实训练验证代理成秒级评分。它学习一个 proposal 是否能让历史 loss trajectory 变好，在推理阶段先让 Astar 生成多个方向，再由 RM 排序，真正执行最有希望的少数候选。

训练方法

作者基于 Qwen3 训练 0.6B / 4B / 8B 三档模型。第一阶段 Mid-training 在 112B evolution tokens 上做 NTP，让模型内化算法迭代语言与三级 hint 结构；第二阶段 SFT 只保留 loss 最终值、末段均值与稳定性综合指标更优的 positive pair，共约 81.1M token；第三阶段 RL 用 Reward Model 作为快速 evaluator，以 GRPO 提高对历史未出现方向的探索能力。这里的关键不是“用了 GRPO”，而是先把不可承受的真实训练 reward 蒸馏成 surrogate reward，才让 evolution search 变得可迭代。

推理 / Serving 方案

Astar 不在用户请求路径 Serving，而运行在算法研发控制平面：读取当前系统状态 → 生成若干 evolution direction → Reward Model 秒级打分 → Agent/工程流水线实现代码 → 训练与离线评估 → 结果写回历史，再进入下一轮。这样将传统“算法工程师每周提出 1–2 个方向”的流程，变成可以连续执行的实验搜索循环。

实验设置 / 离线指标 / 线上 A/B

Astar-8B 的真实执行 single-proposal success rate 达 0.6786，人类专家为 0.3229，最强通用 LLM 为 0.3071；Astar-Reward-8B 预测 proposal 是否有效的 AUC 为 0.8487，明显高于人工打分 0.6142 和通用 LLM。最重要的是 Lazada 广告召回模型上的闭环实验：系统连续自动运行 20 次迭代 / 2 周，Hitrate@200 累计 +23.6%；线上 A/B 相对提升 GMV +4.86%、广告收入 +1.82%、点击 +0.84%、订单 +1.79%。

效率 / 成本收益

真实 proposal 的验证成本从“每个候选都训练几天”变成“RM 先用秒级预测筛掉大多数方向”，将 GPU 成本集中到 top candidates。更深层收益是把组织隐性知识从“少数资深工程师脑中”转为可持续训练的 data asset：实验日志、代码 diff、loss curve 不再只是归档，而是下一代算法的训练集。

与现有主流方法的优劣势 / 适用场景

相比 AutoML / HPO，Astar 的 action space 不是固定超参，而能提出模块、loss、优化器、数据等开放式变更；相比通用 Coding Agent，它不是凭语言知识猜，而是训练在该系统自己的 evolution history 上。代价是高度依赖高质量实验记录、统一可比较的 metric 以及自动化训练平台，且 Reward Model 一旦偏置，会把整个研发搜索引向局部最优。

局限 / 尚未解决的问题 / 未来研究方向

论文目前只证明在一个成熟广告召回系统的强效果，跨业务迁移能力仍未知；Pairwise expansion 产生的样本也并非统计独立；loss 改善与长期业务目标可能不完全一致。更值得研究的是：多目标线上价值作为 evolution reward、失败实验的 counterfactual 利用、跨模型/跨业务 transferable evolution skill、以及让 proposal model 同时优化收益 / 延迟 / GPU 成本 / 稳定性。

对推荐 / 搜索算法工程落地和职业技能的启发

未来高级推荐算法工程师的重要能力会从“亲自试很多模型”转向设计可自我演进的实验系统：规范实验元数据、保留可比较的完整曲线、构建 proposal taxonomy、Reward Model、自动代码/训练/评估闭环。谁能把团队过去三年的 A/B 与 commit 历史变成训练数据，谁就可能拥有真正难复制的 Algorithm Agent。

02 · Graph Recommendation / Scaling · 今日精读

194M 用户 × 28B 边的 GNN：决定工业可行性的不是新 Conv，而是 ID Memory 与 Temporal Sampler

Research Impact Score / 研究价值 9.8/10工业成熟度 ★★★★★创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 是是否有线上 A/B 是阅读优先级 最高

背景 / 业务动机

好友推荐天然依赖多跳社交图，但在 1.94 亿用户、280 亿边上直接部署 message-passing GNN，会遇到两个比模型结构更硬的问题：每个用户一行 256d trainable ID embedding 约需 203GB；时间正确的邻居采样若扫描完整 adjacency，对拥有数万好友的高 degree 用户几乎不可用。

现有问题

丢掉 ID embedding 会失去协同个性化；完整表又难以训练和 Serving。非时间采样把预测时点之后形成的好友边泄漏进训练，离线 AUC 看似更好却不可信；朴素 temporal sampler 为每个节点顺序扫描邻居，随着 degree 增长线性变慢。在线现算多跳图同样无法进入 ranker latency budget。

技术方案与关键模块

Multi-hash ID Embedding 让每个用户由多个哈希槽组合表示，所有用户共享小型表：生产配置仅 2GB，相比 202.88GB full table 缩小超过 98%，而 Features + Multi-hash 的 ROC-AUC 0.6278 甚至略高于 full table 0.6246。Temporal Neighbor Sampling 把每个节点邻接边按 timestamp 排序并存入 CSR；给定 cutoff 先二分找到合法边界，再采 k 个邻居，复杂度从 O(deg+k) 降到 O(log deg+k)。训练系统把 CPU sampler 与 GPU trainer 解耦，用有界队列吸收采样 / GPU 的速率差。

训练方法

图与交互日志分离存储；CPU 构建带时间约束的多层 sampled blocks，PyTorch + DGL/GraphBolt GPU trainer 训练。8×A100 80GB 单机下，CSR 图放 CPU，Multi-hash 表和参数放 GPU。Temporal binary-search sampler 每 batch 595ms，几乎等于不做时间约束的 581ms，而朴素 scan 需要 1473ms。

推理 / Serving 方案

作者明确不在请求时展开 ego graph，而是离线计算全部 194M 用户 GNN embedding，固定周期刷新，再把 GNN score / embedding 作为在线 ranker feature。全量 embedding 计算约 6.57h，因此换来线上 p50/p90/p99 无显著回归。这个设计揭示了工业图推荐的真实 trade-off：把图结构计算前移，换 Serving latency；代价是 freshness。

实验设置 / 离线指标 / 线上 A/B

离线 per-user ROC-AUC：Top-pop 0.5050、MF 0.5316、旧生产 WalkGNN 0.5572、本文系统 0.6278。关闭 temporal sampling 后 AUC 仅 0.5907，说明时间泄漏影响巨大。两周线上 A/B：推荐带来的好友新增 +16.0%、发生好友新增的独立用户 +11.5%、内容 Feed 总时长 +0.28%，ranker 延迟无回归。

效率 / 成本收益

生产配置 Graph CSR 约 225GB CPU memory，但可训练 ID 表只有 2GB；全部模型参数 + Adam 约 6.03GB。训练收敛约 63h。相比在线 per-pair ego graph，离线 embedding 让 ranker 路径变成廉价特征读取 / 内积，系统复杂度大幅降低。

与主流方法的优劣势 / 适用场景

优势在于真正覆盖全图 multi-hop 结构，又避免 full-ID table 与在线子图构建。适合好友、关注、企业关系等图变化相对慢且 topology 信号强的推荐；对短视频 session interest 等分钟级变化业务，固定周期 embedding 会过时，序列模型或 continuous memory 更合适。

局限 / 尚未解决的问题 / 未来研究方向

新用户在当前 graph snapshot 没有邻边，只能靠特征与 hash collision fallback；固定刷新形成 cold window；multi-hash 在 hetero graph 上也未必适合所有 node type。值得研究 Online/Incremental GNN state、动态图 memory、图 embedding 与序列 state 的双通道融合，以及“多快刷新一次最划算”的 compute-value routing。

对推荐 / 搜索算法工程落地和职业技能的启发

大规模推荐里的很多“模型问题”其实是数据结构问题。掌握 CSR、temporal sampling、hash embedding、CPU/GPU pipeline、offline/online split，比再记一个 GNN 变体更接近工业核心。尤其要学会检查 temporal leakage，它在图、序列、特征回填中都可能让离线收益失真。

03 · Agentic Search / Hybrid Retrieval · 今日精读

ProRetrieval：搜索 Agent 的下一步不是“更会写 Query”，而是会生成可执行 Retrieval Program

Research Impact Score / 研究价值 9.7/10工业成熟度 ★★★☆☆创新性 ★★★★★与你方向的相关度 ★★★★★是否官方开源 是 / 匿名代码与数据是否有线上 A/B 否阅读优先级 最高

背景 / 业务动机

真实电商搜索往往同时包含“价格低于 100”“必须是某品牌”“语义上适合露营”“图片风格像这个”等条件，并带 AND / OR / NOT 嵌套。RRF、Self-query Retriever 或单后端 Search-R1 都把检索组合逻辑固定在系统外部，LLM 最多决定 query 文本，不能决定哪部分条件走 SQL、哪部分走 text ANN、哪部分走 image ANN、返回集合如何做布尔组合。

现有问题

单向量检索难保证结构化硬约束；Text-to-SQL 无法表达视觉/语义近邻；固定融合无法适应不同 query 的组合逻辑；让大商业 LLM few-shot 直接写复杂 DSL 虽语法基本正确，但组合策略并不稳定。真正缺少的是可学习的 heterogeneous retrieval action space。

技术方案与关键模块

ProRetrieval 定义一个 Hybrid DSL：结构字段由 SQL predicate 处理，文本和图像语义条件生成 vector-retrieval primitive；每个向量算子先返回 Top-20 IDs，再替换 SQL 中的 placeholder，由 relational engine 完成最终 AND/OR/NOT 逻辑。这使“检索规划”成为可执行程序，而不是自然语言 reasoning trace。DSL 严格包含纯 RRF、self-query、text-to-SQL 等更简单 action space。

训练方法

先自动构造两套 benchmark：Amazon 商品和 Enron 邮件，每域 20k train / 3k test，query 分 L1 单条件、L2 2–3 条件、L3 4–5 条件带嵌套。Qwen3-4B/8B 先用 gold NL→DSL 做 SFT，4B 再做 GRPO / DAPO。Reward 分层覆盖格式、能否执行、最终结果正确性和长度；Text/Image encoder 固定为 Qwen3-Embedding-8B 与 Qwen3-VL-Embedding-8B。一个很重要的结果是：Full DSL 用 SFT 只有 0.680 Hit@1，甚至低于 SQL+Text 的 0.752；RL 才把复杂 action space 真正学会。

推理 / Serving 方案

LLM 先生成一个短 DSL；执行器并发调用 text/image ANN，把候选 ID 注入 SQL，再由数据库完成逻辑融合。论文在单 RTX 4090 上报告端到端约 50ms/query，其中约 80% 时间花在向量检索，而不是 LLM program generation。工程含义很明确：一旦控制语言足够短，Agentic Search 的主要成本重新回到 backend retrieval。

实验设置 / 离线指标 / 线上 A/B

电商 Hit@1：BGE-Reranker 0.618、RankGPT 0.768、GPT-5.5 0.693、4B GRPO 0.809、4B DAPO 0.808、8B SFT 0.820；邮件上 DAPO 0.909，GPT-5.5 0.855。4B GRPO 相对 SFT +12.9pp、相对 GPT-5.5 +11.6pp。图像条件尤其体现 RL 价值：Full-DSL SFT 0.323 → GRPO 0.716。OOD query 的性能下降总体控制在 3pp 内，DSL 执行成功率 >99%。当前没有生产线上 A/B。

效率 / 成本收益

4B RL 模型能超过大闭源模型，说明专门训练“工具编排技能”可能比无止境提升 backbone 更划算；SQL 与 ANN 解耦后，各 backend 可以独立换索引、量化或 cache。更重要的是，复杂 query 不必每次都走所有检索器，未来可以让 program 本身承担 cost-aware routing。

与主流方法的优劣势 / 适用场景

相比 RAG 常见的 query rewrite + dense retrieval，ProRetrieval 的优势是硬条件可验证、跨模态组合可表达、程序可审计；相比端到端 LLM rerank，候选生成阶段更早利用结构约束。适合商品、招聘、房产、企业知识库等同时有 schema 与多模态内容的搜索。缺点是要维护 DSL、数据库 schema 和多个 ANN backend，真实用户 query 的噪声也比合成 benchmark 更复杂。

局限 / 尚未解决的问题 / 未来研究方向

Benchmark 大量由规则 + LLM 自动构造，距真实搜索日志仍有 domain gap；当前 program 没有显式优化 monetary/latency cost，也没有在线纠错。下一步很值得做：Cost-aware Retrieval Program、执行失败自修复、多轮 program refinement、业务日志上的 preference RL，以及把 candidate generation / rerank / RAG evidence selection 统一进一个 typed action language。

对推荐 / 搜索算法工程落地和职业技能的启发

搜索算法工程师需要开始把 SQL、ANN、过滤、Rerank 看成 Agent 的可组合算子，而不是固定 pipeline。未来很重要的技能是设计受约束 DSL、verifiable reward、execution sandbox 和 backend latency model：你不是只训练一个 retriever，而是在训练一个“会调用检索系统”的 policy。

04 · Agentic Recommendation / Memory · 今日精读

CoVeMem：当 Agent Memory 开始“吃梯度”，推荐记忆就不再等于一段用户画像文字

Research Impact Score / 研究价值 9.5/10工业成熟度 ★★★☆☆创新性 ★★★★★与你方向的相关度 ★★★★★是否官方开源 否 / 未确认是否有线上 A/B 否阅读优先级 最高

背景 / 业务动机

Agentic Recommender 常把用户记忆写成自然语言 profile：看了什么、喜欢什么、最近意图是什么。它可解释，但有两个结构性缺陷：每次交互更新文字需要额外 LLM call；更严重的是，协同过滤里最有价值的“哪些用户共同喜欢哪些 item”很难完整序列化为短文本。CoVeMem 的观点很直接：文本适合解释，向量更适合保存 population-level collaborative evidence。

现有问题

纯文本 memory 会压掉图结构信息，且不断 summarize 会产生信息损失和 token/LLM 成本；直接把 LightGCN embedding 塞给 LLM 又存在 representation gap——LLM 不知道这些连续向量该怎样解释。还要避免候选 item 在训练时泄漏进 memory retrieval。

技术方案与关键模块

CoVeMem 保留一个很轻的静态文字 profile，同时用 LightGCN 在 train-only interaction graph 上学习每用户 / 每 item 的 64d state，训练完冻结成 Collaborative Vector Memory Bank。每次决策用候选 item centroid 去用户历史状态中检索 Top-5 最相关 item，而不是机械取最近 5 条；这些 state 经 gated projector 映射到 LLM embedding space，作为 user/item/history soft tokens 注入 prompt。一个共享 LoRA + projector 学会“如何读这些向量记忆”。

训练方法

LightGCN 三层、BPR 训练 50 epochs；Reader 使用 rank-4 LoRA，另做 semantic alignment，让 collaborative state 对齐 item semantic anchor，并通过 candidate-title masking 的 co-training 强迫模型真正依赖 soft token。训练历史严格使用 causal prefix，避免 target leakage。最终不是生成排名文本，而是逐候选的 Yes/No logit readout。

推理 / Serving 方案

Memory bank 与文字 profile 都离线持久化，不需要每次交互调用 LLM 重写。请求时只做若干向量点积选 Top-K history state，映射成 soft tokens。候选采用 pointwise prompt 并行打分，直接读取“Yes”token logit，无需生成和解析 list。与常见 Agent 排序相比，这把决策路径从 generative parsing 改成更稳定的 discriminative readout。

实验设置 / 离线指标 / 线上 A/B

在 Books、Goodreads、MovieTV、Yelp 四个 instruction-grounded benchmark 上，每个 test case 排 10 个候选。CoVeMem 与最强文本协同记忆 Agent MemRec 比较，在 20 个 metric cells 中 19 个持平或更优。例如 MovieTV Hit@1：MemRec 0.5371 → CoVeMem 0.5799；Yelp 0.5173 → 0.5400。论文没有生产线上 A/B。

效率 / 成本收益

最大收益来自 memory maintenance：协同图 state 训练一次、离线持久化，不需要按交互做 LLM rewrite；每次决策只增加少量 soft tokens 和向量检索。对大规模 Agentic Rec 来说，这比“所有记忆都写成人话”更接近可扩展架构。

与主流方法的优劣势 / 适用场景

相比 text-memory Agent，CoVeMem 协同信号更完整、维护便宜；相比传统 LightGCN，它又能结合 instruction 和文字 preference。最适合候选集较小、用户协同行为丰富、同时需要自然语言指令的 Agentic ranking。若 item/user 高频新增，冻结 graph bank 的 freshness 会成为问题；大候选规模 pointwise LLM 也仍昂贵。

局限 / 尚未解决的问题 / 未来研究方向

目前协同 state 依赖静态 LightGCN，Memory 本身虽然“可训练”，但部署后不持续更新；benchmark candidate=10，与工业百/千候选差距较大。下一步应探索 streaming vector memory、分层 ANN memory retrieval、soft-token 与 structured state 的统一接口，以及把 Agent memory 直接共享给召回 / 精排 / 重排。

对推荐 / 搜索算法工程落地和职业技能的启发

Agent Memory 不应被理解成 Prompt Engineering。推荐工程真正需要的是 State Store + Retriever + Reader + Update Policy。学习序列模型、CF embedding、向量检索和 LLM adapter 的交叉设计，会比只会写“用户记忆摘要 prompt”更有长期价值。

05 · CVR / Unified Ranking Backbone · 今日精读

MaskRec：统一 Feature Interaction 与多域序列，不代表让所有 Token 彼此自由 Attention

Research Impact Score / 研究价值 9.4/10工业成熟度 ★★★★☆创新性 ★★★★☆与你方向的相关度 ★★★★★是否官方开源 否 / 未发现是否有线上 A/B 否阅读优先级 最高

背景 / 业务动机

工业 CVR/CTR 模型长期把非序列 feature interaction 与用户行为 sequence 分成不同子网络，再在高层融合。Foundation-style ranking 想把它们都 token 化进同一个 Transformer，但 naive all-to-all self-attention 会让无关 domain 相互污染，破坏每类信息自己的结构。MaskRec 提出一个很值得关注的中间答案：共享 Backbone，但不共享所有信息通路。

现有问题

Separate tower 的问题是跨特征 / 序列交互太晚；完全统一 token stream 又缺乏工业先验：不同 domain sequence 不一定应该直接互看，用户侧和候选侧也需要 candidate-aware interaction，而不是等若干 Transformer layer 自己学出来。

技术方案与关键模块

所有非序列 feature、各 domain behavior sequence、context、global/domain memory token 都进入 Unified Token Space。TopoMask 显式定义每种 token 的 Query-Key 允许矩阵：同源局部建模允许，无关行为域直接连接阻断，跨源信息由 global/domain memory token 聚合。DualQ 在进入 backbone 前就让 user tokens 与 candidate-item/context 做双向 cross-attention，再通过 FiLM 生成 domain-conditioned interaction query。这样 candidate-aware 信号不是被动等待 full attention 学出，而是作为结构化 token 提前注入。

训练方法

多个 MaskRec Block 均为 TopoMask Attention + FFN；最终聚合 global memory、domain memory 和 enhanced query token，经 MLP + sigmoid 预测 post-click conversion，loss 仍是标准 BCE。它的创新恰恰说明：在成熟工业任务里，主要收益未必来自新 loss，而可能来自更正确的 information-routing inductive bias。

推理 / Serving 方案

论文来自腾讯广告算法比赛场景，重点报告离线/平台测试，没有生产 Serving 延迟数据。结构上所有信号一次 forward 进入共享 Backbone，相比“多个 sequence encoder + feature interaction net + late fusion”更容易统一加速；但 structured mask 的 kernel efficiency、token count 与 memory token 容量仍需真实线上验证。

实验设置 / 离线指标 / 线上 A/B

腾讯广告算法大赛 post-click CVR 数据，second-stage train 按 0.9/0.1 划分。HyFormer-style baseline Val/Test AUC 为 0.831827 / 0.824902；MaskRec 达 0.841253 / 0.834640。去掉 DualQ，Test AUC 降至 0.833665；把 dense features 全压成单 token 更明显降到 0.825470，说明“token 化”也要保留字段内部结构。当前没有线上 A/B。

效率 / 成本收益

统一 Backbone 减少多套异构模块和跨模块 feature materialization，但论文未给 FLOPs/latency 的绝对成本。Memory token 从 32/8 减到 16/4 几乎不掉点，提示实际 Serving 可以用容量压缩换吞吐。

与主流方法的优劣势 / 适用场景

相对 DIN/DIEN + DNN/DeepFM 式分模块架构，MaskRec 的 cross-source interaction 更早且统一；相对无约束 Transformer，它显式保留 domain topology，更适合广告、电商多行为域 CVR。缺点是 topology 仍由人设计，换业务需要重新定义 allowed edges；若真实最优交互超出 mask，结构先验也会限制模型。

局限 / 尚未解决的问题 / 未来研究方向

最大空白是线上 Serving 与自动 topology learning。值得继续押注：可学习 sparse mask、按 request 动态拓扑、跨阶段共享 token graph，以及让 attention connectivity 本身接受 latency regularization。长期看，Ranking Foundation Model 很可能不是“一个全连接大 Transformer”，而是一套按业务结构动态路由的信息网络。

对推荐 / 搜索算法工程落地和职业技能的启发

做统一推荐模型时，优先画“哪些信息应该互相看”的拓扑图，再决定 Transformer 结构。Candidate-aware query、memory token、domain mask 这些设计比盲目增加 hidden size 更接近线上收益来源。对精排工程师，信息路由设计会成为新一代 feature crossing。
