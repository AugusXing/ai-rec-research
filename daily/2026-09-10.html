今天的主线：从“统一模型”继续前进到“任务感知 Backbone + 自适应计算边界”

今日最值得看

🥇 MORE · Task-aware Unified Ranking Backbone

把 MMoE/PLE 一类“backbone 后多任务”问题往前推进：Shared / Private Anchor Tokens 跨层持续存在，让每个任务从行为序列中读取不同信息。更关键的是有真实线上 A/B、生产部署和约 30% latency reduction。

🥈 SLOWeave · Deadline-aware Prefill

固定 chunk size 本质上把吞吐与 inter-token latency 的取舍写死。SLOWeave 每个 iteration 在线求“在不击穿最早 decode deadline 下最大的 prefill chunk”，25ms TPOT 下 mixed / long-context goodput 分别提升 39% / 38%。

🥉 Elastic Horizon · Agent RL

不是继续问“horizon 如何越扩越大”，而是识别 effective interaction frontier。用成功轨迹长度 P90 做闭环控制，在 AppWorld / BFCL 上同时提升成功率并节省最多 25% per-step trajectory tokens。

技术趋势

Multi-task moves into the backbone

统一 ranker 若只在末端挂 task tower，会先把不同任务需要的证据压成同一个 shared representation。MORE 把 task-aware sequence reading 与 feature mixing 提前到每层。

Static budgets become controllers

prefill chunk、Agent horizon、multi-agent graph 都开始从固定超参变成根据 runtime / task state 动态决定的控制变量。

Evidence beats generated summaries

EdgeMem 的信号与此前 AtomRec 相呼应：长期 memory 不应只是一段 LLM summary；保留原始 evidence、时间和 episode 结构能同时降低信息损失与构建成本。

Structure is a serving optimization

MORE 的 request-level candidate organization、SLOWeave 的 monotone cost model、ReActNet 的 temporal graph 都说明：很多效率收益并非来自更小模型，而来自把计算结构显式化。

Deep Dive 01 · Industrial Ranking · CIKM 2026

MORE：多任务学习不应该等 Backbone 把信息压完之后才开始

Research Impact Score / 研究价值 9.3/10工业成熟度 ★★★★★创新性 ★★★★★与你方向的相关度 ★★★★★是否官方开源 未确认是否有线上 A/B 是阅读优先级 S+

时间口径：arXiv v1 提交于 2026-09-07，论文已被 CIKM 2026 接收；本轮 recent 更新中进入重点追踪。

背景 / 业务动机：工业推荐精排过去几年有两条 scaling 路线：一条把 feature interaction 做深做宽（Wukong、RankMixer 等），另一条把 behavior sequence 拉长（HSTU、LONGER 等）。HyFormer / MixFormer / OneTrans 等工作开始把两条路线塞进统一的 stackable backbone。但真实业务几乎永远同时预测 click、like、comment、greet、chat、CVR/GMV 等多个目标；传统做法却依然让 backbone 生成一个 task-agnostic representation，到最后才用 MMoE / PLE / task tower 做区分。

现有问题：论文把它定义成结构性瓶颈而不是“专家数量不够”。第一，行为序列对不同任务的重要证据不同：CTR 可能关注曝光新鲜度，评论/深聊更关心主题与内容深度；共享 query 会把它们混在一起。第二，当 task differentiation 只发生在末端时，shared backbone 已把信息压缩到同一语义空间，后面的 gating 只能重加权已有 basis，无法恢复 backbone 内从未形成的 task-aware organization。第三，模型越 scale，新增参数仍主要服务 task-agnostic crossing，multi-task gain 出现递减。

技术方案与关键模块：MORE 引入跨 backbone layer 持续存在的 Anchor Tokens。Shared Anchors 表示跨任务共享语义，Private Anchors 每个任务一个，并加入 learnable task prior。每个 MORE Block 顺序执行三步：① Task-Aware Sequence Reading：Anchor 通过 cross-attention 从共享行为序列中读取与自身任务相关的信号，并用跨层 sequence register 保留演化摘要；② Selective Semantic Mixing：将非序列特征、Shared Anchors、Private Anchors 放进 lightweight mixer，但用 task-boundary mask 让不同 Private Anchor 彼此不可见，降低 negative transfer；③ Task Enhancing：每个任务用独立 FiLM-style branch 从非序列特征生成 affine modulation，再强化自身 Private Anchor。

输入与训练：多行为序列不是只用 item position，而是用行为组合的 Cartesian-product action ID，显式区分同一 item 上 click / interact / chat 等动作组合。目标函数仍是工业可落地的多任务 weighted BCE：各任务 BCE 按 task weight 加和。这一点很重要——收益不是依赖复杂 RL 或额外 teacher，而主要来自信息流架构本身。

推理 / Serving：MORE 把一个 request 下成千候选组织成 request-level sample：用户行为序列只编码一次并 broadcast，candidate-side non-sequential tokens 与 Anchor Tokens 沿 item dimension 组织；在线再按 mini-batch 切候选并共享 user-side computation。这个设计让“更复杂的 task-aware backbone”没有直接变成更高线上成本，论文报告 scoring latency 下降约 30%。

实验设置：论文使用大规模工业数据，覆盖 7 个任务，并与 unified backbone / multi-task baselines 对比。代表模型约 132M parameters、1.85G FLOPs/example，计算量与对比基线处于可比甚至更低区间，而不是通过明显增大 FLOPs 换增益。消融显示，去掉 Cartesian action encoding、跨上下文 anchor 初始化、private sequence reading 都会稳定损伤多任务平均结果，private task-aware sequence reading 的影响尤其明显。

离线指标：MORE 在七个任务上均获得正向 GAUC 提升，并在参数量与 FLOPs scaling 时表现出更好的 multi-task scaling efficiency。相比只把 MTL 留到 post-backbone 的结构，它更有效地把新增计算转换为多个任务的共同收益。

线上 A/B：在陌陌进行两周、平衡流量实验，核心结果包括：usage duration +3.0%、click +2.8%、like +2.0%、comment/interaction +3.6%、greet +2.5%、deep chat +2.0%，统计显著；同时 P99 scoring latency 约下降 30%。论文明确表示已部署到生产。

效率 / 成本收益：这篇工作最值得推荐算法工程师重视的不是某个 GAUC 数字，而是同时交付了效果增益 + request-level serving 重构。它说明 foundation ranker scaling 不必等价于 per-item 计算线性膨胀；先把 user/context 与 candidate state 分离，往往能把结构升级和延迟控制同时完成。

与主流方法比较：相比 MMoE/PLE，MORE 将 task signal 提前到 representation formation 阶段，而不是只做 post-hoc routing；相比 HyFormer/MixFormer，它补上了 unified backbone 的 task-awareness。优势是工业证据强、改造点明确、与现有 BCE/多目标体系兼容；缺点是 Anchor / task-boundary 设计会随任务数增加而带来额外状态与工程复杂度，任务动态增删、极多任务场景以及 delayed reward 目标仍未回答。

适用场景：多目标精排、社交推荐、电商 CTR/CVR/GMV 联合建模、广告多行为目标，以及已经在建设统一 Transformer/Foundation Ranker 的团队。对于仍在 DIN/PLE 规模的系统，也可以先借鉴“任务专属 query 提前进入长序列读取”这一思想，而不必一次性照搬整套 backbone。

局限 / 尚未解决：任务边界目前由人工定义；Private Anchors 与 task-specific branch 仍意味着任务数扩大后参数/计算会增长；不同任务之间何时应该通信、何时应该隔离仍是 hard mask；online label delay、长期价值和跨 stage objective 还未统一。

未来研究方向：Dynamic Task Graph × Anchor Token、task routing × expert routing、跨阶段 shared context state、long-horizon objective、candidate-adaptive compute。如果把 MORE 与 PTDG/UniCon/ReST 串起来，一个很自然的方向是：context 作为共享状态，task dependency 由样本动态决定，任务再在 backbone 内拥有自己的读取路径。

对工程落地 / 职业技能的启发：未来精排工程师只会 MMoE/PLE 已经不够。更值得掌握的是 information flow 设计、长序列共享计算、request-level batching、multi-task scaling 与线上 latency decomposition。这类能力比“再记一个多任务网络结构”更可迁移。

Deep Dive 02 · LLM Serving / Scheduling

SLOWeave：把 Prefill Chunk Size 从静态超参变成实时 SLO Controller

Research Impact Score / 研究价值 8.8/10工业成熟度 ★★★★☆创新性 ★★★★☆与你方向的相关度 ★★★★☆是否官方开源 未确认是否有线上 A/B 否阅读优先级 S

时间口径：arXiv v1 提交于 2026-09-07。

背景 / 业务动机：continuous batching 让 LLM serving 的吞吐大幅提高，但长 prompt 的 prefill 会抢占一次 iteration 的 GPU 时间，导致正在 decode 的请求等太久，最终击穿 TPOT（time per output token）。Chunked prefill 是成熟解法：把长 prefill 拆小，穿插 decode。但 chunk 太小会反复支付 kernel launch / scheduling overhead，太大又制造 latency spike。

现有问题：主流系统通常需要人为选固定 chunk size；最优值依赖 GPU、模型大小、batch composition、prompt length、当前 active decode 数和 SLO。也就是说它并非真正的“模型超参”，而是一个随 runtime state 变化的控制变量。

技术方案：SLOWeave 为每个 active decode request 维护 next-token deadline：上一次 token 完成时间 + 目标 TPOT。每轮调度先计算所有请求中最早的剩余 slack，然后用 iteration cost predictor 估计在当前 active decode 数下加入不同 prefill token 数的耗时。由于 cost 随 chunk size 单调，系统可用 O(log Cmax) 的二分搜索找出在 deadline budget 内最大的合法 chunk；若没有任何正 chunk 可行，就执行 decode-only iteration。

为什么这个设计重要：它把传统“经验调 chunk”改写成 constrained optimization：在所有不违反当前最紧 deadline 的动作中，最大化本轮 prefill progress。论文还给出在 predictor 准确且 decode-only 本身可满足 deadline 时的即时最优性论证。这个思路与推荐系统的 adaptive compute allocation 非常相似。

训练方法：没有模型训练；关键组件是可校准的 iteration cost model / predictor 与 safety margin。系统优化的对象不是权重，而是 runtime control policy。

推理 / Serving 方案：控制器位于 iteration scheduler，读取 active decode count、当前 prefill backlog、每个请求 deadline 和 cost prediction，动态决定这一轮 prefill chunk。它可以作为现有 continuous-batching engine 的调度 primitive，而不要求修改模型本身。

实验设置与指标：论文同时使用可复现实事件模拟器和 iteration-level GPU runtime，覆盖 chat、mixed-context、long-context、bursty workload。25ms TPOT 目标下，相比最强 fixed-chunk baseline，mixed workload goodput 提升 39%，long-context 提升 38%；10ms 更严格目标下分别达到 3.3× 与 2.4×。

代表 GPU 结果：A100/8B mixed workload 中，默认策略约 38.4 req/s、Fixed-1024 52.7 req/s、SLOWeave 67.1 req/s；H100/70B-TP8 long-context 中约 22.1 / 31.4 / 40.8 req/s。论文还报告能耗改善，例如 A100 mixed 的 valid-request energy 从固定策略约 15.1J 降到 12.4J，说明更好的 SLO compliance 不只是“排队更聪明”，也减少无效计算。

线上 A/B：无真实互联网产品 A/B；目前证据来自 simulator + GPU runtime benchmark，距离 vLLM/SGLang 生产默认策略仍有工程化验证空间。

与主流方法比较：相比固定 chunk，SLOWeave 不需要 workload-specific tuning，并能根据最紧迫 decode 动态收缩或放大；相比简单“decode priority”，它尽可能榨出不违反 deadline 的 prefill progress。弱点是对 cost predictor 和 queue overload 敏感：在持续超载、decode-only 都满足不了 SLO 时，任何 controller 都无法创造容量。

适用场景：高并发 chat、长上下文 RAG、Agent 多轮 tool context、混合 prompt-length serving。对推荐 Foundation Model，如果在线同时存在短序列 rank 与长 history encode，也可以借鉴其“deadline-aware adaptive compute”思想。

局限 / 尚未解决：成本模型在动态频率、不同 kernel/backend、prefix cache hit、speculative decode、multi-tenant GPU 上会漂移；只有 TPOT 一个 SLO 还不足以覆盖 TTFT、尾延迟和请求优先级；无界 overload 下没有 starvation-free 保证。

未来研究：SLOWeave × prefix-cache-aware routing × disaggregated prefill/decode × speculative decoding，并从单个 chunk controller 升级成联合决定 chunk、batch、device、precision 与 model route 的 runtime optimizer。

工程 / 职业启发：Serving 能力的核心正在从“会部署 vLLM”升级为 能建 cost model、理解 queueing/SLO、写 online controller、做 tail-latency benchmark。推荐系统做动态算力分配的人和 LLM Serving 工程师正在共享越来越多方法论。

Deep Dive 03 · Agentic RL / Adaptive Compute · EMNLP 2026

Elastic Horizon：Agent 的最大交互步数不该只会单调增加

Research Impact Score / 研究价值 8.8/10工业成熟度 ★★★☆☆创新性 ★★★★★与你方向的相关度 ★★★★☆是否官方开源 是是否有线上 A/B 否阅读优先级 S

时间口径：arXiv v1 提交于 2026-09-07，已接收 EMNLP 2026。

背景 / 业务动机：Web / tool-use Agent 的成功率通常会随着允许交互步数增加而上升，因此 curriculum RL 常从短 horizon 逐渐扩展。但交互成本几乎随步数线性增长，而且到某个区间后成功率开始饱和。继续把最大步数往上推，会让训练 token、环境调用和 credit assignment 难度一起增加。

核心假设：存在一个随 policy 能力变化的 effective interaction frontier：在这个边界之后，多给 step 的边际收益迅速下降。关键不是预先选一个最大 horizon，而是训练过程中估计这个 frontier。

技术方案：Elastic Horizon 是闭环 controller。它观察成功 trajectory 的长度分布，用 90th percentile 作为能力边界信号，周期性调整允许的 interaction horizon。与 open-loop curriculum 只会“越训越长”不同，Elastic Horizon 能从过小初值向上扩，也能从过大初值向下收缩，并稳定在性能饱和带附近。

训练方法：该 controller 包在 agentic RL 训练循环外层，不要求改 backbone；实验覆盖 Qwen2.5 7B / 14B 等 backbone，在 AppWorld 与 BFCL 环境比较 fixed horizon、open-loop schedule 与闭环方案。

实验 / 离线指标：固定 horizon sweep 显示 AppWorld 大致在 K=30–60、BFCL 在 K=20–50 出现饱和区。Elastic Horizon 从不同起点都能收敛到该区间，并在 7B / 14B 设置取得最优或领先 success rate。代表结果中，Qwen2.5-14B 在 AppWorld 的 Mean@8 / Best@8 约为 77.85 / 90.42。

效率收益：论文报告最多节省 25% per-step trajectory tokens；在一个 AppWorld 7B 达到 SR=50% 的对比中，累计 token 约从 50.21M 降到 36.28M，约减少 28%。这说明“少给无效 horizon”可以直接转成 RL 训练成本下降。

推理 / Serving：主要贡献在训练期 curriculum/control，而不是生产 inference router。但其思想可以直接延伸：在线 Agent 根据 task state / uncertainty 动态决定继续 tool-use、stop、escalate 或切换更强模型。

线上 A/B：无。

优劣势：优势是简单、与 RL algorithm/backbone 基本正交，并把 interaction budget 从静态 knob 变成 feedback control；不足是 P90 是启发式统计量，policy 与 controller 联合非平稳，论文尚未给出严格收敛理论，而且 single global horizon 可能掩盖 task/user 难度差异。

适用场景：Web Agent、搜索 Agent、多步 RAG、推荐对话 Agent、需要昂贵 tool/API 调用的 RL 训练。尤其适合“长轨迹能提高上限，但成本已经明显失控”的团队。

未来研究：per-task / per-state horizon、uncertainty-aware stop、model routing × horizon routing、reward-delay-aware frontier。推荐/搜索里可把它与 MaRCA 一类 compute allocation 思路合并：不只决定算多少层，还决定推理多少步。

工程 / 职业启发：Agent 工程越来越像控制系统：要掌握 trajectory statistics、budget controller、stop policy、cost-quality Pareto，而不是只会写 prompt/tool schema。

Deep Dive 04 · Agent Memory / Retrieval

EdgeMem：长期记忆不一定需要先让 LLM 把历史“总结掉”

Research Impact Score / 研究价值 8.6/10工业成熟度 ★★★☆☆创新性 ★★★★★与你方向的相关度 ★★★★☆是否官方开源 部分 / 旧实现是否有线上 A/B 否阅读优先级 A+

时间口径：arXiv v1 提交于 2026-09-03；9 月 9 日 new/recent 信号中被纳入今天追踪。

背景 / 问题：很多 Agent memory 在 ingest 时先让 LLM 把多轮对话总结成 profile、fact 或 memory node。这能压缩 token，但会在未来问题出现前就决定“什么值得保留”，一旦 summary 丢掉 answer-bearing detail，后续 retrieval 再强也无法恢复；而持续做 LLM-based consolidation 还要付 token/API cost。

技术方案：EdgeMem 的原则是保留原始 interaction turns，用轻量本地处理建立 multi-anchor hypergraph，将 content、temporal、episodic 三类线索组织起来。检索返回 source evidence，本体 memory lifecycle 不需要 generative LLM，LLM 只留给最终回答。

训练方法：无模型训练。构建与 retrieval 主要依赖本地 NLP / lexical retrieval / graph-style organization；论文实验中 generative-LLM calls 在 memory construction 与 retrieval 阶段为 0。

推理 / Serving：先从多 anchor 找相关 source turns，再把证据送给一个最终 reader。相比“每次先让 LLM 读完整历史”或“持续生成摘要”，这是 compute-once-lightweight-index / retrieve-evidence / generate-once 的结构。

实验：在 LoCoMo 与 LongMemEval-S 上评估。LoCoMo shared-prompt 对比七个复现系统时，EdgeMem strict-judge 61.01，下一最好为 58.70；论文同时报告 lenient judge 77.86 等指标。桌面 CPU retrieval P95 约 10.73ms，显示结构化 memory 并不必然要求昂贵在线模型。

效率 / 成本：论文口径下 memory build 与 retrieval 均为 0 generative token；对比一些 LLM-memory 方法，构建可能需要百万级 token、每问题再消耗数万 token。真正的价值是把长期 memory 从“生成内容”变成“经营证据索引”。

线上 A/B：无。

与 AtomRec / summary memory 比较：EdgeMem 更强调 source fidelity 与 0-token lifecycle；AtomRec 更强调可演化 atomic units 与协作关系。两者并不冲突：一个很值得研究的组合是 raw evidence layer + atomic semantic layer + provenance links。

局限：论文 arXiv 页面明确提示：当前链接 GitHub 是较早实现，与论文版本显著不同，作者计划 peer review 后更新对应实现。因此不能把现有 repo 当作论文完全复现。另一个问题是纯 lexical/local NLP anchor 在跨语言、强语义改写和视觉 memory 上的上限。

未来方向：evidence-preserving memory + semantic embedding、memory TTL/compaction、privacy deletion、cross-session causal links、retrieval uncertainty，以及将 source provenance 直接用于 recommendation explanation / user-interest refresh。

工程 / 职业启发：推荐系统里的用户画像也有同样问题：不应只把长期行为压成一个 embedding。未来更强的 user state 可能是embedding + atomic memory + evidence index + temporal version的组合。

Important 05 · Multi-Agent Inference

ReActNet：多 Agent 的拓扑与通信语义也可以在推理时按任务生成

Research Impact Score / 研究价值 8.3/10工业成熟度 ★★★☆☆创新性 ★★★★☆与你方向的相关度 ★★★☆☆是否官方开源 未确认是否有线上 A/B 否阅读优先级 A+

时间口径：arXiv v1 提交于 2026-09-04，9 月 9 日 recent/new 信号进入本轮观察。

核心问题：多数 multi-agent framework 固定 agent roles 与通信图，最多离线优化 topology；但不同 query 对“谁先分析、谁向谁提供什么信息”需求不同。固定图会产生冗余 message 和错误信息扩散。

方案：ReActNet 是 training-free inference-time graph engineering：根据 query 与 role-specialized agents 编译一串 temporal directed graphs，每个 graph snapshot 对应一个 reasoning stage，每条 edge 还携带自然语言 communication instruction，明确 source agent 应向 target agent 提供什么信息；最终通过 structured message passing 和 aggregator 得答案。

训练 / Serving：不训练额外模型，代价主要来自 controller 编图和多 agent inference token。论文在 6 个 benchmark 上对比固定/学习型 multi-agent baseline，综合表现强；例如 gpt-4o 配置下总体平均约 92.75。GSM8K 场景中其准确率约 94.4%，并以约 5.9M inference tokens 完成实验，显示动态 graph 不必然比 learned topology 更贵。

线上 A/B：无。局限：推理 token 仍随 agent 数增长；graph compiler 本身的错误会成为新的单点；benchmark 主要是 QA/code/reasoning，距离搜索/推荐业务链路尚有 domain gap。

推荐/搜索启发：Search Agent 不应固定“query rewrite → retrieve → critique → rerank”每次全走；未来更像 task-conditioned workflow router，按 query 难度决定调用哪些 specialist、执行几轮、传哪些 evidence。

Important 06 · RAG / Multi-hop Retrieval

DER-RAG：实体丢失不仅发生在 Retrieval，也会发生在“证据已经找对之后”

Research Impact Score / 研究价值 8.1/10工业成熟度 ★★★☆☆创新性 ★★★★☆与你方向的相关度 ★★★★☆是否官方开源 未确认是否有线上 A/B 否阅读优先级 A+

时间口径：arXiv v1 提交于 2026-09-05，记录在 9 月 9 日更新。

核心问题：multi-hop QA 会同时做 query decomposition 与 corpus chunking。第一类 entity loss 是 sub-question 忘了上一跳解析出的实体，retriever 无法匹配，即 lost-in-retrieval；第二类更隐蔽：sentence chunk 被切出原上下文后，代词失去 subject grounding，即使 gold evidence 已放进 context，generator 仍不知道“它”是谁，作者称之为 lost-in-generation。

方案：DER-RAG 用两个非常轻的结构修补 entity continuity：① two-way query decomposition，把已解析实体显式带入后续 sub-question；② generation 前给每个 sentence 附加 subject entity prefix。无需建 graph、无需修改原 corpus、无需 fine-tuning。

实验：三个 multi-hop QA benchmark 上匹配或超过强 baseline，包括依赖昂贵离线 graph 的方法。论文还通过 retrieval-controlled 实验证明：在固定 gold evidence 时，单纯丢失 entity grounding 也会显著伤害最终生成，说明 RAG evaluation 不能只看 Recall@K。

线上 A/B：无。局限：subject/entity extraction 在复杂共指、多实体、多模态、跨语言场景仍可能失误；QA benchmark 的提升还需在真实搜索日志上验证。

推荐/搜索启发：这是非常工程化的提醒：chunk metadata 应保留 entity/context provenance。商品搜索、知识搜索、review retrieval 如果把 sentence 独立索引，最好让 category/product/entity anchor 随 chunk 一起进入 retrieval 与 generation，而不是只相信 embedding 能自动恢复上下文。
