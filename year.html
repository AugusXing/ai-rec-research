过去一年，推荐系统真正发生了什么？

推荐 / 搜索的主线已经从“更大的 Ranking Transformer”扩展到四层共同演进：Representation → State → Control Plane → Validity。User History 被压成可复用状态，Item ID 变成可维护 Semantic Namespace，Retrieval 变成可编排程序，Serving Compute 变成按请求分配的预算；而 8 月 29 日的新信号又补上了最容易被忽略的一层：系统必须证明离线 Proxy Metric 会导向稳定决策、真实因果增量与正确的在线数值结果。

年度总判断：过去一年真正变化的，不是单个 Backbone，而是推荐系统“什么可以被学习、什么必须被验证”的边界。User：Raw History → Long Sequence → Shared / Intent State → Collaborative Vector Memory；Item：Random ID → Semantic Embedding → Structured / Fresh SID；Retrieval：固定召回器 → Dense×Token×Structured Index → Executable Program → Latent Tool Capability；Ranking：多塔拼装 → Unified Backbone → Topology / Decision Consistency；Alignment：accuracy reward → utility / value / process reward → causal / evolution reward；Serving：固定模型 → request-level routing → build / refresh / correctness budget。下一阶段竞争力将来自共享状态、可验证控制策略、因果价值与系统正确性的联合设计。
主线 01 · Generative Retrieval

Next-item Generation → Structured Identifier → Fresh / Programmable Retrieval → Latent Perception

上一阶段解决了什么：OneRec / Sona 把召回写成 token generation；TIGER / RQ-VAE 类工作让 Item Identifier 具有语义结构；TAGR 处理 fresh item / live-ad remapping；ProRetrieval 又把复杂查询扩展为 SQL × Text ANN × Image ANN 的可执行 retrieval program。

留下了什么问题：生成式图搜和多模态召回并不总能从原始输入直接辨认“真正目标”：一张用户图里可能同时有商品主体、品牌型号、文字、水印和背景。如果线上继续显式调用 crop、grounding、OCR 等工具，链路会再次变成长串行 pipeline。

关键推进：PailitaoGR 给出新的方向：训练期让 Crop Teacher / OCR Teacher 使用更强工具，student 仍只看原图，通过 Target Enhancer、on-policy SID distillation、区域/熵 attention guidance 和 selective auxiliary-evidence distillation，把“Zoom / OCR”能力内化成 latent capability。真实拍立淘日志上相对已有方案平均提升 13.8%，推理时不增加工具调用。

下一阶段：Generative Retrieval 很可能形成两种互补控制语言：一类是 SID 直接生成，另一类是 typed retrieval program；而视觉 / OCR / attribute tools 的能力逐步在训练期被蒸馏进线上 student。最值得研究的是何时直接生成、何时调用工具、何时把工具能力内化，以及这些路径如何共同优化 latency 与 recall utility。

  • PailitaoGR · TAGR · ProRetrieval
主线 02 · Semantic ID

RQ-VAE → Dynamic / Flow-normalized SID → Namespace Infrastructure → Perception Granularity Controller

上一阶段解决了什么：Semantic ID 把 item 从随机 ID 变成可泛化的离散语义结构；Tlow 从 embedding geometry 缓解 residual quantization 串行依赖，TAGR 则把 vocabulary stability 与 fresh remapping 做成生产问题。

留下了什么问题：SID 的 codebook utilization、collision、version/churn、跨时间兼容、fresh assignment 之外，还有一个更深问题：每层 SID 代表的 coarse-to-fine 语义，是否应该反过来约束模型“应该看哪里、看多细”？

关键推进：PailitaoGR 对 SID→visual attention 加 Region-of-Target 与 entropy guidance，让越细粒度的 SID token 越集中到目标区域。SID 因而不只是可生成的 item namespace，也开始成为感知粒度和证据路由的控制信号。

下一阶段：需要统一 Continuous Embedding Service + Discrete Namespace Service + Freshness / Version Controller + Granularity-aware Perception，并让历史行为 token、视觉内容、实时商品变化在版本切换时保持可兼容。

  • Tlow · TAGR · PailitaoGR
主线 03 · Scaling / Serving

More Params → Information Density → Systems-aware Scaling → Correctness-aware Systems

上一阶段解决了什么：TM20K、OneModel 等扩大历史和共享 Backbone；FlashPrefill、CacheRoute、AdaWidth 把 attention、KV locality、embedding width 变成预算；工业 GNN 又把 194M 用户 / 28B 边图上的 ID memory 与 temporal sampler 变成首要系统问题。

留下了什么问题：“更快”如果意味着 build 成本过高、每次 catalog refresh 都要全量重建，或者 kernel 在边界规模下静默算错，系统级优化就失去意义。

关键推进：misi 把 ANN 的优化面扩成 Recall × Query Cost × Build Time × Peak Build RAM × Refresh Cost：10^8 vectors 在 64 CPU cores 上约 5,250 s 构建、3 GiB 构建内存、可在 8 GB memory budget 下从 NVMe serving；代价是纯 RAM 查询仍比成熟 graph baseline 慢 6–16×。与此同时，SGLang #36807 报告 `fast_topk_v2` 在长 row 下因固定 4096 candidate buffer 静默丢候选，64×256K、k=2048 的复现中 64/64 rows 返回错误 Top-K，且 shape/range/count 检查全部正常。

下一阶段：Scaling 必须统一考虑 Parameter / Graph / Index Memory、Build & Refresh Cost、p99 Latency、Numerical / Semantic Correctness。算法工程师需要把 reference correctness、adversarial size sweep 和 rebuild economics 放进模型 / 索引评测，而不是只看吞吐。

  • misi · Scaling GNN · SGLang Top-K correctness
主线 04 · Foundation Model

Shared Backbone → Shared Representation → Structured Routing → Capability Internalization

上一阶段解决了什么：OneModel 把多业务 event sequence 与 User State 合并；WeMM-Embedding 把多模态表示做成检索/排序共享资产；MaskRec 用 TopoMask 说明统一 token space 不代表所有 token 都应全连接。

留下了什么问题：Foundation Model 的线上预算有限，真实系统又常拥有更强但更慢的 teacher、Agent、OCR / Graph / Search tools。如何让 compact online model 获得这些系统能力，而不是把整条工具链搬到 serving path？

关键推进：PailitaoGR 展示了非常通用的模板：training-time tool-rich teacher → inference-time tool-free student。与传统 logits distillation 不同，它只迁移 teacher 相对基准真正带来增益且 student 可感知的能力，并用 student 自己的 SID trajectory 做 on-policy distillation。

下一阶段：Recommendation Foundation Model 可能更像 Shared State + Structured Routing + Capability Distillation，而不是单纯“参数最大”。强 teacher 可以读更长历史、图谱、工具、更多模态，线上 student 只保留被验证有用的 compact state 和 latent capability。

  • OneModel · MaskRec · PailitaoGR
主线 05 · RL / Preference Alignment

Sparse Reward → Utility / Process Reward → Exploration Coverage → Causal / Evolution Value

上一阶段解决了什么：SSR-GRPO、Think-to-Personalize 把 retrieval utility 与 personalized reasoning 写入 RL；TAGR 用 Behavior / Value reward；ES-vs-GRPO 又把 reasoning coverage / Pass@K 纳入优化视野；Astar 则用 Reward Model 把数小时/数天的算法实验反馈代理成秒级 evolution reward。

留下了什么问题：模型可以把 proxy reward 优化得很好，却不一定改变正确的线上动作。比如一个 signal 历史上更常出现在高意向用户中，相关性模型会把“用户本来就会购买”错当作“展示 signal 导致购买”。

关键推进：eBay Stageboost 用两阶段 XGBoost + counterfactual estimation 做 View-Item 页面 signal recommendation，把目标从 outcome prediction 改成 incremental treatment value；线上整体 GMB +0.08%，Parts & Accessories +0.58%。这条线把 alignment 从“符合偏好”推进到“动作真的造成增量”。

下一阶段：推荐 RL / preference optimization 应同时考虑 Reward Density × Exploration Coverage × Causal Incrementality × Verification Cost。用户价值、长期留存、广告收益、页面拥挤等多目标也需要从相关性 proxy 转成 policy-level causal utility。

  • Stageboost · ES for LLM Reasoning · Astar
主线 06 · Reasoning / Re-ranking

Score Fusion → Context / Risk → Information Routing → Decision Stability

上一阶段解决了什么：CAIRO、CRRN、Risk-aware Rerank 让重排从静态 score fusion 转向 context selection / risk constraint；MaskRec 进一步强调哪些信号被允许交互；ProRetrieval 则把 reasoning 压成可执行 retrieval program。

留下了什么问题：LLM listwise scorer 即便 nDCG 相同，也可能因为候选 presentation order 不同而保留完全不同的集合，进而让 reader、threshold policy、推荐曝光做出不同决策。

关键推进：OC-SFT 直接训练候选得分对 permutation 保持一致。论文中 5 个 scorer 的 nDCG@10 差异都小于 0.010，但换顺序后 retained-set overlap 只有 0.66–0.84；OC-SFT 将 multi-document reader 的 answer-flip rate 降到 0.125，并能用单次推理超过 off-the-shelf scorer 十余次 permutation averaging 的稳定性。

下一阶段：Ranking / Re-ranking 指标需要从 nDCG / AUC 扩展到 Decision Stability、Threshold Robustness、Set Overlap、Downstream Flip Rate。真正稳定的 listwise model 应把这些性质在训练期学进去，而不是靠 inference ensemble 兜底。

  • OC-SFT · Official Code
主线 07 · Full-stack Generative Rec

One Model → Shared State / Namespace → Self-Evolving Stack → Tool-rich Training / Tool-light Serving

上一阶段解决了什么：OneRec、TAGR 等证明生成式召回可以覆盖真实推荐/广告流量；Astar 又让 model-development control plane 开始自动演进。

留下了什么问题：Full-stack 并不代表所有模块必须在一次请求里在线执行。Grounding、OCR、长历史 reasoning、图扩展等能力如果都变成同步 tool call，延迟和故障域会迅速膨胀。

关键推进：PailitaoGR 给出一种 full-stack 新解释：训练栈可以非常强——包含 crop/OCR teacher、on-policy trajectory、attention supervision——而线上执行栈保持单模型。Astar 则从研发侧自动决定下一步架构 / loss / data 怎么变。两者共同把“复杂能力”移到 training / evolution control plane。

下一阶段：真正的 Full-stack Generative Rec 很可能包含三层：请求级 policy 决定直接生成 / 检索 / 重排；共享 State / Namespace 负责数据面；研发级 evolution policy 决定 tokenizer、teacher、architecture、reward 和 runtime 如何更新。

  • PailitaoGR · TAGR · Astar
主线 08 · Agentic Search / Context Ranking

Query Rewrite → Tool-use Search → Typed Program / Vector Memory → Validated Evidence

上一阶段解决了什么：Search-R1、Clarify-Then-Search、EviGraph 把 Search 从一次 query 变成多步 tool use；ProRetrieval 用 DSL 编排 SQL/text/image backend；CoVeMem 把长期记忆从自然语言改成 trainable collaborative vector state；Live Catalogue 处理 fresh index。

留下了什么问题：“检索到了看起来更支持答案的 evidence”并不自动意味着 retriever training、system selection、最终 answer quality 都更可靠。RAG 评测开始遇到 validity-composition 问题。

关键推进：Assessing the Downstream Utility of Evidence-Aware Retrieval 在 5 个 benchmark + TREC RAG 2025 中分别测试 answer-support signal 用于 retriever comparison、training、system selection、answer-quality prediction 和 direct filtering。Evidence-aware label 能显著改 leaderboard（与原排序 Kendall τ 约 0.378–0.746，5 个集合中 4 个 top system 变化），但用于 RankNet retriever training 的提升很小且置信区间覆盖 0；直接过滤证据后，不同 answer evaluator 甚至对最终质量是否改善给出不一致判断。

下一阶段：Agentic Search 的完整 contract 不只是 Typed Tools + Persistent State + Fresh Index，还需要 Validated Metric：每个 retrieval / evidence score 都应明确它被验证能支持哪一种 downstream decision，而不能默认“更语义化的指标”天然更正确。

  • Evidence-aware RAG · ProRetrieval · CoVeMem
主线 09 · Model Routing

Fixed Model → Request-aware Compute → Utility-per-Compute → Cost / Freshness / Correctness Router

上一阶段解决了什么：RecGPT-Mobile-V2、AdaWidth、Adaptive Retrieval 等开始让 reasoning tokens、embedding width、模型、device 和 retrieval path 随请求变化；ProRetrieval 已经可以被看作 backend router。

留下了什么问题：当前 router 往往只优化“本次请求跑哪个模型”，但生产成本还来自索引重建、状态刷新、内存占用与 correctness fallback；这些慢变量同样决定总体 TCO。

关键推进：misi 把频繁重建与受限内存纳入 ANN 设计；SGLang Top-K 问题则提醒 router / kernel optimization 必须带 correctness guard。当 fast path 进入已知风险区间时，系统应能够切换到 safe fallback，而不是静默给出错误候选。

下一阶段：统一 Utility-per-Compute Router 应把 retriever set、candidate budget、embedding width、reranker depth、reasoning tokens、model/device、state refresh、index rebuild、safe-kernel fallback 都视为 action，以业务增量收益 / latency / GPU/CPU/IO 成本 / correctness risk 联合优化。

2026.08.29 新增年度判断：今年的“质量”概念正在被重写：Proxy Metric → Decision Validity → Causal Value → Serving Correctness。一个模型即使 AUC/nDCG 更高，也要继续回答四个问题：它会不会因输入顺序改变决策？这个 offline metric 是否真的预测 downstream utility？这个动作是否造成因果增量？高性能 kernel / index 在边界规模下是否仍返回语义正确的结果？这四层会成为推荐 / 搜索下一阶段实验平台的基础 contract。
