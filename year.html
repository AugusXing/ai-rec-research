Rolling 12-Month Review · 更新至 2026.08.17

过去一年，推荐系统真正发生了什么？

沿着“上一阶段解决了什么 → 留下什么问题 → 下一篇关键工作如何推进”去看，主线越来越清晰：推荐/搜索正在从 Stage-specific Predictor 走向 Generative / Foundation / Policy Model + Adaptive Retrieval + Request-aware Serving。

年度总判断：Item 变 Token、Ranker 变 Policy、Social Graph 变 Reasoning Space、长期历史变可压缩 Memory、业务目标变 Reward、模型选择变 Router。进入 2026 年 8 月后，研究重点进一步从“模型够不够强”移动到 可靠解码、Semantic ID 分布、Per-request Compute、Context/Memory 管理、上游不确定性与 Serving Cost。这意味着 Model-System Co-design 正从基础设施话题变成推荐算法本身。
主线 01 · Generative Retrieval

从 Two-Tower + ANN 到 Item-as-Token，再到“可靠生成”

上一阶段：Two-Tower + ANN 解决了亿级 Item 的吞吐，但 User/Item 独立编码限制高阶交互，召回与排序目标割裂。

关键推进：OneRec-V2 把推荐重写成 Item Token 自回归生成；JD GenRec 把 RL / 真实反馈继续前推。Sona 更进一步，用单一生成式模型直接替换 15+ Candidate Generator、Pre-rank 与 Rank。

2026-08 最新变化：DrIG 不再满足于“能生成 Identifier”，而是用 Dual-role Identifier + Set Prior 修补 Prefix Error，并在末端保留 Dense Rerank。研究问题从“能否不用 ANN”变成“如何把生成路径约束、候选恢复和成本放进一个系统”。

下一阶段：Generate / ANN 不会简单二选一，更可能出现 Query-aware Hybrid：简单请求 ANN，复杂请求 GenRetrieval；或者 Gen Candidate → Dense Recover → Policy Rank。

  • OneRec-V2
  • JD GenRec
  • Sona
  • DrIG
主线 02 · Semantic ID

Tokenizer 从实现细节变成流量分配基础设施

上一阶段：FORGE 让 SID 同时承载内容语义与协同行为；HD-Rec 用层级量化与稀疏路由处理跨域共享；音乐推荐实证又说明 Codebook/Depth 并非越大越好。

2026-08-17 新问题：FSGR 发现 SID Token Frequency Bias 会系统性放大头部 Token，最终影响 Item Coverage / Fairness。它用 Balanced Semantic Quantization + Hierarchical Frequency Calibration 同时修 Quantizer 与 Generator。

问题如何变化：以后评估 SID 不能只看 Reconstruction / Recall@K，还要看 Codebook Coverage、Token Gini、Fresh Item Assignment、Long-tail Exposure、层级稳定性。

  • FORGE
  • HD-Rec
  • Audio Embedding → GenRec
  • FSGR
主线 03 · Retrieval Adaptation

Retriever 不再是固定函数：Query 表示本身成为 Runtime State

上一阶段：Dense Retrieval 主要靠训练阶段塑造 Embedding；上线后 Query → Vector → ANN 基本固定。

关键推进：TTT-Embed 冻结 Encoder 与 Corpus Index，只在 Test Time 利用 Reranker 的标量 Reward 优化 Query Embedding，在多个 MTEB Task 上显著提升 nDCG@10。GEM 则更激进：模型先生成 Reasoning，再产生 Embedding Token，让 Test-time Reasoning Budget 直接改变检索表示。

下一阶段：Query Difficulty Router 会决定：直接 Embed、做几步 Test-time Optimization、是否 Reason、是否 Rerank。Retriever 与 Reranker 的接口将从“Top-K 列表”变成“可分配计算预算的联合 Policy”。

  • TTT-Embed
  • GEM
主线 04 · Ranking Foundation Model

从 Feature Tower 到 Transformer-native，再到不确定性与 Request-aware Compute

架构演进：RankMixer 等把多任务 Feature Interaction 做到成熟；OneRank 直接移除 Encoder–Predictor 边界，用 Task Token、Cross-task Attention、Candidate Context 与 Dynamic Matching 完成统一 Transformer Ranking。

Scaling 的现实约束：Meta Adaptive Ranking Model 不再让所有请求跑相同计算，而使用 Request-oriented Computation Sharing、动态路由、Selective FP8 与 Multi-card Serving。STAR 则从另一侧说明：PCVR 里结构化 Token、时间语义、Padding Contract 与 Target-aware Decode 仍能带来很高 ROI。

2026-08-17 新变化：DrEM 把上游 pxtr Prediction Noise 纳入目标函数，同时修监督侧与特征侧噪声，并给出大规模短视频线上 A/B。Ranking 的核心变量从“Feature/Model Capacity”扩展到 Input Uncertainty + Compute Allocation。

  • RankMixer
  • OneRank
  • DrEM
  • STAR
主线 05 · Long Sequence / Scaling / Serving

从“序列更长”到“每个 Token 值不值得付费”

上一阶段：Netflix Scaling、OneRec-V2 等证明更长历史/更大模型有效，但 Prefill、Full Attention、KV Cache、HBM 与 QPS 很快成为第一约束。

关键推进：TM20K 用 Full-attention Teacher 学 20K 历史，再让 Student Token Merge；CoinRAG 把 KV Cache 复用粒度从 Chunk 推向 Query-relevant Nugget；SGLang 等 Serving 系统加入 Session-aware Cache 与面向 Agent/RL Workload 的专用优化。

新的统一问题：到底哪些 Token、KV、Candidate、Expert、Model、Reasoning Step 值得在这个请求上计算？未来最值得押注的是 Per-request Compute Allocation，而不是固定 Compression Ratio。

  • Netflix Scaling
  • TM20K
  • CoinRAG
主线 06 · Foundation Model + Alignment

从 Pattern Matcher 到统一表示，再到稀疏业务目标对齐

上一阶段：OpenOneRec 等把语言知识与推荐能力放到同一 Foundation Model；但更强表示不自动等于业务目标对齐。

关键推进：WEBTOON Progressive Alignment 把 Post-training 拆成 LP → FFT → RFT：密集行为先学习 Policy，稀疏业务指标再训练 Reward Model 做最终 Alignment。

下一阶段：不同 Surface/人群/内容域的 Reward 是否共享？长期留存、疲劳、生态、GMV 与用户体验如何统一？Reward Design、Calibration 与 Counterfactual Evaluation 会比“选 PPO 还是 GRPO”更重要。

  • OpenOneRec
  • Progressive Alignment · 官方代码
主线 07 · RL / Reasoning / Re-ranking

Ranker 从“打分器”变成 List Policy，再从“会 Think”走向“少 Think”

GR2、MetaStrategy 等让模型显式生成列表级策略；REAM 则把研究问题推进到 Reasoning Length / Adaptive Thinking Budget。与此同时，Sona 说明如果统一生成模型足够强，部分传统 Rerank/Rank 边界本身也可能消失。

年度判断：真正工业化的 Reasoning Ranking 必须有 Router：哪类请求值得 Think？Think 多久？是否调用 Frontier Model？什么时候让传统 Ranker 执行？

  • GR2
  • MetaStrategy
  • REAM
主线 08 · Full-stack Generative Recommendation

传统 Cascade 的阶段边界被正面挑战

Sona 在 Yandex Music 用单一生成式模型替代 15+ Candidate Generators、Pre-rank 与 Rank，并报告 Active Users +4.53%、Listening Time +6.30%、Likes +11.42%。SilverTorch 从系统侧做了另一种统一：把 Index、Filter、ANN、Neural Rerank、Multi-task Scoring 收进同一 GPU-native Model Graph。

两条路线正在汇合：一条从模型侧统一 Pipeline，一条从系统侧统一 Retrieval Graph。短期更可能出现“统一 User Representation + 可组合模块 + 动态请求路由”，而不是所有业务一次性拆掉 Cascade。

  • Sona
  • SilverTorch
主线 09 · Agentic Search / Context Ranking

从“检索相关性”到“证据对最终决策的边际价值”

演进：Agentic-R / CoSearch 联动 Retriever 与最终 Answer；RISE、Context Interference 把 Context 干扰变成一等问题；MixRAGRec 让 Router 决定 KG Retrieval Granularity；EAHR 让 Hybrid Retrieval Depth 成为 Query-specific Runtime State；DocMemo 显式维护 Page Belief 做跨轮证据探索。

2026-08-17：Search-R1 Stopping 进一步把“是否继续搜”独立成 Learned Judge，减少 3.70% Retrieval Calls，但作者明确指出 Judge Compute 尚未归一化，因此不能声称总成本必然下降。

下一阶段：Context Ranking 会联合决定读多少、读哪路、何时停止、是否探索、是否进入昂贵推理。指标也应从 Recall@K 扩展到 Answer Utility / Cost / Latency / Calibration。

  • Agentic-R
  • CoSearch
  • Context Interference
  • EAHR
  • DocMemo
  • Search-R1 Stopping
主线 10 · Model Routing / Auto Optimization

推荐系统成熟的 Cascade 思想正在迁移到 LLM / Agent Serving

Pre-Inference Routing 给出一个很重要的经济学条件：Cheap Model 必须有足够 Failure Rate，并且 Failure 能从廉价特征预测，否则复杂 Router 没有价值。ConnectionMind、MetaStrategy 则体现“大模型规划 / 小模型执行”的分工；KernelEvolve 甚至把推荐 Kernel 优化本身变成 Agent 的搜索闭环。

2026 年下半年最值得押注的问题：统一的 Request Value Estimator。它输入 Query/User/Context/候选/系统负载，输出应该用哪个 Retriever、多少候选、哪个 Ranker、多少 Reasoning、是否 Rerank、何时停止。推荐系统过去十年的 Cascade / Calibration / Bandit 经验，会在这里重新变得非常有价值。

  • Pre-Inference Routing
  • ConnectionMind
  • MetaStrategy
给推荐/搜索算法工程师的技能地图：未来 1–2 年最有复利的组合不是“只会大模型”或“只会传统 CTR”，而是 Ranking/Recall 基础 → Transformer/GenRec → Semantic ID / Retrieval → RL/Reasoning → GPU/Serving/KV Cache → Online Experiment / Calibration / Cost Modeling。能把模型增益翻译成真实 QPS、Latency、Coverage、GMV/Retention 与 TCO 的工程师，会比单纯追模型结构更稀缺。
