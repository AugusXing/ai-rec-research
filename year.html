Rolling 12-Month Review · 更新至 2026.09.21

过去一年真正的主线：从“一个模型做更多”走向“目标、状态与执行路径都可被控制”

推荐 / 搜索的演进已经不再是“传统模型 vs LLM”。更稳定的主线是：Semantic ID 让对象可生成；Generative Retrieval 把业务价值前移；Foundation Ranker 统一表示；Reasoning/Re-ranking 处理复杂约束；Agentic Search 让检索计划动态化；RL 让监督可进可退；Serving 则让 attention、state、precision、draft path 和 kernel 本身都变成可路由的执行单元。9 月 21 日的新信号把这条线再推进一步：Controller 之下还需要一个可靠的 Architecture-aware Runtime Contract。

年度总判断：下一代工业推荐 / 搜索系统更像“Shared Backbone + Addressable Policy/State/Executor + Learned Controller + Architecture-aware Runtime”。Controller 决定目标、source、候选预算、reasoning、attention、draft、teacher 与 halt；runtime 则保证这些决策在不同硬件上不会因 state layout、precision、KV ownership 或 kernel fallback 而失真。真正值得积累的能力已从单点模型结构扩展到多目标建模、状态表示、动态预算、在线实验、Serving 调度与 correctness invariant。
主线 01 · Generative Retrieval

Semantic ID → Value-aware Generation → Intent-conditioned Fulfilment → Objective-specific Policy Portfolio

上一阶段解决了什么：TIGER / RQ-VAE 把 item 变成可生成地址；OneRec / OneSearch 把 retrieve 与 rank 的目标向生成模型前移；VARG / GR4AD 开始把下游价值写入生成 policy；Spotify Hypothesis-Driven Shelf Generation 又把“为什么推荐”抽成自然语言 intent，再由 constrained retrieval 兑现目录。

留下的问题：工业系统同时优化 relevance、CTR、GMV/eCPM、生态和长期满意度，单 scalar reward 容易被强目标支配；单 policy beam search 也难在固定 candidate budget 内显式配额。

关键推进：UniPolicy 用 objective prefix + sparse MoE-LoRA + objective-specific FFN，让共享 backbone 内形成多 policy，再按目标并行 beam search。

工业证据：7-day A/B：CTR +0.71%、RPS +1.58%、广告收入 +1.32%。

下一篇关键工作应该推进什么：state-aware quota controller、长期价值 credit、policy 自动增删与 calibration、intent planner 与 objective policy 联动。

主线 02 · Semantic ID

RQ-VAE → Long-tail Namespace → Value-aware SID → Versioned / Constraint-aware Address Layer

上一阶段：Semantic ID 解决 decoder 如何输出 item；HypRQ-VAE 等处理长尾 catalog；EPIC 修正 token likelihood 与 item posterior 错位；VARG 将 downstream value 写入 prefix learning。

留下的问题：地址一旦同时承载语义、协同和商业价值，就面临 catalog 增量、code drift、跨版本兼容、cold item 和探索空间收缩。

最近推进的意义：UniPolicy 说明业务目标未必继续塞进 SID 本身，可以在稳定 namespace 上通过 objective-conditioned policy 产生不同候选，从而把“地址稳定性”和“目标可变性”解耦。

下一阶段：incremental/versioned SID、跨 policy 共享 codebook、cold-item code assignment、探索友好的 code regularization，以及 quota 与 SID tree search 联合优化。

主线 03 · Scaling / Serving

FlashAttention / KV Cache → Speculative Decoding → Adaptive Compute → Architecture-aware Runtime Contract

上一阶段解决了什么：FlashAttention、Paged KV、continuous batching 和 speculative decoding 解决“同一个模型怎样更高吞吐”；SoL-Pi、On-Demand Attention、SwitchSD 进一步把问题改写成“什么时候使用哪条计算路径”。

9/21 的关键推进：今天多个一手 runtime 同时暴露出同一矛盾：模型结构越来越依赖 runtime 对内部 state 的理解。Qwen4 Sparse FA 需要按 context/shape 切 sparse path；vLLM DSV4.1 mHC 把 coefficient generation 与 attention/FFN overlap；SGLang GLM-5.3 mHC 按 token 数选择 fused boundary；Kimi-K3 Metal 则证明 hc 维度本身已成为 backend ABI。

为什么这是阶段变化：过去的 fallback 往往只是慢；现在 fallback 可能让 sparse 结构失去收益、让跨层 state 回 CPU、让 speculative KV 被污染，甚至因 precision policy 不当改变 MoE routing。Serving 已经从“框架层”升级为“模型语义的一部分”。

下一阶段：统一的 shape/hardware cost model；state ownership invariant；token/layer/request 多粒度 execution routing；低比特 precision policy；自动 crossover learning；P99/SLO-aware kernel selection。

主线 04 · Foundation Model / Ranking

Feature Model → Long-sequence Transformer → Generative Pretraining → Transferable Ranker → Structured User State

上一阶段：HSTU / SORT / OneTrans 把长序列 Transformer 推进工业精排；LazFormer 等用行为序列做 autoregressive pretraining，再用 adapter 适配 ranking features；PTDG / MORE / UniRec 推进跨任务共享。

留下的问题：容量不再是唯一瓶颈。长期 preference、短期 session、自然语言 taste、业务 feature 的更新频率完全不同；每次从头重算全部历史既贵又难保持一致。

下一阶段：foundation backbone + mutable user/session memory；textual preference 与 ID embedding 双通道；pretrain / finetune / online adapter 多时间尺度更新；controller 决定何时读取哪类 state。

主线 05 · RL / Preference Alignment

Static Reward → Preference Optimization → On-policy Distillation → Adaptive Teacher Lifecycle

上一阶段：DPO/GRPO 让模型直接利用偏好与环境 reward；OPD/OPSD 用 trajectory 中间 token 提供 dense supervision，缓解终局 reward 稀疏。

留下的问题：teacher 早期有价值，但 student 变强后继续模仿会与 reward optimization 冲突；固定 annealing schedule 不能适应不同 skill 的学习速度。

关键推进：RetireOPD 根据 teacher-student discrepancy 与 relative competence 自动退休 teacher。

下一阶段：per-skill retirement / re-entry、teacher ensemble routing、把 distillation compute cost 纳入 controller。

主线 06 · Reasoning / Re-ranking

Cross-Encoder → Listwise → Single Reasoning Trajectory → Multi-Trajectory Evidence Portfolio

上一阶段：Cross-encoder 强化 pairwise relevance；listwise/generative rerank 显式建模候选关系；reasoning reranker 用 LLM 处理复杂 query-document constraint。

留下的问题：单条 CoT 一旦误解 query 或漏证据，就会把错误放大；“更长”不等于“更全面”。

关键推进：MERIT-Rank 建立 Multi-Trajectory Reasoning Space，再由 joint reranker 融合；MSS-Complement 则从另一侧把 pointwise relevance 推到 set sufficiency。

下一阶段：coverage-aware multi-trajectory list rerank、uncertainty-triggered reasoning、verifier early-exit、蒸馏到低延迟 reranker。

主线 07 · Agentic Search / Context Ranking

Fixed Query → Query-conditioned Retrieval Plan → State-conditioned Complement → Full-pipeline Reward

上一阶段：GeneralQPP 判断是否继续检索；DiBud 把固定 Top-K 变 access budget；ORDER 让 source/index/chunk/reranker 随 query 变化；DUPAR 将 cross-turn cache 变 retrieval state；MSS-Complement 追问当前 state 还缺哪些最小充分证据。

关键推进：F²DR 把 DeepSearch reward 拆成 Content / Trajectory / Answer；MATCH 则用 tool name → argument key → argument value 的层级 gated credit。

下一阶段：把 source selection、query rewrite、retrieval depth、tool parameters、context sufficiency、latency/cost 放入一个统一 action/reward space。

主线 08 · Retrieval Representation

BM25 → Dense → Learned Sparse / Late Interaction → Query-conditioned Retrieval Portfolio

上一阶段：Dense 成为 semantic recall 默认方案，late interaction 提高细粒度匹配，但 lexical/entity、解释性、索引成本仍是短板。

关键推进：SPARSEUP 证明 learned sparse 仍能以倒排友好的形式提供强质量和可解释性；Milvus RocksMQ cache fix 又提醒：检索质量最终还受 cache/index 配置语义支配，模型与基础设施不能分开看。

下一阶段：query-conditioned dense/sparse/late router、effective-config telemetry、cache-aware retrieval scheduling、index state 与模型 state 的联合观测。

主线 09 · Full-stack Generative Recommendation

Retrieve-then-Rank → One-model Generation → Planner + Executor + Ranker 的重新分层

上一阶段：OneRec / OneSearch 证明全链路生成能减少 stage mismatch；Spotify shelf 表明更稳的工业路径可能是“LLM 生成 intent → constrained retrieval 履约 → 成熟 ranker 决定曝光”。

新判断：“统一”不等于“所有目标融成一个 decoder distribution”。UniPolicy 的多 objective policy、Serving 的多 execution path 都指向同一架构：统一参数底座 + 可分解控制面 + 可验证执行面。

下一阶段：planner/retriever/ranker 联合 credit；离线预生成与在线 freshness；multi-policy candidate budgeting；生成候选与传统 ranker calibration。

主线 10 · Model Routing → Execution Routing

Model Router → Retriever/Generator Router → Token/Layer-level Compute Router → Runtime Contract

演进：最初 routing 是“简单 query 用小模型，困难 query 用大模型”；随后扩展到 retriever + generator、tool、planning mode、context policy。SoL-Pi / ODA / SwitchSD 将 controller 下沉到 token 和 decoding strategy；9/21 的 runtime merge 又说明 controller 不能只输出一个 action，还必须确认 action 在当前 hardware/state 下有正确且高效的执行实现。

年度最终判断：Model Routing 这个名字已经过窄，更准确的是 Execution Routing：每个 request/state/token 选择 {model, retrieval plan, candidate budget, context state, tool, attention, precision, draft, reasoning budget, kernel path, halt}。

下一阶段：统一 cost model、quality predictor、uncertainty estimator、hardware capability graph 与 SLO-aware policy learning；线上用 counterfactual logging / bandit / constrained RL 学 execution policy。

2026 下半年最值得押注的研究问题：① Generative Retrieval 的 objective-specific policy 与 quota controller；② Multi-Trajectory / set-level reasoning rerank；③ user/session state 的可寻址 trajectory memory；④ dense+sparse+late-interaction 的 query-conditioned hybrid routing；⑤ token/layer/request 多粒度 adaptive compute；⑥ architecture-aware Serving：sparse/mHC/MoE/KV/state layout；⑦ Full-stack evaluation：从 CTR/NDCG 扩展到 trajectory quality、cost、latency、coverage、correctness 与长期价值。
