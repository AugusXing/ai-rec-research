过去一年真正的主线：从“一个模型做更多”走向“目标、证据、状态、硬件与实验可信度都可被控制”

推荐 / 搜索的演进已经不再是“传统模型 vs LLM”。更稳定的技术形态是：Semantic ID 让对象可生成；Generative Retrieval 把业务价值前移；Foundation Ranker 统一表示；Reasoning/Re-ranking 处理复杂约束；Agentic Search 动态获取证据；RL 让监督随能力变化；Serving 让 attention/state/precision/kernel 可路由；9 月 22 日进一步把 inventory tier、retrieval confidence、实验 comparison admission 与 global cell routing 也纳入 Controller。

年度总判断：下一代工业推荐 / 搜索系统更像“Shared Representation + Heterogeneous Retrieval Portfolio + Stateful Policy + Learned Controller + Verifiable Experiment Harness + Architecture-aware Runtime”。Controller 不只决定 model/tool，而是决定 {objective, retrieval path, inventory tier, candidate budget, evidence acquisition, reasoning, abstention, memory view, precision, draft, hardware cell, halt}；harness 负责保证实验结论可信；runtime 负责保证这些选择在真实硬件上既正确又经济。
主线 01 · Generative Retrieval

Semantic ID → Value-aware Generation → Intent-conditioned Fulfilment → Objective-specific Policy Portfolio

上一阶段解决了什么：TIGER / RQ-VAE 把 item 变成 decoder 可生成地址；OneRec / OneSearch 将候选生成与业务目标前移；VARG / GR4AD 把下游 value 写进生成策略；Spotify Hypothesis Shelf 又把“为什么推荐”抽成自然语言 intent，再由 constrained retrieval 负责目录履约。

留下的问题：工业系统并行优化 relevance、CTR、GMV/eCPM、生态与长期满意度。把一切压成单 scalar reward 容易让强目标支配弱目标，也无法解释 fixed candidate budget 应如何在目标间配额。

关键推进：UniPolicy 用 objective prefix + sparse MoE-LoRA + objective-specific FFN，让共享 backbone 内形成多 policy，再按目标并行 beam search。

9/22 的新连接：Hybrid GPU–CPU Retrieval 提醒我们：即使 policy 统一，serving path 未必应该统一。未来 generative retriever 很可能只服务高价值/高意图深度请求，而 CPU/dense/sparse 路径承担广覆盖。

下一阶段：objective policy × inventory tier × hardware path 的联合 controller；长期价值 credit；policy quota calibration；生成候选与传统 dense/sparse 候选的边际价值估计。

主线 02 · Semantic ID

RQ-VAE → Long-tail Namespace → Value-aware SID → Versioned / Constraint-aware Address Layer

上一阶段：Semantic ID 解决“decoder 如何输出 item”；HypRQ-VAE 等处理长尾 code utilization；EPIC 修正 token likelihood 与 item posterior 错位；VARG 将 downstream value 写入 prefix learning。

留下的问题：地址同时承载语义、协同和价值后，catalog 增量、code drift、跨版本兼容、cold item 与探索空间收缩变成系统问题。

最近阶段的判断：业务 objective 与 address namespace 应逐渐解耦：SID 更像稳定可版本化的“地址层”，policy/controller 决定在什么目标、路径和库存层里访问这些地址。

下一阶段：incremental/versioned SID、cold-item code assignment、跨 policy 共享 codebook、兼容传统 ANN/inverted index 的混合 address layer，以及针对 GPU/CPU inventory tier 的分层 SID。

主线 03 · Scaling / Serving

FlashAttention / KV Cache → Speculative Decoding → Adaptive Compute → Architecture-aware Runtime → Learned Global Control

上一阶段：FlashAttention、Paged KV、continuous batching、speculative decoding 解决“同一个模型如何更高吞吐”；On-Demand Attention、SwitchSD 又把问题改写为“什么时候使用哪条计算路径”。

9/21 的阶段变化：Sparse/mHC/Precision/KV 系列 runtime 更新说明模型结构已经要求 runtime 理解 sparse attention、cross-layer state、router precision、draft KV ownership 与 state layout，Serving 成为模型语义的一部分。

9/22 再推进一步：Google DLB 把控制范围扩展到整个 datacenter：root/leaf router 通过 peer probing 与在线 latency model 选择 cell；22 个月生产、68 endpoint 迁移显示 p50 -17%、p95 -13%，并可平均运行约 20% 更热。

主线 04 · Foundation Model / Ranking

Feature Model → Long-sequence Transformer → Generative Pretraining → Transferable Ranker → Structured User State

上一阶段：HSTU / SORT / OneTrans 把长序列 Transformer 推进工业 ranking；LazFormer 等用行为序列 autoregressive pretraining，再用 adapter 接 ranking features；PTDG / MORE / UniRec 推进跨任务共享。

留下的问题：长期 preference、短期 session、自然语言 taste、实时 feature 的更新频率完全不同。简单把历史无限拉长既昂贵，也让 state consistency、TTL、版本与 serving cache 更复杂。

9/22 的新启发：AutoViewMem 将偏好/事件/约束/时间更新拆成自配置 view，并把 disentanglement 前移到 write path。对推荐 foundation model，这意味着 user state 可能比“单一大序列”更像多视图可寻址 memory。

下一阶段：foundation backbone + mutable user/session memory；ID embedding + textual preference 双通道；不同时间尺度的更新策略；memory provenance/TTL/version；controller 决定何时读哪类 state。

主线 05 · RL / Preference Alignment

Static Reward → Preference Optimization → On-policy Distillation → Adaptive Teacher Lifecycle → Downstream-utility RL

上一阶段：DPO/GRPO 让模型直接利用 preference/environment reward；OPD/OPSD 用 trajectory 中间 token 做 dense supervision；RetireOPD 根据 teacher-student discrepancy 与 relative competence 自动退出 teacher。

9/22 的推进：RAVEL 给搜索/检索一个清晰范式：不要奖励“问题看起来好”，而要奖励它通过回答真正带来的 rank improvement。也就是说，RL 的价值正从“对齐语言偏好”扩展到直接对齐系统 downstream utility。

下一阶段：query rewrite / clarification / source select / tool call / halt 统一 action space；reward 从 final answer 拆到 evidence gain、rank gain、cost、latency、user interruption。

主线 06 · Reasoning / Re-ranking

Cross-Encoder → Listwise → Single Reasoning Trajectory → Multi-Trajectory Evidence Portfolio → Confidence-triggered Reasoning

上一阶段：Cross-encoder 强化 pair relevance；listwise/generative rerank 建模候选关系；reasoning reranker 用 LLM 处理复杂 constraint；MERIT-Rank 再将单条 CoT 扩展成 multi-trajectory evidence portfolio，MSS-Complement 把目标从单文档 relevance 推到 set sufficiency。

留下的问题：高成本 reasoning 不应该对所有 request 都开；一旦上游 recall 失败，重排无法挽救。

9/22 的关键连接：RegimeAbstain 提供 <1ms retrieval confidence，使系统可以在 rerank/reasoning 之前决定：直接回答、补召回、扩大 K、换 retriever、升级 reasoning 或拒答。

下一阶段：coverage-aware multi-trajectory list rerank、uncertainty-triggered reasoning、verifier early exit、reasoning distillation、retrieval confidence 与 reranker confidence 的分层 calibration。

主线 07 · Full-stack Generative Rec

Stage-wise Models → Generative Candidate → Unified Policy → Heterogeneous Full-stack Controller

上一阶段：生成式推荐试图把 recall/rank 目标向统一 decoder 收敛；随后工业实践发现，业务隔离、回滚、inventory freshness、latency budget 不允许所有 stage 真的变成单模型。

现在更可行的系统形态：统一的是 representation / policy / controller，而不是强迫 execution path 统一。Hybrid GPU–CPU Retrieval 是一个强工业信号：不同硬件、不同 inventory、不同模型深度可以并行存在，只要 attribution、aggregation 与 downstream objective 一致。

下一阶段：shared backbone + specialist executors；request-level route；跨 stage credit；候选 source attribution；generation/dense/sparse/graph retrieval 的统一 quota controller；online counterfactual logging。

主线 08 · Agentic Search / Context Ranking

Fixed Query → Query-conditioned Retrieval Plan → State-conditioned Complement → Interactive Evidence Acquisition → Verifiable Research Agent

上一阶段：GeneralQPP 判断是否继续检索；DiBud 把固定 Top-K 变 access budget；ORDER 动态选择 source/index/chunk/reranker；DUPAR 将 cross-turn cache 变 retrieval state；MSS-Complement 追问当前 context 还缺什么必要证据。

9/22 的两条推进：RAVEL 直接用 rank feedback 学“下一步问什么”，把 clarification 变成真正 retrieval action；EvoPilot 则把 Agentic Search 的思想移到算法研发：Agent 也要检索旧实验/incident，但记忆只有变成 executable verifier 才能真正约束行为。

主线 09 · Retrieval Representation

BM25 → Dense → Learned Sparse / Late Interaction → Query-conditioned Hybrid → Hardware-tiered Retrieval Portfolio

上一阶段：Dense 成为 semantic recall 默认方案，learned sparse / late interaction 补 rare lexical/entity 与细粒度匹配；SPARSEUP 等继续改善 inverted-index 兼容性。

关键矛盾：过去常把“选什么 retriever”看成模型问题，9/22 的 Hybrid GPU–CPU Retrieval 则表明 retrieval representation、inventory breadth 与 hardware economics 必须一起设计。GPU 深路径与 CPU 广路径不是同一 ANN 的两个设备实现，而是独立 inventory/model family 的 portfolio。

可靠性补丁：RegimeAbstain 进一步给 portfolio 一个 gate：从 ANN score distribution 判断当前结果是否足够可信，再决定扩 K / 换路 / abstain。

下一阶段：query-conditioned {dense/sparse/late/generative/CPU/GPU} router；pathway marginal value estimator；candidate quota；retrieval confidence；inventory freshness-aware scheduling。

主线 10 · Model Routing → Execution Routing

Model Router → Retriever/Generator Router → Token/Layer Compute Router → Inventory/Cell/Experiment Routing

演进：最初 routing 是“小模型还是大模型”；随后扩展到 retriever + generator、tool、context policy；SoL-Pi/ODA/SwitchSD 下沉到 token/decoding path；9/21 runtime contract 又要求 controller 理解 hardware/state。

9/22 的最终推进：routing 继续向两端扩张：向前，Hybrid Retrieval 决定 inventory/hardware tier；RegimeAbstain 决定是否继续检索/回答；RAVEL 决定下一步信息动作。向后，DLB 决定具体 cell；EvoPilot 甚至决定一个实验 comparison 能否进入知识状态。

因此“Model Routing”已过窄：更准确的是 Execution Routing：每个 request/state/token/experiment 选择 {objective, model, retrieval path, inventory, K, memory view, tool, attention, precision, draft, reasoning budget, hardware cell, abstain/halt, evidence admission}。
