过去一年：推荐系统从“生成候选”走向“统一建模、推理与全链路替代”

这不是一组互不相关的论文。过去一年最清晰的一条演进链是：Generative Retrieval → Semantic ID 基础设施 → Scaling / Serving → Recommendation Foundation Model → Preference Alignment / RL → Reasoning / Re-ranking → Full-stack Generative Recommendation。与此同时，搜索与 RAG 也从“检索文档”推进到“联合训练 Retriever、控制 Context、动态路由模型”。

年度核心判断：2025 年下半年以前，工业界首先证明“生成式推荐可以做”；过去一年真正发生的变化，是大家开始解决它进入主链路之后暴露出来的工程与建模问题：Item 如何 Tokenize、模型如何 Scale、真实用户反馈怎么进入 RL、Thinking 是否真的有用、昂贵 Reasoning 怎么 Serving，以及最后能否把 Recall / Rank / Re-rank 整体统一。

阶段 1 · Scaling 与真实反馈对齐

OneRec-V2 Technical Report

Kuaishou · 2025.08 · Generative Recommendation / RL / Serving

OneRec-V2 的关键不是“再做一个生成模型”，而是把 OneRec-V1 暴露出的两个工业瓶颈——计算分配失衡和 Reward Model 对齐局限——变成系统性方案。

为什么上一阶段还不够？

OneRec-V1 已经证明端到端自回归推荐在快手可以上线，但 Encoder–Decoder 架构里绝大多数 FLOPs 消耗在用户上下文编码。论文报告在典型配置中，97.66% 计算用于 sequence encoding，而真正 target decoding 只占很小一部分；序列越长，这种失衡越严重。另一方面，依赖 Reward Model 的 RL 需要额外 rollout 和打分，还会引入 reward hacking 与分布偏差。

核心方案

  • Lazy Decoder-Only：不再让完整 context 在深层 Transformer 中反复计算，把主要计算集中到需要预测的 item token，并通过 Context Processor 与 lazy cross-attention 读取用户上下文。
  • 真实反馈对齐：使用 Duration-Aware Reward Shaping、Adaptive Ratio Clipping 等机制，把真实观看/交互信号直接用于策略更新，弱化“学会讨好 Reward Model”的风险。
  • 规模扩展：计算下降后模型可以扩到 8B 参数，同时仍观察到有效 scaling。

结果与意义

作者报告总计算量降低约 94%、训练资源降低约 90%；快手/快手极速版线上 App Stay Time 分别提升约 0.467% / 0.741%。这些结果来自作者工业 A/B，自身不是第三方复现。

这一步把研究问题从“端到端生成能不能替代某一段”推进成“推荐模型能否像 LLM 一样真正 Scale，并接受 Post-training / RL”。后续 OpenOneRec、OneReason 的 Foundation Model 与 Reasoning 路线都建立在这一步的计算范式上。

阶段 2 · Semantic ID 成为独立基础设施

FORGE: Forming Semantic Identifiers for Generative Retrieval in Industrial Datasets

Taobao / Alibaba · 2025.09 · Semantic ID / Generative Retrieval

当 Item 要像词一样被生成时，Tokenizer 不再是预处理细节，而会直接决定搜索空间、长尾覆盖、泛化和线上收敛速度。

问题从模型转移到了 Tokenizer

生成式检索通常把每个 Item 映射为多个离散 token。问题是：怎样的 Semantic ID 才“好”？过去研究常在小规模数据上比较，而且必须把整个 Generative Retriever 训练完才能知道某种 SID 是否有效，成本高、结论也难迁移到工业目录。

FORGE 做了什么？

  • 构建来自淘宝的工业级 benchmark：约 14B 用户交互、250M Item，并包含多模态特征与时间连续性。
  • 系统研究 SID 构造、碰撞、平衡性、语义与协同信号组合。
  • 提出无需完整训练 GR 就能更快评估 SID 质量的代理指标。
  • 引入 offline pretraining schema，把线上 convergence 时间约减半。

为什么它影响后续工作？

OneReason、GR2、Sona 等后续系统都越来越依赖 Item Token 的可解释语义与唯一性。FORGE 的价值就在于把“Semantic ID 该怎么构造”从经验技巧提升成可以单独测量、优化和工业部署的模块。作者报告线上 transaction count 提升约 0.35%。

阶段 3 · Recommendation Foundation Model

OpenOneRec Technical Report

Kuaishou · 2025.12 · Foundation Model / Benchmark / Open Source

OpenOneRec 把问题从“生成下一个 Item”改成“一个推荐基础模型是否能同时拥有推荐能力、世界知识、指令遵循和推理能力”。

为什么 Scaling 还不够？

OneRec-V2 证明了模型可以做大，但如果只在孤立的推荐行为数据上训练，大模型仍可能只是更强的 pattern matcher。它缺少通用知识、instruction following，以及跨任务迁移能力。与此同时，社区也没有统一 benchmark 去判断“推荐基础模型”到底应该具备什么。

技术推进

  • RecIF-Bench：覆盖 8 类任务，从基础预测到复杂推荐推理。
  • 开放数据：约 96M 交互、160K 用户。
  • Co-pretraining：将推荐序列与通用语言能力共同训练，并关注 catastrophic forgetting。
  • OneRec-Foundation：发布 1.7B / 8B 模型以及数据处理、训练、评测流程。

结果与下一步

论文报告模型在 Amazon 10 个数据集上相对强基线平均 Recall@10 提升约 26.8%。更重要的不是单一数字，而是这一步为 OneReason 提供了“Item token 与语言空间对齐、推荐任务显式指令化”的前置条件。

阶段 4 · Generative Retrieval 真正处理生产约束

GenRec: A Preference-Oriented Generative Framework for Large-Scale Recommendation

JD.com · 2026.04 · Decoder-only / GRPO / Online A/B

京东 GenRec 的价值在于把生成式检索进入真实电商流量后最棘手的三件事——分页监督歧义、长 SID 序列成本、Reward Hacking——放进一个统一框架。

三个工业问题

  • One-to-many ambiguity：同一 request 的分页机制会导致相同输入对应多个合法正样本，普通 point-wise NTP 会互相冲突。
  • 长序列成本：一个 Item 被多个 SID token 表示后，几百个用户行为会迅速膨胀 prompt。
  • 偏好对齐：纯 reward model 容易让 policy 学到 shortcut，而非真实偏好。

技术方案

  • Page-wise NTP：把一整页交互作为训练单位，减少一对多标签冲突并提供更密集梯度。
  • Asymmetric Token Merger：prefill 时压缩多 token SID，decode 时仍保留完整分辨率，输入长度约减半。
  • GRPO-SR：GRPO + NLL Regularization + Hybrid Reward + Relevance Gate，在增强 preference alignment 的同时约束 reward hacking。

线上效果

作者报告月级线上 A/B 中 Click Count +9.5%、Transaction Count +8.7%。这类量级说明生成式检索已经不只是“替代一个召回通道”，而是可以直接挑战成熟生产 pipeline。

阶段 5 · Scaling 与 Serving 同时成为研究对象

Towards Generalizable and Efficient Large-Scale Generative Recommenders

Netflix · 2026.05 · Scaling / Serving / Freshness

Netflix 的关键发现是：推荐 Scaling Law 并不是“模型越大所有任务都更好”；不同任务有不同 headroom，Prompt、Output Head 与新内容建模往往比继续堆参数更重要。

技术主线

Netflix 将生成式推荐 backbone 从百万级扩到十亿级，并围绕超大 catalog 的 output cost、频繁 retraining、fresh item 与 serving delay 做系统优化。工作涉及 sampled softmax / projected decoding head、multi-token prediction、semantic item tower、collaborative embedding masking 等。

它改变了什么判断？

这篇工作给出了一个重要反例：Recommendation Foundation Model 不应机械照搬 LLM scaling。某些推荐任务会很早 plateau；真正的上限可能来自输入信号、训练目标或 catalog 表示，而不是参数量。这直接影响后来的 GenPage：Netflix 发现丰富 prompt 在当前区间甚至比继续放大模型更有效。

阶段 6 · Recommendation Reasoning

OneReason Technical Report

Kuaishou · 2026.06 · CoT / RL / Generative Recommendation

OneReason 最重要的结论不是“推荐也可以 CoT”，而是先证明了一个反常现象：简单打开 Thinking Mode 往往不如直接预测；有效推荐推理必须先解决 Perception 与 Cognition。

为什么推荐里的 Thinking 容易失效？

语言模型的 CoT 建立在自然语言 token 上，而生成式推荐的 itemic token 对模型来说可能只是离散编号。模型如果不知道 token 对应什么内容，就无从“推理”。此外，用户历史是长行为流，真正需要的是把行为重组为多个兴趣点和兴趣演化，而不是机械复述历史。

三步方案

  • Perception pretraining：让 Item Token 与语言/内容语义建立更强对应。
  • Three-level cognition-enhanced CoT：从局部 item 理解、兴趣归纳到推荐决策，构造更适合推荐的思考轨迹。
  • Specialize-then-Unify RL：先在不同业务域分别强化，再把推理策略统一，避免多域 reward 相互干扰。

演进意义

OneReason 把研究问题从“生成哪个 Item”推进到“模型能否显式解释用户兴趣是如何形成、为何当前意图变化”。它也自然引出下一阶段的成本问题：如果 Thinking 真有用，是否每个请求都值得 Think？这正是 REAM、自适应 reasoning budget、fast-slow serving 的后续方向。

阶段 7A · Reasoning 进入最终 Re-ranking

GR2 Technical Report

2026.06 · Generative Reasoning Re-ranker / RLVR

GR2 把大模型 Reasoning 放到离最终曝光最近的重排环节，并把 Semantic ID、Reasoning Trace、RL with Verifiable Rewards、On-Policy Distillation 与 Serving Distillation 串成一条工业链路。

为什么 Re-ranking 特别适合 Reasoning？

召回负责覆盖、精排负责估分，而最终重排面对的是一个相对小的 slate，却需要同时处理位置、列表多样性、多个正样本和展示形态。它更接近“对一个有限集合做整体决策”，因此比全库 retrieval 更适合显式 reasoning。

核心方案

  • 先用 uniqueness ≥99% 的 Semantic ID tokenizer 让 LLM 能表达十亿级 Item。
  • 通过更强 Teacher + rejection sampling 蒸馏高质量 reasoning trace。
  • 使用针对列表排序设计的 verifiable reward 做 RL。
  • 用 Context Compressor、On-Policy Distillation 与最终 Reasoning Distillation 降低训练/Serving 成本。

最重要的负面发现：Reward Hacking

LLM 会利用 incoming order、position bias 等 shortcut 获得高 reward，却没有真正学会 preference。作者因此强调 conditional verifiable reward。这个结论对整个 Recommendation RL 都很重要：Reward Design 往往比“PPO 还是 GRPO”更决定最终效果。

作者报告相对 legacy baseline 的 R@1 +18.7%、R@3 +7.1%、NDCG@3 +9.6%；属于作者工业数据结果。

阶段 7B · 从生成 Item 到生成整个页面

GenPage: Towards End-to-End Generative Homepage Construction at Netflix

Netflix · 2026.06 · Homepage Generation / Post-training

GenPage 不再问“下一条推荐什么”，而是把用户与请求上下文当 Prompt，直接自回归生成整个多行 Homepage。

为什么这是架构级变化？

传统首页通常包含候选生成、行级/卡片级排序、去重、业务规则与页面布局。GenPage 把这些结构化决策统一成一个 sequence generation 问题，并借鉴 LLM 的 pretraining → post-training recipe。

工业化重点

论文不仅讨论模型，还专门解决 cold start、freshness、business-rule enforcement 与 serving efficiency。线上 WBC 版本相对成熟生产系统带来核心 engagement metric 约 +0.24%，同时 end-to-end latency -20%。值得注意的是：在当前实验区间，丰富 Prompt 的收益大于单纯扩大模型容量。

阶段 8A · LLM 不直接生成 Item，而是生成 Ranking Policy

MetaStrategy: Generative Ranking with Executable LLM Strategies

Taobao · 2026.08 · Nearline LLM / Policy Generation

MetaStrategy 给出了一条比“LLM 直接接管 Ranker”更容易落地的路线：让 LLM 生成结构化、可验证、可编译的排序策略，再由成熟推荐系统执行。

为什么不直接生成列表？

工业重排有大量业务约束、广告与体验 guardrail、多目标融合、位置策略和已有预测模型。直接生成 Item Sequence 很难与这些成熟组件协同。MetaStrategy 让 LLM 输出 typed JSON，控制 CTR/CVR/GMV 权重、内容/类目偏好、体验约束与位置政策，再通过 deterministic validator/compiler 接入现有 Generator-Evaluator 架构。

训练与 Serving

论文使用 production-path replay、selection / relative-rank / baseline-lift rewards、自竞争 curriculum，以及把多个 4B Teacher 迁移到 0.8B Student 的 on-policy distillation。LLM 运行在 nearline，不进入同步排序 RT。

线上效果

淘宝猜你喜欢 7 天随机 A/B 中，作者报告 Click PV +2.11%、Item-detail PV +3.12%、Transaction Amount +2.83%。这条路线的核心优势是可解释、可回滚、兼容既有系统。

阶段 8B · Feature Engineering → Context Engineering

GenRec: An LLM-Backed Recommendation Ranker at Netflix

Netflix · 2026.08 · LLM Ranker / Context Engineering

Netflix GenRec 的路线不是端到端生成整个系统，而是让 Foundation LLM 进入工业 Ranker：把几千个 engineered features 转换成 verbalized user history 与 context。

两阶段训练

Phase 1 先让基础 LLM 学习 Netflix catalog、member behavior 与通用 instruction-following；Phase 2 再用 ranking-specific data、labels 和 reward 做 post-training。论文重点讨论第二阶段，包括输入 verbalization、context engineering、reward integration 与 cost-constrained serving。

Serving：prefill-only

传统自回归 LLM 排序成本很高。GenRec 设计 prefill-only inference，尽可能避免长输出式 decoding，把 LLM 作为高容量 contextual scoring backbone。作者报告在显著减少 Phase-2 标注样本和输入信号的情况下，仍在大型 A/B 中取得显著 offline / online 增益。

这篇工作的长期影响可能是能力结构变化：推荐工程师需要从“做更多离散特征”转向“怎样把用户历史、Item 内容、业务状态组织成 Foundation Model 能理解的 Context”。

阶段 9 · Full-stack Replacement

Sona Technical Report

Yandex Music · 2026.08 · Full-stack Generative Recommendation

Sona 是过去一年最强的“架构终局”信号之一：一个共享 User Encoder 的单模型推荐器，在线替换了 15+ Candidate Generators、Pre-ranking 与 Ranking。

它为什么比普通 Generative Retrieval 更进一步？

很多生成式推荐只替代 Recall。Sona 则让同一个 User Encoder 同时服务 Autoregressive Decoder 与 Ranking Module，并让 next-token prediction 与 ranking distillation 共同更新用户表示。Teacher Ranker 只在训练时提供高质量目标，线上只部署 Encoder + Decoder + Ranking Module。

关键技术

  • Semantic ID 同时融合多模态内容语义与协同行为。
  • History Compression 支持最多 8192 行为，并给近期行为更高分辨率的深层建模。
  • Decoder rollout 产生当前分布的候选，再由 Teacher 给 Ranking Module 提供蒸馏目标，减少 generator–ranker distribution mismatch。

线上 A/B

指标相对生产 Control
Active Users+4.53%
Total Listening Time+6.30%
Likes+11.42%

这些数字均为 Yandex 作者自报。当前最重要的局限是 Catalog Coverage 仍低于传统 Cascade，因此 Full Generative Rec 下一阶段的核心矛盾会是 Quality 与 Coverage/Exploration 的统一，而不仅是继续 Scaling。

并行演进 · Agentic Search / Context Ranking

搜索侧：Retriever 从固定工具变成可学习 Policy，Context 从“越多越好”变成需要 Ranking 的资源

推荐在统一生成，搜索也在发生类似变化：Search Agent 不再只调用固定 Retriever，而开始联合训练检索策略、Refine Evidence，并动态分配 Context Budget。

演进链

  • Agentic-R（2026.01）：Passage 是否有用，不只取决于 query relevance，还应由最终回答是否正确反向定义。
  • CoSearch（2026.04）：Reasoning Agent 与 Generative Document Ranker 联合 RL，Retriever 从外部工具变成 Agent Policy 的一部分。
  • Context Interference（2026.08）：系统性证明最近一轮 Retrieval 的噪声会显著干扰 reasoning，引入 Context Refiner，并将 refinement 纳入 RL training。

对推荐/重排工程师为什么重要？

这会自然产生一个新的 Ranking 层：过去排的是 Document / Item，未来还要排 Evidence、Tool、Model、Context Chunk。因此传统 Learning-to-Rank、重排、模型级联经验会直接迁移到 Agentic Search。
