过去一年，推荐系统真正发生了什么？

主线已经从“更大的 Ranking Transformer”转成系统边界重画：User History 变成可复用 State，Item 变成可维护 Semantic Namespace，Retrieval 变成可编排 Tool Graph，Serving Compute 变成 request-level budget。8 月 28 日又出现一个更深的变化：系统的控制面本身开始被学习——Astar 学“下一步算法怎么改”，ProRetrieval 学“该调用哪些检索算子”，CoVeMem 学“记忆该怎样被读取”，MaskRec 则显式约束“哪些信息可以互相看”。

年度总判断：过去一年的核心演进可以概括为 Representation → State → Control Plane → Self-Evolution。User：Raw History → Long Sequence → Shared / Intent-bearing State → Collaborative Vector Memory；Item：Random ID → Semantic Embedding → Structured / Fresh SID；Retrieval：固定召回器 → Dense×Token×Structured Index → Executable Retrieval Program；Ranking：多塔拼装 → Unified Backbone → Topology-constrained Information Routing；Alignment：稀疏 accuracy reward → utility/value/process reward → evolution surrogate reward；Serving：固定模型 → Dimension/Reasoning/Model/Device Routing；研发：人工试验 → Agent 自动执行 → 模型学习下一步 Evolution Direction。
主线 01 · Generative Retrieval

Next-item Generation → Structured Identifier → Fresh / Programmable Retrieval

上一阶段解决了什么：OneRec / Sona 把推荐召回变成 token generation，TIGER / RQ-VAE 类工作让 Item Identifier 具有语义结构，SSR-GRPO 又开始让 SID prefix 反向监督 dense retriever。

留下了什么问题：静态 SID 面对直播、热点和快速变化商品会过期；单一 generator 也很难处理价格、库存、文本、图片等不同性质的硬/软约束。

关键推进：TAGR 用分钟级 live-ad remapping 解决 fresh SID；Tlow 从 embedding geometry 入手降低量化串行依赖；8 月 28 日 ProRetrieval 更进一步，把检索从“生成 Item ID”扩展成“生成 SQL×Text ANN×Image ANN 的可执行 program”，让不同 backend 成为 policy action。

下一阶段：Generative Retrieval 很可能分化成两类控制语言：Item Namespace 用于直接生成，Typed Retrieval DSL 用于复杂条件编排。最值得研究的是两者如何共享 user state、semantic token 和 reward，并按 query complexity 自动选择直接生成还是调用检索程序。

  • TAGR · Tlow · ProRetrieval
主线 02 · Semantic ID

RQ-VAE → Dynamic / Flow-normalized SID → Namespace Infrastructure

上一阶段解决了什么：Semantic ID 把 item 从随机 ID 变成可泛化的离散语义结构，改善 cold-start 与 generative decoding。

留下了什么问题：Residual code 串行、collision、codebook utilization、version/churn、跨时间兼容与 fresh item assignment 都逐渐成为系统问题。

关键推进：Tlow 用 Normalizing Flow 先将原 embedding 重整为近独立标准空间再量化；TAGR 保持 vocabulary 稳定、动态更新 item→SID mapping；Self-Refreshing Live Catalogue 则从 continuous embedding index 一侧给出类似答案：hash 检测变化，只重算 delta，而非全量 rebuild。

下一阶段：需要统一 Continuous Embedding Service + Discrete Namespace Service + Version/Freshness Controller，同时管理 semantic consistency、delete、库存、回滚和历史行为 token 的兼容性。

  • Tlow · TAGR · Live Catalogue
主线 03 · Scaling / Serving

More Params / Longer History → Information Density → Systems-aware Scaling

上一阶段解决了什么：TM20K、OneModel 等不断扩大历史与 Backbone；FlashPrefill、CacheRoute、AdaWidth 则把 attention、KV locality 与 embedding width 变成可优化预算。

留下了什么问题：Raw scale 会饱和；图模型还有 ID 表、CPU memory、neighbor sampling 等与参数规模不同的系统瓶颈。

关键推进：User Behavioral Densing Law 把问题改写为“最小充分 token capacity”；8 月 28 日工业 GNN 又给出另一种 scaling law：194M 用户若用 full 256d ID 表需约 203GB，而 multi-hash 只需 2GB；timestamp-sorted CSR + binary search 把 temporal sampling 从 O(deg+k) 变为 O(log deg+k)，线上好友新增 +16%、ranker latency 无回归。

下一阶段：Scaling 不再只问“模型多大”，而会统一考虑 Parameter Memory / Graph Memory / State Freshness / Sampler Cost / Online Latency。算法工程师需要掌握数据结构与离线/在线拆分，而不只是模型算子。

  • Densing Law · AdaWidth · Scaling GNN
主线 04 · Foundation Model

Shared Backbone → Shared Representation → Structured Unified Backbone

上一阶段解决了什么：OneModel 把多业务 Event Sequence 和 User State 合并到统一模型；WeMM-Embedding 让多模态表示成为检索/排序/序列共享资产；NMRL 提醒 raw CTR 不能简单端到端污染共享 encoder。

留下了什么问题：统一 token stream 容易产生跨域梯度冲突与错误信息流。Foundation 的核心不只是共享参数，而是决定哪些信息应该共享、何时共享。

关键推进：MaskRec 把 non-seq features、multi-domain behavior sequences、context、global/domain memory 都放入共享空间，但用 TopoMask 显式阻断无关 domain 直接交互，再用 Candidate-conditioned DualQ 注入目标相关证据；腾讯广告比赛 Test AUC 0.824902→0.834640。

下一阶段：Recommendation Foundation Model 更可能是 Shared Token Space + Learnable / Structured Routing，而不是全连接大 Transformer。值得研究可学习 sparse topology、跨阶段共享 state 和按请求动态启用 token graph。

  • OneModel · WeMM-Embedding · NMRL · MaskRec
主线 05 · RL / Preference Alignment

Sparse Reward → Utility / Process Reward → Exploration Coverage / Evolution Reward

上一阶段解决了什么：SSR-GRPO、Think-to-Personalize 把检索 utility 与 personalized reasoning 写进 RL；TAGR 用 Behavior / Value reward 做间歇 on-policy alignment。

留下了什么问题：GRPO 可能 entropy collapse；单一 accuracy reward 容易丢 coverage；真正工业实验一次验证需要数小时甚至数天，reward 延迟极高。

关键推进：ES-vs-GRPO 研究显示 Evolution Strategies 能维持更广 reasoning coverage 和更高 Pass@K，并提出 GRPO→ES 串联；Astar 更关键地训练 Reward Model 预测某算法改动是否会改善 loss，把“几天一次的真实训练验证”代理成秒级 reward，再用于 proposal RL 与候选排序。

下一阶段：推荐 RL 的核心指标会从单点 reward 扩展到 Reward Density × Exploration Coverage × Causal Value × Verification Cost。Reward Model 也会从用户 preference evaluator 扩展成系统 evolution evaluator。

  • ES for LLM Reasoning · Astar · TAGR
主线 06 · Reasoning / Re-ranking

Score Fusion → Context / Trigger / Risk → Information-routing Decision Layer

上一阶段解决了什么：CAIRO、CRRN、Risk-aware Rerank 等让 rerank 从静态 score fusion 转向 context selection、即时 trigger 与 risk constraint。

留下了什么问题：Reasoning trace 本身不保证推荐更准；把所有上下文送进同一个 LLM / Transformer 会引入信息干扰。

关键推进：MaskRec 从 ranking backbone 给出一个非常通用的答案：决策性能依赖哪些信号被允许交互。ProRetrieval 则在搜索前置阶段把 reasoning 压成可执行 program，使“为什么选这个路径”可验证而不是靠自由文本 CoT。

下一阶段：Ranking / Reranking 的 reasoning 更可能表现为结构化 routing graph、typed program、evidence state，而不是长自然语言 CoT。可解释性与 serving efficiency 会因此同时改善。

主线 07 · Full-stack Generative Rec

One Model → Shared State / Namespace → Self-Evolving Stack

上一阶段解决了什么：OneRec、TAGR 等证明生成式召回可覆盖真实广告/推荐流量，且 SID、intent、value alignment 可以共同进入一个系统。

留下了什么问题：Full-stack 不代表所有模块都应该一体训练；index、tokenizer、ranking、reward、serving 的迭代速度不同，人工维护越来越难。

关键推进：Astar 把“模型栈下一步如何演进”本身做成 policy；20 次自动迭代说明 Agent 不再只在 inference-time 调工具，也开始进入 model-development-time control plane。

下一阶段：真正的 Full-stack Generative Rec 可能包含两层 Agent：请求级 policy 决定召回/排序动作，研发级 evolution policy 决定 tokenizer、loss、architecture、data 和 runtime 下一步怎么更新。

  • TAGR · Astar
主线 08 · Agentic Search / Context Ranking

Query Rewrite → Tool-use Search → Retrieval Program + Vector Memory

上一阶段解决了什么：Search-R1、Clarify-Then-Search、EviGraph 把 Search 从一次查询变成多步 tool use / evidence construction；Memory 系统用文字保存长期上下文。

留下了什么问题：固定 retriever action space 不会同时处理 schema、text、image 和 Boolean logic；文本 memory 又丢失 collaborative structure 且维护昂贵。

关键推进：ProRetrieval 用可执行 DSL 编排 SQL/text/image retrieval，4B RL 模型在电商 Hit@1 0.809；CoVeMem 将 LightGCN collaborative states 作为 soft-token memory，19/20 指标不弱于最强 text-memory Agent；Live Catalogue 用 delta sync 让 Agent 的索引跟随商品上下架与改价。

下一阶段：Agentic Search 会收敛成 Typed Tools + Persistent State + Fresh Index + Verifiable Program。LLM 负责选择和编排，不再承担所有检索、记忆和排序计算。

  • ProRetrieval · CoVeMem · Live Catalogue
主线 09 · Model Routing

Fixed Model → Request-aware Compute → Utility-per-Compute Control Plane

上一阶段解决了什么：RecGPT-Mobile-V2、AdaWidth、Adaptive Retrieval 等开始让 reasoning tokens、embedding width、模型与端云路径按请求变化。

留下了什么问题：当前 routing 往往只覆盖单个维度，没有统一衡量一次请求应花多少 token、多少候选、多少 retrieval backend 和多少 graph/state freshness。

关键推进：ProRetrieval 可以被看作 backend router：program 直接决定调用 SQL/text/image 哪些路径；GNN 工作则展示另一种 routing——把 expensive graph expansion 全移到 offline，仅把 precomputed state 送到 online ranker。

下一阶段：统一的 Utility-per-Compute Router 应把 retriever set、candidate budget、embedding width、reranker depth、reasoning token、model size、device、state refresh 都视为 action，并用业务增量收益 / latency / GPU cost 联合优化。

2026.08.28 新增年度判断：过去我们把“推荐算法能力”理解为模型预测能力；下一阶段还要加上系统自我管理能力。值得长期押注的不是单个 Backbone，而是 5 类可复用控制资产：① Evolution History / Reward Model；② Shared User/Item State；③ Semantic Namespace 与 Fresh Index；④ Typed Retrieval / Routing Language；⑤ Request-level Utility-per-Compute Policy。
