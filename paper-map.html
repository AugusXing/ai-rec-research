这张图的目标是帮助推荐 / 搜索算法工程师建立研究路线，而不是收藏论文。每个节点都回答：当前最难的问题是什么、前一篇工作解决了哪一层、下一篇为什么出现、工业成熟度到哪、现在最值得押注什么。

当前技术树中心：Shared State → Specialist Executor → Learned Controller → Counterfactual / Trajectory Measurement。生成式召回、LLM rerank、Agentic Search、Long-context Serving 和 Model Routing 表面上是不同方向，本质都在解决“有限预算下，哪个状态应该被读、哪个执行路径应该被走、结果如何被可靠归因”。
Problem 01 · 如何让召回与排序共享语义，但不牺牲工业执行弹性？

Generative Retrieval / Semantic ID / Unified Rec

RQ-VAE / TIGER→Value-aware Generation→UniPolicy→UNIQUE→Versioned Address + Multi-executor

核心矛盾：retrieval 需要高吞吐和可枚举地址，ranking 需要 target-aware discrimination；强行一个 stage 会牺牲 SLA，完全分离又造成 representation mismatch。

代表推进：UNIQUE 用 flat quantization + early fusion 共享表示，但保留 generative retrieval 与 target-aware ranking 的不同执行语义。

精读路线：RQ-VAE/TIGER → value-aware generative retrieval → UniPolicy → UNIQUE → Hybrid GPU–CPU Retrieval。

成熟度：高；已经从“论文范式”进入真实大流量系统，但 codebook lifecycle、cold item、multi-source accounting 仍是工程难点。

值得押注：versioned Semantic ID、flat/hierarchical hybrid、source-aware candidate accounting、incremental code assignment、retrieval/ranking joint loss balancing。

Problem 02 · 如何把行为统计、安全地交给 LLM 排序？

Semantic + Behaviour Fusion / Missing-feature Robustness

Text Cross-Encoder→Semantic ID Rerank→Behaviour Token→Dual-view Robust Training

核心矛盾：历史 CTR/QSS/CVR 很强，但有曝光偏差、冷启动与 freshness 问题；文本语义泛化强，但个性化不足。

关键论文：Spotify · Robust Fusion of Semantic and Behavioural Signals：0.6B LLM cross-encoder 同时消费 Semantic ID、文本与 QSS，并通过有/无 QSS paired training 保证 fallback。

Research Impact Score / 研究价值 9.6/10 · 工业成熟度 ★★★★★ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★★ · 是否官方开源 否 · 是否有线上 A/B 是，约 +2% search success · 阅读优先级 S+

承接关系：它不是“LLM 加一个特征”，而是把 missing-feature regime 变成训练分布；下一步自然连接 causal debias / propensity correction。

精读路线：Cross-Encoder → Semantic ID → Spotify Robust Fusion → Counterfactual Observability。

值得押注：behavior confidence token、propensity-corrected feature、freshness gate、cold-start routing、行为证据与自然语言 evidence 的统一不确定性建模。

Problem 03 · 超长用户 / Agent 历史，究竟应该“读更多”还是“管理状态”？

Long Sequence → Multi-timescale State → KV Ownership

Long Transformer→Sparse Attention→MuSeR State Cache→HySparse2 KV Bridging

核心矛盾：历史增长速度快于在线预算；完整重算很贵，过度压缩又丢远程兴趣 / 工具证据。

推荐侧：MuSeR 把 10⁴–10⁵ 行为压成异步维护的多兴趣 state，让长期历史退出请求关键路径。

Agent/LLM 侧：HySparse2 用两级 KV sharing 让 prefill 在 self-decoder 后退出，1M token 下显著降低 FLOPs 与 cache。

值得押注：interest/state TTL、drift-triggered refresh、target-aware history retrieval、cache provenance、跨 session state conflict。

Problem 04 · 模型压缩如何避免“离线看起来没事，长轨迹直接崩”？

Quantization → Phase Specialization → On-policy Recovery → Precision Contract

PTQ / QAT→QAD→Disaggregated Quantization→OPD→Task-aware Stability

核心矛盾：静态 perplexity / one-step KL 无法预测长 reasoning；prefill 与 decode 的瓶颈不同；cross-precision 的单 token flip 会沿 trajectory 放大。

关键论文 A：Disaggregated Quantization 将 prefill / decode 的 precision、weights、placement 分离，27B 8K TTFT 1.78×。

Problem 05 · Test-time compute 怎么从“多试几次”升级成真正搜索？

Repeated Sampling → Multi-trajectory → Semantic Search Policy → Model Routing

Best-of-N→Self-consistency→Multi-trajectory Rerank→Learned Concept Policy

核心矛盾：token-level sampling noise 不能保证覆盖不同 reasoning basin；增加 rollout 数常得到大量近重复答案。

关键论文：Beyond Repeated Sampling 用较小 concept generator 先产生多种语义策略，并用 RL 让这些策略最大化大模型下游成功率。

承接关系：它把“search policy”与“answer model”解耦，天然可扩展到 query rewrite、retrieval source、candidate budget、reasoning depth、model choice。

值得押注：cost-aware RL、跨模型 transferable controller、diversity-collapse detection、evidence search policy、online bandit routing。

Problem 06 · 推理加速如何突破“单点 kernel 优化”？

KV Cache → IO-aware Fusion → Draft/Verify → Phase-aware Scheduler

Paged KV→Spec Decode→H-Spec→Flash-dLLM→Global Execution Controller

核心矛盾：FLOPs 下降并不保证 latency 下降，HBM traffic、cache write、weight movement 与 batch shape 可能成为新瓶颈。

关键论文：Flash-dLLM 联合设计 KV cache 和 self draft/verify，在 GSM8K / HumanEval 相对 Elastic-Cache 5.1× / 11×。

值得押注：shared-prefix KV、selective refresh policy、multi-tenant cache allocator、P/D disaggregation、cost-aware heterogeneous scheduling。

Problem 07 · Agent 变多以后，谁来组织它们？

Central Orchestrator → Shared Workspace → Self-organized Organization

Single Agent→Supervisor + Workers→Shared Memory→Agensh

核心矛盾：中心 orchestrator 既是串行 latency 点，也是 context bottleneck；无中心又会产生重复劳动、冲突与验证风暴。

关键论文：Agensh 用 shared workspace / messages / context 让 worker 自认领、执行、验证、合并，ProgramBench 1→128 agents 相对提升约 49%，pandoc 扩到 1024 agents。

Problem 08 · 怎么知道复杂系统的提升到底是谁创造的？

Offline Proxy → Online A/B → Counterfactual Observability → Regime / Trajectory Diagnostics

核心矛盾：raw engagement 混合了曝光偏差、内容质量、模型策略和 stage interactions；aggregate metric 又容易掩盖 cold-start、missing-feature、precision-regime 的失败。

承接：Netflix Counterfactual Observability 用历史 A/B 校准离线增量；Spotify 用 feature-present / feature-missing slice 看鲁棒性；OPD / precision-divergence 则要求 trajectory-level failure audit。

值得押注：propensity logging、candidate provenance、stage attribution、feature regime、kernel/precision version、counterfactual replay、trajectory failure taxonomy。
