沿“核心矛盾”读论文，而不是沿发布时间堆论文

Paper Map 只关心三件事：上一阶段解决了什么 → 留下什么系统矛盾 → 下一篇关键工作如何推进。 9 月 23 日新增四个高价值节点：Graph-feature GPU Pre-ranking、Retrieval–Ranking Shared Representation、Multi-timescale User State、Counterfactual Observability；同时 H-Spec / Expert Coactivation 把 Serving 的研究边界从 runtime 扩展到 state ownership 与 training-time router。

当前优先精读路线：生成式召回：TIGER → OneRec / VARG → UniPolicy → UNIQUE；超大规模召回/粗排：Hybrid GPU–CPU Retrieval → CC Retriever；长序列：DIN/DIEN → HSTU → MuSeR / structured state；AI Search：Dense/Hybrid → RegimeAbstain → RAVEL → Answer-Oriented Context；Serving：KV / Spec Decode → H-Spec → Expert Coactivation → DLB；实验：A/B → Counterfactual Observability → EvoPilot verifier。
问题 01 · 召回与排序为什么长期分离？

Two-stage Representation Gap → Generative Retrieval → Shared Early-fusion Retrieval & Ranking

核心矛盾：召回模型优化“能不能找回来”，排序模型优化“最终是否值得曝光”。两套表示独立训练时，召回阶段会永久丢掉排序真正需要的候选；但把两 stage 完全合并又会破坏候选生成效率。

承接关系：TIGER/RQ-VAE 让 item 可生成 → OneRec/VARG 将 value 写入生成 → UniPolicy 按业务 objective 分 policy → UNIQUE 用 single-layer flat code + shared early-fusion Transformer，同时执行 generative code retrieval 与 target-aware ranking。

Research Impact Score / 研究价值 9.7/10 · 工业成熟度 ★★★★★ · 创新性 ★★★★★ · 与你方向的相关度 ★★★★★ · 是否官方开源 否 · 是否有线上 A/B 是 · 阅读优先级 S+

证据：Mobile Baidu 线上观看时长 +0.96%、分发量 +1.08%、留存 +0.70%，P99 89ms、MFU 44.23%。

值得押注：retrieval/ranking loss conflict、versioned codebook、source-aware shared backbone、按 request 动态 stage collapse，而不是“所有请求都跑同一统一模型”。

问题 02 · 粗排为什么必须是小模型？

Lightweight CPU Pre-rank → GPU Candidate Scoring → Graph-feature-aware Deep Pre-ranking

核心矛盾：数万候选内，模型 FLOPs 不是唯一瓶颈；viewer-author / user-item edge feature 的随机 join、特征搬运与 memory layout 往往先限制模型规模。

关键推进：LinkedIn Connected Content Retriever 在 GPU 上用 sorted-search primitive 将 dense graph affinity 与文档特征 5–10ms join，令 pre-ranking 可使用 50× 参数规模的 full deep model。

Research Impact Score / 研究价值 9.8/10 · 工业成熟度 ★★★★★ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★★ · 是否官方开源 否 · 是否有线上 A/B 是 · 阅读优先级 S+

证据：candidate index >1B；viewer 网络收敛到数万候选；总链路 120ms p99；线上 content time spent +2.5%。

值得押注：GPU feature store、edge freshness、candidate fan-out aware batching、source-specific pre-rank depth，以及“粗排变强后精排应该缩到什么程度”。

问题 03 · 个性化深度与库存广度为什么不应由一个 Retriever 同时承担？

Single ANN Frontier → Heterogeneous Retrieval Portfolio

核心矛盾：GPU 适合 interaction-heavy 深建模但 HBM 昂贵；CPU 适合巨大库存但算力有限。

关键推进：Hybrid GPU–CPU Retrieval 使用独立 inventory/model family：GPU billion-scale 深路径 + CPU 约 20× 更大广路径，并行执行后聚合去重。

问题 04 · 长序列推荐的瓶颈真的是序列长度吗？

Truncated History → Long Transformer → Multi-timescale Cached User State

核心矛盾：10⁴–10⁵ 行为蕴含长期偏好，但每个请求重算完整历史不可承受；长期兴趣、短期 session 与语义状态的更新速度也不同。

关键推进：MuSeR 用分层时间压缩、多兴趣 query、LLM 蒸馏文本语义、异步 user representation refresh 与 adaptive cache，将超长历史变成可维护 state。

Research Impact Score / 研究价值 9.4/10 · 工业成熟度 ★★★★★ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★★ · 是否官方开源 否 · 是否有线上 A/B 是 · 阅读优先级 S+

证据：Baidu APP DAU +0.26%、总时长 +0.89%。重要反例：消融显示多模态语义可能比 temporal compression 本身贡献更大，因此应把它读成“state system”论文而不是“压缩算法 SOTA”。

值得押注：interest-level TTL、drift-triggered refresh、state version/provenance、long/short conflict resolution、按 query 选择 state view。

问题 05 · 推荐模型如何持续扩容，而不是反复从零训练？

Static Growth → Function-preserving Dense Growth → Coactivation-aware Dense-to-Sparse

核心矛盾：推荐数据持续漂移；模型扩容如果只复制权重会造成 forward/update discontinuity，转 MoE 又可能破坏 dense channel 的协同结构。

关键推进：Inherit4Rec 的 D2D 用 hybrid growth + asymmetric training 保持函数与 optimizer continuity；D2S 用 channel coactivation 做 expert partition，再加入 shared expert 与 load balancing。

问题 06 · AI Search 为什么不能继续只优化 NDCG？

Document Relevance → Evidence Support → Trustworthy Context → Answer Utility

核心矛盾：在生成式搜索里，用户不直接阅读 Top-K；Top-K 是 generator 的输入。相关但不支持答案、过时、重复或相互冲突的文档都会伤害最终答案。

关键推进：Answer-Oriented Context Construction 将流程拆为 Answer Support → Content Trustworthiness → Context Organization，并同时评估 retrieval-side context 与 final answer。

问题 09 · Speculative Decoding 的状态应该由谁持有？

Drafter KV Cache → Target KV Reuse → Hybrid State Injection

核心矛盾：parallel drafter 自己维护 KV cache，在高并发下会重新成为 memory bottleneck；完全复用 target KV 又损害 draft quality。

关键推进：H-Spec 让 attention 直接复用 target KV，Mamba 只消费 last-position target hidden state，从而取消 drafter-side KV cache。

问题 10 · MoE Router 为什么应该理解硬件搬运成本？

Token-quality Routing → Load Balance → Expert Coactivation for Speculative Serving

核心矛盾：speculative verification block 激活越多 distinct experts，就越需要从 DRAM 向 NPU/GPU 搬权重，理论并行收益可能被 memory traffic 吃掉。

关键推进：Expert Coactivation 在训练中结合 global load balancing、shared experts、consistency loss 与 autoregressive expert selection，提高块内 expert 共激活。

问题 11 · Raw Engagement 为什么不足以评价推荐系统？

Clicks/Views → Debiased Metrics → Counterfactual Incrementality

核心矛盾：内容质量、模型策略、曝光位置、用户覆盖与级联 stage 混在 raw engagement 里；指标涨了不代表模型真正创造增量。

关键推进：Netflix Counterfactual Observability 使用 logged propensity、SNIPS/Hájek、relativity 与 incrementality，对单阶段和级联系统估计“移除某 item/row/decision 后会怎样”。

当前最值得押注的问题

从 Paper Map 抽出的 6 个未来节点

① Stage-collapsing controller：哪些 request 需要独立召回/粗排/精排，哪些可共享 forward。
② GPU-resident feature graph：高价值 edge feature 怎样以低延迟、高 freshness 被模型直接消费。
③ Multi-timescale user state：state 的 TTL、refresh、version、drift 与 cost。
④ Reliable context/slate：support、trust、complementarity 与 marginal utility。
⑤ Training-aware serving：router/architecture 直接感知 KV、expert traffic 与并发。
⑥ Counterfactual experiment fabric：跨 source/stage/model 的可归因日志与自动 verifier。
