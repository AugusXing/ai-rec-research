问题 01 · 多兴趣模型为什么最后学成了几个几乎一样的向量？

Diversity Regularization → Multi-positive Exclusive Assignment

核心矛盾：传统多兴趣方法把“collapse”看成 representation similarity，于是加正交/对比损失；但如果每个样本只有一个 positive，主损失可能长期只更新同一个最匹配 interest，其他 slot 没有稳定职责。

关键推进：MIMA 将同 request 多个 positive 形成 set，用 Hungarian one-to-one assignment 将不同正样本独占地分给不同 interest，再用 routing probability 校准跨兴趣 score。

证据：工业 HR@100/500/1000 相对提升约 7.98%/12.24%/13.03%；7-day A/B 交易笔数 +5.60%、金额 +5.44%。

押注：soft matching、dynamic K、长期 slot identity、MoE expert/candidate ownership；先改 credit assignment，再考虑更强 backbone。

问题 02 · 超长用户历史应该每个 Candidate 都重新检索，还是压成可复用状态？

Target-aware Retrieval → Target-independent Compression → Temporally Anchored Cache

核心矛盾：SIM/TWIN 式 target-aware retrieval 精度高但 candidate loop 重复成本大；简单 summary token 可缓存，却常缺时序与互补性。

关键推进：ChronicleRec：recency-aware merge + interleaved causal query tokens + multi-horizon pretraining，让 Chronicle Tokens 按时间锚组织，且 target-independent，可每个用户计算一次后缓存。

承接：“每 candidate 找历史” → “每 user 压历史” → “按时间锚、按 horizon 学互补 state”。

押注：incremental Chronicle、cache TTL、version compatibility、长期 token + 实时 recent state 两层结构，以及 recall/pre-rank/rank 共用 user-state protocol。

问题 03 · 为什么历史越长，推荐准确率可能反而下降？

Full History → Semantic Retrieval → Preference-stage Modeling

核心矛盾：历史中存在“语义相似但处于错误兴趣阶段”的行为；单纯加 sequence length 或加 retrieval K 都可能引入 preference-inconsistent noise。

关键推进：DRIFT 用 semantic/time/category distribution drift 学 soft boundary，自适应切成 preference-consistent subsequence；recent context 再 cross-attend 这些长期阶段并 gated fusion。

证据：最高 Recall@20 +21.6%，训练时间最高 -97.4%；说明“过滤错误阶段”与“减少 token interaction”可以同时成立。

押注：把 drift score 变成 cache refresh signal、retrieval filter、compute-budget controller。

问题 04 · Relevant Item 已在 Top-K 池里，但没有进入下游短名单，应该重训召回器吗？

Retriever-only → Post-hoc Generative Verifier

核心矛盾：下游只能消费很短 prefix；深 top-K recall 高并不等于有效 recall。重训成熟 retriever 成本与风险高。

关键推进：Recommendation Retrievers Need Verifiers 冻结 drafter，只对 top-K candidate identifier 计算 generative likelihood，再用 reciprocal-rank fusion 修正 consumed prefix。

问题 05 · Linear Attention 解决长 Prompt 后，为什么 Generative Rec 仍然卡在大 Beam？

Per-beam Full State → Shared Context + Transition Log + Ancestry

核心矛盾：recurrent linear attention 的 state 对单流很省，但 beam=256/512 时复制每 beam full state 会形成新的显存与 HBM traffic 瓶颈。

关键推进：OneLA 只保存一份 shared prefill state，每步记录紧凑 GTR，并用 ancestry index 表达 beam 分叉；projection replay 只计算当前 query 所需 state 信息。

证据：end-to-end decode 1.54–2.46×；large-beam 场景 persistent state 与 state write 显著下降。

押注：beam budget × serving cost 联合优化、ancestry-aware scheduler、与 constrained SID decode/speculative decoding 融合。

问题 06 · 粗排与精排各自变强，整条链路为什么仍可能变差？

Stage-wise Optimization → Teacher Alignment → Joint Cross-stage Fusion

核心矛盾：pre-ranking 先决定 candidate survival，ranking 无法恢复已被过滤 item；单向 teacher-student alignment 也可能让 fusion 层彼此抵消。

承接：COPR / Rethink / HCCP → PTDG / MORE → UniRec：shared embedding + vertical consistency + horizontal preference aggregation + AGRR。

问题 07 · Router 需要执行历史，但为什么不应该直接读完整历史？

Query-only Router → Full-history Router → Gated Execution Memory

关键推进：Gated-Memory Routing 用 Memory Write Gate + Retrieval Gate + Role/Backbone Router + Adaptive Halting，把 routing 从 model-id classification 推到 compact execution-state control。

问题 08 · 检索 / Agent 什么时候继续找信息，什么时候停止？

承接：GeneralQPP 用 score-shape 判断 retrieval sufficiency → Elastic Horizon 管多轮长度 → SAFARI 用 exploration-rich trajectory + Monte-Carlo contrastive preference 学探索边界。

问题 09 · Serving 优化能不能从“人工调 Kernel”升级成“Agent 生成 + Oracle 验证”？

Compiler / Hand-written Kernel → Agent-generated Megakernel + Mid-state Oracle

关键推进：ForgeMegakernel 用 coding agents 沿 10 个 milestone 生成 per-model decode kernel，并由独立 mid-state oracle 检查 correctness/performance。14 个 operation、8 个 model family 上对 SGLang 0.5.18 几何平均约 1.21×。

问题 10 · 一个 Bad Case 是否值得修改全局 Harness？

Per-case Patch → Cross-instance Failure Attribution → Versioned Evolution

关键推进：Ecdysis 先聚合 recurring failures，再由 Analyst/Critic/Engineer 形成 modification specification，避免按单个失败过拟合全局 runtime。

与 ForgeMegakernel 的共同模式：Agent 可以提修改，但必须由独立 evidence/oracle 判断是否值得进入全局版本。推荐系统的规则、召回策略、feature pipeline 与 kernel 都可以遵循这一闭环。

最值得押注的交叉点：MIMA × ChronicleRec × Generative Verifier × OneLA 基本覆盖了下一代推荐链路的四个结构变量：谁负责用户哪种兴趣、长历史变成什么可复用状态、谁有资格进入昂贵下游、生成式候选如何在可接受成本下执行。它们比“再换一个更大的 backbone”更接近真正的系统级增益。
