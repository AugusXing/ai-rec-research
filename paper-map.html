不是按年份堆论文，而是沿“核心矛盾”读技术

Paper Map 持续回答：上一种方法解决了什么，为什么还不够，下一篇关键工作把矛盾推进到了哪里？今天新增五个值得长期追踪的问题：推荐系统能否自动诊断到代码级 refinement；性能优化能否跨 Serving Stack Agent 化；RAG 的索引配置是否应 query-conditioned；模型与 Harness 是否应该共同演化；长上下文的瓶颈是否已从权重转向 runtime state lifecycle。

当前推荐精读路线：Agentic RecOps：AURA → FlashVector（质量诊断 / 性能诊断两条控制面）；生成式召回：HypRQ-VAE → EPIC → Generative Verifier → VARG；工业 Ranking：PTDG → MORE → UniRec → LazFormer；长期状态：ChronicleRec → DRIFT → LION；Agentic Search：GeneralQPP → SAFARI → Question’s Gambit → DiBud → ORDER → CoSQ；Self-improving Agent：Ecdysis → ForgeMegakernel → ScienceBuddy；Serving：KVShareArena → OneLA → adaptive verification → ForgeMegakernel → FlashVector / JustFit。
问题 01 · 推荐系统能不能自己解释“为什么用户体验差”，再把诊断变成可验证代码修改？

Aggregate Metrics → Case Mining → Agentic Diagnosis → Code-level Refinement

核心矛盾：CTR/GMV/watch-time 只能告诉你系统整体发生了什么，很难解释某类用户 / session 为什么失败。人工 SQL + case review 又无法扩展到百万级 session，更无法稳定连接到具体代码和训练管线。

关键推进：AURA 让 specialized agents 读取生产 engagement logs，抽取 failure pattern 与代表性 case，再结合 recommender code、data 与 training pipeline context 提出并实现 refinement。系统已在大型 media-streaming company 的两个 consumer platforms 上做生产数据测试。

承接关系：传统指标监控 → LLM 日志总结 → LLM evaluator → AURA 的 diagnosis-to-code loop。它把“推荐研发自动化”从 AutoML/超参搜索推向用户体验层。

成熟度判断：高潜力、早期工业验证；真正缺的不是 demo，而是 diagnosis precision、patch acceptance、离线 replay / A/B uplift 与 rollback 数据。

值得押注：causal hypothesis generation、bad-case sampling、patch blast-radius prediction、shadow/canary evaluator、自动 rollback、长期生态指标 guardrail。

问题 02 · 性能优化为什么还停留在“专家逐层手工调”？

Kernel Tuning → Compiler Search → Kernel Agent → Cross-stack Performance Agent

核心矛盾：真实推荐 Serving 的瓶颈跨 GPU kernel、framework graph、C++ model server、feature service 与 queueing。单点 microbenchmark 变快，不保证 end-to-end throughput / P99 变好。

关键推进：FlashVector 把 coding/performance agent 扩展到异构 serving stack，并用组件测试 + full-stack load test 验证候选修改。Unity Vector advertising platform 生产部署：model server 最高 2× throughput、1.98× latency speedup；feature store 最高 1.6× throughput。

承接关系：FlashAttention / Triton kernel → ForgeMegakernel（agent-generated kernel）→ FlashVector（kernel→graph→server→feature service）。

成熟度：很高，已经跨技术栈并落真实广告平台；但业务 A/B、平均 TCO 与长期稳定性仍需更多公开证据。

值得押注：performance patch provenance、自动回归集、SLO-aware reward、不同 GPU SKU 自适应、成本/能耗/延迟多目标优化、自动 canary。

问题 03 · 一个固定 RAG 索引真的能服务所有 Query 吗？

Fixed Index → Source Routing → Query-conditioned Index / Retrieval Plan

核心矛盾：不同 query 需要不同 chunk granularity、metadata filter、source mix 与 reranker，但大多数 RAG 在 preprocessing 时就把这些超参固化。

关键推进：ORDER 先按 semantic query cluster 学习 chunking + metadata + reranking configuration 并预构建索引；在线 nearest-centroid 路由。QRe 再选 collection，UMS 在 selected sources 间分配 retrieval budget。

Research Impact Score / 研究价值 9.2/10 · 工业成熟度 ★★★☆☆ · 创新性 ★★★★☆ · 与你方向的相关度 ★★★★★ · 是否官方开源 未发现 · 是否有线上 A/B 否 · 阅读优先级 S

承接关系：single retriever → hybrid retrieval → source router → ORDER 的 index/router；与 DiBud 的 access budget、CoSQ 的 selective escalation 天然互补。

成熟度：中等。思路工程合理，但多 index 的 storage/update consistency 与 router error cost 仍需大规模线上证据。

值得押注：index routing + access budget + reranker/model routing 联合学习，P95-aware cost、dynamic cluster、冷启动 query fallback。

问题 04 · 长期 Agent 只升级模型，为什么很快又撞到固定 Tool / Prompt / Workflow 的上限？

Static Harness → Prompt Search → Harness Evolution → Model-Harness Co-evolution

核心矛盾：固定 harness 会锁死模型能力；只改 harness 不训练 model 又会出现工具协议与 policy 不匹配。两者如果一起无约束优化，又容易共同过拟合 evaluator。

关键推进：ScienceBuddy 用 recursive-in-recursive self-improvement：inner loop 固定 model 演化 harness，outer loop 在改进 harness 下用 RL 训练 model。Qwen3.5-4B 三个 outer cycles 后，held-out single-attempt 42.2%→73.3%；官方代码已开源。

承接关系：Ecdysis（failure attribution 后修改 harness）→ ForgeMegakernel（agent patch + oracle）→ ScienceBuddy（harness evolution + RL）。

值得押注：独立 holdout evaluator、harness mutation safety、version binding、off-policy replay、判断“该改模型还是该改工具”的 attribution。

问题 05 · 长上下文推理的真正瓶颈还是模型权重吗？

Weight Quantization → KV Paging / Offload → State-lifecycle Scheduling

核心矛盾：权重量化后，大模型可以塞进较小内存，但 KV cache、临时 buffer、组件 residency 会随着 context 快速增长；“权重放得下”不代表“200K context 跑得起来”。

关键推进：JustFit 用 KVExec、PhaseSwap、StateTrans 联合管理压缩 KV、组件 residency 与 serving transition。在 24 GiB M4 Pro + Qwen3.8-27B MXFP4 上完成 212,992 positions 单请求，是 mlx-vlm baseline 30,720 的 6.93×。

承接关系：PagedAttention / KV quantization → KVShareArena / state reuse → JustFit 的 lifecycle-oriented state scheduling。

值得押注：multi-tier KV、automatic compression/offload、cross-request reuse、prefill/decode split、memory-pressure-aware scheduler。

问题 06 · Semantic ID 只表达语义就够了吗？

Semantic Address → Item-level Preference → Value-aware / Ranker-aligned Address

核心矛盾：Generative Retrieval 的 token probability 决定 item 是否进入候选，但传统 SID 主要优化语义量化；同一语义桶内的商业价值、个性化与 downstream ranker preference 没有进入地址。

承接：RQ-VAE / TIGER → HypRQ-VAE → EPIC → Generative Verifier → VARG 的 value-aware token + Prefix-GRPO。

问题 07 · 推荐预训练为什么常常“预训练很强，线上 Ranker 迁不过去”？

Behavior Pretraining → Sparse-only Transfer → Sparse + Dense Transfer Contract

核心矛盾：工业 ranking feature space 与预训练行为序列不一致；全量迁移容易 negative transfer，只迁 sparse 又浪费 dense backbone；多 epoch 还会造成 sparse 先过拟合、dense 没学够。

关键推进：LazFormer：生成式行为预训练 + sparse/dense transfer、residual adapter、asymmetric multi-epoch、长序列压缩与 hybrid sparse attention。

证据：线上 Orders +3.38%、GMV +9.85%，A10 QPS 仅下降 12.1%。

值得押注：跨场景 foundation ranker、adapter routing、不同 sparse/dense learning clock、request-level sequence budget。

问题 08 · 持续学习时，新偏好应该写回共享模型，还是写入独立状态？

Continual Fine-tuning → Anti-forgetting → Sparse Mutable Memory

核心矛盾：所有流式行为都更新共享 decoder，会让高频偏好覆盖稀有 / inactive user；per-user adapter 又随用户数线性增参。

关键推进：LION 用 query-driven sparse KV memory 给 preference delta 独立写入空间，并用 consolidation loss 强化稀有偏好。

承接：ChronicleRec 解决 serving 侧“历史如何缓存”，DRIFT 解决“读哪段历史”，LION 解决训练侧“变化写到哪里”。

值得押注：统一 mutable memory + cacheable user state、memory TTL/compaction、drift-triggered write、分布式一致性。

问题 09 · Top-K 真的是检索预算吗？

Fixed Top-K → Score Early Exit → Certified Access Budget

核心矛盾：Hybrid Retrieval 中 Top-K 是输出规模，不是真实成本；不同 query 的 inverted posting、ANN probe、RRF certification 工作量差异巨大。

关键推进：DiBud 以 access budget 为输入，增量读 sparse/dense list，在能数学认证相对次序时输出 exact RRF prefix。

证据：校准到 95% quality 后，held-out nDCG@20 95.05%–97.68%，访问量减少 65.92%–99.53%。

问题 10 · Deep Search 为什么第一轮就决定后面的大部分上限？

Single Query → Iterative Search → Planned First Move

核心矛盾：第一轮 retrieval 如果进入错误证据子空间，后续 Agent 往往只是在错误方向继续扩展。

关键推进：Question’s Gambit 把 first move 独立成 clue decomposition → complementary queries → pooled rerank，再进入原 agent loop。

证据：GPT-5.5 BrowseComp-Plus accuracy 83.1→90.5，gold evidence recall 72.9→85.9。

承接：GeneralQPP（够不够）→ SAFARI（继续不继续）→ Gambit（第一步怎么走）→ DiBud（走多深）→ ORDER（走哪套 index）→ CoSQ（是否应该升级 / abstain）。

问题 11 · 多兴趣模型为什么最后学成几个几乎一样的向量？

Diversity Regularization → Multi-positive Exclusive Assignment

核心矛盾：collapse 不只是 representation similarity；如果训练样本只有一个 positive，主损失会长期只更新同一个最匹配 interest。

关键推进：MIMA 将 request 内多 positive 做 Hungarian one-to-one assignment，让每个 positive 独占不同 interest，再学习 activation probability。
